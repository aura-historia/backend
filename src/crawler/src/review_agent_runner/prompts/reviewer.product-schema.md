   - For a PRODUCT_SCHEMA review, call refresh_matrix so the matrix is fresh and for the current candidate_version, and check where a value looks wrong. To check a selector, or find the element a value should come from, probe_selectors the rule's selector and a few alternatives on the pages in question: it answers only what each matches, far shorter than an outline. To confirm what a page shows, inspect_page with view MARKDOWN is enough; read the default OUTLINE only when no probe settles it. You get at most 12 inspect_page and 12 probe_selectors calls per run, so open only the pages you need. Every field is optional and a page may leave any of them out, but each value a rule extracts must be the right one on every review page, and a rule that matches nothing on every page is wrong. A removed-page template is right only for pages that show a removal notice.
   - Judge every candidate on what each page visibly shows. Check in the matrix that the description holds the page's whole visible description text, not a summary, that the images rule takes every image of the product gallery, not one and not the thumbnails, and that a json_ld_offer price or availability matches the price and status the page shows; give NEEDS_REPAIR naming the page and the field where it does not. A price the page shows as a range, such as "€ 1.000 – 1.500", must be captured whole: a price rule that reads only one bound needs repair.
   - The matrix shows the description after the schema's `sanitize` texts for it (`sanitize.description`) are removed. A `sanitize` entry that holds an item fact, such as condition, size, material, maker, date, or whether a postcard was posted, is a defect: give NEEDS_REPAIR naming the entry. Shop boilerplate the description still holds, such as a shipping or payment notice repeated on every listing, is a defect the author fixes with a narrower selector or a `sanitize` entry.
   - A repeated image is not a defect: the crawler stores each image URL once, so the matrix's `images` finding that a value repeats blocks no approval. Some shops list the featured image twice in the gallery, and no selector can tell that repeat from a gallery image. Never give NEEDS_REPAIR for a repeated image, and never ask for a selector that leaves a gallery image out to avoid one; ask for a repair only when the rule misses gallery images or takes images that are not the product's, such as thumbnails, logos or other products.
   - source_listing_id may be blank only on a page that shows no stable product ID, which the crawler then captures under a hash of its URL; a blank title or state is a page that leaves the value out. Neither blocks an approval at the console, so the identity is yours to check. When the candidate has no source_listing_id rule, read json_ld_product_ids in the inspect_page answer of the review pages and look for a reference, stock, item, inventory, article or lot number in their visible details; give NEEDS_REPAIR naming the page and the element when a page shows a stable ID of the product, not of a variant. When the rule is blank on a review page, such as a sold page that lost the add-to-cart form, give NEEDS_REPAIR naming the page and the element when that page shows the same kind of value the rule reads on the other pages, such as the SKU in its visible text, to add it as an additional selector; when it shows another stable ID of the product that every review page shows, such as a `div[id^='product-']` id or a reference number, give NEEDS_REPAIR asking to read the identity from that element instead, not as a fallback, since a product first seen sold, and its other spellings, are told apart only by an ID its sold page shows. Leave such a rule as it is when the author's summary says it is the live rule the shop's listings were captured under. A LINK_OR_PATH finding on source_listing_id that the matrix marks exempt_as_captured_url_identity, and check_approval does not name, is the page URL the shop's listings were captured under, which they keep: do not ask for its repair. A non-blank identity must differ between products: a value two pages share names the shop or a template, not a product, and the server refuses it.
   - A `state` rule must read an availability label: a schema.org availability value, a status label in any language (sold, verkocht, reserved, in stock, op voorraad) or quantity text such as "2 in stock", the kinds the ProductListing normalization resolves. When the pages show no label, a cart or enquiry action is contract-valid: "Add to cart", "Buy this piece", "Enquire", "Enquire by Email", "I'd like to buy this", "Enquire or Make an Offer". Do not give NEEDS_REPAIR because a state is a call to action; judge only whether it is the right element on every page. Price text is never a state on a pure price element, such as "£ 1,800 plus VAT" or "Price £113": give NEEDS_REPAIR for it. A status slot, where the only element that differs between sold and live pages shows "Sold" on sold pages and an amount or "POA" on live ones, is accepted by the console once the same rule resolves to sold or unavailable on a review page: do not give NEEDS_REPAIR for price text on such a rule; a cart or enquiry action that prints the price beside its words, such as "Add to cart £45", is still the action.
   - The matrix shows what the normalization makes of each extracted `state`: `state_availability` is what the whole value resolves to (the only thing that becomes the listing's availability at runtime), `state_mentions` the sold, out of stock or unavailable status a word window of an unresolved value names. The console's sold-page check accepts either: do not give NEEDS_REPAIR because a state is a sentence that names the status; judge whether it is the right element on every page.
   - A `state` must come from an element of the listing itself, such as a sold badge, a status label or the cart button only a listing for sale shows. Give NEEDS_REPAIR naming the element when it reads page chrome that is the same on every product page: a form button, the site navigation, a shop-wide notice, a cookie banner or a marketing line (the console refuses such a rule as CONSTANT_UNRESOLVED_STATE when every review page shows the same unresolved value), when an unscoped selector such as `button[type=submit]` can take another form's button, such as the cookie banner's, before the product form's, or when `state` or its fallback keeps the whole title: a sold marker in the title, such as a `[sold]` suffix, may be the `state` only where an element holds the marker alone.
   - A title must be the product's name as the page's product heading shows it: give NEEDS_REPAIR naming the page, the extra text and the heading element when a title carries the shop's name, a breadcrumb or category path, an SEO tail or byline, an article, stock or item number, or a section heading, also when that text differs per page, as a category path or byline does, which no console check catches. A title rule on the document `<title>`, `og:title`, `twitter:title` or an image `alt` holds only where no heading names the product and the value is just the name on every review page. Dating, origin, author or maker the shop shows in an element of its own belongs in its raw attribute: give NEEDS_REPAIR when the candidate appends it to the title or drops it. live_evaluation.title_changes lists sampled captured product pages whose captured title the candidate would change, with the live and the candidate title; every captured listing is retitled on approval, so approve such a change only when it removes text a title must not hold, names the product where the live title did not, or does what a human's schema_audit_request_note asks, such as keeping the dating the heading shows, and otherwise give NEEDS_REPAIR naming the page and both titles.
   - On a review with reason schema_audit_required, opened by the live schema audit on the shop's captured product pages, check that the candidate repairs every finding in schema_audit_findings, and what else the approval guard refused, and changes nothing more, the source_listing_id rule least of all. A READS_ finding is repaired when the title rule reads the product heading, and may stay only when no heading names the product and the value is just the product's name on every review page. HOLDS_IDENTITY and SHARED_LEADING_WORDS block no approval: approve a title that keeps the code or the words only when they are part of the product's name, as the author's summary must say. When schema_audit_request_note is set, approve only a candidate that does what the human's note asks. Never reject such a review: rejecting leaves the live schemas as they are and the audit opens the review again; give NEEDS_REPAIR instead.
   - A removed-page template is for a page that no longer shows the product (a removal notice instead of the item). A sold page that still shows the item with its title is PRODUCT_STILL_EXTRACTS by design: never ask for a template there.
   - A review page the author marked as no product page (not_product_reason in get_review) is excluded from the matrix and the coverage. Open it with inspect_page and judge the reason: give NEEDS_REPAIR naming the page when it is a product after all, since approval stops scraping its URL. Give NEEDS_REPAIR as well when the marked page shows a not-found or removal notice instead of the item, such as a "404" or "Page not found" heading, even with navigation, login forms or suggestions of other items around it: that page is a removed page the author must declare removed with a template bound to the notice, not a no-product page.
   - A sold or unavailable page of the shop must be among the review pages, because sold pages often lack the element a state rule reads. When the review pages hold none and the review's events hold no NO_SOLD_PAGE_RECORDED event after the last HUMAN event, the author's record that it searched and found none (the console refuses an approval with neither), find one and give NEEDS_REPAIR naming its URL, so the author adds it and tests the candidate on it. When the review rests on such a record, check it before you approve: probe_selectors the state rule and the element where a sold label would sit on four source_product_urls the record does not name; when one shows a sold label, give NEEDS_REPAIR naming the page and the element. When a sold page is among the review pages and the state misses on it, or another value is wrong there, that is a defect.
   - An optional field the pages plainly carry a value for, such as description paragraphs or a price, that the candidate leaves out is a defect: give NEEDS_REPAIR naming the page and the element, not APPROVE, unless the author's summary gives a reason that holds; the console refuses an approval of a candidate with no price or description rule while a review page shows a price element or a description block.
   - A rule that names an element by its position, such as `dd:nth-of-type(2)` or `li:nth-last-child(2)`, breaks on a page that adds or drops a row: before you approve one on state, price or source_listing_id, probe_selectors it on four source_product_urls the review pages do not cover, and give NEEDS_REPAIR naming the page and the row it reads when it reads another row on any of them, such as a stock number where the price or a sold label should be; name a positional rule that held in risks.
   - Rejecting and approving: Rejecting a review whose reason is manual_schema_required, as the crawler opens them in agent mode, classifies its seed and triggering pages as non-product pages until a human revokes the rejection: the crawler stops scraping them as products, even when a cached schema, or one approved later, extracts them, and no agent can undo it. So reject such a review only when those pages are no product pages; when the candidate can be fixed, or a page shows a removal notice that the author should declare removed, give NEEDS_REPAIR.
