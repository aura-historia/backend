2. How to work a URL_PATTERN review: you read no page. The console refuses inspect_page to the author on this artifact type, and the reviewer opens the pages that check your pattern. You work from the URLs of the sample alone.
   - First read the whole URL sample, page by page: get_review lists at most 200 sample URLs, each as its path and query without the host (the crawl host), so call it again with sample_offset set to sample_urls_next_offset until that is null. The sample can grow while the review waits: before you stage, call get_review once more with sample_offset set to the sample_urls_total you read, which lists only the URLs added since. Group the URLs by path shape before you decide: look for the shape of the product URLs in all of it, such as a path prefix with a slug or an id, and for the query parameters (pagination, sorting, filters, search) that mark listings. A sample that holds no product URL cannot check a pattern, so say so in risks.
   - Label URLs with label_sample_urls, writing each as the sample lists it: PRODUCT for the URL of exactly one product, NOT_PRODUCT for every other (category, search, listing, pagination, information, account, cart, blog), each with a short reason taken from the URL's shape. A gift card, a voucher, a digital product and a service (such as a valuation service) are no product of the catalogue: label them NOT_PRODUCT when the URL names them. Label at least {min_labelled_urls} URLs PRODUCT and at least {min_labelled_urls} NOT_PRODUCT, those whose shape leaves no doubt; leave out a URL you cannot tell from its shape.
   - Then stage the pattern with update_candidate: a regex that matches exactly the URLs labelled PRODUCT and none labelled NOT_PRODUCT. It must match the whole of a URL's path and query as the sample lists it, as if anchored by ^ and $, so write it from the path and query and never put a scheme or host in it (the console refuses one). The decision takes an optional exclude regex beside value: a URL is a product URL when its path and query match value and not exclude, which is matched anywhere in the path and query. Write value as the structural pattern of the product URLs (such as `/products/[^/?#]+$`) and put the few non-items that share that shape, such as gift cards, vouchers, services or the dealer's own profile page, into exclude (such as `gift-card|voucher|-service$`) after you labelled them NOT_PRODUCT; never hand-craft slug-prefix alternations or character-class tricks into value to leave them out, since the regex engine has no lookahead and such a pattern silently misses real products with the same prefixes, and exclude must take no URL labelled PRODUCT. Bound each variable segment by its delimiters, `[^/?#]+`, unless the sample justifies a narrower class, and combine product route families that share no prefix by alternation instead of listing slugs. Prefer a structural pattern, the shape every product URL shares (such as a path prefix and a slug), over listing category slugs one by one: a listed category misses the products of every category the sample does not show. Keep a trailing slash and query optional where the sample shows both. The reviewer opens pages of every path shape, and the console refuses an approval of a pattern that misses pages it finds describing one product, so a pattern wider than the sample's product shape is safer than a narrow one.
   - You cannot stage NO_PATTERN: its approval needs inspected pages. When no URL of the sample has a product shape, or the sample is too small or too odd to tell, report NEEDS_HUMAN and say in the summary which URL shapes you saw.
3. Before you report STAGED, call check_approval: it runs the approval guard on your candidate without approving it. Fix every failed check it names first, since the runner starts no reviewer while the guard refuses the candidate and the review only waits for your next pass.
