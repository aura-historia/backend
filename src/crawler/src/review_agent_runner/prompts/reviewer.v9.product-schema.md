   - For a PRODUCT_SCHEMA review, call refresh_matrix so the matrix is fresh and for the current candidate_version, and read pages with inspect_page where a value looks wrong. To confirm a value or what a page shows, view MARKDOWN is enough and far shorter; check a selector only against the default OUTLINE. You get at most 12 inspect_page calls per run, offset reads included, so open only the pages you need. Every required field must extract the right value on every review page. An optional field may miss on some pages, but a rule that matches nothing on every page is wrong. A removed-page template is right only for pages that show a removal notice.
   - source_listing_id is marked optional in the matrix but must be non-blank on every review page and differ between products: the server refuses an approval with a blank one, and a value two pages share names the shop or a template, not a product.
   - A `state` rule must read an availability label: a schema.org availability value, a status label in any language (sold, verkocht, reserved, in stock, op voorraad) or quantity text such as "2 in stock", the kinds the ProductListing normalization resolves. When the pages show no label, a cart or enquiry action is contract-valid: "Add to cart", "Buy this piece", "Enquire", "Enquire by Email", "I'd like to buy this", "Enquire or Make an Offer". Do not give NEEDS_REPAIR because a state is a call to action; judge only whether it is the right element on every page. Price text is never a state on a pure price element, such as "£ 1,800 plus VAT" or "Price £113": give NEEDS_REPAIR for it. A status slot, where the only element that differs between sold and live pages shows "Sold" on sold pages and an amount or "POA" on live ones, is accepted by the console once the same rule resolves to sold or unavailable on a review page: do not give NEEDS_REPAIR for price text on such a rule; a cart or enquiry action that prints the price beside its words, such as "Add to cart £45", is still the action.
   - The matrix shows what the normalization makes of each extracted `state`: `state_availability` is what the whole value resolves to (the only thing that becomes the listing's availability at runtime), `state_mentions` the sold, out of stock or unavailable status a word window of an unresolved value names. The console's sold-page check accepts either: do not give NEEDS_REPAIR because a state is a sentence that names the status; judge whether it is the right element on every page.
   - A removed-page template is for a page that no longer shows the product (a removal notice instead of the item). A sold page that still shows the item with its title is PRODUCT_STILL_EXTRACTS by design: never ask for a template there.
   - A review page the author marked as no product page (not_product_reason in get_review) is excluded from the matrix and the coverage. Open it with inspect_page and judge the reason: give NEEDS_REPAIR naming the page when it is a product after all, since approval stops scraping its URL.
   - A sold or unavailable page of the shop must be among the review pages, because sold pages often lack the element a state rule reads. When the review pages hold none and the review's events hold no NO_SOLD_PAGE_RECORDED event after the last HUMAN event, the author's record that it searched and found none (the console refuses an approval with neither), find one with inspect_page and give NEEDS_REPAIR naming its URL, so the author adds it and tests the candidate on it; when one is there and the state or another required field misses on it, that is a defect.
   - An optional field the pages plainly carry a value for, such as description paragraphs or a price, that the candidate leaves out is a defect: give NEEDS_REPAIR naming the page and the element, not APPROVE, unless the author's summary gives a reason that holds; the console refuses an approval of a candidate with no price or description rule while a review page shows a price element or a description block.
   - A rule that names an element by its position, such as `dd:nth-of-type(2)`, breaks on a page that adds a row before it: name it in risks, and give NEEDS_REPAIR when a review page shows the list differing.
   - Rejecting and approving: Rejecting a review whose reason is manual_schema_required, as the crawler opens them in agent mode, classifies its seed and triggering pages as non-product pages until a human revokes the rejection: the crawler stops scraping them as products, even when a cached schema, or one approved later, extracts them, and no agent can undo it. So reject such a review only when those pages are no product pages; when the candidate can be fixed, or a page shows a removal notice that the author should declare removed, give NEEDS_REPAIR. A review whose reason is missing_required_value holds pages that leave the title or state empty under the live schemas, and rejecting it classifies no page. Approve it only when each such page is covered, by a rule that now reads the value from the page or by a removed-page template where the page shows a removal notice, and the candidate loses no value of a page the live schemas capture today; otherwise give NEEDS_REPAIR naming the page.
