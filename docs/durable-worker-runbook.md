# Durable CDC and worker operations

This runbook describes the **post-legacy-source target**, not verified live state. PostgreSQL is business truth; the approved path is DMS CDC → seven-day Kinesis stream → versioned router Lambda → ten scoped Standard SQS source/DLQ pairs → worker Lambdas. `CdcRouterEnabled` and each worker queue mapping are separately gated. [Migration F7](migration-f7-dms.md) owns DMS slot/LSN, first start, capture, archive evidence, and external source decommissioning; [event flow](events/flow.md) owns per-table routing. Neither a CDK declaration nor removal of native/Sequin source proves that any mapping is enabled, DMS is running, or old external subscriptions have stopped.

## Activation and legacy handoff

1. Obtain stage/account/release and operator approvals, check deployment identities, schema/job compatibility and the [F7 preconditions](migration-f7-dms.md#preconditions-and-approval-record). Protected initialization applies schema and initial FX with consumers off; it never starts DMS. Never invent an LSN or restart a task with a new first-start point.
2. Inventory old externally operated Sequin subscriptions, process deployments, in-flight requests and any legacy in-memory jobs/DLQs; preserve evidence and settle or explicitly account for work not held by SQS. Code removal cannot recover lost work or decommission Sequin, replication slots, or secrets. Stop old delivery/consumers under approval before activating the replacement; never run two consumers of one queue. Do not turn off required fanout merely to get one successful queue probe.
3. Follow F7 for the separately approved DMS first start, real table/DELETE/control capture, router enabling at `TRIM_HORIZON`, checkpoint/archival checks, then activate each scoped Lambda mapping independently once source compatibility and queue backlog are confirmed. Record safe identifiers, counts, lag, and timestamps only. Do not log or paste source records, archive bodies, credentials, recipients, or raw provider data.
4. Decommission external subscriptions, old processes, slots and credentials only under a separately approved live plan with proof of ownership, stopped delivery, drained work, retained replay windows and rollback posture. Source-code removal is not evidence that any of these steps happened. A rollback to a native consumer requires a separately approved compatible artifact, disabled Lambda mapping and settled work; do not assume the removed native runtime exists to resume.

## Failure custody and controlled redrive

The Kinesis router prevalidates the whole per-record route and confirms every required SQS send before checkpointing. It returns the earliest unconfirmed sequence and stops; partial sends can duplicate jobs on retry. After three retries or one hour, the **original invocation** goes to the private retained S3 failure archive (90-day object expiry). This is not a worker queue DLQ. Check mapping-specific archive-delivered/dropped and destination-failure signals; an archive delivery failure is not proof of a retained object. Preserve original source ARN, sequence and envelope; repair the cause, use the fail-closed decoder, test replay in isolation and obtain approval before any live replay. Never silently skip poison records.

Scoped SQS source queues retain jobs seven days; paired DLQs retain them 14 days. Standard source-to-DLQ transfer retains the original enqueue age—there is no guaranteed 21-day total window. Each worker acknowledges only a completed service outcome; `ReportBatchItemFailures`, timeout, panic, malformed job, dependency failure and unknown completion leave records for ordinary SQS retry/redrive (five receives). The raw normalization mapping batches ten; other worker scopes batch one. Do not confuse Lambda asynchronous-invocation DLQs, provider ingress DLQs, the router S3 archive, and these worker SQS DLQs. Monitor queue oldest age/depth, DLQ count, router iterator age, DMS lag/slot WAL and Lambda errors. Before a small controlled redrive, identify the failed domain keys and authoritative state, repair root cause, assess duplicate effects and remaining retention; use separately authorized operator access. Runtime roles cannot purge, replay or redrive. Never purge a queue to clear alarms.

Raw revision inserts only wake `product-listing-normalization-lambda`. It reads PostgreSQL stream heads, atomically records terminal normalization progress with zero or one canonical write/event, and returns unfinished/capped drains as SQS failures for retry. It has **no scheduled raw-backlog reconciliation**: inspect persisted pending heads, queue age/DLQ and CDC gaps; a missing/expired wake-up requires an approved recovery plan, not a fabricated successful completion. The pre-removal native normalizer's 30-second reconciliation loop was legacy behavior and is not an activation gate. Crawler R17 local scheduling, review, raw-capture completion and provenance remain separate; a crawler capture success does not mean canonical normalization completed.

## ProductListing ingestion FIFO command recovery

The separate `product-listing-ingestion-queue-${stage}.fifo` (seven-day retention) and `product-listing-ingestion-dlq-${stage}.fifo` (14-day retention) are command ingress, **not** CDC worker queues or Shopify's old input/DLQ. Its event source delivers up to ten records without a batching window and uses partial batch responses. The Lambda validates every SQS message ID before work, then processes in received order within one invocation budget (45-second timeout with response headroom). It stops after the first non-complete command, regardless of group, and returns that SQS ID and **every** unprocessed successor as failures. A confirmed completed prefix is not retried by the response; if the response is lost, durable command receipts protect its redelivery. Malformed/unsupported commands, business rejection, conflicts, setup/credential failure, timeout, panic, and uncertain commit all remain for native retry/redrive (five receives). An incomplete command in a FIFO group blocks later delivery for that group; partial-response failures need not appear as Lambda `Errors`.

Before admitting producers, deploy the queue and DLQ, apply the receipt migration, upload the matching consumer artifact, deploy and verify its published-version mapping, then enable command publication under release approval. Before rolling out the USER/DELEGATED_USER fingerprint-scope correction, check the live source queue, DLQ, and receipt table for any previously accepted v1 delegated-user commands; if present, plan a compatibility cutover rather than silently invalidating their fingerprints. The Shopify producer code forwards to the FIFO (deployment remains a separate release gate); the WooCommerce API route retains its URL and authentication but forwards mapped raw-capture commands. Synchronous partner API writes and crawler capture are unchanged. Both Shopify and API retain PostgreSQL. To pause consumption, disable the ingestion event source mapping (coordinate with producers so the seven-day source retention cannot silently expire). Check source age and visible backlog, DLQ depth, Lambda errors/throttles and bounded `CompletedRecords`/`FailedRecords`/`UnprocessedRecords` counters. Per-attempt structured logs include a completion `outcome` or bounded failure `error_code`, `duration_ms`, and a safe `sqs_message_id`. Only verified decoded commands include `command_id`, `submission_id`, `listing_source_id`, operation, original `item_index`, and log-safe `request_id`/`correlation_id` (nonempty ASCII letters/digits/hyphen/underscore, at most 128 bytes). Unsafe trace IDs are logged as empty fields, never as original text. Missing/malformed bodies and setup failures have no command correlation; unprocessed successors are not decoded and report zero execution duration. SQS IDs that fail the log-safe character/length check appear as `invalid` in logs, but the original IDs remain in the partial-batch response. Codes distinguish wire/budget/timeout/panic from service-owned `RECEIPT_*`, `CREATE_*`, `UPDATE_*`, `UPSERT_*`, `WITHDRAW_*`, `CAPTURE_RAW_*`, `FINGERPRINT_CONFLICT`, and `COMMIT_UNCONFIRMED`; inspect these with persisted receipts and current PostgreSQL state, not as proof of a definite rollback or a safe skip. Preserve safe SQS message IDs, `commandId`, `submissionId` for correlation only, and persisted receipts. Diagnose and repair the root cause against current PostgreSQL state before a small authorized redrive; an older DLQ command may conflict with newer state. Never blindly redrive, delete/acknowledge failures, purge a queue, or infer exactly-once execution from FIFO ordering. See [event flow](events/flow.md#v1-ingestion-command-execution-installed-consumer) and the [infra ingress settings](../infra/README.md#productlisting-command-ingress-1859-cdk-scope).

## Shopify forwarding handoff

The Shopify EventBridge rule and existing Standard `shopify-lambda-queue-${stage}`/`shopify-lambda-dlq-${stage}` remain the provider ingress boundary. The Shopify Lambda keeps private PostgreSQL source lookup/runtime credentials and upstream SQS consumption; its stage-local FIFO URL and exact `sqs:SendMessage` grant support the forwarding handler, but source code and infrastructure readiness are not evidence that AWS has deployed this change. No provider payload, credentials, or raw command bodies belong in logs or release evidence.

Under release approval, deploy the shared ProductListing FIFO source/DLQ and command-receipt migration first, upload/deploy the matching ingestion consumer version, and verify its active mapping, IAM, PostgreSQL access, queue age/DLQ alarms and safe per-record outcomes **before** deploying/enabling Shopify forwarding. Check a stage-specific change set for replacement of the retained Shopify upstream queue/DLQ and FIFO queues; confirm the Shopify mapping and EventBridge rule remain targeted at the upstream queue. A CloudFormation dependency ordering consumer creation before producer functions is not proof that a separately released runtime, mapping or database is healthy. Hold the cutover if any gate fails; coordinate the existing upstream backlog and retention window. This repository change does not confirm live deployment or a completed cutover.

After cutover, track **both** acknowledgment boundaries independently. EventBridge acceptance means only that its rule delivered to the upstream Shopify queue. For an eligible raw observation, Shopify may acknowledge the upstream SQS record only after confirmed FIFO `Accepted` admission; a rejected/unconfirmed/not-attempted send remains a partial SQS failure for upstream retry (five receives, then the **Shopify DLQ**, subject to four-day source retention). An unconfirmed send may already have reached the FIFO, so preserve original identity on retry and do not treat upstream DLQ presence as proof no downstream command exists. Terminal/ignored provider inputs are distinct from forwarded commands. The downstream ingestion Lambda acknowledges the FIFO record only after committed `APPLIED` PostgreSQL state/receipt (or matching replay); failures or uncertain commits retry/redrive to the **ingestion DLQ** under its seven-day source and 14-day DLQ retention. Neither boundary means canonical normalization, CDC delivery or search projection has finished.

On failure or rollback, inspect upstream age/depth and DLQ, FIFO age/depth and DLQ, safe command/receipt identifiers, and authoritative PostgreSQL raw and command receipts. Repair before small authorized redrive, checking for duplicates and later state; never blindly move Shopify DLQ messages or FIFO DLQ commands, purge either queue, or infer an unconfirmed send was rejected. To stop new forwarding, roll back/fence the Shopify producer under approval without disabling the shared consumer needed by other producers; to pause downstream consumption, disable its mapping only with a plan for the seven-day FIFO retention. Existing synchronous capture must not run concurrently with forwarding for the same provider observation without a documented compatibility plan. See [event flow](events/flow.md#shopify-queue-forwarding-boundaries-runtime-deployment-gated).

## WooCommerce webhook queue handoff

Before enabling WooCommerce forwarding, verify the shared FIFO source/DLQ, command-receipt schema, compatible consumer artifact and active mapping, and the API Lambda's stage-local queue URL plus source-ARN-only `sqs:SendMessage` grant. Exercise a signed webhook with the exact body bytes and a valid bearer/capability plus source grant (the consumer checks mapped commands' current grant at execution): an authorized ignored status must return bodyless `204` without a queue message or provider receipt; a mapped observation must return bodyless `204` only after confirmed FIFO acceptance. Test an unavailable/unconfirmed send and oversized encoded message: neither is a `204`. Do not treat CDK synthesis or an updated public contract as proof that the runtime cutover has deployed.

For mapped observations, the HTTP response transfers custody only to the shared FIFO. The consumer later evaluates provider receipts, source order and raw capture in PostgreSQL; a conflict or an ambiguous restore barrier may enter the ingestion DLQ **after** an HTTP `204`, never as an immediate capture `409`. Investigate failed command IDs, FIFO age/DLQ and authoritative raw/provider and command receipts before controlled redrive; do not assume the provider will retry an already acknowledged delivery. For `503`/`500`/timeout or a lost reply, an attempted send may already be queued: retry with the same signed bytes, source, topic, caller and delivery ID if present, inspect queue/receipts, and do not infer a rollback. Without a delivery ID, a retry cannot recover the original command identity after a lost reply and has no provider receipt-based retry-deduplication guarantee. Pause or roll back the WooCommerce producer under approval without disabling the shared consumer; do not run synchronous capture and forwarding concurrently for the same observation. Keep payloads, signatures and secrets out of logs and operator evidence.

## Projection fences and rebuild

PostgreSQL and its event/revision facts are authoritative; OpenSearch is rebuildable. ProductListing withdrawal and search-filter deletion use content-free, externally versioned `projectionDeleted: true` tombstones. Deploy mappings and **all** readers before writers, exclude tombstones before search/ranking/percolation, and fence old physical-DELETE writers including in-flight requests. Never TTL or physically delete tombstones: remote delete-version memory expires after `index.gc_deletes`. For a rebuild, isolate a new index generation, fence old writers, replay/rebuild from authoritative facts, catch up committed changes, verify IDs/source versions/deletion visibility and only then switch the alias. Withdrawn ProductListings retain state for backfill; hard-deleted search filters need retained deletion facts or an externally fenced fresh-generation rebuild. An index reset, expired SQS job, or missing source history is not a recovery mechanism.

## Notification recovery limits

`notification_deliveries` is authoritative for intent and lease state. Active claims defer until persisted expiry +5s; claim/status races defer 1s, never complete. EMAIL uses SES after committing the claim; finalization retries must reuse the same lease token, completion time and provider receipt/error tuple. Only confirmed terminal finalization acknowledges the SQS job. SES acceptance with a lost finalization response can cause a duplicate after the five-minute lease expires. Preserve safe delivery/attempt IDs and PostgreSQL state; check provider evidence under approved access before any controlled replay. Do **not** automatically resend historic customer email, log rendered content or recipient details, or treat provider timeout as definitely unsent.
