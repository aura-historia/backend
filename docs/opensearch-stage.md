# Stage OpenSearch (issue #1782)

## Ownership and state

The backend operator owns this **independent** Hetzner service, its persistent Docker volume, certificate and credentials. Baseline inspected: `de161a2b68bb0f82fe8e691475ad5b791c2e66f6` (2026-09-25). `opensearch/stage/compose.yaml` pins OpenSearch **3.8.0** by digest: one node, a 16 GiB container limit and 6 GiB JVM heap. The application indexes use one primary and zero replicas. The 3.8.0 node on this machine has a persistent volume and serves authenticated HTTPS on **loopback only**, `127.0.0.1:19200`; no cluster transport port is published. It was upgraded locally from an empty 3.1.0 installation with the same volume; the two application indices remained green. `product-listings`, `user_search_filters`, and `hybrid-search-pipeline` are present. These are source/live-local observations, not deployed AWS evidence.

Mappings include five built-in language analyzers, 768-dimensional Faiss HNSW fp16 vectors, percolator fields and permanent external-version tombstones. Search readers exclude tombstones. PostgreSQL retains authoritative business data and embedding outputs. No tombstone TTL, physical deletion, unbenchmarked compression or extra search service is configured. The single host is an accepted stage outage domain: host/volume loss interrupts search until reconstruction. No production availability claim is implied.

**Not yet activated:** the public TLS gateway, certificate and actual AWS-to-Hetzner IPv4 path. The DNS A record resolves to `148.251.91.20`, but the gateway is deliberately disabled until a publicly trusted hostname certificate is available. No AWS credentials, SSM parameters, AWS NAT/EIP acceptance or representative capacity test have been verified. Do not enable search-dependent workloads before those gates.

## Reproducible host setup

Docker Engine/Compose, `jq`, >=16 GiB of spare RAM, suitable persistent disk and `vm.max_map_count >= 262144` are needed; this host reported 16438223. Restrict Docker group/socket access (equivalent to root). From the repository root, create a private mode-0600 `opensearch/stage/.env` containing a strong random `OPENSEARCH_INITIAL_ADMIN_PASSWORD` with upper/lowercase letters, digits and punctuation. `OPENSEARCH_CERT_DIR` is only needed for the public profile. Private `.env`, `.admin-curl`, `.credentials/` and `certs/` are Git-ignored. Store copies in an access-controlled backup/secret store, never in Git, tickets or logs. `docker inspect` exposes environment variables to Docker operators. Keep administrator credentials separate from AWS runtime credentials.

```sh
docker compose --env-file opensearch/stage/.env -f opensearch/stage/compose.yaml up -d opensearch
```

On a **fresh** volume only: the image installs the bundled demo security config behind loopback. Before ever starting `gateway`, replace the admin password, rotate the reserved `kibanaserver` password and delete all unused demo users. The reserved accounts cannot be edited with the Security REST API: use the image's `securityadmin.sh` to back up the current `internalusers` configuration, change only those hashes and reapply only `-t internalusers`; do **not** upload the entire demo configuration or overwrite the runtime users. Then sync the private `.env` and restart the container; verify the old admin password fails. This was done on this host. Do not reuse the bundled node/admin certificates as a public trust chain. The loopback-only node uses image-internal self-signed HTTPS. The gateway's upstream is on the private Docker bridge; its `tls_insecure_skip_verify` applies **only** to that internal hop, never to clients.

Use an admin-only local curl config (mode 0600, Basic credentials and `insecure` for the *loopback* self-signed node) at `opensearch/stage/.admin-curl`; do not put passwords in shell history or command arguments. On a new installation create role documents from `opensearch/stage/roles/*.json` via `PUT /_plugins/_security/api/roles/aura_stage_<role>`; privately create a distinct random-password internal user `aura_stage_<role>` with `opendistro_security_roles: ["aura_stage_<role>"]` for each role. The four roles are `reader`, `product_projector`, `filter_projector`, `percolator` (file names use hyphens). Reader searches the two application indexes; projectors only index their respective documents; percolator searches saved filters and creates/closes PITs. No runtime user has security/cluster administration, index management or unrelated-index access. Rotate users via the security API and then their SSM references as a controlled operation, never during an ordinary Lambda release.

After checking that the indices/pipeline do **not** exist, apply the assets once, from the repo root:

```sh
curl --config opensearch/stage/.admin-curl --fail-with-body -H 'Content-Type: application/json' -X PUT --data-binary @opensearch/stage/hybrid-search-pipeline.json https://127.0.0.1:19200/_search/pipeline/hybrid-search-pipeline
jq '.settings += {"number_of_shards":1,"number_of_replicas":0}' opensearch/mappings/product_listings.json | curl --config opensearch/stage/.admin-curl --fail-with-body -H 'Content-Type: application/json' -X PUT --data-binary @- https://127.0.0.1:19200/product-listings
jq '.settings += {"number_of_shards":1,"number_of_replicas":0}' opensearch/mappings/user_search_filters.json | curl --config opensearch/stage/.admin-curl --fail-with-body -H 'Content-Type: application/json' -X PUT --data-binary @- https://127.0.0.1:19200/user_search_filters
```

Never recreate existing indices, reset aliases, delete documents or reapply old security backups as part of code deployment. Subsequent mapping changes and rebuild/alias cutover belong to controlled #1803 operations. Routine `docker compose up` preserves `stage_data`; **never use `down -v`** on a populated volume. A normal CDK/Lambda release only reads SSM references and has no host lifecycle hook. Engine upgrades require a planned outage, verified PostgreSQL reconstruction inputs/backup, pinned-image review, adapter checks on the candidate engine, an explicit Compose change/restart, and post-restart version/green/security checks. Do not downgrade a migrated data volume.

## Public TLS and AWS gate

The gateway profile uses Caddy at `https://opensearch.stage.aura-historia.com:9443`, independently of the existing `internal-agent.aura-historia.com` service on ports 80/443/8080. It proxies only application search/projection/percolation paths; admin APIs are not routed. **Do not start it without** a valid publicly trusted full chain and matching private key in a host-private directory containing `fullchain.pem` and `privkey.pem`, readable by Caddy. Set `OPENSEARCH_CERT_DIR` in the private `.env` to that directory. Obtain/renew the certificate using the domain operator's DNS-01 automation or an explicitly coordinated existing proxy/ACME setup; do not seize 80/443, assume access to `/etc/letsencrypt`, or use a self-signed/Cloudflare-origin-only public certificate. Caddy is not the certificate issuer here. Monitor certificate expiry and reload/recreate the gateway after renewal. Start only after negative permission checks:

```sh
docker compose --profile public --env-file opensearch/stage/.env -f opensearch/stage/compose.yaml up -d gateway
curl --fail-with-body --max-time 5 https://opensearch.stage.aura-historia.com:9443/product-listings/_search
```

The unauthenticated request should be rejected (401, not a successful `curl --fail-with-body`); make an authenticated reader request with a private curl config for a successful search. Also verify wrong credentials (401), wrong hostname/untrusted CA (TLS failure without `-k`), an unauthorized write/security request (403), and the correct certificate chain/hostname with `openssl s_client` or `curl -v`. Do not use `-k` against the public endpoint. No IP allowlist is required for stage when TLS and authentication are enforced; never publish 9300 or the loopback admin port. The host/operator controls host firewall and cert renewal.

AWS stage configuration: `/opensearch/stage/endpoint-url` = `https://opensearch.stage.aura-historia.com:9443`; per-role SSM username/password pairs are `/opensearch/stage/{reader,product-projector,filter-projector,percolator}/{username,password}`. Supply them through the existing secure deployment process, not this repo. After the actual #1777 NAT/EIP is known, prove IPv4 connectivity and authorized/unauthorized behavior **from a private AWS subnet**; a local curl is not that proof. Keep worker mappings disabled until the endpoint, certificate, SSM values and search-dependent acceptance all pass. No crawler work is included.

## Monitoring, recovery and evidence gates

Check loopback `/_cluster/health`, `/_nodes/stats/jvm,fs`, index status, Docker restart count, host free disk/inodes, JVM/native RSS, gateway HTTPS 401/200 behavior, certificate expiry and p95 search/percolation latency. Alert on unavailable endpoint, repeated restarts, disk >80%, sustained heap >75%, certificate <30 days and sustained latency/timeouts. Prefer off-host snapshots with tested restore if retaining a large index becomes cheaper than rebuilding; until then reconstruction from PostgreSQL (#1803) is the policy. Retain permanent tombstones during rebuild, measure rebuild duration, and keep enough free disk for index growth and recovery. This 16 GiB / 6 GiB choice is an initial stage limit, not a capacity guarantee; no representative document/embedding count or latency series has been recorded yet. Measure them in #1786 before broad activation. Host storage, transfer, backups, certificates, and operator time have ongoing cost; no cost quote or recovery-time guarantee is claimed.

**Evidence (2026-09-25):** OpenSearch 3.8.0 after volume-preserving upgrade, green one-node application indices (2 active primary shards, 0 unassigned); Docker RSS 6.766 GiB / 16 GiB. Local 3.8.0 checks: reader search 200, reader write/security/unrelated-index 403, projector search/other-index write 403, percolator PIT create and valid-PIT close 200, no credentials 401; empty-index hybrid RRF, 768-dimensional KNN and saved-filter percolate requests succeeded with zero hits. An invalid PIT ID returns 500 from 3.8.0, so it is not a valid close-permission probe. Cargo's `test-api` library tests passed (7); the combined adapter-test command timed out after `product-listing-opensearch` passed 68 tests and 9/10 `search-filter-opensearch` tests were seen passing. The remaining test and representative populated-data latency are not verified. `npm --prefix infra test`, `npm --prefix infra run synth:all`, and `cargo depgraph-check check` passed. Local checks cannot substitute for publicly trusted TLS or AWS-subnet checks. Do not mark the public acceptance or capacity gates complete until actually measured.
