# Crawler networking

All crawler egress is fail-closed. Spider roots, scraper HTML fetches, image probes, and review live inspection accept only public HTTP(S) destinations.

## Destination policy

Before each request, the crawler:

1. accepts only HTTP or HTTPS URLs with DNS hostnames, no userinfo, no IP literals, and ports 80 or 443;
2. resolves the hostname immediately;
3. rejects absent, mixed, or non-public DNS answers; and
4. pins the approved addresses in the HTTP client for that request.

This prevents a request from following DNS rebinding to a private address. Automatic redirects are disabled; each permitted redirect is explicitly validated and bounded. Spider navigation remains confined to the host of its crawl root, which a root redirect may move to that host's one-`www` twin (bare or `www.`), while scraper navigation may use only the ListingSource's crawl host or its one-`www` equivalent. A redirect outside the applicable boundary fails rather than becoming a new crawl target. A page inside a spider crawl that answers a redirect (301, 302, 303, 307, 308) is not stored: the spider follows the redirect when its target is on the crawl root's own host, passes the public-target rules above and robots.txt, and is at most five redirects from a page the crawl found, and then requests the target as a page of the crawl, stored in the [stored spelling](#stored-urls) and deduplicated against the pages the crawl knows or already fetched, so a trailing-slash twin is fetched once and a twin not yet fetched is fetched. The spider does this itself through Spider's crawl queue rather than through the HTTP client, which never follows a redirect, so every hop is checked and the client stays pinned to the root host's addresses; a redirect to the root's twin host is therefore not followed inside a crawl. A redirect the spider does not follow is counted as rejected in the crawl diagnostics, and its page is stored as before. A redirect answered when the crawl is ending is carried over in the frontier. The spider treats an unrelated root redirect as terminal before URL state is persisted; the failure log names the redirect target (`redirect_url`), so a shop that moved can be told apart from a parked domain. Redirect targets and final URLs in spider diagnostics and logs are written in the [stored spelling](#stored-urls), without credentials or session parameters.

A shop may serve its root on the crawl root's host while every page it links lives on the twin. The spider's preflight therefore reads the root page it ends on, within the page-body limit, and moves the crawl root to the twin as a redirect there would, when the page links at least five distinct pages on the twin, and more distinct pages there than on the root's own host. Links are resolved as Spider resolves them, against the page's `<base>` element if any, and a page counts once, however often the root page links it and whether with or without its trailing slash or the parameters its [stored spelling](#stored-urls) drops, and under either scheme or letter case, as the crawl does not fetch a page twice for them, so one product repeated in a slider, the menu and the footer does not tip the balance; links the spider never follows and links to any other host, other subdomains included, do not count. The move happens at most once per crawl, never back to a host a root redirect left, and counts against the redirect bound; the crawl then runs on the twin alone, with its robots.txt and pinned addresses, unless the twin redirects back, which undoes the move. The crawl's diagnostics carry the move with both page counts (`root_reroot`), in the stored spelling, into its completion log, or into its failure log when Spider's crawl failed or its pages yielded no product URL. A preflight that fails after the move, on the twin's root page, its redirects or its robots.txt, or by running out of its time budget, carries the move into its failure log too, so a twin that fails is not taken for the crawl root's host. Nothing is persisted: each crawl judges the root page again.

A ListingSource's crawl host is a local canonical hostname: lowercase, no trailing dot, and at most one leading `www.` removed. A presentation URL whose host repeats `www.` names no crawl root, and two crawl-enabled ListingSources never share a crawl host ([ListingSource scope](README.md#listingsource-scope)). The crawl root's host is retained separately so spider navigation remains exact-host constrained.

## TLS trust

Every crawler request verifies certificates against the operating system's trust store, through the platform verifier Spider's client also uses. The spider and the scraper therefore accept the same shops. A shop whose chain ends at a root the host does not trust fails as a connect error, and the logged details name the cause, for example `UnknownIssuer`.

On Linux the trust store is the system CA bundle (`SSL_CERT_FILE`/`SSL_CERT_DIR` or the distribution's default paths), read once per process. An image without a CA bundle fails closed: the crawler logs once that the trust store is unavailable, and every HTTPS request fails. Windows and macOS use the OS certificate engine, which can also accept roots that the Mozilla-derived Linux bundles do not include yet.

## Crawler identity

Every crawler request (spider pages and robots.txt, scraper HTML fetches, image probes, and review live inspection) sends the single user agent `AuraHistoriaBot/<version> (+https://aura-historia.com)`, defined once in the crawler's network module.

- The crawler identifies itself honestly instead of posing as a browser. robots.txt groups are matched against the leading `AuraHistoriaBot` token, so a shop can allow or refuse the crawler by name.
- Use the bare product-token form. Some shop firewalls reject the `Mozilla/5.0 (compatible; ...)` form from unverified addresses, and a pinned browser version goes stale and gets blocked as outdated.
- A 401 or 403 from the crawl root is reported as `AccessDenied` with the root status and the user agent in the crawl diagnostics. Spider's own reading of the refusal (a blocked status, a JavaScript challenge, a recognised vendor block) keeps precedence over the generic `crawl_root_access_denied` reason.

## Request headers

Every crawler request sends one header set besides its [user agent](#crawler-identity), defined once in the crawler's network module: `Accept: */*`, and no `Accept-Language`, cache directive or other preference. Spider pages and robots.txt, scraper HTML fetches and robots.txt, image probes, and review live inspection, which shares the scraper's fetcher, all send it. So the scraper fetches the site the spider learned the URL patterns from, and the review console shows what the scraper captures. Only `Accept-Encoding` differs, because each client names the transfer encodings it decodes: the spider `gzip, br, deflate`, the scraper's clients `gzip,br`, except image range probes, which ask for `identity` because a byte range of a compressed body does not decode. Each decodes what it names before it reads a body, so a body size limit counts decoded bytes.

The set states no preference on purpose, so a shop answers with the storefront it serves a visitor who states none, in its own language and currency:

- A language preference, whatever language it names, makes Shopify Markets localize the storefront to the country of the request's IP address. Every price on the page, the visible price, `og:price` and the JSON-LD offers alike, is converted into that country's currency at the day's rate. No selector can recover the shop's own price, and the converted price passes every [plausibility check](extraction-and-review.md#plausibility-checks). Without a preference a multilingual shop serves its default language, the one the spider stored its URLs from.
- A browser-style `Accept` that prefers `text/html` makes some shops redirect every page to a locale-prefixed copy, such as `/artworkdetail/...` to `/en-us/artworkdetail/...`, which the URL pattern learned from the spider's unprefixed URLs does not take.
- A cache directive (`Cache-Control: no-cache`, `Pragma: no-cache`) only asks a shop's cache to pass the request on to its origin.


## robots.txt

Spider and scraper honour robots.txt through one RFC 9309 implementation in the crawler's network module:

- The group naming `AuraHistoriaBot` applies, otherwise the `*` groups; the longest matching `Allow`/`Disallow` rule decides and `Allow` wins ties.
- robots.txt redirects are followed up to five times, to any public host. A 4xx answer other than 429 (401 and 403 included), a redirect to a target the crawler may not request or too many redirects means robots.txt is unavailable and everything is allowed. A 429 or 5xx answer, or a transport failure (body read included) on a redirect target off the shop's host, means robots.txt is unreachable and everything is disallowed. A transport failure on the shop's own host fails the request or crawl like any other transport failure.
- Percent escapes match regardless of hex case, so `Disallow: /*%2b*` covers `%2B` and `%2b` alike.
- `Crawl-delay`, capped at 60 seconds, only ever raises the component's own delay between requests.

The scraper checks robots.txt per origin before every HTML request, redirect hops included. It reuses a fetched policy for one hour and an unreachable one for 15 minutes; concurrent requests to an origin share one robots.txt fetch, which counts against the fetch timeouts and is not retried inline, for a redirect hop either. `Crawl-delay` is a minimum spacing between request starts on the shop's domain, bare and `www` host together. Every request, redirect hops included, waits for that spacing and the latency throttle, and the wait does not count against the fetch timeouts: they bound network time only, so a slow shop is paced rather than timed out. Scraper and review live inspection share one fetcher, so both count against the same spacing; a live inspection gives up after 25 seconds, and a request abandoned while it waits hands its start back. A schema-matrix refresh fetches every review page at that spacing, so it runs in the background, one per review, with a deadline of 90 seconds per page; the matrix endpoint answers `202` while it runs and reports the matrix or the failed fetch on the next poll. A refused URL is not requested: it fails with `RobotsDisallowed` or `RobotsUnreachable`, receives the URL retry cooldown described in [Scheduling and retries](scheduling-and-retries.md#fetch-retries), and neither opens nor closes a [scrape circuit](scheduling-and-retries.md#scraper-circuits), since nothing reached the shop. A redirect to a URL robots.txt disallows is judged by its target's URL ([redirect removal evidence](#redirect-removal-evidence)); only a refusal that is no removal is retried.

The spider reads robots.txt once per crawl, after the root preflight. A root robots.txt disallows fails the crawl as `RobotsBlocked`; an unreachable robots.txt fails it as `ServerError`. The Spider library's own robots handling is off, and its only pre-fetch veto is a regex deny list. So the rules reach it as deny-list patterns, which are exact for `Disallow` rules and for literal-prefix `Allow` exceptions; rules that do not compile into a deny list fail the crawl as `RobotsBlocked`. Other `Allow` exceptions are not carved out, so the spider may skip more than robots.txt asks, never less. When such an exception was written for a `Disallow` (its pattern extends the `Disallow`, as Shopify's `Allow: /*/account/login` does), the crawl diagnostics count the rule and `crawler.spider.robots_rules_failing_closed` names it.

## Stored URLs

The crawler stores a page under the URL it fetched, so the scraper requests and robots.txt judges the same URL the spider saw; a product page the shop also serves under its [canonical URL](#canonical-product-urls) is stored there instead. The only changes are removals: the fragment, credentials, query parameters that do not identify the page, and a query left empty. The spider decodes HTML character references in a link and applies the same removals before Spider requests it, so the URL fetched is the URL stored. Path and query keep their percent-encoding, hex case, parameter order and trailing slash byte for byte. `%20`, `+` and `%2B` stay distinct, as robots.txt rules such as Shopify's `Disallow: /collections/*+*` distinguish them, and so do `/product/1/` and `/product/1`: some shops serve a page under one of them only and answer the other with 404, and a rule such as `Disallow: /product/*/` tells them apart.

Parameters that do not identify a page are closed lists of names, matched case-insensitively ([`query.rs`](../../src/crawler/src/spider/utils/url/query.rs)): tracking and session identifiers (`utm_*`, click ids, osCommerce-style session ids) and product variants, and presentation parameters, the facets, sort orders, list views and currencies under which a shop shows a page it also links without them. Every other parameter is kept, as one the crawler does not know may be the product id (`single.asp?id=113`): dropping it would collapse a shop's products onto one URL, while keeping a stray one only costs a duplicate fetch. `view`, page sizes and bare generic names such as `filter` or `dir` stay for that reason, since Joomla routes pages through `view`, offset pagination counts in page sizes and older shops name pages with the others. So two URLs that differ only in such parameters name one page. Spider does not follow a link that carries a presentation parameter, so facet combinations do not spend the crawl budget; a page the shop links only that way is not crawled. A link with only tracking, session or variant parameters is followed under its URL without them, as some shops link a page only that way (Shopify collections link each product with `?variant=`); Spider skips repeat links by their spelling before the rewrite, so each such spelling still costs a fetch, except that an [incremental crawl](scheduling-and-retries.md#discovery-coverage) does not fetch one whose page it already stores. A shop whose page identity rests on one of these names is not supported yet: per-ListingSource overrides need persisted configuration and are a follow-up.

The spider neither follows nor stores shop actions, printer-friendly copies, back office, downloads and non-HTML files ([`blacklist.rs`](../../src/crawler/src/spider/utils/url/blacklist.rs)). The rules match whole path segments, with or without a file extension (`/cart`, `/wishlist.php`, `/account/login`, `/print`), action and search parameters (`?add-to-cart=`, WordPress's `?s=`, `?print=`), and the actions PrestaShop's `controller` and OpenCart's `route` parameters name, never substrings, so a product slug such as `cartier-tank` stays crawlable. Action words no product slug uses as a word also match as a whole token of a segment or file stem separated by `-`, `_` or `.` (`/product-compare`, `/wishlist_add`, `catalogue_detail_printerfriendly.php`); words that also name products, such as `cart`, `basket`, `register` or `print` (`tea-cart`, `woodblock-print`), match only as a whole segment.

A row stored before these removals keeps its URL: the removed parameters cannot be recovered from the stored spelling, so the spider cannot move it as it moves the earlier spellings below. Such a row is still scraped and judged as the page without the parameters, so a redirect between the two spellings is not a move. Where the spider also stores the page without the parameters, both rows stay until a cleanup retires rows whose stored spelling is not the crawler's spelling, which is a follow-up.

Otherwise a path with and without its trailing slash names one page. A URL pattern takes a URL when it matches the URL with or without the slash, so a pattern written for either spelling takes the page, and URL-pattern inference shows the LLM each page without the slash. A redirect that only adds or removes the slash, or the [language segment](#redirect-removal-evidence) before the path, is neither a URL move nor a redirect to a non-product page, and the URL keeps its stored spelling; a redirect to another page moves the row there only while neither spelling of that page has a row; otherwise the [duplicate-target rule](#duplicate-targets) decides. The review console treats both spellings as one page as well: a review page matches its crawler URL in either spelling, and a second review page or sample label of the page in the other spelling is a duplicate. A page the shop links in both spellings keeps one row, under the slashed spelling, whichever the spider meets first: shops that tell the spellings apart serve the slashed one by default (WordPress and WooCommerce), and a row only ever moves from the unslashed spelling to the slashed one, so the choice never flips back. A crawl therefore stores an unslashed spelling only while it has met neither spelling of the page, still stores the slashed spelling after the unslashed one so the row moves there, and counts the page once.

Rows stored under an earlier spelling move to the fetched spelling when the spider rediscovers the page, and keep their scrape state and raw-capture identity: rows stored without the trailing slash, and rows stored while the crawler re-encoded queries (`%20` as `+`, sorted parameters, decoded path escapes), which cannot be rewritten from the stored form alone, because `+` may have been fetched as `+` or `%20`. Until then the scraper requests the stored spelling, so a shop that answers it with 404 withdraws the listing until the moved row captures it again under the same identity. A row stays put when the fetched spelling already has a row, and a re-encoded row when the shop also links that spelling itself; when several fetched spellings share one earlier spelling, the first in URL order takes the row.

## Canonical product URLs

A shop often serves one product under several URLs: Shopify under `/products/<p>` and under every collection that lists it (`/collections/<c>/products/<p>`), a multilingual shop under a language segment (`/en/...`) as well. The spider stores such a page once, under its canonical URL, through the path every discovered URL is stored by, so the rules apply to every page a crawl stores. They apply in this order ([`canonical.rs`](../../src/crawler/src/spider/utils/url/canonical.rs)):

1. the page's `<link rel="canonical">`;
2. the page's `hreflang` alternate that is the page without a leading language segment, so `/en/x` is stored as `/x` when it names `/x` as a translation;
3. a platform rule, once a page of the crawl carried the platform's markers (Shopify's `Shopify.shop` storefront script): Shopify's `/collections/<c>/products/<p>` is `/products/<p>`, behind the same language segment if any.

The spider reads only a page's `<head>`. A rule proposes a URL only when the ListingSource's product pattern takes both the page and the proposal, and the proposal is another page on the page's own origin (scheme, host and port) that the spider would follow ([never followed](#stored-urls) pages are refused); a canonical link or alternate must also pass the crawl's robots.txt rules. So must the platform rule's URL: where robots.txt disallows `/products/<p>`, a collection page is stored as fetched. Anything else fails closed and the page is stored as fetched: a canonical link to another host, to `www.` or `http` from a page served without them, to a home, category or other non-product page, or one that does not parse; conflicting canonical links; a relative link on a page with a `<base>` element. Storage also keeps the fetched URL when a [rejection](operations.md#manual-authoring) covers the page or its canonical URL, when the canonical URL is no [duplicate target](#duplicate-targets), and when a batch would canonicalize a page onto a page it canonicalizes too, in either trailing-slash spelling, so two pages that name each other never retire each other. Without a product pattern no page is canonicalized: a crawl that waits on a URL-pattern review canonicalizes the pages it stored while waiting only when the decision arrives during the crawl, and otherwise the next crawl does.

A row stored under the duplicate URL or one of its [earlier spellings](#stored-urls) before moves to the canonical URL while no spelling of the canonical URL has a row, and keeps its scrape state and raw-capture identity; a spelling that is itself the canonical URL is not the duplicate's row. Otherwise the duplicate's row is retired with the terminal disposition `DUPLICATE`: the scraper never selects it, a crawl that finds the URL again neither moves nor revives it, and nothing is captured for it: a listing is identified by its `source_listing_id`, which the duplicate shares with its canonical page, so the listing keeps being captured from the canonical URL, and a removal captured for the duplicate would withdraw it. The scraper retires a URL the same way when it redirects to a duplicate target ([scrape completion](scheduling-and-retries.md#scrape-completion-fences)). Nothing revives a retired URL, a [crawl-root move](README.md#listingsource-scope) included.

### Duplicate targets

A retirement is terminal and captures nothing, so only a page that is certainly scraped as the same product under its own row may retire another URL: a product URL of the same ListingSource that is not itself retired, in every trailing-slash spelling that has a row. For the spider, a stored canonical URL qualifies when its row will be such a product URL after the write that stores the page; anything else fails closed.

The scrape reads what the crawler stores at the target right after the fetch, before it extracts anything from the page, so a duplicate costs no extraction and a conflict between identities is never compared for it:

- A redirect to a page that another ListingSource stores, or that the crawler stores as a non-product page it has not retired (a shop that sends sold items to a category page), is a redirect to a non-product page whatever the page shows: the URL captures a removal and stays a candidate ([scrape completion](scheduling-and-retries.md#scrape-completion-fences)).
- A redirect to a product URL of the ListingSource that is scraped under its own row retires the URL as `DUPLICATE`, whichever identity the two pages derive. A product the shop replaced behind the URL by another one is thereby retired instead of failing every pass as an identity conflict; the listing captured under the old identity is neither withdrawn nor reconciled, because nothing shows the product is gone (reconciling identities is [#2489](https://github.com/aura-historia/backend/issues/2489)).
- A redirect to a page whose rows disagree, or that the ListingSource retired as a duplicate, whatever class it was stored with, neither retires nor removes the URL, because a removal could withdraw a listing its canonical page still carries: the scrape is recorded without a capture as `RedirectDestinationUnsettled`, so the URL is checked again at its normal scrape interval.
- A redirect onto a page an [operator rejected](operations.md#manual-authoring) as no product page is a verified removal, with its evidence logged: the operator's verdict says the page the URL now shows is no product, so the product it named is gone. The URL stays a candidate and is not classified `other`, which only a URL requested as the rejected page is. The [mass-removal guard](scheduling-and-retries.md#mass-removal-guard) holds it like any removal.

### Duplicate source listing ids

A shop may serve one product under spellings no canonical rule collapses, such as a product page that differs only in its category, page or sort query parameters. The scraper finds them by identity: a first scrape of a URL (one that carries no identity yet) whose page derives a `source_listing_id` that another product URL of the ListingSource carries and has not retired retires the scraped URL as `DUPLICATE` instead of capturing it, and logs `crawler.product_url_retired_duplicate_of_known_identity`. The row that already carries the identity keeps its scrape state, and the listing keeps being captured from it, so the first stored row wins whatever spelling it has; the rule does not prefer a shorter or canonical-looking URL. A URL that carries the identity itself is a recapture, not a duplicate, and a different identity under the same URL stays an identity conflict ([#2489](https://github.com/aura-historia/backend/issues/2489)). The identity is stored when the raw capture is flushed, so two spellings scraped within one flush window can both be captured; the next pass retires neither, as each then carries the identity. The rows are not reconciled, and the spider still stores every spelling it finds ([#2682](https://github.com/aura-historia/backend/issues/2682)).

## Redirect removal evidence

A product URL that redirects is judged by where it leads, but a redirect withdraws its listing only with evidence that the page is gone. That the target lies outside the ListingSource's product URL pattern is not enough: the pattern is learned from the URLs the spider stored, and shops also redirect live pages, for example to a copy under a language or country segment chosen from the [request headers](#request-headers) or the visitor's country, as Butchoff redirects `/artworkdetail/…` to `/en-us/artworkdetail/…`. A redirect on the URL's own host, bare or `www.`, is removal evidence when it leads to:

- the shop's homepage, with or without a language segment (`/`, `/en-us/`);
- a page the crawler stores as no product page of the ListingSource ([duplicate targets](#duplicate-targets));
- a page outside the product URL pattern on which every cached schema of the ListingSource fails, judged once more against the live schemas in case an approval changed them during the scrape; a page that leaves a required value empty records [`MissingRequiredValue`](extraction-and-review.md#missing-required-values) instead;
- a page a [removed-page template](extraction-and-review.md#removed-page-templates) matches, as for any fetched page;
- a page an operator rejected ([duplicate targets](#duplicate-targets));
- a page outside the product URL pattern that robots.txt disallows (below).

A redirect that only adds, removes or replaces the language segment before the path (`/x` to `/en-us/x`, `/en/x` to `/de/x`, with the segments the [canonical-URL rules](#canonical-product-urls) recognize) is never removal evidence: like a redirect that only changes the trailing slash, it leads to the page the row is [stored under](#stored-urls), which is extracted from the target, or opens or joins a product-schema review when the cached schemas fail on it.

A redirect that changes the path and adds a language segment (`/artworkdetail/1/old` to `/en-us/artworkdetail/1/new`) is judged as the target without the segment when the row is stored without one, and the row moves to that spelling when the product URL pattern takes it, so the row stays a product URL of the ListingSource. A target the pattern takes only with its segment keeps it, as does a row stored with a segment. Recognizing a segment is a guess about the path (`/art/12`), so the segment is dropped only where the pattern takes the rest.

A redirect outside the pattern to a page a cached schema extracts moves the row there like any redirect to another product page. Without a cached schema nothing shows whether such a page is a product page, unless an operator rejected it: the scrape records `RedirectTargetUnverified` without a capture, so the URL returns at its normal scrape interval, and the page opens no schema review, seeds no schema generation and costs no LLM call; a schema comes from the pages the spider stored. A ListingSource without a usable pattern treats only the homepage as a non-product target.

A target robots.txt disallows is not fetched, so it is judged by its URL alone, on the shop's own host. The homepage and a page outside the product URL pattern are removal evidence: a shop that sends sold items to a disallowed `/sold/` withdraws them, logged with the target as the final URL and no status (`REDIRECT_TO_HOMEPAGE`, `REDIRECT_TO_DISALLOWED_PAGE`). A page the pattern takes, the page itself behind a language segment, a target on another host and any target of a ListingSource without a usable pattern fail closed as a `RobotsDisallowed` refusal. A removal is captured only when the [mass-removal guard](scheduling-and-retries.md#mass-removal-guard) admits it.

## Rate-limit answers

A shop that answers a spider page with 429 has asked for less traffic, so the spider stops the crawl instead of pacing it down. A 503 with `Retry-After` or a spent quota asks the same, a maintenance page included: `RateLimit-Remaining: 0`, `X-RateLimit-Remaining: 0`, or a structured `RateLimit` field (IETF draft) that lists any policy with `r=0`, such as `RateLimit: "default";r=0;t=30`. A malformed field or a quota value that does not parse says nothing. The wait is the usable `Retry-After`; without one, the `t` (reset seconds) of the `RateLimit` field's policies (the longest of the spent ones, unknown when a spent one has none, else the longest of all) or the draft's earlier `RateLimit-Reset` seconds. `X-RateLimit-Reset` is not read, since shops send it as an epoch or as seconds. Every wait is capped at 24 hours like `Retry-After`. A 503 with neither never counts, nor does any status Spider synthesizes for a page it could not fetch (a transport failure, a body-less answer). The pages delivered before that answer are kept, the crawl diagnostics record the answer with the wait it asked for, and the crawl ends as `RATE_LIMITED`; the ListingSource's next crawls then run slower until one completes ([scheduling](scheduling-and-retries.md#rate-limited-crawls)). With at most one usable page it fails as `RateLimited`. A 429 limits the client, not the page, so Spider does not retry it; a 503 keeps Spider's bounded retries. Spider's own reading of a refused root (a vendor block, a JavaScript challenge) keeps precedence over the rate-limit signal.

The crawl diagnostics also count every delivered page by the status class of its final answer (2xx, 3xx, 4xx other than 429, 429, 5xx), so a crawl that was refused or throttled part-way no longer looks complete.

## Bot challenges

A shop, or the firewall in front of it, sometimes answers a request with a bot challenge or interstitial instead of the page: a Cloudflare challenge, a hoster's bot-check page, a `202` interstitial. Such an answer is a fetch outcome, never a page. The scraper's fetcher, which review live inspection shares, fails it as `BotChallenge` before anything is extracted, so it records no capture, removal, sold state or `MissingRequiredValue`, is never a schema seed page and never opens a schema review or schema generation. Its URL records `BotChallenge` with the answer's status and is retried on the [transient fetch-failure cooldown](scheduling-and-retries.md#fetch-retries), not inline, since an immediate repeat meets the same challenge; the answer still proves the shop responsive, and a challenge counts towards the [status burst](scheduling-and-retries.md#scraper-circuits) whatever status it came with, so a shop that challenges every page cools down as a whole instead of having each URL refetched every cooldown. A console live fetch that meets one answers `502` with `reason` `BOT_CHALLENGE` and says so, so a reviewer never reads it as a page failing the schemas. A spider crawl whose root page is a challenge fails as `CloudflareChallenge` or `BotProtection` instead of a tiny crawl, whatever status the challenge came with, and the crawl diagnostics count every delivered page that was one (`bot_challenge_pages`).

A spider crawl whose pages were mostly challenges has not seen the shop either. When bot challenges are more than half of the pages a crawl received and the run finds no product URL among them, it fails as `BotProtection`, whoever served the challenges, instead of `NoProductUrls`, `NoUrlPattern` or an inference sample too small to classify: the shop's protection, not a missing catalogue, kept the product pages away, so the run takes that kind's transient cooldown, and its failures escalate to `NEEDS_OPERATOR` on the [shared failure streak](scheduling-and-retries.md#spider-failure-escalation), since only a person can resolve a shop's block. For the same reason it does not classify its URLs when the ListingSource's stored product URL pattern matched none of them, nor when it has none yet: challenges open no URL-pattern review and no inference replaces a pattern that may still fit the shop or runs on challenged pages. A first classification waits at its page threshold while challenges are most of the pages received so far; a crawl whose pages end up mostly challenges stores no URL and reports the skipped classification as an inference sample too small to classify, counting only the pages that were not challenges, which the rule above then turns into `BotProtection`. It still replaces the ListingSource's [frontier](scheduling-and-retries.md#discovery-coverage) like the failure it replaces. At half or less the run keeps its own failure, and a run that finds product URLs succeeds however many of its pages were challenges.

Recognition is conservative, so an ordinary page is never taken for a challenge ([`bot_challenge.rs`](../../src/crawler/src/network/bot_challenge.rs)). It considers only a success answer or `403`, and a `405` only with AWS WAF's own evidence, the status AWS WAF serves its captcha with; any other `405` keeps its meaning, and `429` and `503` keep their [rate-limit](#rate-limit-answers) and circuit meaning. It then needs one well-known marker: a vendor's challenge header (`cf-mitigated: challenge`, an AWS WAF challenge action, SiteGround's captcha header), markup only a vendor's challenge page carries (Cloudflare's challenge script, AWS WAF's challenge and captcha page, DataDome's captcha, SiteGround's captcha redirect), or the exact title of a known interstitial on a page small enough to be one. A vendor's server header, cookies, injected detection scripts or challenge host named in a policy are no evidence: many healthy shops sit behind the same vendors. A challenge the detector does not know is fetched as a page, as before.

A firewall's block page is no challenge: no client passes it. Cloudflare's block pages, unless they carry Cloudflare's challenge script, therefore keep the meaning of the `403` they were answered with: the page titled "Attention Required! | Cloudflare" or with its "Sorry, you have been blocked" error details, and the "Access denied" pages for the errors 1005 (ASN), 1006 to 1008 (IP address), 1009 (country), 1010 (browser signature), 1012 and 1020 (firewall rule). Only these codes mark the latter, since Cloudflare's other errors share its templates and title, rate limiting (1015) among them. Akamai's "Access Denied" page (title, the sentence "You don't have permission to access" and the `errors.edgesuite.net` reference link; catawiki.com answers a datacenter client with it) is a block too: Akamai serves it for every refusal of its edge and it holds no script or challenge, so no client passes it. A page with that title but without the Akamai reference link is a plain `403`. A block page's URL records `HTTP_403` like any other `403`, and a spider crawl whose root is one fails as `AccessDenied` with that kind's cooldown and the reason `firewall_block_root_page`, ahead of Spider's own reading of the vendor. The failure log names the block's vendor and the marker that proved it (`hard_block`), never the page, which can show the crawler's IP. Below the root a block page is a delivered `403` like any other: it does not count as a `bot_challenge_pages` page and does not stay in the frontier, since no later crawl passes it either.

## Resource rails

Spider fetches use a bounded per-request timeout plus whole-crawl bounds: at most 500,000 pages and 10 minutes, raised for a robots.txt `Crawl-delay` ([crawl-delay budget](scheduling-and-retries.md#discovery-coverage)). [Scheduling](scheduling-and-retries.md#spider-crawl-completion) defines how a crawl stopped by either bound is recorded. Its response limit must be supplied through `SPIDER_MAX_SIZE_BYTES`; accepted values range from 1 MiB through 8 MiB, and the limit applies to declared and streamed response bodies.

Scraper HTML and image requests also use bounded redirects, timeouts, and response bodies. An HTML fetch attempt starts from a fixed timeout and grows with the host's smoothed response latency, to a fixed upper bound, so a shop that is slow throughout is waited for instead of timed out; the whole fetch with its retries grows by the same amount, while DNS and connect timeouts stay fixed. Image-cache results never exempt the current target from destination checks.

On a shop that redirects every path to its trailing-slash form (WordPress and WooCommerce by default), a URL stored without the slash costs a redirect on each fetch: where the shop links paths without it, and for rows [stored before the crawler kept the slash](#stored-urls) until the spider rediscovers them. Once the scraper's fetcher sees a host redirect a path to exactly its slashed form, later fetches to that host request the slashed form of extension-less paths directly; a slashed form answering 404 or 410, or refused by robots.txt, is followed by a fetch of the stored form within the same budget. A host that redirects a slashed path back loses the preference. The preference lives in process memory only and never changes a stored URL.

These rails are safety and availability limits, not a claim that every public address is reachable from every deployment.
