## Concrete wrong schemas found

1. Hingstons schema 2 `state` = `.product_meta`. Live extraction: `Categories: Antique Oak Furniture - SOLD, Antique Sideboards - SOLD`. Category text, not availability. It only "works" because this shop renames categories with "- SOLD".
2. Hingstons schema 2 `source_listing_id` = `div.product[id]` -> `product-53036`; schemas 0/1 use `button.single_add_to_cart_button[value]` -> `53036`. When a product sells, schema 0 stops applying, schema 2 produces a different identity, `handle_successful_scrape` rejects with `crawler.product_url_move_rejected_identity_conflict`, the outcome is `skipped` with no durable state, so the URL is retried every pass and the sold transition is never captured.
3. Harrison: the primary page fails both schemas live. `images` = `div.product-image-grid a[rel^="lightbox"]` with cardinality `all`; the page has 8 image anchors plus 12 thumbnail anchors with `href="#"`. One element without an image candidate fails the whole page (`rule.rs` `extract_image_url_from_element`). Seed pages with 8 images or fewer pass. The reviewer approved it anyway; the console allowed that.
4. Collinge schema 1 is the "sold" template, but all 4 seed pages were available products, so it was never validated against a sold page.
5. `.env` sets `CRAWLER_SCHEMA_LLM_REVIEW_MODE=jev_auto`. That value is invalid; `SchemaLlmReviewMode::from_env` silently falls back to `auto_approve_high_confidence`. The variable is undocumented.

## After the manual approvals (19:01 to 19:11 UTC)

- Scraping resumed: Collinge 46 captures, Harrison 45, no domain failures.
- Harrison: within 2 minutes the primary page triggered fresh generation, auto-approved on that single page. New schema 2 extracts `images` as the `href` of the first non-`#` anchor with cardinality `first` (one image only) and takes `rawYear`, `rawHeight`, `rawWidth`, `rawDepth` from `span[itemprop="description"] p:nth-of-type(4..8)`. Positional paragraphs in free-text descriptions will hold different content on other products. Because ranking counts populated fields, this schema can outrank schema 0 wherever both apply.
- Collinge: fresh schema 2 auto-approved on one page. It takes price from `.product__details li:nth-child(6)` and `source_listing_id` as text of `li:nth-child(5)`, while schemas 0 and 1 use `input[name="page_id"]`. That recreates the identity-conflict problem seen on Hingstons.
- Collinge: 4 URLs ended in `SchemaRegenerationExhausted` because the details-list price selector does not match their layout. They retry after the 30 minute cooldown and will regenerate again.

## Structural causes (code)

- Auto-approval gate = model self-reported HIGH + every seed page has non-empty `title` and `state` (`schema_review_gate.rs`, `schema_evaluation.rs::raw_extraction_has_required_values`). Nothing checks that state resolves to an availability, price parses, title differs between pages, or images are product images.
- Fresh generation evaluates coverage on the single triggering page with the schema that already applied, so the gate is tautological; HIGH then persists.
- `review_required` defaults to false in `server.rs` and `dev.rs`; in that mode every generated schema persists with no matrix at all.
- Ranking at scrape time (`score_prepared_product`) counts populated fields, including an unresolvable `state`, so a richer wrong schema beats a correct minimal one. No per-schema success tracking, no retirement (issue #1545), lists only grow, no dedupe on save.
- `REJECTED` / `NEEDS_REPAIR` are never read by the scraper: after a rejection the next pass regenerates immediately (LLM budget) and will likely produce the same schema.
- Correction loop feeds back only a code string (`llm_runtime.rs::correction_request`); semantic failures from the matrix are never sent back to the model.
- Projection drops `header`, `footer`, `nav`, `aside` subtrees and JSON-LD, collapses wrapper classes, and silently stops at 2,000 nodes with no marker or log.
- Seed pages: `ORDER BY RANDOM()`, mixes `DORMANT_SOLD`, no removed/soft-404 filter, no template diversity (issue #1581).
- Text extraction joins descendants with `""` (`Sold€1.200`).

## Console UX under production incidents

- A pending review silently blocks a whole source; the UI shows "1 Pending" but not "1122 URLs blocked for 25h". `/api/listing_sources` already returns `blocked_urls`, `pending_reviews`, `llm_calls_count`, `last_successful_crawl`; `app.js` never calls it.
- No view of scrape health at all: domain failure streaks, URL error kinds, LLM budget, identity-conflict loops, fresh-generation churn. The only path is CloudWatch.
- Approve is allowed when the primary page fails every schema (issue #2056).
- `/api/reviews` polled every 5s re-renders the list; selection is lost on refresh (issue #2058).
- Extracted Data shows the schema chosen on the Selector tab; to see which schema actually covered a page you switch tab, change schema, switch back. Coverage line says "1/1 covered" while the visible schema failed.
- Reject and Needs repair have no visible consequence (and none in the scraper).
- Auto-approved reviews look identical to human-approved ones except for a note; there is no "re-open" action.
- Preview iframe did not render in the embedded browser (inspect request blocked client-side); issue #2054 covers styling.

## Console UX research (click-through, 2026-10-14 19:25 UTC)

Measured in the browser at 1440x900 and with curl against the running `dev` server.

| Measurement | Value |
|---|---|
| Preview reloads for 5 clicks (2 schema chips, 3 tabs) | 5 |
| Server time per preview reload (live shop fetch) | about 2.6 s |
| Re-evaluate (matrix refresh) | about 12 s |
| Polled `/api/reviews` payload for 6 reviews | 144 KB every 5 s |
| Left edge of first extracted value in a 1440 px window | 1422 px |

Data loss risks:
- Editing an approved review rewrites the whole live schema list from that review (`persist_product_schemas`). Older approved reviews are never superseded and stay "Live schema editable". The Collinge initial review has 2 schemas while the live list has 3; one "Save field" there would silently drop the fresh schema.
- Save field, Move, Add and Delete schema on an approved review go live at once, with no confirmation, diff against live, or undo.
- Approve, Reject and Needs repair use `prompt()`; cancelling the notes prompt still performs the action (#2056).

Wrong or misleading information:
- Fresh-generation reviews open on Schema 0, but the generated schema is the last one. Nothing marks which schema is new (the review stores existing plus new).
- Extracted Data shows raw strings only. On Collinge it shows `Stock Number: 38088` as ID, `Price: £795` and state `Enquire about this Antique` without saying whether price parses or state resolves to an availability.
- "Open URL" changes the preview, but Extracted Data still shows the review page's results, so a custom URL looks evaluated when it is not.
- Error text says "no element matched selector" when the selector matched an element with empty text (Collinge schema 0 price: match count 1).
- The header shows "Not approved by LLM", "Approve" and "High" together.
- The sidebar is titled "Pending Reviews" but lists all statuses; the list is capped at 200 rows with full payloads.

Performance and flow:
- `rerenderWorkbench` rebuilds the whole detail view, including the iframe, on every schema chip, field, tab, page or rule-type change. Each rebuild refetches the shop, loses preview scroll and the picked element, and costs about 2.6 s.
- Review pages store only `html_hash`, so the preview and matrix always use the live page. Reviewers never see the HTML the model saw; sold or changed pages make old reviews unreproducible.
- Re-evaluate and Save run 12 s with no progress indicator or disabled buttons.
- API errors in button handlers are not caught; failures appear only in the browser console.
- Fresh reviews contain only the triggering page; there is no way to evaluate a schema on other product URLs of the source.
- Preview CSP allows only `'self'`, so shop CSS and images do not load (#2054).
- No URL state, no keyboard navigation, no status filter or sort (#2058).
