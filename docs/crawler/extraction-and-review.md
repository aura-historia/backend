# Crawler extraction and review

## Extraction contract

The scraper fetches active and sold product URLs, detects verified removed-page templates, and first evaluates cached schemas. It applies every cached schema to the same parsed page, checks each candidate's extraction independently, and ranks the plausible candidates. A bad candidate rejects that schema only; an external or system failure aborts the attempt and does not trigger generation.

Raw extraction remains source evidence. The crawler keeps raw strings, ordered image candidate groups, duplicates, relative values, rejected candidates, and configured raw attributes. It stores a validated, canonical image projection separately for generic raw values. Validation keeps the first candidate of each group that is a safe public target and not too small: a width and height in the URL query or path decide, otherwise a probe reads the size from the image. An image whose size stays unknown is kept, unless its URL names a thumbnail; that name alone never rejects an image, because shops also name full-size uploads that way. Extracted values must never invent auction identity, lot data, or attribution.

A text rule captures the visible text of each matched element, trimmed at both ends with its internal whitespace kept ([`visible_text.rs`](../../src/crawler/src/scraper/css_selector/rule/visible_text.rs)). A `<br>` or a block element boundary starts a new line, and table cells are separated by a space, wherever markup whitespace does not already separate the text on either side, so `Top Hat<br>Pen` does not become `Top HatPen`; inline elements such as `span`, `a` or `sup` add nothing, so `£<span>2,800</span>` stays one value. Struck-through text (`del`, `s`, `strike`), such as a superseded price, is dropped unless it is all the element's text, and whitespace already next to it stands in for a following break, so `£25 <del>£50</del><br>VAT` gives `£25 VAT`. `source_listing_id` joins its text as written instead, so a captured identity does not change with how its text is laid out. Removed-page templates match the separated text, whitespace-collapsed and lowercased, because a matched notice is compared with the titles cached schemas extract from the same page.

A rule evaluates its primary selector and then its `additional_selectors`, in that order, and its cardinality decides what the additional selectors mean ([`rule.rs`](../../src/crawler/src/scraper/css_selector/rule.rs)). With `first`, the default, they are fallbacks: the first selector that yields a value wins and the later ones are not evaluated, so a price rule can name the structured-data price before the visible one. With `all` they aggregate: every selector's matches are collected in selector order, so a gallery or a description can span separate blocks. Aggregation never captures the same content twice: an element is extracted at most once across all selectors of a rule, and an element nested inside, or containing, an element the rule already extracted is skipped, so a description rule that selects a container and its paragraphs keeps the container only. `description` and raw attributes keep equal text from separate elements once, in order; `images` keeps its duplicates as raw evidence and the [plausibility checks](#plausibility-checks) report them. A `first` text rule that yields no value reports whether its selectors matched no element or matched only empty ones, so its error and per-field log line tell a selector that does not fit the page from a page that leaves the value empty. The schema matrix counts a text rule's empty elements apart from its matches, so the review console makes the same distinction for an optional field left empty.

A matching page hash and effective schema-set fingerprint can skip extraction. Otherwise the crawler hashes its generic raw-input envelope. Equal input refreshes crawler scrape metadata without creating a new operational capture.

The crawler does not normalize extracted values. Price parsing, currency, availability and language belong to the [ProductListing normalization worker](../events/flow.md#productlisting-write-flow), which reports what it cannot normalize. Generic raw values keep every supplied price, state and text value as extracted.

### Plausibility checks

Before a candidate is used, the crawler checks the raw strings it extracted from one page ([`plausibility.rs`](../../src/crawler/src/scraper/plausibility.rs)):

- `title` is not blank; `state` is not blank and no longer than a label;
- `price` and the estimates, when present, are not blank, no longer than a label and do not consist of zero digits only;
- no `title`, `state`, price, estimate or `description` value carries CSS rules or script source;
- the extracted `source_listing_id`, checked before the URL-hash fallback replaces a blank one, is present, capturable and one identifier rather than a list of three or more class-like words, such as a whole `<body class>` that holds the post id but changes with the template and the product's tags;
- `images` do not repeat an image.

Each finding names its field and check. At runtime a `title`, `state`, CSS/script or uncapturable-identity finding rejects the candidate; price, estimate and image findings rank it below candidates with fewer such findings, and completeness and stored order break ties; a blank or word-list identity does not affect selection. Free-text states such as "Viewing by appointment only." pass, and the worker reports them. Rejected candidates and schema repair stay crawler-side and never enter the business [normalization replay corpus](../normalization-replay.md).

### Missing required values

A `title` or `state` rule takes its first non-blank value, whatever its cardinality. One whose matched elements are all empty yields a blank value instead of failing, so the blank check rejects the candidate with the rest of its extraction intact, and the schema matrix and review console show the field as blank rather than unmatched. When no cached candidate is plausible and one was rejected only for blank `title` or `state` values, the page leaves a required value empty where a cached schema found its element. A new schema cannot supply it, so the scraper opens no review, joins none and runs no generation; the URL records `MissingRequiredValue` with the field instead, stays a product URL, and is [not retried](scheduling-and-retries.md#fetch-retries): the next scrape at its normal interval evaluates the page again, at no review or generation cost. The listing keeps its last capture, and a later scrape that extracts the value clears the outcome. A page on which the cached schemas find no title element at all cannot be told apart from a new template and still needs schema work.

An untitled product page is skipped, not captured under a title the crawler derives from other content such as a description line or an image's alt text: that would not be the shop's name for the item, and the crawler extracts values without deriving or normalizing them. Where a shop shows the name in another element of the page, the reviewer names that element as a fallback in the title rule's `additional_selectors`, and the schema matrix checks it like any other selector.

The review pages show different products, so the review gate also compares each candidate's extractions of them ([`cross_page.rs`](../../src/crawler/src/scraper/plausibility/cross_page.rs)): a `title` or `source_listing_id` that two pages share names the shop, the category or a page template, and an image that two pages share is a default share image or placeholder rather than a product photo. Images compare by the URL they resolve to, without the fragment, and without the query when the path names an image file, because sizes, cache busters and CDN signatures differ per page. Runtime extraction sees one page at a time and cannot run these checks. A shop that gives two products the same title fails them too; a reviewer approves such a schema knowingly.

Every schema of a ListingSource must derive the same identity from a page, because runtime selection may pick any of them and a scrape whose identity differs from the one the listing was captured under is rejected as a [conflict](scheduling-and-retries.md) rather than captured as a second listing. The matrix therefore also compares, on each review page, the identities of the candidates that apply to it ([`identity_agreement.rs`](../../src/crawler/src/scraper/plausibility/identity_agreement.rs)): an identity another applying candidate contradicts, or one that differs from the identity the crawler URL naming the page was captured under, however the two URLs spell the page, is a finding that names the contradicting identities. A schema written for a sold page whose identity element differs from the active-page schemas' therefore shows the conflict even when it is the only schema that applies to that page. Blank and uncapturable identities are left to the per-page checks.

The schema matrix lists the per-page, cross-page and identity agreement findings of every candidate on every review page, and the review console shows each next to its field. Any finding on any candidate's extraction keeps a generated schema out of auto-approval, including an extraction that a rejecting finding withdrew from a page another candidate covers, and a blank identity: the identity rule is applied to every review page, sold, archived and price-on-request variants included, and a schema without an identity rule, or whose rule matches nothing on one of them, reports a blank identity there. At runtime such a page gets the URL-hash identity, which changes when the product moves and, where the page was captured from another variant, is rejected as an identity conflict, so a reviewer approves such a schema only knowingly.

Shipping interpretation runs in downstream raw normalization using the pure `product-listing-normalization` crate. It
combines item-specific `rawShipment`/`rawShipmentNote` text with description context;
contradictory or unsupported delivery clauses veto the observation. Duration ranges
remain complete text with their units and dispatch/delivery context.
Selectors must exclude shared footers and site policies. Explicit phrases cover all 14
catalog languages; phrase tables, language fixtures and input bounds are executable in
[`shipping.rs`](../../src/product-listing-normalization/src/shipping.rs). Interpretation
uses no LLM, interpretation agent or model fallback, and adds no schema-generation calls
or native description ingestion.

Successful page fetch time travels as the crawler capture's `source_occurred_at`, outside
the content hash. Schema evaluation, normalization, capture retries and queue delivery keep
that acquisition time. Historical captures without it remain readable and cannot establish
shipping observations. Matching page/input hashes retain the existing capture deduplication:
they do not advance shipping observation time. A new immutable raw revision can observe
unchanged shipping assertions when other captured item content changed. See the
[shipping contract](../shipping.md#deterministic-crawler-item-assertions) for application rules.

## Schema lifecycle

Fresh generation begins only after cached candidates are exhausted. It creates a new schema from the current page; it never edits a cached schema. A generated schema persists only after it applies and its extraction passes the rejecting plausibility checks.

Initial generation is product-schema-only: its response contract offers no page classification, every seed sample is treated as a product page, and a sample the model considers non-product is excluded from schema coverage and reported as a risk rather than classified. Single-page classification may produce a product schema, a verified removal, or a verified non-product result. A removal needs selector-bound evidence and results in raw deletion capture. A stored removed-page template is removal evidence only while no cached product schema still applies to the page with a title other than the not-found notice and, when the crawler URL already carries a captured source listing id, the same identity; a related-item card on a removed page is therefore not product evidence. When product evidence exists it wins, the page is scraped normally (a candidate that then fails a rejecting plausibility check reaches fresh generation, not withdrawal) and the conflict is logged as an over-broad template to fix. A removed-page regex that matches any text is rejected both when proposed and when applied. A non-product result changes that URL only; one page never rewrites a domain URL pattern.

Every generated product schema must pass deterministic rule validation (selector syntax and attribute names) before it can be reviewed or persisted. An invalid response is returned to the model with a fixed correction code plus the offending field and value during bounded response correction, and the retry log carries the same detail without the prompt or HTML; if it stays invalid, generation ends with a schema-generation validation failure. The review gate rejects invalid candidates before review persistence, so review artifacts and approved schemas only ever contain valid rules, and model output is never reported as a database failure.

Generated selectors are grounded in page structure. Optional fields remain absent rather than guessed. A configured optional rule (identity, description, price, price estimates, raw attributes) that matches nothing on a page leaves that field empty with a per-field diagnostic; it never fails the page, so one page without a description does not reject the schema or trigger fresh generation. Title and state fail closed on a miss, or on [empty elements](#missing-required-values) through the blank check, and images fail closed unless the image container exists and is empty. The `images` rule skips matched elements without a value (no image URL candidate, or no attribute of an `attribute` rule), such as `href="#"` slots a gallery mixes in with its image links, and fails only when every element it matched lacks one. Such a gallery fails the page: its selector matched elements, so it is not treated as an empty container. Rules of other fields still fail on an element without their attribute. The schema matrix counts the skipped elements per page so a reviewer can tighten a loose selector; the count is review information and does not block deterministic approval. The schema matrix reports the [plausibility findings](#plausibility-checks) of every candidate on every page; a rejecting finding fails that page like an apply error, so the page is not covered. The schema matrix and the review gate report optional-field misses separately from page failures: a miss on some pages stays visible to the reviewer and does not block deterministic approval, while an optional rule that matches nothing on every page its candidate applied to is a defective selector and keeps a generated schema in human review. The matrix counts only matches with visible text for a text rule, because a blank element yields no usable value: a price selector that matches only blank cells, such as a spacer next to the price, is such a total miss rather than an approvable schema that captures the shop without prices. At runtime a description or price miss is logged at warn level so selector drift on cached schemas stays visible at the production log level; identity, estimate and raw-attribute misses stay at debug or trace. State selectors represent availability or a cart action, not price text. Raw attribute selectors are review/display inputs and participate in the raw-input hash; an attribute reaches existing cached schemas only through a [review edit](#review-rail) or regeneration.

## Review rail

The review rail records generated URL-pattern and product-schema artifacts as auditable state. Artifacts may be pending, approved, rejected or superseded. When review gating is enabled, pending artifacts do not become active crawler configuration.

A reviewer gives a pending review one of three verdicts:

- **Approve** (`POST /api/reviews/{id}/approve` with the `expected_candidate_version` the approver read) makes the candidate the active configuration, supersedes other pending reviews of the same artifact and releases the work waiting on it for an immediate retry. An approval based on another version is refused with the 409 of a stale candidate edit, so an edit made since is never approved unseen, and approval moves the review past the approved version, so an edit based on the pending review is refused instead of rewriting the live configuration. Approving a URL pattern also classifies the domain's stored active URLs with the decision, so a crawl that [waited on the review](scheduling-and-retries.md#spider-crawl-completion) needs no second crawl.
- **Reject** (`POST /api/reviews/{id}/reject`) closes the review without changing configuration and, like approval, releases the work waiting on it: a domain whose crawl waits on a URL-pattern review, so its next crawl can open a new one, and the pages [waiting on a product-schema review](scheduling-and-retries.md#fetch-retries), for an immediate retry. Rejecting a manual schema review also classifies its seed and triggering pages as non-product pages ([manual authoring](operations.md#manual-authoring)).
- **Needs repair** (`POST /api/reviews/{id}/needs-repair` with a non-blank `notes`) records why the candidate needs repair and when, and leaves the review pending. The review keeps its candidate, pages and waiting pages, stays editable, holds back exactly the work any pending review holds back, and remains the one pending review of its artifact, so no second review opens. The review API returns the latest note and time as `repair_request`, and the console marks a pending review with one as waiting for repair. The reviewer repairs the candidate and then approves or rejects the review; a repeated needs-repair verdict replaces the note. Reviews stored with the legacy terminal `NEEDS_REPAIR` status stay closed.

A verdict on a review that is no longer pending is refused with 400 and an `error` message. Every review and review-page route answers an unknown review or review page with 404 and an `error` message.

Approving a product-schema review needs a candidate that covers every review page, counted as the console counts coverage: a page is covered when the candidate's [removed-page templates](#removed-page-templates) capture it as removed in the review's stored schema matrix, or else when at least one candidate schema applies to it there, as the deterministic coverage of [schema lifecycle](#schema-lifecycle) defines it; a page the stored matrix did not evaluate is not covered, and a template that matches a page a candidate schema still extracts leaves that page to the schemas. Without a stored matrix, or with one that no longer decodes, every page counts as not evaluated; a candidate change drops the stored matrix, so a stored matrix never vouches for an older candidate. An approval with incomplete coverage is refused with 409, an `error` message and the review's current `coverage` (`covered` pages, the `removed` pages among them, `total` and `not_evaluated` pages), and the review stays pending, unless the request carries that same coverage as `acknowledged_coverage`; the console sends it only after the reviewer confirms a dialog that states the counts. An acknowledgement of other counts, such as one confirmed before a page joined or a matrix was stored, is refused with the same 409. The check and the approval run under the review's row lock, which page joins, candidate edits and matrix stores take too. URL-pattern reviews have no page coverage; their approval ignores the acknowledgement.

A review records its ListingSource, and URL-pattern reviews also record their domain. Candidate changes increment the review version and invalidate any cached schema matrix, so a stale live inspection cannot overwrite current review state. A matrix refresh fetches the pages the review holds when it starts, then evaluates on them what approving the review's current candidate would make live: its schemas, merged with the live list for a legacy single-schema append or repair, and its removed-page templates rebased onto the stored ones. The matrix records that evaluation as `live_evaluation` (the candidate version, a fingerprint of the evaluated schemas and templates, and when the pages were fetched), and the matrix API answers it with `not_evaluated_pages`, the review pages it did not evaluate. Pages that join the review while it runs, such as waiting pages, do not fail it: it stores and answers the matrix of the pages it evaluated, which names them, and the console marks a review page missing from that matrix as not evaluated, and counts it as not covered, until the next refresh. When the candidate changes after that evaluation, or a page it evaluated is removed, before the matrix is stored, the refresh stores nothing and is answered 409 with the review's current `candidate_version`; the console shows why and evaluates again only when asked. The matrix summary schema generation records judges the generated matrix only, so it leaves with that matrix: dropping the cached matrix or storing a refreshed one removes it. Review identities and matrix references use the TypeID policy in [object IDs](../object-ids.md).

A reviewer edits a product-schema candidate as a whole (`POST /api/reviews/{id}/candidate` with the candidate's keys), which also adds or removes schemas, or one rule at a time (`POST /api/reviews/{id}/schema-field` with `schema_index`, `field` and `rule`; only an explicit `null` rule deletes an optional one, a missing `rule` is refused): a core field by its schema key, a raw attribute as `raw_attributes.<key>`. The console offers the keys of the [raw attribute registry](../../src/crawler/src/scraper/css_selector/raw_attribute_registry.rs) (`GET /api/raw-attribute-keys`), and an edit may introduce only those; a key the candidate already holds, such as one generated before the registry named its keys, stays editable and removable. Both edits also carry the `expected_candidate_version` they were based on, the `candidate_version` the review API reported, and are refused with 409 once the candidate has changed since, so concurrent writers, such as a human reviewer and the author agent, never silently overwrite each other's edits; the writer reloads the review and applies its edit to the current candidate. An accepted edit answers with the review's new `candidate_version`, a refused one with an `error` message, and a 409 that carries `candidate_version` names the review's current version: the request may be retried once the review is reloaded. Adding or removing a review page changes the page set, not the candidate, and takes no version: adding a page twice is refused as a duplicate and a removed page is gone, so page changes cannot overwrite each other. The next matrix evaluates the whole edited list.

A reviewer can add further pages of the ListingSource to a pending or approved product-schema review (`POST /api/reviews/{id}/pages` with `{"url": ...}`, or the console's Product View), such as sold, price-on-application or photo-less variants, so the schema matrix tests the candidate beyond its seed pages. Only http(s) URLs on the default port and without credentials on one of the ListingSource's domains are accepted, checked before the fetch and again on the final URL after redirects. A redirect to a page that is not a product page (outside the domain's decided URL pattern, or the homepage while none is decided) is refused. A page already on the review under the crawler's URL normalization, `www.` or scheme spelling is a duplicate, and a reviewer adds a bounded number of pages per review. A reviewer can remove a page they added (`DELETE /api/review-pages/{id}`), for example once the shop has deleted it; seed pages cannot be removed. Adding or removing a page drops the cached matrix. These pages carry the `REVIEWER_ADDED` role and are no operator verdict: rejecting the review does not classify them as non-product pages.

A page that fails every cached schema while the ListingSource's product-schema review is pending joins that review instead of opening or generating another. The crawler attaches it once per page identity with the `WAITING_PAGE` role, up to a bounded number per review, and drops the cached matrix, so the reviewer sees each template variant that needs the schema. Further failing pages wait without being attached. A reviewer can remove a waiting page like one they added, for example once the shop has deleted it; a removed page that still loads and still fails every cached schema joins again on its next retry. Waiting pages are no operator verdict either.

Editing an approved product-schema review rewrites the ListingSource's live schema list, so it is refused unless that review's candidate is still the live list, which the review API reports as `candidate_is_live` and the console shows by offering edits on that review only; approval stores the list that went live, including a merged append or repair, as the review's candidate. Once a later review has changed the live schemas, the schemas of older approved reviews are read-only. Unused schemas are not retired automatically: the schema matrix shows every candidate's outcome on every review page, the console names the schemas that apply to none of them, and a reviewer who confirms that the shop no longer uses a schema's template deletes it from the candidate of a pending manual review, whose approval replaces the live list, or of the approved review whose candidate is still the live list.

Every accepted review mutation appends one event to the review's append-only trail in the mutation's own transaction: candidate and field edits, removed-page declarations among them, reviewer page additions and removals, needs-repair, approval and rejection. A refused or failed mutation appends none; an event is never changed and is deleted only with its review. An event records its actor, its action, the review's `candidate_version` after it, a verdict's notes and the action's details. The actor is `AGENT_AUTHOR` or `AGENT_REVIEWER` for a request with the author or reviewer agent's [token](operations.md#review-agents), `HUMAN` for the review token, a browser session or the `dev` binary's local console, and `SYSTEM` for the crawler's direct approval of an inferred URL pattern in `auto` mode; events of the single review agent that preceded the two roles keep `AGENT`; the crawler's other writes, opening reviews, attaching waiting pages and creating an auto-approved schema review, record no event. A mutation that replaces the ListingSource's live configuration keeps what it replaced: an approval keeps the live schema list and stored removed-page templates, or the domain's URL-pattern decision, and the ones it made live, plus the coverage it was accepted under and the stored matrix's `live_evaluation`, or the stored live evaluation of the URL sample (`url_sample_evaluation`); an edit through the approved review whose candidate is live, which only a human may make, keeps the live schema list. A human [restores](operations.md#review-service) what an approval replaced from its event while what it made live is still live, recorded as a `RESTORED` event on the approved review. `GET /api/reviews/{id}` returns the trail as `events`, oldest first, and the console shows each event with its actor; changes made before the trail existed have none.

A review-approved `NO_PATTERN` is a completed URL classification. It suppresses new pattern inference until an explicit reset returns the domain to `UNKNOWN`.

### Approval guard

In `agent` authoring mode ([review agents](operations.md#review-agents)) an approval by a review agent goes ahead only when the approving agent changed neither the candidate version it approves nor the review's pages, as the event trail records it (`APPROVER_IS_AUTHOR`, refused alone), and deterministic checks on what the server itself evaluated and stored pass; the agent's judgement, a matrix it computed or one it sends are never evidence. They run in the approval's transaction under the review's row lock, after the version check, and a refusal answers 409 with an `error` message and `failed_checks`, each named by `check`, and leaves the review pending. A product-schema approval needs:

- a stored live matrix (`LIVE_MATRIX_MISSING`) that evaluated the approved candidate version and exactly the schemas and templates approval would make live now, so a changed live list or stored template set behind a merge or rebase counts, and no page that left the review (`LIVE_MATRIX_OUTDATED`), fetched within the configured age (`LIVE_MATRIX_EXPIRED`). The approval does not fetch the shop itself: a refresh fetches every review page at the shop's crawl delay, which would hold the review's row lock, and with it page joins and edits, for minutes and outlast the request;
- every review page evaluated (`PAGES_NOT_EVALUATED`) and covered as approval coverage counts it, without an acknowledgement (`PAGES_NOT_COVERED`): a page declared removed counts only where the matrix shows a template capturing it as removed;
- no product page on which a schema leaves `title` or `state` empty and no other schema applies (`REQUIRED_FIELD_EMPTY`);
- no rule of a schema that matches nothing on every page that schema applies to (`RULE_MATCHES_NOTHING`);
- no extraction of any schema on any page that fails a per-page, cross-page or identity agreement plausibility check (`IMPLAUSIBLE_EXTRACTION`), the findings that keep a generated schema out of [auto-approval](#plausibility-checks), so the guard is never less strict than that gate.

A URL-pattern approval needs a decided candidate (`CANDIDATE_UNDECIDED`) and the review's URL sample classified by what the crawler knows independently of the candidate. A sample URL is a product URL when the crawler captured a product from it, or when its page describes one schema.org `Product` in the review's stored live evaluation of the sample; one the crawler's URL classification without a pattern puts in the category, imprint or info class is not a product URL, whatever markup its page carries. The sample must hold a product URL (`NO_CAPTURED_PRODUCT_URL`), the decision must classify every product URL as a product (`PRODUCT_URLS_NOT_MATCHED`) and none of the others (`NON_PRODUCT_URLS_MATCHED`).

The live evaluation of a URL-pattern review's sample (`GET /api/reviews/{id}/matrix?refresh=true`, refreshed like a schema matrix and refused with 409 when the candidate changes meanwhile) fetches, at the shop's crawl delay, a bounded spread of the sample URLs nothing else classifies, half among those the decision takes and half among those it leaves, and records per URL whether the decision takes it and what its page showed: `PRODUCT_MARKUP`, `NO_PRODUCT_MARKUP`, `REDIRECTED` or `FETCH_FAILED`. A page shows a product when exactly one schema.org `Product` is a top-level item of its JSON-LD (a script's node, a member of a top-level array or of a top-level `@graph`, `@type` as a string or in an array; nodes naming the same `url`, or else the same `@id`, are one product) or of its microdata (an `itemtype` ending in `schema.org/Product` inside no other item), and neither lists more than one; a product nested in another item, such as a list, a redirected or failed page and a script that is not valid JSON show nothing. A page without product markup is no evidence either way. The evaluation is stored with its `live_evaluation`, the candidate version, a fingerprint of the decision and when the first URL was fetched, and a candidate change drops it. Approval fetches nothing: a stored evaluation of another version, decision or sample is outdated (`LIVE_MATRIX_OUTDATED`) and one fetched longer ago than the configured age has expired (`LIVE_MATRIX_EXPIRED`); without one only captured products count. On a domain without captured products and without structured product markup nothing independent shows which URLs are products, so the agent stages its candidate and a human decides. Human approvals and every other verdict skip the guard.

### Removed-page templates

A page the shop keeps at HTTP 200 with a removal notice and no product markup fails every cached schema and opens or joins the ListingSource's product-schema review like any failing page. The reviewer declares it removed on that review instead of authoring a schema for it: the candidate's optional `removed_page_schemas` list (`POST /api/reviews/{id}/candidate`, or the console's Removed Page tab) holds removed-page templates under the same contract and validation as a generated one, a selector bound to the notice with either its text or a regex, and a regex that matches any text is rejected. Like the candidate's schemas, the list starts from the ListingSource's stored templates when the review opens, so the reviewer also edits or retires stored templates there, for example one that turned out too broad. A candidate posted with the list replaces the candidate's templates, an empty list retiring every one; a candidate posted without the key keeps them unchanged, so an edit of the schemas alone never retires a template. A stored row that does not decode fails the opening. A stored template that today's validation rejects opens with the rest and matches nothing, as at runtime; it refuses approval, and any save that changes the templates, until the reviewer fixes or retires it, while edits that leave the templates unchanged still save. Templates can be changed only while the review is pending; approval still needs a valid product schema list, so to keep the cached schemas as they are the reviewer drops the starter schema from the candidate.

The schema matrix lists the review pages the reviewed templates, stored and new, match (`removed_page_matches`) and what the removal guard makes of each with the candidate's schemas live: removed, or still a product because a candidate schema extracts it with a title other than the notice. A template that also matches a product page, or a candidate schema that still extracts the notice page, is therefore visible before approval. Approval replaces the ListingSource's stored templates with the reviewed list in the same transaction that makes the schemas live, and releases the waiting pages, so the page that joined the review is captured as removed on its next scrape and opens no new review. A stored row that does not decode fails the approval and leaves the review pending. The review records the stored list it opened with, and approval keeps changes other writers made to the stored list since then: a template generated in `auto` or `review` mode, which still appends, stays stored, and one retired meanwhile stays retired unless the reviewer changed it. Stored templates follow the [precedence rule](#schema-lifecycle) of generated ones. An approved review keeps the list that went live and its templates are read-only, so an older review never overwrites a list a later review changed.

## LLM limits

LLM use is limited to URL-pattern inference, product-schema generation, fresh page classification, and schema evaluation. Provider selection belongs to executable wiring; crawler services rely on the generic LLM capability.

LLM use is optional. In manual and agent authoring modes, every point that would infer a URL pattern or generate a product schema opens a pending manual review instead, so operator-authored artifacts enter crawler configuration only through the same review rail and validation as generated ones. Fresh page classification has no manual counterpart: non-product pages are excluded through the URL pattern, and removed pages through [removed-page templates](#removed-page-templates) declared on the review. The operator contract, including the auto and review modes, is in [crawler operations](operations.md#authoring-modes).

Crawler LLM calls are governed by bounded concurrency, minimum request-start spacing, bounded provider retries, and a per-ListingSource budget. A request reservation does not hold the scheduling mutex while it waits, and retry sleeps release the request permit. This keeps expensive recovery explicit and prevents unlimited generation.
