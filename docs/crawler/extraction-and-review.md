# Crawler extraction and review

## Extraction contract

The scraper fetches active and sold product URLs, detects verified removed-page templates, and first evaluates cached schemas. It applies every cached schema to the same parsed page, checks each candidate's extraction independently, and ranks the plausible candidates. A bad candidate rejects that schema only; an external or system failure aborts the attempt and does not trigger generation.

Raw extraction remains source evidence. The crawler keeps raw strings, ordered image candidate groups, duplicates, relative values, rejected candidates, and configured raw attributes. It stores a validated, canonical image projection separately for generic raw values. An image's `srcset` is read with the HTML standard's candidate grammar, so a URL that holds commas, such as a CDN's `w_400,h_300` transformation, stays whole, and its widest candidate joins the group. Validation keeps the first candidate of each group that is a safe public target and not too small, at least about 200×150 pixels in either orientation, so small archive photos pass while icons, logos and thumbnails of 150×150 or less stay below it: a width and height in the URL query or path decide, otherwise a probe reads the size from the image. An image whose size stays unknown is kept, unless its URL names a thumbnail; that name alone never rejects an image, because shops also name full-size uploads that way. Ranking counts only validated images towards a candidate's completeness. The offline ranking that the [parser fixture tests](../../src/crawler/tests/scraper_parsing_pipeline.rs) use and the schema matrix have no network access, so they apply the part of this rule that the URL decides, as if DNS resolution and the probe accepted every image ([`image_validation.rs`](../../src/crawler/src/scraper/scraper_service/image_validation.rs)): an image whose URL fails the target check (scheme, credentials, a host that is empty, made only of dots or an IP literal, port) or gives dimensions that are too small does not count, while one whose URL gives no size counts, thumbnail-named or not. A schema that extracts only such small thumbnails therefore cannot outrank one that extracts full-size images. Extracted values must never invent auction identity, lot data, or attribution.

A text rule captures the visible text of each matched element as a browser lays it out ([`visible_text.rs`](../../src/crawler/src/scraper/css_selector/rule/visible_text.rs)). A `<br>` or a block element boundary starts a new line, table cells are separated by a space, and every other run of HTML whitespace, such as markup indentation, collapses to one space; the value is trimmed, so `Top Hat<br>Pen` does not become `Top HatPen` and an indented breadcrumb gives `Antique Silver Early English Antique Spoons`. Paragraphs are separated by one line break, never a blank line, so a description keeps its line structure while the markup whitespace between its blocks, and a spacer paragraph of only non-breaking spaces, adds nothing; a line break inside `<pre>` starts a new line too. Non-breaking spaces are text, as in a browser, because shops use them to separate thousands and currency symbols. Inline elements such as `span`, `a` or `sup` add nothing, so `£<span>2,800</span>` stays one value. Text hidden from view is dropped: descendants with the `hidden` attribute (except `hidden="until-found"`, collapsed content the browser reveals on search), an inline `display: none`, or a screen-reader-only class (`screen-reader-text`, `sr-only`, `visually-hidden`, `visuallyhidden`), so a WooCommerce sale price gives `£2,950` instead of `Original price was: £3,450.£2,950Current price is: £2,950.`. `aria-hidden="true"` hides text from screen readers, not from view, so it is kept: WooCommerce marks the visible sale price that way. The one exception is an `aria-hidden` element directly followed by a screen-reader-only copy that only adds separators to its text, which is captured through that copy, because the visible rendering can lose a separator, as in Shopify's `€11.327<sup>95</sup>` next to `€11.327,95`. A rule that selects a hidden element itself still extracts its text, so a description rule names a collapsed tab panel directly rather than a container around it. Struck-through text (`del`, `s`, `strike`), such as a superseded price, is dropped unless it is all the element's text, so `£25 <del>£50</del> VAT` gives `£25 VAT`. Attribute values have their whitespace collapsed and are trimmed. `source_listing_id` joins its text and keeps its attribute value as written instead, hidden text and whitespace included, so a captured identity does not change with how its text is laid out. Removed-page templates match the separated text, whitespace-collapsed and lowercased, because a matched notice is compared with the titles cached schemas extract from the same page.

A rule reads its value from one of these extraction kinds ([`rule.rs`](../../src/crawler/src/scraper/css_selector/rule.rs)): the visible `text` of an element, an `attribute`, `image_url`, an `attribute_or_text`, a `json_ld_offer` or a `json_ld_product`. `attribute_or_text` takes the named attribute when it is not blank and the element's text otherwise, so one rule reads an `<input type="submit" value>` and a `<button>` label, or a text-less image's `alt` and a text label, as alternatives for one field. `json_ld_offer` reads the `availability` or the `price` (the `lowPrice` of an `AggregateOffer` without one) from the `offers` of the JSON-LD document in the matched `<script type="application/ld+json">`, as written, in document order and through nested offers and the item the page is about: a `@graph`, a `mainEntity` and a `ProductGroup`'s variants, never another product the document names, such as a related or listed one. A price is followed by its offer's `priceCurrency`, so the worker reads the currency the offer states. A price of zero digits only is no value, because templates publish it for price-on-request items, which the page shows without a price; a visible zero price stays a value with its plausibility finding. A script whose JSON does not parse or holds no such value is blank. `json_ld_product` reads the `product_id` (`productID`) or the `sku` of the top-level schema.org `Product` in that script, as written, the first non-blank value in document order: the document itself, the members of an array and of a `@graph`, never a product nested in another node, such as a listed or related one, and a node counts as a `Product` under the same `@context` rules as `describes_one_product` below; a string or number is a value, an object is none. It exists for the shops that publish their listing ID only there, since the projection strips scripts; the property persists as `product_id` or `sku`, in the snake_case every rule kind and property is stored in, an intentional exception to the `SCREAMING_SNAKE_CASE` of persisted enum values that keeps the stored product schemas in one format; any other property, or none, fails deserialization. The `attribute_or_text` and both JSON-LD kinds are blank like a text rule, so the [plausibility checks](#plausibility-checks) and the `title`/`state` [missing required value](#missing-required-values) handling apply to a JSON-LD value like any other. Script elements are not part of the schema-generation projection, so generated schemas use the older kinds and the JSON-LD kinds are authored manually, by an author agent included: `json_ld_product_ids` in the page-projection answer shows the `productID` and `sku` such a rule would read.

The crawler captures a `state` as the raw text its rule extracts. Turning that text into an availability is the backend's job: the [normalization worker](../events/flow.md#productlisting-write-flow) resolves schema.org availability URLs, common multilingual status labels and quantity text, and reports a label it does not recognise as an `AvailabilityUnrecognized` normalization issue while the availability stays unchanged. A schema therefore carries no label mapping.

A rule evaluates its primary selector and then its `additional_selectors`, in that order, and its cardinality decides what the additional selectors mean ([`rule.rs`](../../src/crawler/src/scraper/css_selector/rule.rs)). With `first`, the default, they are fallbacks: the first selector that yields a non-blank value wins and the later ones are not evaluated, so a price rule can name the structured-data price before the visible one. With `all` they aggregate: every selector's matches are collected in selector order, so a gallery or a description can span separate blocks. Aggregation never captures the same content twice: an element is extracted at most once across all selectors of a rule, and an element nested inside, or containing, an element the rule already extracted is skipped, so a description rule that selects a container and its paragraphs keeps the container only. `description` and raw attributes keep equal text from separate elements once, in order; `images` keeps its duplicates as raw evidence and the [plausibility checks](#plausibility-checks) report them. A value is blank when it is empty after trimming, non-breaking spaces included, for text and attribute rules alike, `source_listing_id` included. With `all`, a blank item is dropped, so a list never holds a blank value, unless an attribute rule matched only blank elements: it then yields its first blank value, as a `first` rule does, so the blank check reports the field instead of it reading as unmatched. With `first`, a blank value is skipped for the next matched element and then the next selector, so the first non-blank value wins. An identity rule therefore takes its first non-blank item with either cardinality and keeps it as written. An element without the attribute of a `first` attribute rule ends the search: the rule fails when it reaches that element before any value and otherwise yields its first blank value, as it does when every match is blank, so the `BLANK` [plausibility check](#plausibility-checks) reports a blank price, identity, description or raw attribute instead of the field reading as unmatched. A `first` text rule, or an `all` rule, that yields no value reports whether its selectors matched no element or matched only empty ones, so its error and per-field log line tell a selector that does not fit the page from a page that leaves the value empty. The schema matrix counts a text rule's empty elements apart from its matches, so the review console makes the same distinction for an optional field left empty.

A page whose hash and scraper-context fingerprint both match its last scrape skips schema selection: its images are not validated again and no raw input is built. The page hash covers what the effective ordered schema set extracts from the page, each schema's raw values or the fact that it does not apply. A change to anything a schema reads, such as visible text, a price, an attribute, a link or an image candidate, therefore changes the hash wherever it is on the page, while content no schema extracts does not: the form tokens, nonces, session ids in links and randomised form labels some shops render on every request leave an unchanged page on the skip path. The fingerprint covers the extractor version and the effective ordered schema set ([`hash.rs`](../../src/crawler/src/scraper/scraper_service/util/hash.rs)). The removal checks run before this comparison, and a verified removal forgets both values, so a page that comes back unchanged after its removal is captured again. The check for a page that a rejected review [classified as non-product](operations.md#manual-authoring) runs before this comparison too, in every authoring mode, so the check reaches unchanged pages without an extractor version raise. Otherwise the crawler hashes its generic raw-input envelope. Equal input refreshes crawler scrape metadata without creating a new operational capture.

A change to raw extraction itself, such as text separation or image candidates, changes the page hash of every page whose extraction it alters, so that page is extracted again at its next scrape. Raise the extractor version with every change that alters the captured values of an unchanged raw extraction, such as image validation or a runtime check that decides which cached schema a page uses; without the raise, such a change reaches a page only when its extraction or its schemas change. After a raise, every page is extracted once more at its next scheduled scrape, which fetches the page anyway but validates its images again, and is skipped again afterwards; a page whose raw input did not change creates no new capture, while a page that every cached schema now fails is handled like any other page that fails them ([schema lifecycle](#schema-lifecycle)). Changes outside the runtime scrape, such as schema authoring, review, the schema matrix or the offline ranking, need no raise, and a normalization fix is [replayed](../normalization-replay.md) in the ProductListing worker instead.

The crawler does not normalize extracted values. Price parsing, currency, availability and language belong to the [ProductListing normalization worker](../events/flow.md#productlisting-write-flow), which reports what it cannot normalize. Generic raw values keep every supplied price, state and text value as extracted.

### Plausibility checks

Before a candidate is used, the crawler checks the raw strings it extracted from one page ([`plausibility.rs`](../../src/crawler/src/scraper/plausibility.rs)):

- `title` is not blank; `state` is not blank, no longer than a label and not price text: an amount with a currency symbol, code or word, or after "price", such as "£ 1,800 plus VAT", unless the value is a status label the ProductListing normalization resolves once the amount is set aside, such as "Sold for £500", or a cart or enquiry action such as "Add to cart £45"; availability labels and quantities carry no amount;
- `price` and the estimates, when present, are not blank, no longer than a label, do not consist of zero digits only and are no availability label without an amount, such as the `Sold` a sold page shows in the price's place (`AVAILABILITY_TEXT`; a price on application such as `POA` stays plausible);
- `description` and each raw attribute, when present, are not blank;
- no `title`, `state`, price, estimate or `description` value carries CSS rules or script source;
- the extracted `source_listing_id`, checked before the URL-hash fallback replaces a blank one, is present, capturable and one identifier rather than a list of three or more class-like words, such as a whole `<body class>` that holds the post id but changes with the template and the product's tags;
- `images` do not repeat an image.

Each finding names its field and check; a stored field name is read back only as a core field or a registered raw attribute key, and any other name is rejected rather than taken for a raw attribute. At runtime a `title`, `state`, CSS/script or uncapturable-identity finding rejects the candidate; price, estimate and image findings rank it below candidates with fewer such findings, and completeness and stored order break ties; a blank or word-list identity, a blank description, a blank raw attribute and price text in `state` do not affect selection, so a live schema that reads a price element keeps capturing; the matrix still shows the price text and, like every finding, it keeps the candidate out of deterministic approval, and out of an agent's approval unless the same rule resolves to sold, out of stock or unavailable on a review page: a status slot that shows the amount while the item is for sale and the sold label afterwards, which the matrix still marks with the finding (`exempt_as_status_slot`). Otherwise a new or repaired schema cannot go live that way without a human's knowing approval. A blank description reaches the worker, which clears it; a blank raw attribute stays in the source payload and is left out of the generic raw values, because the worker keeps attribute values as given. Free-text states such as "Viewing by appointment only." pass, and the worker reports them. Rejected candidates and schema repair stay crawler-side and never enter the business [normalization replay corpus](../normalization-replay.md).

### Missing required values

A `title` or `state` rule takes its first non-blank value, whatever its cardinality. One whose matched elements are all empty yields a blank value instead of failing, so the blank check rejects the candidate with the rest of its extraction intact, and the schema matrix and review console show the field as blank rather than unmatched. When no cached candidate is plausible and one was rejected only for blank `title` or `state` values, the page leaves a required value empty where a cached schema found its element. A new schema cannot supply it, so the scraper runs no generation and, outside `agent` mode, opens or joins no review; the URL records `MissingRequiredValue` with the field instead, stays a product URL, and is [not retried](scheduling-and-retries.md#fetch-retries): the next scrape at its normal interval, or at once when an approval re-arms the page, evaluates it again, at no generation cost. In `agent` mode nobody adds the page from the console, so the scrape opens, or joins, the ListingSource's pending product-schema review with the reason `missing_required_value` for it, the review the console opens for such a page (candidate: the live schemas and stored templates), with the page it already fetched as a waiting page: no extra fetch, once per page, within the review's waiting-page cap, so the pages of one source that leave the same field blank share one review. The review agents then repair the schema or declare a removed-page template; the URL's outcome and no-retry behaviour stay as above, and the scrape logs the blank fields and the review (`Page left a required value blank`). A rejection of a `missing_required_value` review judged its pages: a page such a rejected review holds, in any spelling the crawler treats as that page, opens and joins no review until a product schema list goes live after the rejection, under which the page may fill the field or fail anew; a page the rejected review never held, such as one past its waiting-page cap, opens one as before, and a human still adds any such page from the console. The listing keeps its last capture, and a later scrape that extracts the value clears the outcome. A page on which the cached schemas find no title element at all cannot be told apart from a new template and still needs schema work. Before recording the outcome, a scrape selects once more against the live schemas when an approval changed them during the scrape, so a fix applies at once.

Some shops empty the product name when an item sells. A URL whose last capture recorded a title therefore keeps that title (stored crawler-side as the URL's last captured title, cleared by a captured removal): when no cached candidate is plausible and one is rejected only for a blank `title`, its state present, the best such candidate is captured with the last captured title in its raw `title` value. The sold or changed state the page still shows reaches the listing, and the source payload keeps the blank extraction as evidence of what the page showed. A titled plausible candidate always wins; a page that also leaves its state blank, or a URL captured without a title before, records `MissingRequiredValue` as above, since nothing would be captured that the page or an earlier capture did not show.

An untitled product page that was never captured is skipped, not captured under a title the crawler derives from other content such as a description line or an image's alt text: that would not be the shop's name for the item, and the crawler extracts values without deriving or normalizing them. Where a shop shows the name in another element of the page, the reviewer names that element as a fallback in the title rule's `additional_selectors`, and the schema matrix checks it like any other selector.

The review pages show different products, so the review gate also compares each candidate's extractions of them ([`cross_page.rs`](../../src/crawler/src/scraper/plausibility/cross_page.rs)): a `source_listing_id` that two pages share names the shop, the category or a page template, a shared `title` does so only when the pages that share it also share an identity or an image, or when every review page shares it (pages with distinct identities and images that share a title are two products with the same name), and an image that two pages share is a default share image or placeholder rather than a product photo. Images compare by the URL they resolve to, without the fragment, and without the query when the path names an image file, because sizes, cache busters and CDN signatures differ per page. Runtime extraction sees one page at a time and cannot run these checks. A candidate whose `images` rule yields no image that the URL rule of the [offline ranking](#extraction-contract) keeps, on any review page it extracts, fails a check on each of them: markup cannot tell an empty product gallery from thumbnails or another feature's empty image container, such as a customer review box, which applies as an empty gallery on pages that have photos. A page without images is no finding while another page the candidate extracts yields one, because one page cannot tell a product without photos from a wrong selector; a candidate that extracts only one review page, such as the triggering page of a fresh generation, gets the finding when that page yields none. A reviewer approves a schema with this finding knowingly, for a shop that sells unphotographed items.

Every schema of a ListingSource must derive the same identity from a page, because runtime selection may pick any of them and a scrape whose identity differs from the one the listing was captured under is rejected as a [conflict](scheduling-and-retries.md) rather than captured as a second listing. The matrix therefore also compares, on each review page, the identities of the candidates that apply to it ([`identity_agreement.rs`](../../src/crawler/src/scraper/plausibility/identity_agreement.rs)): an identity another applying candidate contradicts, or one that differs from the identity the crawler URL naming the page was captured under, however the two URLs spell the page, is a finding that names the contradicting identities. A schema written for a sold page whose identity element differs from the active-page schemas' therefore shows the conflict even when it is the only schema that applies to that page. Blank and uncapturable identities are left to the per-page checks.

The schema matrix lists the per-page, cross-page and identity agreement findings of every candidate on every review page, and the review console shows each next to its field. Any finding on any candidate's extraction keeps a generated schema out of auto-approval, including an extraction that a rejecting finding withdrew from a page another candidate covers, and a blank identity: the identity rule is applied to every review page, sold, archived and price-on-request variants included, and a schema without an identity rule, or whose rule matches nothing on one of them, reports a blank identity there. At runtime such a page gets the URL-hash identity, which changes when the product moves and, where the page was captured from another variant, is rejected as an identity conflict, so a reviewer approves such a schema only knowingly. A repeated image is the one exception: it lowers the candidate's rank and shows in the matrix, but keeps no schema out of approval, because capture keeps each image URL once and no selector can tell a gallery's repeat of its featured photo from another gallery image.

Shipping interpretation runs in downstream raw normalization using the pure `product-listing-normalization` crate. It
combines item-specific `rawShipment`/`rawShipmentNote` text with description context;
contradictory or unsupported delivery clauses veto the observation. Duration ranges
remain complete text with their units and dispatch/delivery context.
Selectors must exclude shared footers and site policies. Explicit phrases cover all 14
catalog languages; phrase tables, language fixtures and input bounds are executable in
[`shipping.rs`](../../src/product-listing-normalization/src/shipping.rs). Interpretation
uses no LLM, interpretation agent or model fallback, and adds no schema-generation calls
or native description ingestion.

Successful page fetch time travels as the crawler capture's `source_occurred_at`, outside
the content hash. Schema evaluation, normalization, capture retries and queue delivery keep
that acquisition time. Historical captures without it remain readable and cannot establish
shipping observations. Matching page/input hashes retain the existing capture deduplication:
they do not advance shipping observation time. A new immutable raw revision can observe
unchanged shipping assertions when other captured item content changed. See the
[shipping contract](../shipping.md#deterministic-crawler-item-assertions) for application rules.

## Schema lifecycle

Fresh generation begins only after cached candidates are exhausted. It creates a new schema from the current page; it never edits a cached schema. A generated schema persists only after it applies and its extraction passes the rejecting plausibility checks.

Initial generation is product-schema-only: its response contract offers no page classification, every seed sample is treated as a product page, and a sample the model considers non-product is excluded from schema coverage and reported as a risk rather than classified. Single-page classification may produce a product schema, a verified removal, or a verified non-product result. A removal needs selector-bound evidence and results in raw deletion capture. A stored removed-page template is removal evidence only while no cached product schema still applies to the page with a title other than the not-found notice and, when the crawler URL already carries a captured source listing id, the same identity; a related-item card on a removed page is therefore not product evidence. When product evidence exists it wins, the page is scraped normally (a candidate that then fails a rejecting plausibility check reaches fresh generation, not withdrawal) and the conflict is logged as an over-broad template to fix. A removed-page regex that matches any text is rejected both when proposed and when applied. A non-product result classifies the crawler URL the scrape requested `other`, also when it redirected to the classified page, so that URL is not fetched again every pass; it changes that URL only, and one page never rewrites a ListingSource's URL pattern.

Every generated product schema must pass deterministic rule validation (selector syntax and attribute names) and may name only raw attribute keys of the [raw attribute registry](../../src/crawler/src/scraper/css_selector/raw_attribute_registry.rs), the registry check a [console edit](#review-rail) also applies, before it can be reviewed or persisted. Unregistered keys are refused rather than dropped, all named in one correction, so the model re-keys or omits those values instead of the crawler silently discarding them. An invalid response is returned to the model with a fixed correction code plus the offending field and value during bounded response correction, and the retry log carries the same detail without the prompt or HTML; if it stays invalid, generation ends with a schema-generation validation failure. The review gate rejects invalid candidates before review persistence, so review artifacts and approved schemas only ever contain valid rules, and model output is never reported as a database failure.

Generated selectors are grounded in page structure. Optional fields remain absent rather than guessed. A configured optional rule (identity, description, price, price estimates, raw attributes) that matches nothing on a page leaves that field empty with a per-field diagnostic; it never fails the page, so one page without a description does not reject the schema or trigger fresh generation. Title and state fail closed on a miss, or on [empty elements](#missing-required-values) through the blank check. The `images` rule skips matched elements without a value (no image URL candidate, or no attribute of an `attribute` rule), such as `href="#"` slots a gallery mixes in with its image links, and fails closed unless the gallery is empty: the image container its selector names exists and holds no image, or every element it matched is a gallery placeholder. A placeholder is an element whose own class, id, `rel` or gallery data attribute names an image context, such as `gallery`, `thumb` or `lightbox`, and that holds no image URL candidate, no image markup, no attribute naming an image file and no text, such as the `<a rel="lightbox" href="#"></a>` slots a gallery renders for a product without photos. A URL capture can never fetch is no image URL candidate and makes neither a slot nor a container hold an image: a URL without a host, such as the `//:0` of the hidden `<img>` some galleries put in such a slot, and a `data:` URI, which galleries and lazy loaders render as a blank or blurred placeholder and capture never keeps because it fetches only public `http` and `https` URLs. An `<img>` or `<source>` whose every image source holds only such URLs, and no other attribute of which holds a URL a lazy loader could load, is therefore no image markup, and neither is a `<picture>` that holds only such elements and names no image of its own. A hidden image with a real URL still is, because lazy-loading galleries hide their images until a script runs, and so is an image whose `data:` placeholder stands next to a real lazy source such as `data-src`. Elements without a value that are not all placeholders, such as navigation links, labelled controls, layout elements or gallery slots and wrappers whose image the rule cannot read, mean a selector that does not fit the page and fail it. An empty gallery yields no images, and the page applies when its other rules do: no per-page [plausibility check](#plausibility-checks) rejects a page without images; the missing images only lower the candidate's completeness, and only a candidate that yields no image on any review page stays in human review. Rules of other fields still fail on an element without their attribute. The schema matrix counts the skipped elements per page; next to extracted images they show a loose selector a reviewer can tighten, while on an empty-gallery page they are its placeholders. The count is review information and does not block deterministic approval. The schema matrix reports the [plausibility findings](#plausibility-checks) of every candidate on every page; a rejecting finding fails that page like an apply error, so the page is not covered. The schema matrix and the review gate report optional-field misses separately from page failures: a miss on some pages stays visible to the reviewer and does not block deterministic approval, while an optional rule that matches nothing on every page its candidate applied to is a defective selector and keeps a generated schema in human review. The matrix counts only matches with visible text for a text rule, because a blank element yields no usable value: a price selector that matches only blank cells, such as a spacer next to the price, is such a total miss rather than an approvable schema that captures the shop without prices. An attribute or image URL rule counts every element it matched, blank or skipped, so the count describes what the selector matched and a blank attribute is left to the `BLANK` check. At runtime an optional-field miss is a debug diagnostic, trace for raw attributes, because pages legitimately leave such fields empty, such as a sold item without a price. A scrape logs the misses of the cached schemas that apply only once it selects from them, so a page skipped as unchanged logs none, and a cached schema that fails to apply logs its apply failure with the failing field, the error naming its selector, and the misses of its optional rules, so selector drift that breaks a required rule shows what else it missed. A `state` selector reads an availability label (a schema.org availability value, a status label or quantity text the ProductListing normalization resolves) or, when the page shows no label, a cart or enquiry action such as "Add to cart" or "Enquire by Email"; it never reads price text, which the [plausibility checks](#plausibility-checks) report and approval refuses, except in a status slot an agent's approval accepts as described there. The review agents' prompts state this contract, so the reviewer neither disputes a cart or enquiry action nor accepts price text. Raw attribute selectors are review/display inputs and participate in the raw-input hash; an attribute reaches existing cached schemas only through a [review edit](#review-rail) or regeneration.

## Review rail

The review rail records generated URL-pattern and product-schema artifacts as auditable state. Artifacts may be pending, approved, rejected or superseded. When review gating is enabled, pending artifacts do not become active crawler configuration.

A URL-pattern decision is `NO_PATTERN` or a `PATTERN`: a regex `value` and an optional regex `exclude`, both matched anywhere in the URL in the crawler's [spelling of it](networking.md#stored-urls), with or without the trailing slash. A URL on the crawl host is a product URL when it matches `value` and not `exclude`; the exclusion takes out the few non-items that share the product URL shape, such as gift cards, vouchers, services or the dealer's own profile page, because the regex engine has no lookahead and a pattern that lists slug prefixes misses real products. A URL the exclusion takes is classified as one the pattern does not match, by the spider, by the reclassification of the stored URLs on approval and by the sample. The exclusion is a regex that is not blank, validated like `value`; the console and the agents' `update_candidate` take it as `decision.exclude`, and the live pattern stores it with `url_pattern` and clears it with it.

A reviewer gives a pending review one of three verdicts:

- **Approve** (`POST /api/reviews/{id}/approve` with the `expected_candidate_version` the approver read) makes the candidate the active configuration, supersedes other pending reviews of the same artifact and releases the work waiting on it for an immediate retry. An approval based on another version is refused with the 409 of a stale candidate edit, so an edit made since is never approved unseen, and approval moves the review past the approved version, so an edit based on the pending review is refused instead of rewriting the live configuration. Approving a URL pattern also classifies the ListingSource's stored active URLs with the decision, so a crawl that [waited on the review](scheduling-and-retries.md#spider-crawl-completion) needs no second crawl.
- **Reject** (`POST /api/reviews/{id}/reject`) closes the review without changing configuration and, like approval, releases the work waiting on it: a ListingSource whose crawl waits on a URL-pattern review, so its next crawl can open a new one, and the pages [waiting on a product-schema review](scheduling-and-retries.md#fetch-retries), for an immediate retry. Rejecting a manual schema review also classifies its seed and triggering pages as non-product pages until a human revokes the rejection ([manual authoring](operations.md#manual-authoring)).
- **Needs repair** (`POST /api/reviews/{id}/needs-repair` with a non-blank `notes`) records why the candidate needs repair and when, and leaves the review pending. The review keeps its candidate, pages and waiting pages, stays editable, holds back exactly the work any pending review holds back, and remains the one pending review of its artifact, so no second review opens. The review API returns the latest note and time as `repair_request`, and the console marks a pending review with one as waiting for repair. The reviewer repairs the candidate and then approves or rejects the review; a repeated needs-repair verdict replaces the note. The review API also reports `agent_rounds`, the review agents' needs-repair verdicts since a human last changed or judged the review, counted from the [event trail](#review-rail), and, in `agent` mode, `human_required` once a pending review's rounds reached `CRAWLER_REVIEW_AGENT_MAX_REPAIR_ROUNDS`: such a review waits for a human, and the console refuses every agent change, verdict and live page fetch on it until a human's own change or verdict hands it back ([review agents](operations.md#review-agents)).

A verdict on a review that is no longer pending is refused with 400 and an `error` message. Every review and review-page route answers an unknown review or review page with 404 and an `error` message. A URL-pattern review whose ListingSource has no crawl root cannot be judged: its sample labels and an approval the [approval guard](#approval-guard) checks are refused with 409 and an `error` that names the review and asks for its rejection.

`GET /api/reviews/{id}` reads a review whose stored candidate fails the validation approval applies, so the reviewer can see and repair it: for a pending review, or the approved review whose candidate is live, `candidate_error` says what fails (otherwise `null`), the crawler logs that reason at ERROR once per such request, not on the matrix and other reads of the review, and approval stays refused until an edit repairs it. A product-schema candidate an edit, approval or matrix refresh refuses answers 400 with an `error` that names what fails: that the candidate does not decode or holds no schema, or the schema index, the field (a raw attribute as `raw_attributes.<key>`), the selector and why the selector is invalid. A decided review's candidate is a record and is not judged by today's validation.

Approving a product-schema review needs a candidate that covers every review page, counted as the console counts coverage: a page is covered when the candidate's [removed-page templates](#removed-page-templates) capture it as removed in the review's stored schema matrix, or else when at least one candidate schema applies to it there, as the deterministic coverage of [schema lifecycle](#schema-lifecycle) defines it; a page the stored matrix did not evaluate is not covered, and a template that matches a page a candidate schema still extracts leaves that page to the schemas. Without a stored matrix, or with one that no longer decodes, every page counts as not evaluated; a candidate change drops the stored matrix, so a stored matrix never vouches for an older candidate. An approval with incomplete coverage is refused with 409, an `error` message and the review's current `coverage` (`covered` pages, the `removed` pages among them, `total` and `not_evaluated` pages), and the review stays pending, unless the request carries that same coverage as `acknowledged_coverage`; the console sends it only after the reviewer confirms a dialog that states the counts. An acknowledgement of other counts, such as one confirmed before a page joined or a matrix was stored, is refused with the same 409. The check and the approval run under the review's row lock, which page joins, candidate edits and matrix stores take too. URL-pattern reviews have no page coverage; their approval ignores the acknowledgement.

A review records its ListingSource. Candidate changes increment the review version and invalidate any cached schema matrix, so a stale live inspection cannot overwrite current review state. A cached matrix is read with its [cross-page findings](#plausibility-checks) evaluated again from the extractions it holds, by the console, the [approval guard](#approval-guard) and the review tools alike, so a cross-page check added after it was cached applies without a refresh; one that does not load counts as no matrix until a refresh replaces it. Reading the matrix fetches nothing; only an explicit refresh does, as one of the console's [live jobs](operations.md#review-service). A matrix refresh fetches the pages the review holds when it starts, then evaluates on them what approving the review's current candidate would make live: its schemas as they are, and its removed-page templates rebased onto the stored ones. The matrix records that evaluation as `live_evaluation` (the candidate version, a fingerprint of the evaluated schemas and templates, and when the pages were fetched), and the matrix API answers it with `not_evaluated_pages`, the review pages it did not evaluate. Pages that join the review while it runs, such as waiting pages, do not fail it: it stores and answers the matrix of the pages it evaluated, which names them, and the console marks a review page missing from that matrix as not evaluated, and counts it as not covered, until the next refresh. When the candidate changes after that evaluation, or a page it evaluated is removed, before the matrix is stored, the refresh stores nothing and is answered 409 with the review's current `candidate_version`; the console shows why and evaluates again only when asked. The matrix summary schema generation records judges the generated matrix only, so it leaves with that matrix: dropping the cached matrix or storing a refreshed one removes it. Review identities and matrix references use the TypeID policy in [object IDs](../object-ids.md).

A reviewer edits a product-schema candidate as a whole (`POST /api/reviews/{id}/candidate` with the candidate's keys), which also adds or removes schemas, or one rule at a time (`POST /api/reviews/{id}/schema-field` with `schema_index`, `field` and `rule`; only an explicit `null` rule deletes an optional one, a missing `rule` is refused): a core field by its schema key, a raw attribute as `raw_attributes.<key>`. The console offers the keys of the [raw attribute registry](../../src/crawler/src/scraper/css_selector/raw_attribute_registry.rs) (`GET /api/raw-attribute-keys`), and an edit may introduce only those; a key the candidate already holds, such as one generated before the registry named its keys, stays editable and removable. Both edits also carry the `expected_candidate_version` they were based on, the `candidate_version` the review API reported, and are refused with 409 once the candidate has changed since, so concurrent writers, such as a human reviewer and the author agent, never silently overwrite each other's edits; the writer reloads the review and applies its edit to the current candidate. An accepted edit answers with the review's new `candidate_version`, a refused one with an `error` message, and a 409 that carries `candidate_version` names the review's current version: the request may be retried once the review is reloaded. Adding or removing a review page changes the page set, not the candidate, and takes no version: adding a page twice is refused as a duplicate and a removed page is gone, so page changes cannot overwrite each other. The next matrix evaluates the whole edited list.

A reviewer can add further pages of the ListingSource to a pending or approved product-schema review (`POST /api/reviews/{id}/pages` with `{"url": ...}`, or the console's **Add to review** in the page preview), such as sold, price-on-application or photo-less variants, so the schema matrix tests the candidate beyond its seed pages. Only http(s) URLs on the default port and without credentials on the ListingSource's crawl host, with or without `www.`, are accepted, checked before the fetch and again on the final URL after redirects. A redirect to a page that is not a product page (outside the ListingSource's decided URL pattern, or the homepage while none is decided) is refused; one that only changes the trailing slash or the [language segment](networking.md#redirect-removal-evidence) before the path leads to the page itself. A page already on the review under the crawler's URL normalization, with or without its [trailing slash](networking.md#stored-urls), or in another `www.` or scheme spelling is a duplicate, and a reviewer adds a bounded number of pages per review. A reviewer can remove a page they added (`DELETE /api/review-pages/{id}`), for example once the shop has deleted it; seed pages cannot be removed. Adding or removing a page drops the cached matrix. These pages carry the `REVIEWER_ADDED` role and are no operator verdict: rejecting the review does not classify them as non-product pages. A page of a pending review that is no product, such as the dealer's profile the URL pattern takes, is marked instead with `POST /api/reviews/{id}/pages/{review_page_id}/not-product` and `{"reason": "..."}` (1 to 500 characters saying what the page shows; the author agent or a human, any page including seed and triggering pages) and unmarked with `DELETE` on the same route. A marked page is left out of the schema matrix and of the coverage and approval guard, so no schema has to resolve it and no check compares it with the product pages; marking or unmarking drops the cached matrix and is a `PAGE_MARKED_NOT_PRODUCT` or `PAGE_NOT_PRODUCT_CLEARED` event that counts as a change of the review like a page addition. Approving the review retires the marked pages' URLs as product URLs of the ListingSource (class `other`, retry delay cleared, named as `retired_not_product_urls` in the approval's event), and later crawls keep them `other` as they keep a rejected page, though the URL pattern still takes them.

Two reads fetch pages of the review's ListingSource without changing the review, for the [review agents](operations.md#review-agents) and anyone else. `GET /api/reviews/{id}/page-projection` with `page` (a review page of that review) or `url` fetches the page live and answers its outline ([`outline.rs`](../../src/crawler/src/scraper/css_selector/schema_generation/outline.rs)): the elements, attributes and texts the schema generation prompt shows the LLM as YAML, one element per line in CSS notation indented by depth with its text after ` | `, in about half the characters, where a run of five or more siblings of the same structure (tags, attribute names and the values of `class`, `itemprop`, `name`, `property`, `rel` and `type`) shows its first two members and every member whose text holds a digit and counts the rest in one line. The elements are those of the YAML projection ([`projection.rs`](../../src/crawler/src/scraper/css_selector/schema_generation/projection.rs): no scripts, styles, navigation, header or footer; shortened texts and attributes; layout wrappers left out with their children in their place, except a wrapper with a class or id that directly holds paragraphs, headings, lists or tables, which stays as the selectable container of that prose, such as a CMS's description field; each `srcset` or `data-srcset` as its widest candidate, split and picked as image extraction does, and the number of the others; each `data:` URI, also one inside a value such as a JSON image list, as its media type followed by `,…`, such as `data:image/svg+xml,…`, never usable in a selector; at most a bounded number of lines in at most 100,000 characters, the first in document order, with a last line counting the lines left out), the `final_url` after redirects and `describes_one_product`: whether the page's JSON-LD or microdata describes exactly one schema.org `Product` (a bare `Product` or `prefix:Product` JSON-LD type counts only where the node's `@context` maps it to schema.org, or the node has none), markup the projection strips with the scripts, and `json_ld_product_ids`, the `product_id` and `sku` of the page's top-level JSON-LD `Product` that a `json_ld_product` rule reads, each `null` when the page has none. Both are information and decide nothing. `POST /api/reviews/{id}/evaluate` takes a product-schema candidate in the shape of a whole candidate edit plus at most four `urls`, checks it as an edit would be checked, and evaluates on the review's pages and those URLs, fetched live at the shop's crawl delay, what approving it would make live, as a matrix refresh does; the URL pages are `input` page references by their position in `urls`. The evaluation stores nothing: the candidate, its version, the stored matrix and the event trail stay as they are, and its matrix has no `live_evaluation`, so it never stands in for the review's live matrix in an approval. It answers the matrix when it finishes within the request, otherwise `202` with an `evaluation_id` to poll at `GET /api/reviews/{id}/evaluations/{evaluation_id}` for about ten minutes after it finished. Both reads take only a URL of the review's ListingSource under the review-page rule above, checked before the fetch, and answer `400` otherwise. Both are [live jobs](operations.md#review-service) under the console's cap, above which they answer `429` with `reason` `LIVE_JOBS_BUSY` and `Retry-After`, and a review agent's on a review that [waits for a human](operations.md#review-agents) answers `409` `HUMAN_REQUIRED` before anything is fetched.

A page that fails every cached schema while the ListingSource's product-schema review is pending joins that review instead of opening or generating another. The crawler attaches it once per page identity with the `WAITING_PAGE` role, up to a bounded number per review, and drops the cached matrix, so the reviewer sees each template variant that needs the schema. Further failing pages wait without being attached. A reviewer can remove a waiting page like one they added, for example once the shop has deleted it; a removed page that still loads and still fails every cached schema joins again on its next retry. Waiting pages are no operator verdict either.

Editing an approved product-schema review rewrites the ListingSource's live schema list, so it is refused unless that review's candidate is still the live list, which the review API reports as `candidate_is_live` and the console shows by offering edits on that review only; approval stores the list that went live as the review's candidate. A review shows, edits and approves exactly the candidate stored at its candidate version, with no live schemas merged in, so a reviewer who deletes schemas from a candidate never gets them back on approval. Once a later review has changed the live schemas, the schemas of older approved reviews are read-only. Unused schemas are not retired automatically: the schema matrix shows every candidate's outcome on every review page, the console names the schemas that apply to none of them, and a reviewer who confirms that the shop no longer uses a schema's template deletes it from the candidate of a pending manual review, whose approval replaces the live list, or of the approved review whose candidate is still the live list.

Every accepted review mutation appends one event to the review's append-only trail in the mutation's own transaction: candidate and field edits, removed-page declarations and [sample labels](#approval-guard) among them, reviewer page additions and removals, the author's [no-sold-page record](#approval-guard), needs-repair, a review agent's `HANDED_TO_HUMAN` hand-off ([review agents](operations.md#review-agents)), approval, rejection and the revocation of a rejection. A refused or failed mutation appends none; an event is never changed and is deleted only with its review. An event records its actor, its action, the review's `candidate_version` after it, a verdict's notes and the action's details. The actor is `AGENT_AUTHOR` or `AGENT_REVIEWER` for a request with the author or reviewer agent's [token](operations.md#review-agents), `HUMAN` for the review token, a browser session or the `dev` binary's local console, and `SYSTEM` for the crawler's direct approval of an inferred URL pattern in `auto` mode; the crawler's other writes, opening reviews, attaching waiting pages and creating an auto-approved schema review, record no event. A mutation that replaces the ListingSource's live configuration keeps what it replaced: an approval keeps the live schema list and stored removed-page templates, or the URL-pattern decision, and the ones it made live, plus the coverage it was accepted under and the stored matrix's `live_evaluation`, or the candidate's `sample_labels`; an edit through the approved review whose candidate is live, which only a human may make, keeps the live schema list. A human [restores](operations.md#review-service) what an approval replaced from its event while what it made live is still live, recorded as a `RESTORED` event on the approved review; a human's [revocation](operations.md#manual-authoring) of a rejection is a `REJECTION_REVOKED` event on the rejected review that keeps the URLs it classified again. `GET /api/reviews/{id}` returns the trail as `events`, oldest first, and the console shows each event with its actor. `GET /api/review-events?since=<RFC 3339 time>` lists the events of all reviews since then, oldest first by default (`dir=desc` for newest first) and at most `limit` (default and maximum 1,000) with `truncated` set when more exist, so a client reads on from the last event's time, each with its `event_id`, its review's `artifact_type` and ListingSource and without the action's details; the [review agent runner](operations.md#review-agent-runner) builds its daily digest from it.

A review-approved `NO_PATTERN` is a completed URL classification. It suppresses new pattern inference until a human [restores](operations.md#review-service) the decision its approval replaced; a [crawl-root move](README.md#listingsource-scope) keeps it.

### Approval guard

In `agent` authoring mode ([review agents](operations.md#review-agents)) an approval by a review agent goes ahead only when the approving agent changed neither the candidate version it approves nor the review's pages, as the event trail records it (`APPROVER_IS_AUTHOR`, refused alone), and deterministic checks pass on what the server itself evaluated or stored: a product-schema review's live matrix, or the sample labels the author agent or a human set on a URL-pattern review. The approving agent's own judgement and anything it sends with the approval, such as a matrix, are never evidence. They run in the approval's transaction under the review's row lock, after the version check, and a refusal answers 409 with an `error` message and `failed_checks`, each named by `check`, and leaves the review pending. A product-schema approval needs:

- a stored live matrix (`LIVE_MATRIX_MISSING`) that evaluated the approved candidate version and exactly the schemas and templates approval would make live now, so a changed stored template set behind a rebase counts, and no page that left the review (`LIVE_MATRIX_OUTDATED`), fetched within the configured age (`LIVE_MATRIX_EXPIRED`). The approval does not fetch the shop itself: a refresh fetches every review page at the shop's crawl delay, which would hold the review's row lock, and with it page joins and edits, for minutes and outlast the request;
- every review page evaluated (`PAGES_NOT_EVALUATED`) and covered as approval coverage counts it, without an acknowledgement (`PAGES_NOT_COVERED`): a page declared removed counts only where the matrix shows a template capturing it as removed;
- no product page on which a schema leaves `title` or `state` empty and no other schema applies (`REQUIRED_FIELD_EMPTY`);
- no rule of a schema that matches nothing on every page that schema applies to (`RULE_MATCHES_NOTHING`);
- no extraction of any schema on any page that fails a per-page, cross-page or identity agreement plausibility check (`IMPLAUSIBLE_EXTRACTION`), the findings that keep a generated schema out of [auto-approval](#plausibility-checks), so the guard is never less strict than that gate, except for price text in the `state` of a status slot, which the refusal does not list;
- at least one review page that shows a sold or unavailable product (`NO_SOLD_PAGE_TESTED`): a page a template captures as removed, or whose extracted `state` the ProductListing normalization resolves to sold out, out of stock or unavailable, whether read from a label or from JSON-LD `availability`, or that names such a status in a window of up to four words, such as a sold notice written as a sentence (only a `state` that resolves as a whole becomes the listing's availability at runtime); or the author's record that it found none. The check reads each `state` through the normalization the scraper uses at runtime, and the schema matrix (`state_availability`, `state_mentions`) and the refusal, which lists the states it saw, show that reading. The crawler stores no state per crawled URL that says whether the source has a sold page, so the check applies to every agent approval of a product-schema review. The record is a `NO_SOLD_PAGE_RECORDED` event on the review (`POST /api/reviews/{id}/no-sold-page` with 3 to 50 distinct `urls` on the crawl host of the review's ListingSource, http or https, and `notes` saying how they were searched; the author agent's `record_no_sold_page` tool, or a human) that keeps the URLs it names. The author agent names only pages the console projected for the review (`GET /api/reviews/{id}/page-projection`, the agents' `inspect_page`) since its latest `HUMAN` event, in any spelling the crawler treats as that page; a record naming another page is refused with 409 and `reason` `PAGES_NOT_INSPECTED`, naming those pages. A human's record is their own account. It changes no candidate, so it moves no version and does not count as authoring, and the reviewer agent may not record it. A pending product-schema review only takes it, and it stands for the review whatever its later versions until a later `HUMAN` event hands the review back;
- no page the candidate covers that shows a price or a description block while no schema applying to it has a `price` rule (or an estimate rule, which captures what an auction-style shop shows there) or a `description` rule (`CONTENT_RULE_MISSING`, naming the pages): a price element of the page's own content (class, id or `itemprop` naming a price, outside navigation, header, footer, carts and lists of other products) holding an amount with its currency, as the `state` price-text check detects it but also beside a status label ("Sold for £500" shows a price), and not all zeros, or a description element holding at least eight words of prose. The matrix records these page signals when it evaluates the pages, so a stored matrix without them is outdated (`LIVE_MATRIX_OUTDATED`). They are heuristics: only the guard of an agent approval applies them, a human approves what the pages do not call for.

A URL-pattern approval needs a decided candidate (`CANDIDATE_UNDECIDED`) and rests on the candidate's sample labels alone: in `agent` mode the crawler does not guess what a product page is, neither by keywords in a URL ([review agents](operations.md#review-agents)) nor by a page's schema.org `Product` markup, which is information for whoever inspects a page. Only labels on the crawl host of the review's ListingSource count, since every URL the decision applies to lies there. They must mark at least `CRAWLER_REVIEW_AGENT_MIN_LABELLED_URLS` URLs `PRODUCT` and as many `NOT_PRODUCT` (`TOO_FEW_LABELS`), and the decision, its exclusion included, must classify every `PRODUCT` URL as a product page (`PRODUCT_LABEL_NOT_MATCHED`) and no `NOT_PRODUCT` URL (`NOT_PRODUCT_LABEL_MATCHED`), so an exclusion that takes a `PRODUCT` URL fails the first check, matching each URL in the crawler's spelling, with or without its trailing slash, as the spider does; a `NOT_PRODUCT` URL also counts as taken when the decision takes it on http or https, with or without `www.`, which the crawler treats as one page, or in an earlier spelling a row stored before the crawler kept URLs as fetched still carries ([stored URLs](networking.md#stored-urls)). `NO_PATTERN` takes no URL, so a human decides it. A pattern must not be clearly narrower than the shop's product URLs either (`PATTERN_TOO_NARROW`): the console records on each sample URL whether its page described exactly one schema.org `Product` when an agent or a human last inspected it (`describes_one_product` of the page projection), and the check fails when at least 8 sample pages were inspected, the pattern, a URL its exclusion takes not counted, takes less than half of the share of the sample that the inspected product pages suggest (taken URLs over sample URLs against product pages over inspected pages), and it misses at least one inspected product page; a page labelled `NOT_PRODUCT`, such as a gift card marked up as a `Product`, is no product page here. The refusal reports the taken and sampled URL counts, the product and inspected page counts and up to ten missed product pages. It is a heuristic over a sample the author chooses, so each of the three conditions has to hold, and a pattern that follows its labels while the inspected pages show no missed product passes. The labels belong to the candidate, so the approved candidate version names exactly the labels an approval is judged on, and its event keeps them; they do not expire, since any change of the candidate moves its version. Human approvals and every other verdict skip the guard.

The author agent or a human sets a pending URL-pattern review's labels as a whole with `POST /api/reviews/{id}/sample-labels` (the `expected_candidate_version` and `labels`, each a `url`, its `label`, `PRODUCT` or `NOT_PRODUCT`, and a short `reason`; an empty list removes them), or in the console. A label names a URL on the crawl host of the review's ListingSource, on http or https, with or without `www.` (any other is refused with 400): a URL of the review's sample, or an http(s) URL on the default port and without credentials; it is stored in the crawler's spelling of the URL, and a page takes one label, on http or https, with or without `www.` or its trailing slash, so its labels never count twice. The candidate keeps them as `sample_labels` with when they were set (`labelled_at`). Setting them changes the candidate: it moves the candidate version, is refused with the 409 of a stale edit when based on another version, and is recorded as a `CANDIDATE_EDITED` event of its actor, so the four-eyes rule counts it as authoring; the reviewer agent's attempt answers `403` `REVIEWER_CANNOT_CHANGE_CANDIDATES`. Saving a decision classifies the review's sample URLs again under it in the edit's transaction, so their candidate match and class and the summary's `candidate_product_count` always describe the decision the review holds. A whole-candidate edit keeps the stored labels and is refused with 400 when it names other ones; it is decoded and stored as the candidate it decodes to, so a key the candidate does not have is refused with 400. A key stored before then is ignored when read and dropped by the next edit or labelling. A URL-pattern review has no live matrix: its matrix request answers 400.

A pending URL-pattern review's sample starts as the crawl's first URLs when the review opens and grows while it waits: `GET /api/reviews/{id}` first adds URLs the crawl has stored for the ListingSource since then, at most once a minute per review and up to 1,000 sample URLs in all, picking the ones not yet in the sample in the order of a hash of the URL so later URLs of every path shape are in reach. An added URL takes its previous class from the stored class and its match flags from the review's current and candidate patterns, and the summary's `sample_count` and `candidate_product_count` follow. A failed refresh is logged and the read goes on. The agent tools page the sample: `get_review` takes `sample_offset` and lists at most 150 URLs (fewer when their JSON passes a byte bound) as `sample_urls` with `sample_urls_offset`, `sample_urls_total` and `sample_urls_next_offset`, which is null on the last page, so an agent reads the whole sample by calling it again with the next offset. The label checks of the approval guard apply to labelled URLs as before, whether or not the sample holds them. The console lists the whole sample.

### Removed-page templates

A page the shop keeps at HTTP 200 with a removal notice and no product markup fails every cached schema and opens or joins the ListingSource's product-schema review like any failing page. The reviewer declares it removed on that review instead of authoring a schema for it: the candidate's optional `removed_page_schemas` list (`POST /api/reviews/{id}/candidate`, or the console's **Removed pages** tab) holds removed-page templates under the same contract and validation as a generated one, a selector bound to the notice with either its text or a regex, and a regex that matches any text is rejected. Like the candidate's schemas, the list starts from the ListingSource's stored templates when the review opens, so the reviewer also edits or retires stored templates there, for example one that turned out too broad. A candidate posted with the list replaces the candidate's templates, an empty list retiring every one; a candidate posted without the key keeps them unchanged, so an edit of the schemas alone never retires a template. A stored row that does not decode fails the opening. A stored template that today's validation rejects opens with the rest and matches nothing, as at runtime; it refuses approval, and any save that changes the templates, until the reviewer fixes or retires it, while edits that leave the templates unchanged still save. Templates can be changed only while the review is pending; approval still needs a valid product schema list, so to keep the cached schemas as they are the reviewer drops the starter schema from the candidate.

A removal page that keeps the product template with an empty title element records [`MissingRequiredValue`](#missing-required-values) instead and, outside `agent` mode, opens or joins no review. A human adds such a page to the ListingSource's product-schema review from the console's list of these pages (`POST /api/listing-sources/{id}/missing-value-pages/review` with the page's `url`): the page must be a product page of the ListingSource whose last scrape recorded the outcome, and the ListingSource must have live schemas, both checked before the page is fetched (`409` otherwise), and the shop must serve it without redirecting it to a non-product page (`400` otherwise). It joins the pending review as a reviewer-added page, or, when none is pending, a review opened for it with the reason `missing_required_value` once the fetch succeeded, whose candidate is the live schema list and the stored templates; rejecting that review classifies no page. The reviewer declares the template there and the matrix evaluates it like any review page's.

The schema matrix lists the review pages the reviewed templates, stored and new, match (`removed_page_matches`) and what the removal guard makes of each with the candidate's schemas live: removed, or still a product because a candidate schema extracts it with a title other than the notice. A template that also matches a product page, or a candidate schema that still extracts the notice page, is therefore visible before approval. A template whose notice is the title a candidate schema extracts from a page without a rejecting finding takes that product's name for a removal notice, as a text template on the title element whose text the name contains does: the removal guard cannot tell the name from a notice and would withdraw the page, so each such match names the product title (`product_title`), and the console asks the reviewer to check the template's breadth. The report decides nothing: one page cannot tell a product's name from the notice of a removal page that keeps the product template, so the template is too broad unless the page is such a notice. Validation catches a regex that matches any text on its own; this is the breadth check for text, and regex, templates that only the review's pages reveal. Approval replaces the ListingSource's stored templates with the reviewed list in the same transaction that makes the schemas live, and releases the waiting pages, so the page that joined the review is captured as removed on its next scrape and opens no new review. A removal a template captured records the templates that matched; the same transaction re-arms every page of the ListingSource whose last removal a template captured that the new list no longer holds unchanged, retired or narrowed, so a product page an over-broad template withdrew is scraped and recaptured at once rather than at its next scrape interval ([re-armed pages](scheduling-and-retries.md#fetch-retries)). A stored row that does not decode fails the approval and leaves the review pending. The review records the stored list it opened with, and approval keeps changes other writers made to the stored list since then: a template generated in `auto` or `review` mode, which still appends, stays stored, and one retired meanwhile stays retired unless the reviewer changed it. Stored templates follow the [precedence rule](#schema-lifecycle) of generated ones. An approved review keeps the list that went live and its templates are read-only, so an older review never overwrites a list a later review changed.

## LLM limits

LLM use is limited to URL-pattern inference, product-schema generation, fresh page classification, and schema evaluation. Provider selection belongs to executable wiring; crawler services rely on the generic LLM capability.

LLM use is optional. In manual and agent authoring modes, every point that would infer a URL pattern or generate a product schema opens a pending manual review instead, so operator-authored artifacts enter crawler configuration only through the same review rail and validation as generated ones. Fresh page classification has no manual counterpart: non-product pages are excluded through the URL pattern, and removed pages through [removed-page templates](#removed-page-templates) declared on the review. The operator contract, including the auto and review modes, is in [crawler operations](operations.md#authoring-modes).

Crawler LLM calls are governed by bounded concurrency, minimum request-start spacing, bounded provider retries, and a per-ListingSource budget. A request reservation does not hold the scheduling mutex while it waits, and retry sleeps release the request permit. This keeps expensive recovery explicit and prevents unlimited generation.
