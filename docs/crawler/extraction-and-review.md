# Crawler extraction and review

## Extraction contract

The scraper fetches active and sold product URLs, detects verified removed-page templates, and first evaluates cached schemas. It applies every cached schema to the same parsed page, checks each candidate's extraction independently, and ranks the plausible candidates. A bad candidate rejects that schema only; an external or system failure aborts the attempt and does not trigger generation.

Raw extraction remains source evidence. The crawler keeps raw strings, ordered image candidate groups, duplicates, relative values, rejected candidates, and configured raw attributes. It stores a validated, canonical image projection separately for generic raw values. Validation keeps the first candidate of each group that is a safe public target and not too small: a width and height in the URL query or path decide, otherwise a probe reads the size from the image. An image whose size stays unknown is kept, unless its URL names a thumbnail; that name alone never rejects an image, because shops also name full-size uploads that way. Extracted values must never invent auction identity, lot data, or attribution.

A text rule captures the visible text of each matched element, trimmed at both ends with its internal whitespace kept ([`visible_text.rs`](../../src/crawler/src/scraper/css_selector/rule/visible_text.rs)). A `<br>` or a block element boundary starts a new line, and table cells are separated by a space, wherever markup whitespace does not already separate the text on either side, so `Top Hat<br>Pen` does not become `Top HatPen`; inline elements such as `span`, `a` or `sup` add nothing, so `£<span>2,800</span>` stays one value. Struck-through text (`del`, `s`, `strike`), such as a superseded price, is dropped unless it is all the element's text, and whitespace already next to it stands in for a following break, so `£25 <del>£50</del><br>VAT` gives `£25 VAT`. `source_listing_id` joins its text as written instead, so a captured identity does not change with how its text is laid out. Removed-page templates match the separated text, whitespace-collapsed and lowercased, because a matched notice is compared with the titles cached schemas extract from the same page.

A rule evaluates its primary selector and then its `additional_selectors`, in that order, and its cardinality decides what the additional selectors mean ([`rule.rs`](../../src/crawler/src/scraper/css_selector/rule.rs)). With `first`, the default, they are fallbacks: the first selector that yields a value wins and the later ones are not evaluated, so a price rule can name the structured-data price before the visible one. With `all` they aggregate: every selector's matches are collected in selector order, so a gallery or a description can span separate blocks. Aggregation never captures the same content twice: an element is extracted at most once across all selectors of a rule, and an element nested inside, or containing, an element the rule already extracted is skipped, so a description rule that selects a container and its paragraphs keeps the container only. `description` and raw attributes keep equal text from separate elements once, in order; `images` keeps its duplicates as raw evidence and the [plausibility checks](#plausibility-checks) report them.

A matching page hash and effective schema-set fingerprint can skip extraction. Otherwise the crawler hashes its generic raw-input envelope. Equal input refreshes crawler scrape metadata without creating a new operational capture.

The crawler does not normalize extracted values. Price parsing, currency, availability and language belong to the [ProductListing normalization worker](../events/flow.md#productlisting-write-flow), which reports what it cannot normalize. Generic raw values keep every supplied price, state and text value as extracted.

### Plausibility checks

Before a candidate is used, the crawler checks the raw strings it extracted from one page ([`plausibility.rs`](../../src/crawler/src/scraper/plausibility.rs)):

- `title` is not blank; `state` is not blank and no longer than a label;
- `price` and the estimates, when present, are not blank, no longer than a label and do not consist of zero digits only;
- no `title`, `state`, price, estimate or `description` value carries CSS rules or script source;
- the extracted `source_listing_id`, checked before the URL-hash fallback replaces a blank one, is present, capturable and one identifier rather than a list of three or more class-like words, such as a whole `<body class>` that holds the post id but changes with the template and the product's tags;
- `images` do not repeat an image.

Each finding names its field and check. At runtime a `title`, `state`, CSS/script or uncapturable-identity finding rejects the candidate; price, estimate and image findings rank it below candidates with fewer such findings, and completeness and stored order break ties; a blank or word-list identity does not affect selection. Free-text states such as "Viewing by appointment only." pass, and the worker reports them. Rejected candidates and schema repair stay crawler-side and never enter the business [normalization replay corpus](../normalization-replay.md).

The review pages show different products, so the review gate also compares each candidate's extractions of them ([`cross_page.rs`](../../src/crawler/src/scraper/plausibility/cross_page.rs)): a `title` or `source_listing_id` that two pages share names the shop, the category or a page template, and an image that two pages share is a default share image or placeholder rather than a product photo. Images compare by the URL they resolve to, without the fragment, and without the query when the path names an image file, because sizes, cache busters and CDN signatures differ per page. Runtime extraction sees one page at a time and cannot run these checks. A shop that gives two products the same title fails them too; a reviewer approves such a schema knowingly.

Every schema of a ListingSource must derive the same identity from a page, because runtime selection may pick any of them and a scrape whose identity differs from the one the listing was captured under is rejected as a [conflict](scheduling-and-retries.md) rather than captured as a second listing. The matrix therefore also compares, on each review page, the identities of the candidates that apply to it ([`identity_agreement.rs`](../../src/crawler/src/scraper/plausibility/identity_agreement.rs)): an identity another applying candidate contradicts, or one that differs from the identity the page's crawler URL was captured under, is a finding that names the contradicting identities. A schema written for a sold page whose identity element differs from the active-page schemas' therefore shows the conflict even when it is the only schema that applies to that page. Blank and uncapturable identities are left to the per-page checks.

The schema matrix lists the per-page, cross-page and identity agreement findings of every candidate on every review page, and the review console shows each next to its field. Any finding on any candidate's extraction keeps a generated schema out of auto-approval, including an extraction that a rejecting finding withdrew from a page another candidate covers, and a blank identity: the identity rule is applied to every review page, sold, archived and price-on-request variants included, and a schema without an identity rule, or whose rule matches nothing on one of them, reports a blank identity there; such a page is captured under the URL-hash identity, which differs from the identity captured from the other variants, so a reviewer has to accept it.

Shipping interpretation runs in downstream raw normalization using the pure `product-listing-normalization` crate. It
combines item-specific `rawShipment`/`rawShipmentNote` text with description context;
contradictory or unsupported delivery clauses veto the observation. Duration ranges
remain complete text with their units and dispatch/delivery context.
Selectors must exclude shared footers and site policies. Explicit phrases cover all 14
catalog languages; phrase tables, language fixtures and input bounds are executable in
[`shipping.rs`](../../src/product-listing-normalization/src/shipping.rs). Interpretation
uses no LLM, interpretation agent or model fallback, and adds no schema-generation calls
or native description ingestion.

Successful page fetch time travels as the crawler capture's `source_occurred_at`, outside
the content hash. Schema evaluation, normalization, capture retries and queue delivery keep
that acquisition time. Historical captures without it remain readable and cannot establish
shipping observations. Matching page/input hashes retain the existing capture deduplication:
they do not advance shipping observation time. A new immutable raw revision can observe
unchanged shipping assertions when other captured item content changed. See the
[shipping contract](../shipping.md#deterministic-crawler-item-assertions) for application rules.

## Schema lifecycle

Fresh generation begins only after cached candidates are exhausted. It creates a new schema from the current page; it never edits a cached schema. A generated schema persists only after it applies and its extraction passes the rejecting plausibility checks.

Initial generation is product-schema-only: its response contract offers no page classification, every seed sample is treated as a product page, and a sample the model considers non-product is excluded from schema coverage and reported as a risk rather than classified. Single-page classification may produce a product schema, a verified removal, or a verified non-product result. A removal needs selector-bound evidence and results in raw deletion capture. A stored removed-page template is removal evidence only while no cached product schema still applies to the page with a title other than the not-found notice and, when the crawler URL already carries a captured source listing id, the same identity; a related-item card on a removed page is therefore not product evidence. When product evidence exists it wins, the page is scraped normally (a candidate that then fails a rejecting plausibility check reaches fresh generation, not withdrawal) and the conflict is logged as an over-broad template to fix. A removed-page regex that matches any text is rejected both when proposed and when applied. A non-product result changes that URL only; one page never rewrites a domain URL pattern.

Every generated product schema must pass deterministic rule validation (selector syntax and attribute names) before it can be reviewed or persisted. An invalid response is returned to the model with a fixed correction code plus the offending field and value during bounded response correction, and the retry log carries the same detail without the prompt or HTML; if it stays invalid, generation ends with a schema-generation validation failure. The review gate rejects invalid candidates before review persistence, so review artifacts and approved schemas only ever contain valid rules, and model output is never reported as a database failure.

Generated selectors are grounded in page structure. Optional fields remain absent rather than guessed. A configured optional rule (identity, description, price, price estimates, raw attributes) that matches nothing on a page leaves that field empty with a per-field diagnostic; it never fails the page, so one page without a description does not reject the schema or trigger fresh generation. Title and state fail closed on a miss, and images fail closed unless the image container exists and is empty. The `images` rule skips matched elements without a value (no image URL candidate, or no attribute of an `attribute` rule), such as `href="#"` slots a gallery mixes in with its image links, and fails only when every element it matched lacks one. Such a gallery fails the page: its selector matched elements, so it is not treated as an empty container. Rules of other fields still fail on an element without their attribute. The schema matrix counts the skipped elements per page so a reviewer can tighten a loose selector; the count is review information and does not block deterministic approval. The schema matrix reports the [plausibility findings](#plausibility-checks) of every candidate on every page; a rejecting finding fails that page like an apply error, so the page is not covered. The schema matrix and the review gate report optional-field misses separately from page failures: a miss on some pages stays visible to the reviewer and does not block deterministic approval, while an optional rule that matches nothing on every page its candidate applied to is a defective selector and keeps a generated schema in human review. The matrix counts only matches with visible text for a text rule, because a blank element yields no usable value: a price selector that matches only blank cells, such as a spacer next to the price, is such a total miss rather than an approvable schema that captures the shop without prices. At runtime a description or price miss is logged at warn level so selector drift on cached schemas stays visible at the production log level; identity, estimate and raw-attribute misses stay at debug or trace. State selectors represent availability or a cart action, not price text. Raw attribute selectors are review/display inputs and participate in the raw-input hash; adding a new attribute requires schema regeneration for existing cached schemas.

## Review rail

The review rail records generated URL-pattern and product-schema artifacts as auditable state. Artifacts may be pending, approved, rejected, marked for repair, or superseded. When review gating is enabled, pending artifacts do not become active crawler configuration.

A review records its ListingSource, and URL-pattern reviews also record their domain. Candidate changes increment the review version and invalidate any cached schema matrix, so a stale live inspection cannot overwrite current review state. Review identities and matrix references use the TypeID policy in [object IDs](../object-ids.md).

A reviewer can add further pages of the ListingSource to a pending or approved product-schema review (`POST /api/reviews/{id}/pages` with `{"url": ...}`), such as sold, price-on-application or photo-less variants, so the schema matrix tests the candidate beyond its seed pages. Only http(s) URLs on the default port and without credentials on one of the ListingSource's domains are accepted, checked before the fetch and again on the final URL after redirects. A redirect to a page that is not a product page (outside the domain's decided URL pattern, or the homepage while none is decided) is refused. A page already on the review under the crawler's URL normalization, `www.` or scheme spelling is a duplicate, and a reviewer adds a bounded number of pages per review. A reviewer can remove a page they added (`DELETE /api/review-pages/{id}`), for example once the shop has deleted it; seed pages cannot be removed. Adding or removing a page drops the cached matrix, and a matrix evaluated over a different page set is not stored. These pages carry the `REVIEWER_ADDED` role and are no operator verdict: rejecting the review does not classify them as non-product pages.

A page that fails every cached schema while the ListingSource's product-schema review is pending joins that review instead of opening or generating another. The crawler attaches it once per page identity with the `WAITING_PAGE` role, up to a bounded number per review, and drops the cached matrix, so the reviewer sees each template variant that needs the schema. Further failing pages wait without being attached. A reviewer can remove a waiting page like one they added, for example once the shop has deleted it; a removed page that still loads and still fails every cached schema joins again on its next retry. Waiting pages are no operator verdict either.

Editing an approved product-schema review rewrites the ListingSource's live schema list, so it is refused unless that review's candidate is still the live list; approval stores the list that went live, including a merged append or repair, as the review's candidate. Once a later review has changed the live schemas, the schemas of older approved reviews are read-only.

A review-approved `NO_PATTERN` is a completed URL classification. It suppresses new pattern inference until an explicit reset returns the domain to `UNKNOWN`.

## LLM limits

LLM use is limited to URL-pattern inference, product-schema generation, fresh page classification, and schema evaluation. Provider selection belongs to executable wiring; crawler services rely on the generic LLM capability.

LLM use is optional. In manual authoring mode, every point that would infer a URL pattern or generate a product schema opens a pending manual review instead, so operator-authored artifacts enter crawler configuration only through the same review rail and validation as generated ones. Fresh page classification has no manual counterpart; non-product pages are excluded through the URL pattern. The operator contract, including the auto and review modes, is in [crawler operations](operations.md#authoring-modes).

Crawler LLM calls are governed by bounded concurrency, minimum request-start spacing, bounded provider retries, and a per-ListingSource budget. A request reservation does not hold the scheduling mutex while it waits, and retry sleeps release the request permit. This keeps expensive recovery explicit and prevents unlimited generation.
