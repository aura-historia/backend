# Crawler scheduling and retries

## Work admission and scheduling

Spider and scraper loops use global bounded schedulers. Before either begins work, it refreshes the complete authoritative ListingSource scope. If that refresh fails, no candidates are selected for that pass.

The crawler scheduler is deployed as one process. Spider work is selected by configured domain. Scraper work is selected by eligible domain and URL: a pass avoids selecting the same domain twice, and the production server takes up to 100 due URLs per selected domain. Process-local `DomainLock` (scoped per component), `UrlLock`, and `ListingSourceLock` instances coordinate concurrent workers in that process. Spider and scraper hold independent domain locks: each component excludes only itself for a domain, so a spider crawl and a scraper batch may run on the same domain concurrently. Combined request pressure is bounded by each component's own per-domain limits (in-flight cap, minimum delay, and adaptive throttle), not by mutual exclusion. When the scraper opens a domain circuit it records whether the spider was active on that domain so operators can attribute the failure. Different domains remain concurrent; multi-process scheduler coordination is outside the current design. Durable crawler state supplies cooldowns and failure metadata across later runs.

Lock contention is temporary deferral, not skipped work. A spider candidate or scraper domain contended by another worker of the same component is left eligible for the next scheduler pass without changing its durable state; the current pass excludes that domain so other domains can continue. This avoids a tight same-pass retry loop while preserving candidate accounting through explicit `deferred_urls` (every candidate of a deferred domain batch plus URLs that lost a URL or ListingSource lock race, in the same unit as `total`, `succeeded`, `failed` and `skipped`) and `deferred_domains` (whole batches that lost the scraper domain lock) counts, both distinct from `skipped`. Expected lock contention is logged at debug level and never as a warning. The scraper domain lock is held for one scraper-domain batch because primary/seed transport observations and the fenced domain-circuit update form one serialized operation; the spider domain lock is held for one spider run. Unrelated domains remain concurrent.

The production server currently schedules spider work every 72 hours and scraper work every 10 minutes. These are runtime composition settings, not public timing guarantees.

## Fetch retries

A scraper request receives up to three inline attempts. Backoff begins at one second and is capped at two seconds. `Retry-After` never blocks a domain worker.

Spider fetches follow the same bounded inline principle. The crawl-root preflight retries transient transport failures (DNS, connect, timeout) a bounded number of times within a fixed wall-clock budget for the whole redirect chain, and never retries policy, TLS or redirect failures; HTTP statuses are left to Spider, which retries each page a bounded number of times except when the body was already truncated by the transport ceiling or the answer was 429 ([rate-limit answers](networking.md#rate-limit-answers)). A preflight failure carries the same typed failure kind as a Spider-detected one, so it receives the same durable cooldown profile instead of a generic short retry.

Schema-generation outcomes (exhausted regeneration, a fresh schema whose extraction fails a rejecting plausibility check, recorded as `FreshSchemaNormalizationFailed`, rejected classification, exhausted LLM budget, generated schemas that fail deterministic validation, recorded as `SchemaGenerationValidationFailed`, and an identity conflict, recorded as `SourceListingIdConflict`) give the URL a 30-minute retry cooldown instead of an immediate retry. An identity conflict is a page whose selected schema derives another `source_listing_id` than the one its listing was captured under; the page is not captured, because the new identity would start a second listing, and it stays in conflict until the reviewer aligns the schemas' identity rules. A page that leaves a required value empty (`MissingRequiredValue`, see [missing required values](extraction-and-review.md#missing-required-values)) needs no schema work and is not retried: it is recorded as scraped without a capture, so it returns at its normal scrape interval and keeps the outcome until a scrape extracts the value.

A page that fails every cached schema while its ListingSource's product-schema review is pending waits on that review (`PendingSchemaReview`). Its first wait gets the 30-minute schema cooldown; each further consecutive wait on the same review doubles the delay, capped at four hours, so a page that cannot succeed before the reviewer decides is not refetched every cooldown. Due waiting pages are ordered after every other due URL of their domain batch, so they never take batch slots ahead of pages the cached schemas may still extract. The streak ends with any other outcome and starts again at 30 minutes when the page waits on a different review. The reviewer's verdict decides what happens to the waiting pages: needs-repair keeps the review pending, so they keep backing off; approval and rejection both close it and, in the transaction that closes it, release every waiting page of the ListingSource for an immediate retry and clear its wait and streak. A released page that fails every cached schema again starts a new streak on the review it then waits on. A wait is recorded only while its review is still pending, so a scrape that overlaps the reviewer's decision does not hold back a page the decision released.

After final failure, the crawler records retry metadata and a future `next_retry_at`; it does not hold a worker open. HTTP 404 and 410 are terminal removals. Unsafe targets and other terminal outcomes are not retried immediately. Retryable transport and selected HTTP failures receive a durable cooldown. A URL robots.txt disallows (`RobotsDisallowed`) is retried after 24 hours; one refused because robots.txt was unreachable (`RobotsUnreachable`) is retried after 15 minutes. Neither is retried inline, and neither affects domain health ([robots.txt](networking.md#robotstxt)). After a `RobotsUnreachable` refusal the rest of the domain batch is deferred, since robots.txt refuses the whole origin.

A domain batch also stops at a wall-clock budget (five minutes by default) and defers its remaining URLs. The pass waits for its slowest domain, so a shop with a long `Crawl-delay` would otherwise hold back every other domain's next pass; such a shop is scraped a few URLs per pass instead.

## Scraper domain circuits

URL retry state and domain health are separate. HTTP 408, 429, 503 and 504 and a failed DNS resolution open the `listing_source_domains` scraper circuit on the first observation. A timeout, a connection failure or a DNS timeout also comes from a slow host, which is the shop segment the crawler targets, so one of them is recorded as domain evidence without opening the circuit: the batch continues and the next pass selects the domain normally. The circuit opens on the second consecutive failure of the same kind, in the same batch or a later pass with no responsive fetch between, or when at least three distinct URLs of one batch, and at least half of the URLs attempted in it, fail that way. The fetch attempt timeout grows with the domain's observed latency within bounds ([networking](networking.md#resource-rails)), so a shop that answers slowly throughout is waited for rather than tripped. The domain stores a consecutive same-kind `scrape_failure_streak`, stable `last_scrape_error_kind`/status diagnostics, and `next_scrape_at`; the streak increments only when the failure kind is unchanged and resets to one when it changes, and recorded evidence leaves `next_scrape_at` empty. Cooldowns grow exponentially from the failure kind's base (15 minutes for both HTTP 503 and 504) and are capped at 24 hours. A `Retry-After` value is retained as structured fetch metadata and can extend the durable domain cooldown without blocking the worker. The circuit-open event records the domain's smoothed fetch latency, its sample count, the effective attempt timeout and the batch's attempted and timed-out URL counts, so an opening can be judged against the shop's speed.

An open domain is excluded before candidate selection. When its cooldown expires, selection returns exactly one probe URL and the scraper uses `DomainProbe` mode, which suppresses schema-seed fan-out; a domain that only holds recorded evidence has no cooldown and is selected as a normal batch. Recovery is based on an explicit transport observation of the primary request: a responsive HTTP result, including 404/410, proves the domain is responsive and closes the circuit, clearing recorded evidence with it, on the next fenced state update. Pre-fetch application or local failures do not prove recovery, while downstream schema, plausibility, review, or database failures after a responsive fetch cannot erase that observation. A probe transport failure increments the same streak and reopens the circuit. Within a batch the scraper carries the domain snapshot forward from one fenced write to the next, so evidence recorded by an earlier URL counts for a later one.

A single 500/502 remains URL-scoped; three distinct 500/502 failures in one domain batch open the short `HTTP_5XX_BURST` circuit and stop the remaining URLs for that domain. A terminal status that can only mean the shop rejects the crawler as such (401, 403, 405, 418, 421, 451 or 501) likewise stays with its URL, but when three distinct URLs of one batch answer the same such status in a row, with no other outcome between them, the domain is treated as failing uniformly: the `HTTP_STATUS_BURST` circuit opens with that status as its diagnostic (`last_scrape_status_code`), the remaining URLs are skipped and the domain cools down for 30 minutes, growing like every other kind. A repeated status on one URL is one piece of evidence, any other fetch outcome ends the run, and HTTP 404 and 410 are product removals that never count. Such a status is still a responsive answer, so the probe after the cooldown closes the circuit unless it is rejected with one of these statuses again, which reopens it with the next, longer cooldown. The open event also reports the run's URL count and the cooldown.

First-time schema generation samples only product URLs from the primary candidate's explicitly supplied persisted `domain_id`. Normal and probe requests must carry that identity. `ScraperService` exposes one request-based operation: `scrape(ScrapeRequest) -> ScrapeOutcome`. `ScrapeMode::Normal` permits domain-scoped seed fan-out, `ScrapeMode::DomainProbe` performs only the supplied probe URL, and `ScrapeMode::PrimaryOnly` is used by direct/manual callers and permits an absent domain without seed fan-out. Mode and domain are therefore explicit request data rather than task-local execution state. The sample query keeps the existing URL eligibility rules and excludes domains whose scraper cooldown is still active, so schema seeding cannot fetch another persisted domain indirectly. Seed selection returns each URL together with its current raw-input fence. If a primary request fails, its URL receives the failure metadata; if a schema-seed request fails, the seed URL receives that metadata and its own fence is used for the write. This keeps primary and seed retry state independent even when they share a domain, while the domain update still uses the candidate's fenced domain snapshot. A domain-opening seed transport failure is attributed to that same domain; no seed failure is attributed to the primary candidate's domain when the persisted IDs differ.

Opening and closing updates are fenced by the candidate's complete domain snapshot, including the last failure kind. URL and domain failure writes use independent fences and transactions: a stale URL fence does not prevent a current domain failure from opening the circuit, and a stale domain fence does not roll back a valid URL failure. A domain-opening write reports both outcomes separately, and only an actually applied domain row is reported as opened. A process-local scraper-scoped `DomainLock` serializes scraper batches for the same crawler domain; spider work on that domain writes disjoint `listing_source_domains` columns and is not excluded. Unrelated domains continue independently.

Spider failures use the same durable principle. Repeated failures of the same kind increase the domain cooldown. Access blocks, JavaScript-only sites, and similar durable blockers receive longer cooling than transient connection, rate-limit, or server failures. Unclassified internal or configuration failures (persisted as `spider_run_error`) start with a short retry and double on each consecutive failure, capped at 24 hours, so a persistent fault cannot retry every few minutes indefinitely.

Failures that need a site or configuration change before a crawl can succeed (a robots.txt block, a redirect off the domain, a TLS or URL problem, an inference sample too small to classify, a pattern that matches no crawled page, or a completed classification without a pattern) do not retry forever. After five consecutive failures of the same kind the domain is recorded as `NEEDS_OPERATOR`, loses its cooldown and is no longer selected. The state is visible per domain in the [ListingSource overview](operations.md#review-service) and the review console; an operator resolves it by registering the right domain or removing and re-registering the domain, which replaces its pattern and crawl state, or by disabling crawling for the ListingSource. Transient failures keep retrying because the site may recover, and durable blocks already cool for a month.

## Spider crawl completion

Every spider run records a stable `last_crawl_outcome` for its domain. A crawl that delivers usable pages ends as `COMPLETED`, as `PAGE_BUDGET_REACHED` when the page bound stopped discovery on purpose, or as `HARD_TIMEOUT_TRUNCATED` when the wall-clock bound cut it short or the spider stopped on a [rate-limit answer](networking.md#rate-limit-answers); the crawl diagnostics tell the two apart and carry the shop's `Retry-After`. A spider error is recorded as `FAILED`. A crawl with at most one usable page is a failure, whatever stopped it, and so is a crawl that delivered pages but no product URL: `NoProductUrls` when the domain's pattern matched none of them and `NoUrlPattern` when its classification is complete without a pattern. Both keep the crawled URLs, leave the last full-crawl time untouched and follow the recoverable cooldown and [needs-operator escalation](#scraper-domain-circuits). The completion log of every run carries the completion, a truncated flag, the product URL count and the pattern. A run that fails while the Spider library is still crawling stops that crawl and its in-flight requests and returns only once the crawl has ended, so the spider domain lock outlives the last request and a domain never has two library crawls at once. A crawl stopped early, on a rate-limit answer or because its run ended, says so and why in its completion log.

URLs discovered before a truncation are kept and classified like any other. Only `COMPLETED` and `PAGE_BUDGET_REACHED` count as a full crawl: they clear failure and truncation state and start the normal recrawl interval. A truncated crawl leaves failure metadata and the last full-crawl time untouched and schedules a follow-up sooner than the normal interval. That delay starts at one day, doubles with each consecutive truncation and is capped at the normal recrawl interval, so a domain too large for one crawl settles into the normal schedule instead of looping.

A crawl that needs a product URL pattern while a pattern review is pending, or opens one, is neither a success nor a failure. It finishes discovery and stores every URL under the pattern state it has, and re-reads the domain's pattern state after each batch of URLs it stores and before it records its outcome. When it finds the review decided, the crawl stores the URLs it stored while waiting again, classified with the decision, classifies the rest with it too and ends as a crawl with that decision does, so no URL it stored after the decision stays unclassified. Otherwise it is recorded as `AWAITING_URL_PATTERN_REVIEW` and leaves failure and truncation state untouched. The review's decision classifies those stored URLs in the deciding transaction and releases the domain, so they need no second crawl from the root: a domain whose discovery was full keeps its last full-crawl time and returns at the normal interval, one whose discovery was cut short is due at once. An undecided review holds the domain back for at most the normal recrawl interval before the spider refreshes its sample. The pending review in the console queue and the domain's crawl state in the ListingSource overview are where an operator sees the wait ([review service](operations.md#review-service)).

## Scrape completion fences

The crawler marks a URL scraped only after raw capture reports a terminal persisted outcome (`Changed`, `Unchanged`, `Duplicate`, or `Stale`). Crawler-local completion writes fence on the raw-input SHA-256 observed by that candidate: a later capture makes an older completion or error write a no-op.

A capture rejected because its ListingSource no longer exists is terminal for that queued item but is not treated as persistence. The next authoritative scope refresh disables the stale local work. Other capture failures stay retryable.

`ACTIVE` and `DORMANT_SOLD` URLs remain scrape candidates and are scheduled alike. The scraper records every captured URL `ACTIVE`, sold pages included, and no longer writes `DORMANT_SOLD`; a URL that still holds it stays valid. A verified removal captures a raw delete, then returns the URL to `ACTIVE` for future checks.

## Throughput and ordering

Scraper workers hand observations to one bounded collector per scheduler pass. Producers wait for capacity. The collector flushes a partial batch when it reaches its size limit, its maximum age, or channel close, and never overlaps flushes.

Within a `(ListingSourceId, candidate URL)` raw stream, capture order is preserved. Independent streams may run in parallel. Local crawler state and business raw capture use separate Postgres transactions, so a committed capture followed by a failed local mark is safely retried through the unchanged path.
