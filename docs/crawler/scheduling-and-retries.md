# Crawler scheduling and retries

## Work admission and scheduling

Spider and scraper loops use global bounded schedulers. Before either begins work, it refreshes the complete authoritative ListingSource scope. If that refresh fails, no candidates are selected for that pass.

The crawler scheduler is deployed as one process. Spider work is selected by ListingSource. Scraper work is selected by ListingSource and URL: a pass avoids selecting the same ListingSource twice, and the production server takes up to 100 due URLs per selected ListingSource. Process-local `WorkLock` (one per ListingSource and component) and `UrlLock` instances coordinate concurrent workers in that process. Spider and scraper hold independent work locks: each component excludes only itself for a ListingSource, so a spider crawl and a scraper batch may run on the same ListingSource concurrently. Combined request pressure is bounded by each component's own per-host limits (in-flight cap, minimum delay, and adaptive throttle) and by the [politeness group](networking.md#politeness-groups) both components share, not by mutual exclusion. When the scraper opens a scrape circuit it records whether the spider was active on that ListingSource so operators can attribute the failure. Different ListingSources remain concurrent; multi-process scheduler coordination is outside the current design. Durable crawler state supplies cooldowns and failure metadata across later runs.

Lock contention is temporary deferral, not skipped work. A spider candidate or scraper batch contended by another worker of the same component is left eligible for the next scheduler pass without changing its durable state; the current pass excludes that ListingSource so others can continue. This avoids a tight same-pass retry loop while preserving candidate accounting through explicit `deferred_urls` (every candidate of a deferred batch plus URLs that lost a URL lock race, in the same unit as `total`, `succeeded`, `failed`, `awaiting_schema_review` and `skipped`) and `deferred_batches` (whole batches that lost the scraper work lock) counts, both distinct from `skipped`. Expected lock contention is logged at debug level and never as a warning. The scraper work lock is held for one scraper batch because primary/seed transport observations and the fenced scrape-circuit update form one serialized operation; the spider work lock is held for one spider run. Unrelated ListingSources remain concurrent.

The production server currently starts a spider pass every hour and scraper work every 10 minutes; a spider pass only crawls ListingSources that are [due](#discovery-coverage). These are runtime composition settings, not public timing guarantees.

## Fetch retries

A scraper request receives up to three inline attempts. Backoff begins at one second and is capped at two seconds. `Retry-After` never blocks a scraper batch.

Spider fetches follow the same bounded inline principle. The crawl-root preflight retries transient transport failures (DNS, connect, timeout) a bounded number of times within a fixed wall-clock budget for the whole redirect chain, and never retries policy, TLS or redirect failures; HTTP statuses are left to Spider, which retries each page a bounded number of times except when the body was already truncated by the transport ceiling or the answer was 429 ([rate-limit answers](networking.md#rate-limit-answers)). A preflight failure carries the same typed failure kind as a Spider-detected one, so it receives the same durable cooldown profile instead of a generic short retry.

Schema-generation outcomes (exhausted regeneration, a fresh schema whose extraction fails a rejecting plausibility check, recorded as `FreshSchemaNormalizationFailed`, rejected classification, exhausted LLM budget, generated schemas that fail deterministic validation, recorded as `SchemaGenerationValidationFailed`, and an identity conflict, recorded as `SourceListingIdConflict`) give the URL a 30-minute retry cooldown instead of an immediate retry. An identity conflict is a page whose selected schema derives another `source_listing_id` than the one its listing was captured under; the page is not captured, because the new identity would start a second listing, and it stays in conflict until the reviewer aligns the schemas' identity rules.

A product URL whose redirect nothing settles (`RedirectTargetUnverified`, `RedirectDestinationUnsettled`, see [redirect removal evidence](networking.md#redirect-removal-evidence)) is recorded as scraped without a capture, together with the target it ended at. It is no failure and leaves `failure_count` at zero; instead, each further consecutive scrape that ends unsettled at the same target doubles its recheck delay, from the one-day scrape interval up to 30 days, so a URL whose redirect stays unsettled is not fetched daily forever; one that many product URLs share is [removal evidence](networking.md#redirect-removal-evidence) instead. The streak ends with any other outcome, except a shared-target removal the [mass-removal guard](#mass-removal-guard) holds, and starts again at one day when the target changes. A `RedirectTargetUnverified` URL waits out its delay only while its ListingSource stores no product schema: once one is stored, by a review verdict, a restore or generation, a schema can judge the target, so the URL is due again at its scrape interval. Only the first scrape of a streak logs `Leaving a redirected product URL until its next scrape` at WARN; later ones log at DEBUG, and the scraper pass summary counts them per ListingSource under `skip_reasons.unsettled_redirect`.

Approving a product-schema review, or restoring what an approval replaced, re-arms in its transaction the pages of the ListingSource the new configuration may decide differently: every page whose last removal a [removed-page template](extraction-and-review.md#removed-page-templates) captured that the configuration no longer holds unchanged. A re-armed page is due at once, as a page never scraped, unless a retry cooldown a later fetch outcome set, such as a [bot challenge](networking.md#bot-challenges)'s, still holds it back, and keeps its outcome and capture until that scrape replaces them. A URL retired as `DUPLICATE` is never re-armed. A scrape that matched a template before the change committed records its removal after the change, and is left due at once the same way when the change no longer holds that template unchanged. A rejection changes no configuration and re-arms nothing.

A page that fails every cached schema while its ListingSource's product-schema review is pending waits on that review (`PendingSchemaReview`). Its first wait gets the 30-minute schema cooldown; each further consecutive wait on the same review doubles the delay, capped at four hours, so a page that cannot succeed before the reviewer decides is not refetched every cooldown. Due waiting pages are ordered after every other due URL of their batch, so they never take batch slots ahead of pages the cached schemas may still extract. The streak ends with any other outcome and starts again at 30 minutes when the page waits on a different review. The reviewer's verdict decides what happens to the waiting pages: needs-repair keeps the review pending, so they keep backing off; approval and rejection both close it and, in the transaction that closes it, release every waiting page of the ListingSource for an immediate retry and clear its wait and streak. A released page that fails every cached schema again starts a new streak on the review it then waits on. A wait is recorded only while its review is still pending, so a scrape that overlaps the reviewer's decision does not hold back a page the decision released. A wait ends the batch: every page of the ListingSource fails the same cached schemas, so the remaining candidates are deferred without a fetch and counted in `deferred_urls` (logged as `crawler.scraper.batch_awaits_schema_review`), and they keep their due state. The ListingSource is not selected again while any of its pages has a wait whose retry delay has not passed, so a pending review costs one fetch per cooldown instead of a batch; the verdict that releases the waiting pages releases the ListingSource with them. A wait is no failure: a page that only waited stays a [schema seed](#scraper-circuits), and the scraper pass log and [metrics](operations.md#metrics-and-alarms) count waiting pages apart from failed ones (`awaiting_schema_review` in the log; the metrics count them in neither `ScrapesFailed` nor `UrlFailures`).

After final failure, the crawler records retry metadata and a future `next_retry_at`; it does not hold a worker open. HTTP 404 and 410 are terminal removals; a redirect is one only with the [evidence](networking.md#redirect-removal-evidence) a redirect must show. Unsafe targets and other terminal outcomes are not retried immediately. Retryable transport and selected HTTP failures receive a durable cooldown. A URL robots.txt disallows (`RobotsDisallowed`) is retried after 24 hours; one refused because robots.txt was unreachable (`RobotsUnreachable`) is retried after 15 minutes. Neither is retried inline, and neither affects the [scrape circuit](#scraper-circuits) ([robots.txt](networking.md#robotstxt)). A page whose own robots directives refuse capture (`PageDirectiveDisallowed`) is retried after 24 hours and not inline; the shop answered it, so it counts as responsive for the circuit ([page robots directives](networking.md#page-robots-directives)). A [bot challenge](networking.md#bot-challenges) answered instead of the page (`BotChallenge`) is not retried inline either; it receives the five-minute transient cooldown and is no extraction failure. After a `RobotsUnreachable` refusal the rest of the batch is deferred, since robots.txt refuses the whole origin.

A product page that answers a page error is not retried indefinitely. Page errors are the statuses a page answers on its own: HTTP 500 and 502, which stay URL-scoped unless a burst opens the [scrape circuit](#scraper-circuits), and every other 4xx and 5xx no rule of its own covers (not 404 and 410, which are removals, not 408, 425, 429, 503 and 504, and not the crawler-rejection statuses 401, 403, 405, 418, 421, 451 and 501). The first page error of a run keeps the cooldown of its status, five minutes for 500 and 502 and a day for the others; each further one in a row doubles it, capped at a day, and the tenth in a row parks the URL, after about 42 hours of 500s or ten days of daily retries: it is fetched again only after 30 days, and is parked again unless the page then answers. A parked URL keeps its row, disposition and last capture, and `crawler.scraper.product_url_parked_after_page_errors` logs it at WARN with the URL, status and `page_error_streak`. The run is the URL's own `page_error_streak`: each page error counts one more, and any other fetch failure, a wait on a schema review, a scraper outcome of a fetched page and every completed scrape reset it, so failures of other kinds never count into it. A schema seed starts its own run, as it is drawn only without a fetch failure since its last scrape.

A scraper batch also stops at a wall-clock budget (five minutes by default) and defers its remaining URLs. The pass waits for its slowest batch, so a shop with a long `Crawl-delay` would otherwise hold back every other ListingSource's next pass; such a shop is scraped a few URLs per pass instead.

## Scraper circuits

URL retry state and the scrape circuit of a ListingSource, kept on `listing_sources`, are separate. HTTP 408, 429, 503 and 504 and a failed DNS resolution open the circuit on the first observation. One exception: a 429 from a shop on a listed shared platform ([politeness groups](networking.md#politeness-groups)) whose `Retry-After` the platform's group pause covers in full (at most 60 seconds) is deferred instead: the URL gets its 429 retry cooldown, the circuit stays closed and the batch continues once the group's pause ends (`crawler.scraper.rate_limit_deferred`). A 429 without `Retry-After` or with a longer one, the third distinct URL of one batch answering 429, and a 429 to the probe of an open circuit open the circuit as before. A timeout, a connection failure or a DNS timeout also comes from a slow host, which is the shop segment the crawler targets, so one of them is recorded as circuit evidence without opening the circuit: the batch continues and the next pass selects the ListingSource normally. The circuit opens on the second consecutive failure of the same kind, in the same batch or a later pass with no responsive fetch between, or when at least three distinct URLs of one batch, and at least half of the URLs attempted in it, fail that way. The fetch attempt timeout grows with the host's observed latency within bounds ([networking](networking.md#resource-rails)), so a shop that answers slowly throughout is waited for rather than tripped. The ListingSource stores a consecutive same-kind `scrape_failure_streak`, stable `last_scrape_error_kind`/status diagnostics, `next_scrape_at` and `scrape_failing_since`, when the streak began; the streak increments only when the failure kind is unchanged and resets to one when it changes, and recorded evidence leaves `next_scrape_at` empty. Cooldowns grow exponentially from the failure kind's base (15 minutes for both HTTP 503 and 504) and are capped at 24 hours. A `Retry-After` value is retained as structured fetch metadata and can extend the durable circuit cooldown without blocking the worker. The circuit-open event records the host's smoothed fetch latency, its sample count, the effective attempt timeout and the batch's attempted and timed-out URL counts, so an opening can be judged against the shop's speed.

A ListingSource whose circuit is open is excluded before candidate selection. When its cooldown expires, selection returns exactly one probe URL and the scraper runs it as a circuit probe, which suppresses schema-seed fan-out; a ListingSource that only holds recorded evidence has no cooldown and is selected as a normal batch. Recovery is based on an explicit transport observation of the primary request: a responsive HTTP result, including 404/410, proves the shop is responsive and closes the circuit, clearing recorded evidence with it, on the next fenced state update. Pre-fetch application or local failures do not prove recovery, while downstream schema, plausibility, review, or database failures after a responsive fetch cannot erase that observation. A probe transport failure increments the same streak and reopens the circuit. Within a batch the scraper carries the circuit snapshot forward from one fenced write to the next, so evidence recorded by an earlier URL counts for a later one.

A single 500/502 remains URL-scoped; three distinct 500/502 failures in one batch open the short `HTTP_5XX_BURST` circuit and stop the remaining URLs of that batch. A terminal status that can only mean the shop rejects the crawler as such (401, 403, 405, 418, 421, 451 or 501) likewise stays with its URL, but when three distinct URLs of one batch answer the same such status in a row, with no other outcome between them, the shop is treated as failing uniformly: the `HTTP_STATUS_BURST` circuit opens with that status as its diagnostic (`last_scrape_status_code`), the remaining URLs are skipped and the ListingSource cools down for 30 minutes, growing like every other kind. A [bot challenge](networking.md#bot-challenges) rejects the crawler the same way whatever status it was answered with, so challenges with the same status, a `202` interstitial on every page for instance, form such a run too. A repeated status on one URL is one piece of evidence, any other fetch outcome ends the run, and HTTP 404 and 410 are product removals that never count. Such a status is still a responsive answer, so the probe after the cooldown closes the circuit unless it is rejected with one of these statuses or a challenge again, which reopens it with the next, longer cooldown. The open event also reports the run's URL count and the cooldown.

First-time schema generation samples only product URLs of the ListingSource the request names. `ScraperService` exposes one request-based operation: `scrape(ScrapeRequest) -> ScrapeOutcome`. The normal mode permits seed fan-out within that ListingSource, the circuit-probe mode performs only the supplied probe URL, and the primary-only mode is used by direct/manual callers and never fans out. The mode is therefore explicit request data rather than task-local execution state. The sample query keeps the existing URL eligibility rules and draws nothing while the ListingSource's scrape circuit cools down or it has no crawl root, so schema seeding cannot fetch around an open circuit. It takes only URLs whose retry is due and that recorded no fetch failure or [schema-generation outcome](#fetch-retries) since their last completed scrape; a review wait is neither, so a page a decided review released is drawn like any other. In every authoring mode it also leaves out every page a rejected `manual_schema_required` review [classified as a non-product page](operations.md#manual-authoring), in any spelling of the page, so a new review is never judged on a page already rejected: when too few other product URLs remain, the review opens with fewer seed pages, or with its primary page alone, never with a rejected one. Seed selection returns each URL together with its current raw-input fence. If a primary request fails, its URL receives the failure metadata; if a schema-seed request fails, the seed URL receives that metadata and its own fence is used for the write. This keeps primary and seed retry state independent, while the circuit update still uses the candidate's fenced circuit snapshot, so a seed transport failure counts towards the circuit of the ListingSource both belong to.

Opening and closing updates are fenced by the candidate's complete circuit snapshot, including the last failure kind. URL and circuit failure writes use independent fences and transactions: a stale URL fence does not prevent a current circuit failure from opening the circuit, and a stale circuit fence does not roll back a valid URL failure. A circuit-opening write reports both outcomes separately, and only an actually applied circuit update is reported as opened. The scraper's process-local `WorkLock` serializes scraper batches of the same ListingSource; spider work on that ListingSource writes disjoint `listing_sources` columns and is not excluded. Unrelated ListingSources continue independently.

Spider failures use the same durable principle. Repeated failures of the same kind, the three kinds of a crawl whose pages yield no product URL (`InsufficientInferenceSample`, `NoProductUrls`, `NoUrlPattern`) counting as one, increase the ListingSource's crawl cooldown. Two short retries come first; then site and configuration problems cool down longer than transient connection, rate-limit or server failures. Access blocks and JavaScript-only sites take one short retry and then [wait for an operator](#spider-failure-escalation). Unclassified internal or configuration failures (persisted as `spider_run_error`) start with a short retry and double on each consecutive failure, capped at 24 hours, so a persistent fault cannot retry every few minutes indefinitely.

<a id="spider-failure-escalation"></a>

No classified crawl failure retries forever: a shop that keeps failing the same way costs a crawl preflight every few days, and only a person can tell whether it recovers, needs another crawl root or should no longer be crawled. A ListingSource whose streak reaches its kind's escalation count is recorded as `NEEDS_OPERATOR`, loses its cooldown and is no longer selected. Kinds where the shop refuses the crawler (`AccessDenied`, `JavascriptRequired`) escalate on their second consecutive failure, one short retry after the first, since the shop does not let the crawler in by itself. Every other kind escalates on its fifth: transient ones (an unreachable host, a Cloudflare or other bot challenge, a server error, a rate limit, an empty or tiny crawl) about two and a half days after the first failure, and those that need a site or configuration change (a robots.txt block, a redirect off the crawl root's host, a TLS or URL problem, an inference sample too small to classify, a pattern that matches no crawled page, or a completed classification without a pattern) about a week after it. `BotProtection` counts into the same streak as the three no-product kinds, so a shop that alternates challenged and no-product crawls escalates like one that repeats either. Unclassified internal or configuration failures are the crawler's own and keep their capped retry.

The state is visible in the [ListingSource overview](operations.md#review-service) and the review console with the failure kind and streak, and every escalation logs `crawler.spider.crawl_failed` with `needs_operator` and counts in the crawler-wide `CrawlRunsFailed` metric, which the failure [alarm](operations.md#metrics-and-alarms) reads. An operator resolves it by resuming the crawl once the shop or its configuration is fixed, which returns the source to the schedule with a new streak, by changing the source's presentation URL, which [moves](README.md#listingsource-scope) it to another crawl root and clears its crawl state, by disabling its `WEB_CRAWL` ingestion, or by [labelling](README.md#listingsource-scope) a shop the crawler cannot scrape, which records why. A resumed or moved source that keeps failing escalates again after its full streak.

## Spider crawl completion

Every spider run records a stable `last_crawl_outcome` for its ListingSource, unless the URL-pattern review it waited on was decided first (below) or the ListingSource [moved to another crawl root](README.md#listingsource-scope) while it ran. A crawl that delivers usable pages ends as `COMPLETED`, as `PAGE_BUDGET_REACHED` when the page bound stopped discovery on purpose, as `HARD_TIMEOUT_TRUNCATED` when the wall-clock bound cut it short, as `STOPPED` when the crawler's [shutdown](operations.md#stopping-the-crawler) ended it, or as `RATE_LIMITED` when the spider stopped on a [rate-limit answer](networking.md#rate-limit-answers), whatever ended the crawl after that answer. A spider error is recorded as `FAILED`. A crawl with at most one usable page is a failure, whatever stopped it, and so is a crawl that delivered pages but no product URL: `NoProductUrls` when the ListingSource's pattern matched none of them and `NoUrlPattern` when its classification is complete without a pattern; an [incremental crawl](#discovery-coverage) is judged on the pages it fetched. Both keep the crawled URLs, leave the last full-crawl time untouched and follow the recoverable cooldown and [needs-operator escalation](#spider-failure-escalation). A crawl whose pages were mostly [bot challenges](networking.md#bot-challenges) fails as `BotProtection` instead, on the transient cooldown and the same escalation. The completion log of every run carries the completion, a truncated flag, the product URL count and the pattern. A run that fails while the Spider library is still crawling stops that crawl and its in-flight requests and returns only once the crawl has ended, so the spider work lock outlives the last request and a ListingSource never has two library crawls at once. A crawl stopped early, on a rate-limit answer, because its run ended or because the crawler shuts down, says so and why in its completion log.

A crawl that completed (not cut short, not mostly bot challenges) with fewer URLs than the inference minimum but at least a small floor (five by default) does not fail where the URL pattern is authored by an operator or agent rather than inferred by the LLM: it opens the same manual URL-pattern review with the URLs it has, so a small shop is reviewed instead of cooled down; LLM inference and a crawl below the floor keep failing with `InsufficientInferenceSample`. Where an operator or agent authors the pattern, a crawl opens its URL-pattern review only once its sample holds 200 URLs (the fetch-free method's seed size), counting the URLs earlier crawls of the ListingSource stored, or once the crawl completed. A crawl that ends earlier with fewer, such as one a shop's rate limit stopped, is no failure as long as it adds URLs to the sample: it stores its URLs unclassified, opens no review, and the next crawl, due as its outcome sets, starts its sample from the stored URLs. A crawl that ends early without adding a URL to the stored ones shows that waiting gathers no more, so it classifies the sample it has: it opens the review at the inference minimum or above and otherwise fails with `InsufficientInferenceSample` on its cooldown, so a shop whose crawls never reach 200 URLs is not left waiting without an outcome.

The failure log of a run whose crawl delivered too few pages to classify their URL pattern (`InsufficientInferenceSample`) carries what the crawl reported once it ended (completion and truncated flag, pages delivered, accepted and rejected by host, blacklist or duplicate, status histogram, robots.txt policy and `Crawl-delay`, request delay and budget), so a shop whose links leave the crawl's host, whose pages fail or whose `Crawl-delay` left the crawl few pages can be told apart.

URLs discovered before a truncation are kept and classified like any other. Only `COMPLETED` and `PAGE_BUDGET_REACHED` of a full crawl count as a full crawl: they clear failure and truncation state and start the normal recrawl interval. A truncated full crawl leaves failure metadata and the last full-crawl time untouched, and schedules a follow-up that continues from the [frontier](#discovery-coverage) it left instead of starting over. A crawl that ran out of its wall-clock budget with unvisited URLs left is too large for one crawl: it counts one more consecutive truncation and continues six hours later, so such a shop is covered in several steps a day. Any other truncated crawl, one that ended within its budget leaving only pages it could not fetch, such as bot challenges, or one that could not tell its frontier, fits one crawl: it resets the truncation count and continues one day later. Its truncation log carries the size of the frontier it left (`frontier_left`) and the time the run waited on the database (`db_wait_ms`), so a large shop can be told apart from a starved run.

A crawl the crawler's shutdown ends is no truncation: it stops like one at the hard timeout, stores the URLs it discovered and keeps its frontier, but records `STOPPED`, counts no truncation, leaves failure metadata, rate-limit state and the last full-crawl time untouched and makes the ListingSource due again a minute later, from that frontier. A run whose too small sample or unmatched pattern the shutdown caused ends the same way instead of counting a failure.

### Rate-limited crawls

A shop that answers the spider with a [rate limit](networking.md#rate-limit-answers) has asked for less traffic, not reported a fault, so a `RATE_LIMITED` crawl leaves failure and truncation metadata and the last full-crawl time untouched. It increments the ListingSource's rate-limit streak and holds its next crawl back until the later of the wait the shop asked for (its `Retry-After`, else its quota reset) and a backoff that starts at one hour and doubles with each step of the streak, capped at one day; the shop's wait is itself capped at one day when read. That hold is kept apart from the crawl timer, so a review decision that releases the ListingSource cannot bring the next crawl forward. A run that fails, or waits for a URL-pattern review, after a rate-limit answer stopped its crawl records the same streak step and hold, and keeps its own failure kind, count and cooldown, whichever is later; a review decided before such a run records its wait leaves it recorded as `RATE_LIMITED`.

Each step of the streak doubles the delay between request starts of the ListingSource's crawls, from at least the default delay, up to one minute, and robots.txt `Crawl-delay` can still only raise it. A full crawl clears the streak and restores the configured pace; an [incremental crawl](#discovery-coverage) never does, and is held back and slowed like any other crawl. A crawl the wall-clock bound cut short without a rate-limit answer steps the streak down by one, so a shop whose catalogue no longer fits one crawl at the slowed pace recovers its pace one step at a time instead of staying slow; a renewed rate limit steps it up again. Failures keep the streak. The completion log of a crawl carries the delay it ran with.

A crawl that needs a product URL pattern while a pattern review is pending, or opens one, is neither a success nor a failure. It finishes discovery and stores every URL under the pattern state it has, and re-reads the ListingSource's pattern state after each batch of URLs it stores and before it records its outcome. When it finds the review approved, with a pattern or `NO_PATTERN`, the crawl stores the URLs it stored while waiting again, classified with the decision, classifies the rest with it too and ends as a crawl with that decision does, so no URL it stored after the decision stays unclassified. Otherwise it is recorded as `AWAITING_URL_PATTERN_REVIEW` and leaves failure and truncation state untouched. The review's decision classifies those stored URLs in the deciding transaction and releases the ListingSource, so they need no second crawl from the root: a ListingSource whose discovery was full keeps its last full-crawl time and returns at the normal interval, one whose discovery was cut short is due at once, or once a [rate-limit hold](#rate-limited-crawls) ends. Releasing the ListingSource clears its wait timer and its `AWAITING_URL_PATTERN_REVIEW` outcome and records no other, since the waiting crawl's completion is not kept: the ListingSource has no `last_crawl_outcome` until its next crawl records one. A restore of an approved pattern releases the ListingSource the same way, but a ListingSource whose crawl waits on a newer, still pending review keeps that wait's outcome, so a ListingSource reports the wait only while it has a pending URL-pattern review. The wait is recorded only while the review is still pending: a rejection stores no decision for the re-reads to find, and an approval can commit after the last one. A crawl whose review was decided before it records the wait records no outcome, unless a [rate-limit answer](#rate-limited-crawls) stopped it, so the ListingSource keeps the outcome, failure and truncation state and timer the decision left; a full discovery still counts as the last full crawl, so the ListingSource returns as a released one does. After a rejection the crawl's URLs stay as stored, and the ListingSource's next crawl can open a new review. An undecided review holds the ListingSource back for at most the normal recrawl interval before the spider refreshes its sample. The pending review in the console queue and the ListingSource's crawl state in the ListingSource overview are where an operator sees the wait ([review service](operations.md#review-service)).

## Discovery coverage

A crawl is bounded in time, and a shop rarely fits one crawl, so discovery carries over between crawls instead of restarting from the root each time.

- **Crawl kinds.** A ListingSource is due for a full crawl when its last full crawl is a week old or missing, and otherwise for an incremental crawl once its last spider run of any kind is a day old. An incremental crawl walks the listing and category pages from the root again to find new product URLs, but does not fetch product URLs the ListingSource already stores, nor URLs it retired as [duplicates](networking.md#canonical-product-urls), under any spelling that names them: either trailing-slash spelling, a link carrying parameters the [stored spelling](networking.md#stored-urls) drops, such as a session id, and a link of Shopify's `/collections/<c>/products/<p>` shape to a stored `/products/<p>`. The crawl root is never such a page, whatever the ListingSource stores: under every spelling that names it, either trailing-slash spelling, another letter case, parameters the stored spelling drops or a directory index file such as `/index.php` or `/en/default.aspx`, the crawl requests it from the shop. The Spider library skips only the spellings it was told before the crawl, so the crawl answers a request for any other spelling of a known page itself, without asking the shop, though Spider still counts that link against the page bound and waits the request delay before it; an incremental crawl never records a full crawl, so full crawls stay weekly. A full crawl that follows a truncated one, which left a frontier, skips the known pages the same way and spends its budget on the frontier and on new links; a full crawl that finds no frontier fetches every page, so removals are noticed. It is judged on the pages it fetched: when it found product pages the ListingSource stores linked, a stored pattern that matched none of its pages is neither classified again nor a `NoProductUrls` failure, and a healthy root that links only stored product pages is no tiny crawl; an incremental crawl that found no stored product page linked is judged like a full crawl. Its completion clears failure state; neither kind of incremental ending touches the truncation count, the rate-limit streak or the last full-crawl time. Every crawl, of either kind, waits for the ListingSource's failure cooldown, review wait and [rate-limit hold](#rate-limited-crawls), and runs at the pace its rate-limit streak sets. Due ListingSources are crawled least recently run first, by their last run of any kind, so a shop whose truncated crawls continue every few hours never takes the spider's slots ahead of another shop's daily incremental crawl; among sources never run, those never fully crawled go first.
- **Frontier.** The links a crawl found and the seeds it was given but did not visit are its frontier. Only links the crawl itself would request count, resolved where Spider resolves them (against the page's first absolute `<base>` element if any, otherwise the page URL): on the crawl root's host, not its `www` twin, under the root's scheme, in the [stored spelling](networking.md#stored-urls) and allowed by the URL blacklist and robots.txt. Every crawl that delivers usable pages replaces the ListingSource's stored frontier with its own, at most 20,000 URLs. So does a run that fails only because those pages yield no product URL (`NoProductUrls`, `NoUrlPattern` or an inference sample too small to classify, or `BotProtection` when they were mostly [bot challenges](networking.md#bot-challenges)), so a shop whose product pages lie deeper than one crawl reaches further with each such run; the run is still recorded as that failure, with its cooldown, until the [needs-operator escalation](#spider-failure-escalation) stops a site without a catalogue. Any other failed run keeps the previous frontier: one with at most one usable page (a transport failure, a refused or challenged root, a rate limit before any page) or one whose pages could not be classified or stored. A [crawl-root move](README.md#listingsource-scope) drops it, and a URL whose page was retired as a duplicate, in either trailing-slash spelling, is never visited from it. The next crawl, of either kind, first walks from the root for at most half of its budget, then, once the root page was neither refused nor answered with a bot challenge, visits the frontier, together with what that walk found but did not reach, for the rest of its time and pages. Seeds pass the same rules as found links, are fetched by the same crawl and are classified, canonicalized and stored through the same path. A page answered with a bot challenge or a rate limit is not visited: it stays in the frontier. A crawl that leaves a frontier is cut short unless the page bound stopped it; one that leaves none, within its bounds, is complete.
- **Continuation budget.** A full crawl that continues the frontier of truncated crawls runs one more configured wall-clock budget per consecutive truncation that ran out of time, at most three, so a shop too large for one crawl needs fewer runs. At most one in three spider slots runs such an extended crawl at a time, and none with fewer than three slots, so continuations cannot hold every slot while other shops wait; a continuation that finds no extended slot free, an incremental crawl and the crawl of a shop whose rate-limit streak is not zero run the configured budget.
- **Crawl-delay budget.** A crawl's wall-clock budget is raised for a shop whose robots.txt `Crawl-delay` would leave it fewer than 40 pages, enough for the URL-pattern inference sample, up to one hour; the delay between requests stays as the shop asked. A pace slowed by rate limits does not raise it, since that shop asked for fewer requests. The completion log carries the budget the crawl ran with (`crawl_budget_ms`), next to its request delay, seed count, the stored product pages it found linked and did not fetch again (`known_skipped`), the links to known pages it answered itself (`known_fetches_saved`) and the frontier it left.

## Scrape completion fences

The crawler marks a URL scraped only after the ingestion queue confirms the raw observation (`Accepted`) or the observation is discarded as unsendable. The queue's acceptance is the crawler's persisted outcome; the consumer captures it afterwards. Crawler-local completion writes fence on the raw-input SHA-256 observed by that candidate: a later capture makes an older completion or error write a no-op.

An observation that exceeds the queue's message limit or cannot be encoded is terminal: it is never sent, logged with its ListingSource, URL and encoded size, counted in `discarded_unsendable_count` of `crawler.raw_capture.batch`, and its scrape completes so the page is not resubmitted until it is due again. A rejected, unconfirmed or unattempted submission, a missing or contradictory item outcome and a failed submission stay retryable. A ListingSource that left the admin scope is disabled by the next scope refresh.

`ACTIVE` and `DORMANT_SOLD` URLs remain scrape candidates and are scheduled alike; a `DUPLICATE` URL is never scraped again. A scrape that a redirect takes to a product URL the ListingSource already stores under another row records the redirected URL `DUPLICATE` and captures nothing, so it is not fetched again on every pass; a redirect to a page the crawler stores otherwise is handled by the [duplicate-target rule](networking.md#duplicate-targets), before the page is extracted. The scraper records every captured URL `ACTIVE`, sold pages included, and no longer writes `DORMANT_SOLD`; a URL that still holds it stays valid. A verified removal captures a raw delete, then returns the URL to `ACTIVE` for future checks. Each new removal the [mass-removal guard](#mass-removal-guard) admits logs `crawler.scraper.verified_removal` at INFO with its evidence: the kind (`GONE_STATUS` for a 404 or 410, `REDIRECT_TO_HOMEPAGE`, `REDIRECT_TO_NON_PRODUCT_PAGE`, `REDIRECT_TO_STORED_NON_PRODUCT_PAGE`, `REDIRECT_TO_REJECTED_PAGE`, `REDIRECT_TO_DISALLOWED_PAGE`, `REDIRECT_TO_SHARED_PAGE`, `REMOVED_PAGE_TEMPLATE`, `REMOVED_PAGE_CLASSIFICATION` or `PERSISTENT_PAGE_DIRECTIVE_REFUSAL`), the status the shop answered and the final URL, where known. Like an unchanged product page, a recheck that finds the page still removed captures nothing when that raw delete is already the URL's last captured raw input, and refreshes only the crawler scrape metadata. Before a new raw delete is captured, the crawler forgets the URL's page hash, scraper-context fingerprint and captured raw input under the usual fence. If the capture or the completion write after it fails, the URL therefore never stays on the product capture from before the removal. A page that returns, changed or not, is extracted and captured as an upsert.

## Mass-removal guard

A verified removal withdraws a listing, so a fault that makes every page of a shop look removed, such as a redirect the crawler misreads, would withdraw its whole catalogue within a few passes. A scraper batch therefore holds its new removals until it has scraped its last URL. When they are at least 10 and more than half of the URLs the batch scraped, not counting rechecks of pages whose removal is already captured, the batch captures none of them and logs `crawler.scraper.mass_removal_held` at WARN with the ListingSource, its crawl host, the count, the share and the count per evidence kind. Each held URL is recorded as scraped without a capture (`MassRemovalHeld`): it keeps its listing and returns at its normal scrape interval, and the batch's other pages are captured as usual, so prices and sold states keep updating. The ListingSource is not paused and the guard keeps no state: it applies again to every batch until the cause is fixed. A batch with fewer new removals is never held, so a shop with few due URLs keeps capturing its own few removals.

An operator who has verified a real bulk clearance confirms it in the review console for the ListingSource, for one hour to seven days (`POST /api/listing-sources/{id}/mass-removal-confirmation`, the source page's **Confirm bulk removal**; [operations](operations.md#review-service)). The confirmation is stored on the ListingSource with its end time and the actor; the guard reads it when a batch's removals are a mass removal, and until the end time the source's batches capture every removal and log the share at INFO as `crawler.scraper.mass_removal_confirmed` with the end time. Confirming makes the source's held URLs due at once, as a [re-arm](#fetch-retries) does, so the next batches capture them. Once the end time passes, or a human revokes the confirmation (`DELETE`, **Revoke**), the guard holds the next batch again without a restart; a confirmation whose read fails holds the batch. Other ListingSources stay guarded.

## Throughput and ordering

Scraper workers hand observations to one bounded collector per scheduler pass. Producers wait for capacity. The collector flushes a partial batch when it reaches its size limit, its maximum age, or channel close, and never overlaps flushes.

Within a `(ListingSourceId, candidate URL)` raw stream, submission order is preserved: one ListingSource's observations are submitted in input order, one bounded submission at a time, and only different ListingSources run in parallel. An accepted submission followed by a failed local mark is safely retried through the unchanged path, because the consumer deduplicates raw input.
