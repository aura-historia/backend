Evidence comes from the `crawler_demo` DB, JSON logs (INFO in rounds 1–2, DEBUG in rounds 3–4), the review console, live page fetches and a code audit.
Scope for ranking: **small/medium non-JS single-dealer shops, no auction houses**. Large catalogues and marketplaces count only where they expose a general bug.
Delete this file once the findings are turned into issues.

## Findings, ranked for small/medium shops

### 1. One slow LLM call freezes the whole crawler — not ticketed

- Round 3: one scraper pass started at 13:59:21 and was **still running at 14:32**. Witney, Founders, AFD and Puckhaber were spidered by 14:05–14:17 and had **0 scraped URLs**. Heymann's circuit expired at 14:02 and was never probed. The spider pass took 1108 s because Puckhaber's end-of-crawl URL classification waited 8.5 min for an LLM permit.
- Cause: the LLM governor defaults to **1 permit with 2 s spacing** (`llm_runtime.rs:13-14`). Schema calls use a **180 s timeout** (`product_schema_service.rs:222,239`) and are retried up to 3 times. Observed latencies were 15–137 s, with repeated 180 s timeouts on Marc Maison and Georgian pages. The scraper pass is a barrier: it joins every domain worker before the next pass starts (`service/cron/scraper.rs:1339-1486`). Fresh generation runs inline in the domain worker.
- Round 4 restarted with `CRAWLER_LLM_MAX_CONCURRENT_REQUESTS=3`: four initial schemas finished within 90 s, but 180 s timeouts kept recurring. One scraper pass still took 828 s, with 98 of 202 URLs skipped. Also observed: a `MAX_TOKENS` truncation retry (4096 → 8192 output tokens) and a "must contain exactly one schema, got 2" validation retry. Each costs another full LLM round trip.
- Fix direction:
  - Make scheduling slot-based so a pass never waits for its slowest domain (#1206 is closed, but the scraper is still pass-based).
  - Give spider URL classification its own LLM lane or priority.
  - Use more than one permit with per-source fairness.
  - Lower timeouts to about 60–90 s and bound the total retry time.
  - Move fresh generation to a queue instead of the domain worker.

### 2. URL patterns are never validated — not ticketed

- Validation only checks that the regex compiles (`url_classification_service.rs:180-186`). Evidence:
  - Moxhams: `[\w%.-]+` excludes the comma in `/stock/785,small-...html`, so **0/766** URLs matched.
  - Japantik: the `$` anchor fails on `?variant=`, so 0/181 matched.
  - Tübingen: `-(art|g|p|km)\d+$` matched 36 URLs and missed 39 `-art-nr-NNNN` URLs.
  - Marc Maison: the pattern itself includes the wishlist action path.
- A freshly inferred pattern that matches nothing is accepted. Reclassification only happens when the pattern was loaded from the store (`spider_service.rs:336`), and that happens at the next crawl, 7 days later.
- `NO_PATTERN` is persisted after one LLM answer and is permanent until someone resets it (`url_pattern_service.rs:179-186`).
- Fix direction:
  - Validate against the inference sample: require a minimum match count and ratio, check that the pattern doesn't cover category, query or action URLs, and feed counter-examples back to the LLM.
  - Treat "0 product URLs" as a crawl failure.
  - Log the pattern and its match ratio at INFO.
  - Give `NO_PATTERN` a retry/expiry.
  - For flat-slug platforms (Magento), fall back to page content such as JSON-LD `Product`, `og:type=product` or `catalog-product-view`. Mayfair pages carry all three. #1594 (research) covers this idea.

### 3. Dead shops look healthy — partly #1912, #2090

- "Crawl completed successfully" was logged for Mayfair (0 products), Moxhams (0) and every crawl that hit the 600 s hard timeout: 15 of the 25 crawls that passed preflight (rounds 1–6).
- `last_crawled` gets set, and the next crawl is 7 days later (`spider/candidate_service.rs:73`).
- Insufficient samples, robots blocks and redirect problems retry every 6 h forever, with no terminal "not a shop / moved" state.
- #1912 covers only the timeout part. #2090's health view doesn't include spider state.

### 4. Politeness: we get shops to block us — #1913 is parked, and its un-park conditions are now met

- Heymann: the spider fetched 684 pages at about 1.6 pages/s. The **first scraper request got 429 with Retry-After 1800**, and a curl from the same IP was also 429. It was **still 429 at 14:32**, 70 min later. antieksite.nl returned 403 after the crawl.
- The **scraper never reads robots.txt**: there is no `robots` reference outside `spider/`, so it ignores Disallow and `Crawl-delay` (antieksite has `Crawl-delay: 30`). This is un-park condition 2 of #1913. The scraper circuit opened while the spider was active on Tübingen, which is close to condition 1.
- The spider has no per-status counters. Mid-crawl 429/403/5xx pages count as "crawled", so a truncated discovery looks complete.
- A single 20 s fetch timeout opens the domain circuit and stops the batch (`docs/crawler/scheduling-and-retries.md`). Tübingen (slow, cheap hosting) kept tripping it. #1911 covers repeated terminal statuses, not slow hosts.
- Fix direction:
  - Un-park #1913: one per-domain limiter shared by spider and scraper, fed by robots `Crawl-delay`, with spider rate adapting to 429.
  - Respect robots in the scraper.
  - Count status codes in spider diagnostics.
  - Require 2–3 timeouts before opening a circuit on hosts with a high baseline latency.

### 5. URL hygiene and canonicalization — partly #1491, #1899

- Query strings are never stripped (`spider/utils/url.rs:39-45`):
  - Japantik: 204/385 URLs were `customer_authentication/login?return_to=...`.
  - antikmoebel: 34 % `?currency=`. Tübingen: 40 % `?filter_material=` / `?gridcookie=`.
  - Crawl budget goes to facets.
- HTML entities are not decoded in some hrefs: stored `?amp;currency=EUR&page=8` and `category=26245&amp;page=3`.
- Duplicates:
  - Shopify `/collections/x/products/y` vs `/products/y`: French Metro has 754 URLs for 485 products, and Founders has 5 IDs on more than one URL.
  - The unanchored regex matches both forms.
  - The scraper then rejects canonical moves as `product_url_move_rejected_destination_known`. The skip has no durable state, so the same URLs are re-picked and logged at WARN every pass.
- The blacklist is substring-based (`url.rs:6-30`). `wishlist` misses `whishlist`. `cart` would also block products like "cartel clock" or "Cartier". There is no login/account/search entry.
- The trailing slash is always removed, so every LASSCO fetch is a 301 to `/product/x/`.
- Fix direction:
  - Use a per-domain query-parameter policy: drop tracking, currency, sort, filter and variant parameters by default, and keep only parameters the pattern needs.
  - Decode entities.
  - Canonicalize with `<link rel=canonical>` at spider time.
  - Persist a terminal state for the "destination known" case.
  - Use a token-based blacklist.

### 6. Schema robustness for small-shop templates — partly #2098–#2100, #1581, #2091

- **An optional field that is present but empty aborts the whole page** (`product_schema.rs:191-193`). Examples are Anticstore `description` and a Marc Maison seed page. This is not ticketed; #2099 covers images only. Each failure triggers fresh generation and spends LLM budget.
- The required `state` forces nonsense on galleries without availability. Witney's schema uses the page title as `state`, and its deterministic gate passed; only the LLM's own LOW confidence stopped it. Georgian got "Product Enquiry" and LASSCO got "Contact" (30 %), and both were auto-approved.
- Seed pages are not diverse: all 4 AFD seeds were sold, so the schema has no price and a sold-only `state` badge (#1581).
- Positional selectors break across pages: Puckhaber price `:nth-child(2)` failed on 2/4 seeds, and raw attributes use `nth-of-type`.
- Duplicate schemas: French Metro and Founders each have schema 0 identical to schema 1 (#2100).
- Unstable or empty identity:
  - Marc Maison `source_listing_id` = "Style Japonism, Chinoiserie / Ref.12432".
  - Witney's is empty although the URL carries `item_web_ref=10001` (#2098 is related).
- An approved broken schema (antikmoebel, whose price element is empty) produces cached fail → fresh generation (including 180 s timeouts) → "regeneration exhausted" → 30 min cooldown, repeated every cycle (#2094).
- Fix direction:
  - Make optional fields soft-fail.
  - Make `state` optional, or add a typed "no availability shown" result.
  - Add a plausibility gate: state resolves to an availability, price parses.
  - Prefer label-anchored selectors.
  - Allow URL-derived identity.

### 7. The LLM budget silently stops all scraping of a source — partly #2094

- The candidate query filters on `s.llm_calls_count < $3` (`scraper/candidate_service.rs:390`). Once a source reaches 20 lifetime calls, **none of its URLs are scraped**, not just regenerated. The counter never resets, and this is visible only in a DEBUG "LLM usage summary".
- antikmoebel reached 4 calls in 1 hour. #2094 understates the impact.

### 8. Discovery budget is about 1,200 pages per shop per week — partly #1912

- 600 s × (500 ms delay, effectively serial) ≈ 1,175 pages. 15 of the 25 crawls that passed preflight (rounds 1–6) hit it (all except Heymann 684, Moxhams 819, Witney 239, Robin 32 pages), and each run starts again from the root.
- There is no sitemap support. The spider `sitemap` feature is not enabled, and #1885 was closed without it.
- For medium shops, this means a stable fraction of products is never discovered: French Metro 485/861, LASSCO 1011/~10k.
- Fix direction: bounded sitemap seeding, persist the crawl frontier between runs, and add incremental recrawls of category pages (daily) instead of a 7-day full crawl.

### 9. Host and redirect edge cases — not ticketed

- An apex that serves 200 while every link points to `www.` is rejected by the exact-host whitelist (`website_spider.rs:357`) → 2 URLs.
- The cross-domain root redirect error doesn't include the target, so "shop moved" can't be told apart from "parked domain" (`website_spider.rs:385-390`).
- Robots-blocked language root (Delaval `/fr/`): no attempt at alternate roots or the sitemap.
- The crawl root is always `https://{domain}` (`service/cron/spider.rs:117`). A small shop with broken TLS that works over plain HTTP (antixx.de) shows up as a generic `ConnectError` and is retried every 6 h. Nothing says "TLS handshake failed; HTTP works". Decide on a policy (HTTP fallback, or a clear terminal state).

### 10. Throughput — not ticketed

- Debug build measurements: about 3 s per URL (1 s throttle + latency, then about 1.8 s processing). Founders, with 15–20 images per product, takes **13.9 s per URL**, almost all after the fetch.
- Image validation runs sequentially per schema candidate and per image, with a DNS resolve on every call (`image_validation.rs:84-125`, `cached_schema_selection.rs:133-142`).
- The image cache is an unbounded `Mutex<HashMap>` (`image_validation.rs:31`), so it grows for as long as the server runs.
- Fix direction: validate images once per page (not per candidate), in parallel and with a cap, and use a bounded LRU cache.

### 11. Config and console

- `.env` `CRAWLER_SCHEMA_LLM_REVIEW_MODE=jev_auto` is still invalid and silently falls back to auto-approve. With `CRAWLER_REVIEW_REQUIRED=true`, the initial and fresh schemas were still auto-approved.
- `GET /api/listing_sources` serializes `last_successful_crawl` as `[2026,288,13,29,45,...]`. `OffsetDateTime` lacks `time::serde::rfc3339` (`review/model/listing_source_overview.rs`).
- Pending reviews of disabled sources (Roldán, Alys) stay at the top of the console.
- A 30-minute scheduler stall, robots blocks, `NO_PATTERN` and 0-product crawls are all invisible in the console (#2090).
- I approved broken schemas without any warning (#2056).

## Observability

From an audit of 372 INFO records (rounds 1–2) and 1,435 records with DEBUG (round 3):

| Question an operator has | Answerable from INFO today? |
|---|---|
| Which shops got 0 products from the last crawl, and why? | No: the domain is only in spans; the pattern and match ratio are not logged |
| Is the crawler stalled? | No: there is no pass-duration alarm, no LLM queue wait and no per-domain pass breakdown |
| Why wasn't URL X updated? | No: there is no per-URL INFO outcome; DEBUG is about 13 records / 14.5 KB per URL |
| Which LLM calls failed or timed out, and for which shop? | No: timeouts produce only "Retrying..."; the invocation events carry no top-level source |
| Was a crawl truncated or rate-limited? | Partly: only the library's `crawl hard timeout` WARN, without span context, while our own log says "successfully" |

Specific problems:

- **64 % of INFO records and 58 % of bytes** are `crawler.raw_capture.batch` heartbeats, logged every ~5 s with no source context.
- Key outcomes have **no `event` name**: "Crawl completed successfully", "Spider run failed", "Found no product URL pattern", "Completed LLM invocation", "Schema generation confidence evaluated", "Scraper run failed", "Scraper scheduler pass complete".
- Context sits in the `spans` array rather than at top level, which is hard to query in CloudWatch Insights. The domain key varies: `domain`, `listing_source_domain`, `crawl_root_url`, or only the opaque `cd_…`/`ls_…` IDs. "Scraper run failed" carries only `domain_id`.
- Diagnostics are missing exactly where they're needed: the redirect target, crawl diagnostics on `InsufficientInferenceSample`, robots crawl-delay, a status-code histogram, deterministic gate failure reasons (stored only in `crawler_reviews.validation_summary`), and LLM budget exhaustion.
- There are no metrics, only a "Performance summary" log line.

Proposals:

1. **Stable event names on every outcome**, with top-level `listing_source_id`, `listing_source_name` and one `domain` key:
   - `crawler.spider.crawl_completed` (with `truncated`, a status histogram, `product_urls`, `pattern`, `sample_match_ratio`, `query_url_share`, `crawl_delay`)
   - `crawler.spider.crawl_failed` (with the cause details: redirect target, sample size and diagnostics)
   - `crawler.spider.pattern_classified`
   - `crawler.schema.generated` (with the gate result and failing fields)
   - `crawler.llm.invocation` (for every outcome, including timeouts, with `governor_wait_ms`)
2. **One compact INFO wide event per URL**, `crawler.scraper.url_outcome`, of about 500 bytes. Outcome enum: `captured_changed | unchanged | sold | skipped:<reason> | failed:<kind>`. Fields: `schema_index`, `score`, fields present, `http_status`, `fetch_ms`, `process_ms`, `image_probes`, `llm_calls`.
3. **Pass summaries** with a per-domain breakdown, skip reasons, the slowest domain and LLM wait time. Log the raw-capture batch only when it does work, or fold it into the pass summary.
4. Wrap the library's hard-timeout WARN into our crawl event, and drop `log.file` paths on stdout.
5. **EMF metrics** for alarms:
   - products captured per source per day (alarm when a source has 0 in 24 h)
   - `pattern_matched_zero` count
   - circuit opens
   - pass duration (alarm above 15 min)
   - LLM governor wait (alarm above 60 s)
   - LLM calls/tokens per source
   - budget-exhausted sources
6. Extend the console health view (#2090) with spider state (last crawl, truncated, pattern, product count, last error and next attempt), budget usage and a scheduler stall banner. Fix the timestamp serialization.
