## Findings, ranked for small/medium shops

### 1. The scraper's hard-coded `Accept-Language: de-DE…` makes Shopify serve geo-converted prices — not ticketed

- What happened: all 58 Markies captures and 6/6 priced Reindeer captures hold USD (`$38,247.00` for a £28,000 item). The page's `og:price`, JSON-LD and visible price all switch together, so no selector avoids it. The same URL without `Accept-Language` returns GBP with `localization=GB`. In production the currency follows the scraper's egress country (US here; EUR from an EU region). *Which currency appears is environment-dependent; the mechanism is not.*
- Cause: `src/crawler/src/scraper/scraper_service/html_fetcher.rs:296` sets `de-DE,de;q=0.9,en-US…` on every scraper request. The spider sends no `Accept-Language` (`src/crawler/src/spider/discovery/website_spider.rs:38`), so spider and scraper see different sites. The review console's live fetch uses the scraper's headers, so the matrix shows the converted price as correct.
- Impact: Shopify is the most common small-dealer platform. Wrong-currency prices are worse than missing ones: they pass every plausibility check and feed price history and alerts.
- Fix direction: send no `Accept-Language` (or one neutral value) from both spider and scraper, consistently. Consider forcing the store currency (`?currency=` or a `localization` cookie) for Shopify. Add a capture check when a price currency differs from the source's fallback currency.

### 2. Locale redirects turn live listings into verified removals — not ticketed (same class as closed #2599)

- What happened: Butchoff answers the scraper's `de-DE` request with `302 → /en-us/artworkdetail/…`. The approved pattern `^https?://[^/]+/artworkdetail/…` (sampled by the spider, which gets no redirect) does not match, so **all 439 scraped product pages were captured as `DELETE` with `removalEvidence: VERIFIED`**. Every page is live (curl 200 without the header). The URLs stay `ACTIVE` with `last_scraped` set, so this repeats every scrape and no schema review ever opens.
- Cause: `src/crawler/src/scraper/scraper_service/pipeline/scrape_product.rs:381` (`is_redirect_to_non_product_page`, `:34`) treats any same-host redirect outside the pattern as a removal; F1's header triggers the redirect.
- Impact: silent mass deletion of a whole shop. At INFO level the run logged nothing for it (F10).
- Fix direction: remove the header (F1). Do not treat a redirect whose path differs only by a locale/country prefix (or whose target serves 200 product markup) as verified removal. Raise a domain-level alarm when one pass verifies more than N removals for a domain.

### 3. The matrix shows images that capture then drops; the reviewer gets no warning — partly #2539 (closed)

- What happened: Antique Silver Spoons' thumbnails (`_PadWzc1LDc1…`: 75×75 base64-encoded in the path) and Moxhams' 98 px thumbnails (`width="98"` only in HTML) showed 8/8 and 3/3 images in the matrix with no finding. Capture kept **0 images on 76 and 89 listings**. After the selectors were switched to the main images, new captures carry images. Pages captured earlier keep empty galleries until their daily re-scrape.
- Cause: capture validation needs a size probe (`src/crawler/src/scraper/scraper_service/image_validation.rs`); the offline matrix accepts unknown sizes as valid by design (documented in `docs/crawler/extraction-and-review.md` §Raw extraction). #2539 added the URL-decidable part only.
- Impact: every manual or agent reviewer can approve a schema that captures no images, on old template shops that render small thumbnails.
- Fix direction: probe image sizes in the live matrix (it already fetches pages live), or use the HTML `width`/`height` attributes as a hint, and report "capture would reject all images".

### 4. One item under several category URLs becomes several raw streams — covered by #2115 (open)

- Koopman: 443 captures for 189 distinct `source_listing_id`s (254 extra). The same pattern appears on Butchoff, Westland (7 ids) and Moxhams (2 ids, changed slugs). Listings are unique on `(listing_source_id, source_listing_id)` (`migrations/20260725090000_initial_business_schema.sql:451`), so the streams merge into one listing. *Hypothesis:* a removal verified on one path could remove a listing that is still live on another path. Scrape cost is multiplied 2–4× on such shops.

### 5. SiteGround's 202 captcha is treated as a tiny crawl and retried forever — partly #2400 (open), #2693

- What happened: Lennox Cato returns `202` plus a meta refresh to `/.well-known/sgcaptcha`. The spider library flagged an anti-bot (mislabelled `Cloudflare`), but `anti_bot_signal` ignores any 2xx (`src/crawler/src/spider/discovery/website_spider.rs:1325`), so the kind falls back to `TinyCrawl`. TinyCrawl is Transient (`website_spider.rs:104-113`) and never escalates to NEEDS_OPERATOR (`src/crawler/src/service/cron/spider.rs:142`).
- Fix direction: treat a 202 or meta-refresh challenge (or a detected anti-bot on a ≤1-page crawl) as `BotProtection` (DurableBlock).

### 6. The CSS-only rule model cannot reach state on common dealer templates — not ticketed

- Robert Young (Shopify) and Koopman show no price and no state; availability exists only in JSON-LD (`InStock`). Moxhams marks sold items with a text-less GIF ("ITEM HAS BEEN SOLD") and keeps the price. Pendulum's "£refer" items have no button (state only in Woo's `instock` CSS class). Sutcliffe has "SOLD" as free paragraph text on some posts. A text rule cannot read an `<input type=submit value>`, and one rule cannot mix text and attribute, which forced two-schema workarounds (Moxhams, Antique Silver Spoons).
- Result: state captured as "Email enquiry", "ENQUIRE", "Secure this piece", "send enquiry", an image path, or an artwork title. None of these resolve to an availability. Koopman pages without ENQUIRE have no state element at all and keep reopening reviews.
- Fix direction: allow a JSON-LD `offers.availability` (and `price`) source for rules, plus a mapping from shop-specific CTA labels to availabilities per source. Allow per-selector extraction kinds or a value/text fallback.

### 7. Over-matched non-product pages cost one review round each — not ticketed (behaviour per #2490)

- Rust `regex` has no lookaround, so a pattern like `/shop/[^/]+$` or `/[a-z0-9-]+/$` (WordPress posts) cannot exclude `about`, `contact` or category slugs. Rejecting a manual review reclassifies only its seed and triggering pages; the waiting pages are released and join the next review. Sutcliffe needed 3 rejections for 3 pages, and `contact/`, `press/`, `services/` were still waiting at stop.
- Fix direction: let a rejection (or a bulk console action) classify chosen waiting pages, or add an explicit URL exclude list beside the pattern.

### 8. A broken apex blocks the crawl although www works — covered by #2123 (open)

- Butchoff and Koopman were registered as apex domains (as dealers do). The apex robots.txt was unreachable (here a 503 from the gateway for an upstream certificate mismatch; in production likely a TLS error). Preflight failed (`src/crawler/src/spider/discovery/robots.rs:43`) with a 6 h cooldown, and nothing tried the www host. Moving the crawl root through the console fixed it at once.

### 9. Scraper timeouts on a slow host while its spider crawl runs — partly #1913 (parked)

- Pendulum: robots.txt and page fetches timed out at 21:43 while the spider crawled the same domain at 8 concurrent requests. The circuit opened for 10 min. Responses later took <2 s.

### 10. Mass verified removals are invisible at INFO — partly #2117 (open)

- The 439 Butchoff deletions and 15 other removals produced no INFO/WARN line. The only evidence was the capture file.
