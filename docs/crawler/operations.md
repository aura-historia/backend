# Crawler operations

This document is needed because crawler operation has separate state, credentials, migrations and review access.

## Runtime prerequisites

The `server` binary needs:

| Input | Purpose |
|---|---|
| `LOCAL_DB_URL` | Required connection URL of the crawler-local Postgres database. The operator creates the database; `server` only migrates it. Unset or blank fails startup; see [single-server deployment](#single-server-deployment). |
| `AURA_API_BASE_URL`, `CRAWLER_API_TOKEN` | Base URL of the Aura Historia API (`https`; `http` only for a loopback host) and a bearer token that may read admin ListingSources (`GET /v1/admin/listing-sources`, scope `listing-sources:read` for a delegated token). The token is never logged. Unset or invalid values fail startup. |
| `PRODUCT_LISTING_INGESTION_QUEUE_URL` | Required URL of the product-listing ingestion FIFO queue that receives raw observations. |
| AWS credentials | The SDK default credential chain, allowed `sqs:SendMessage` on that queue and nothing broader. |
| `SPIDER_MAX_SIZE_BYTES` | Required spider page-body ceiling; use a value from 1 MiB through 8 MiB. |
| `VERTEX_AI_PROJECT_ID`, `VERTEX_AI_LOCATION` | Vertex AI configuration; not read with `CRAWLER_AUTHORING_MODE` `manual` or `agent`. |
| Application Default Credentials | Vertex AI authentication; `GOOGLE_APPLICATION_CREDENTIALS` is one local option. |

`CRAWLER_AUTHORING_MODE` is the one setting that decides how URL patterns and product schemas are authored and reviewed; see [authoring modes](#authoring-modes). With `manual` or `agent` the crawler makes no LLM call and needs no Vertex AI setting.

`VERTEX_AI_MODEL` selects the schema model. `CRAWLER_VERTEX_AI_CHEAP_MODEL` and operation-specific model settings can select lower-cost models. `CRAWLER_LLM_MAX_CONCURRENT_REQUESTS` and `CRAWLER_LLM_MIN_REQUEST_INTERVAL_MS` bound all crawler LLM calls.

Optional `CRAWLER_CLOUDWATCH_LOG_GROUP` and `CRAWLER_CLOUDWATCH_LOG_STREAM` enable CloudWatch log export. That deployment needs permission to create the group and stream and put log events. Logs must expose operational outcomes and identifiers without raw source payloads.

The local `dev` binary runs the same pipeline through the shared [composition root](README.md#binaries) and reads the same LLM, spider and review settings. It replaces the API, the ingestion queue and CloudWatch export with demo ListingSources, which carry their shops' presentation URLs, a raw-observation file and stdout logging, and defaults `SPIDER_MAX_SIZE_BYTES` to 8 MiB when it is unset; `server` requires the variable and its spider rejects each crawl without it. Without `LOCAL_DB_URL`, `dev` starts the [local database](#local-database) itself and uses its `crawler_demo` database. With it, `dev` uses that database as given, like `server`: a run against a copy of `crawler_demo` leaves the demo state untouched, and a `.env` written for `server` points `dev` at the server database.

`server` and `dev` apply crawler-local migrations at startup. Migrations under [`src/crawler/migrations`](../../src/crawler/migrations/) are the authoritative crawler database contract; do not repair the live schema by hand. This lifecycle is outside the AWS Deploy/Migrate/Initialize workflows: manual Migrate owns only business PostgreSQL migrations, and FX-only Initialize never migrates crawler state.

The crawler scheduler is deployed as a single process. Its spider and scraper workers may process many ListingSources concurrently, while process-local per-component ListingSource locks plus URL locks coordinate work inside that process. Spider and scraper may work on the same ListingSource concurrently, each bounded by its own per-host throttle. Different ListingSources remain concurrent; multi-process or horizontally scaled scheduler coordination is outside the current design.

## Stopping the crawler

`server` and `dev` stop gracefully on SIGTERM (`systemctl stop`) or SIGINT (Ctrl+C). The crawler logs `crawler.shutdown.started` naming the signal, stops the review console and starts no new spider or scraper pass, spider crawl or scraper batch; a running scraper batch finishes its current URL and defers the rest to a later run, and every running spider crawl ends as soon as its in-flight page requests are dropped, stores the pages it delivered, keeps its frontier and records the outcome `STOPPED`: no truncation or failure is counted, and the ListingSource is due again a minute later, resuming from that frontier ([crawl outcomes](scheduling-and-retries.md#spider-crawl-completion)). Running work then has a grace period, 60 seconds by default, to finish, and raw observations already scraped are flushed to raw capture before the process exits 0 with `crawler.shutdown.completed`. Work still running when the grace period ends is abandoned and the process exits 0 with `crawler.shutdown.grace_period_expired`; an abandoned spider crawl or scraper URL records no outcome and is selected again after restart; its frontier is the one the previous crawl left. A second signal during the grace period exits at once with 128 plus the signal number. Give the service manager a stop timeout longer than the grace period (systemd's default `TimeoutStopSec` of 90 seconds is enough) so it does not escalate to SIGKILL first. The review agent runner lets its running agent processes finish before it exits ([stop and undo](#stop-and-undo)).

For the same local trial, `server` with `CRAWLER_START_REVIEW_AGENT_RUNNER=true` in `agent` mode starts `review-agent-runner` from next to itself as its child, with `dev`'s defaults (the console on `server`'s bind port, a 30-second interval, state in `target/review-agents`) and stops it with itself. It is off unless set: the [single-server deployment](#single-server-deployment) runs the runner as its own service, and a second runner would work the same reviews.

## Local database

[`src/crawler/docker-compose.yml`](../../src/crawler/docker-compose.yml) starts PostgreSQL 16. The Linux and Windows scripts both create the crawler server and demo databases, migrate them, report their status, reset them, and stop the container. Keep both script sets aligned.

The container runs Postgres with `max_connections=300`. The crawler's [pools](#postgres-pools) together default to the sum of the spider and scraper concurrency plus 18, which is 128 for `dev`, and stock PostgreSQL's 100 connections make a large `dev` run fail with `too many clients already`. A Postgres you point `LOCAL_DB_URL` at instead needs `max_connections` above the pools' sum plus the sessions you open yourself.

The local workflow requires Docker and `sqlx-cli` with PostgreSQL support. From `src/crawler`, use the matching scripts in `scripts/linux/` or `scripts/windows/`:

- `db-up` starts Postgres and creates local databases.
- `db-migrate` applies crawler migrations.
- `db-status` reports migration status.
- `db-reset` rebuilds local crawler databases.
- `db-down` stops the container.

To run `server` against this container, start it with `db-up` and set `LOCAL_DB_URL=postgres://postgres:postgres@localhost:5432/crawler_server`; `server` never starts Docker itself.

The `dev` entry points wait for this container while it starts: a server on a Unix socket or on a host that resolves only to loopback addresses is retried 30 times with back-off. They fail at once on answers that waiting cannot change, an unknown database or a refused login, and on a `LOCAL_DB_URL` host that does not resolve. A server on any other host, which no dev run starts, fails startup when it has not accepted a connection within 30 seconds. A wrong port on a loopback host is indistinguishable from a starting container and still waits the full 30 attempts.

## Postgres pools

The crawler holds two connection pools on its database. Spiders, scrapers and raw capture share the crawl pool, sized by `db_max_connections` (by default the spider and scraper concurrency plus 10). The review console has its own pool of at most 8 connections, opened on first use, so console reads cannot take the connections crawling waits for and saturated crawling cannot time out the console. Both wait at most 30 seconds for a connection before failing with `PoolTimedOut`.

Each pool is sampled every second and reported once a minute as the `DbPool*` [metrics](#metrics-and-alarms). A minute in which every connection of a pool was in use at a sample also logs `Crawler Postgres pool had every connection in use` with the pool, its limit, its peak and the saturated samples, so sqlx's slow-acquire warnings and `PoolTimedOut` failures can be read against those numbers when the pool size is tuned.

## Review service

The server also hosts the crawler review console. It binds to `127.0.0.1:7878` unless `CRAWLER_REVIEW_BIND_ADDR` overrides it. The console keeps the selected review, and for a product-schema review its page and schema, in the URL fragment (`#review=<id>&page=<id>&schema=<index>`), so a reload, browser back or a shared link reopens it. `#sources` and `#reviews` open the two views without a review; without a fragment the console opens on Sources. `<index>` is the schema's 0-based position, as the API's `schema_index` names it, while the console labels schemas from 1: `schema=0` opens Schema 1. Each queue entry is a link to that fragment, so opening another review, like browser back, asks before discarding unsaved edits. Its queue refreshes every 15 seconds while the tab is visible, pauses while it is hidden, and never reloads the selected review or its unsaved edits.

`CRAWLER_REVIEW_AUTH_TOKEN` protects review reads and mutations when configured, and is mandatory for a non-loopback bind and for `server` in `agent` mode. Mutations require bearer-token authorization. The local `dev` binary is the only exception: on a loopback bind without a configured token it accepts mutations from same-origin browser requests, identified by an `Origin` that matches a loopback `Host`. The console can exchange that token for a short-lived `HttpOnly`, `SameSite=Strict` session cookie for browser reads and iframe previews; it does not authorize ordinary mutations. An API request whose `Authorization` header matches no configured token is refused with `401`, even with a valid session cookie or on the tokenless local console. A non-loopback deployment needs TLS at the serving proxy because the cookie is secure.

A human restores what an approval replaced with `POST /api/reviews/{id}/restore` (optional `notes`) or the console's **Restore previous** action on the approved review: the ListingSource's schema list and removed-page templates, or its URL-pattern decision, come back as the approval's event recorded them, and the restore re-queues work as the approval did: pages waiting on a product-schema review are retried at once, pages the restored configuration may decide differently are [re-armed](scheduling-and-retries.md#fetch-retries), and a restored URL-pattern decision classifies the ListingSource's stored URLs again. Any approval whose event keeps what it made live can be restored, whether a human, an agent or the crawler approved it, once, and only while that configuration is still live: after a newer approval or a live edit the restore answers `409` and changes nothing, so a newer change is never overwritten. Restoring an approval that replaced no schema list leaves the ListingSource without schemas, so its next scraped page opens a new review. An agent's restore answers `403` with `reason` `RESTORE_NEEDS_HUMAN`. A restore is recorded as a `RESTORED` event; captures made while the approved artifact was live stay until the pages' next scrape.

`GET /health` is the only unauthenticated liveness endpoint and returns no crawler state. With a review token configured, `/api/health` is authenticated.

The console fetches a shop's pages for a review in four live jobs ([review rail](extraction-and-review.md#review-rail)): a product-schema review's live matrix refresh (`GET /api/reviews/{id}/matrix?refresh=true`), a candidate evaluation (`POST /api/reviews/{id}/evaluate`), a page projection (`GET /api/reviews/{id}/page-projection`) and a selector probe (`POST /api/reviews/{id}/selector-probe`). `CRAWLER_REVIEW_MAX_CONCURRENT_LIVE_JOBS` (default 20, a whole number of at least 1) caps how many run at once, for all reviews, humans and review agents together, so neither agents nor open console tabs multiply the load on the shops: a refresh or an evaluation holds its place until it finishes in the background, a projection until its page is projected, a probe until it answers, and a request that joins a running refresh takes none. Each job parses the pages it fetched on a blocking thread within its place, so the cap also bounds that parsing, and a slow, deeply nested page never holds up the console's other requests. A job above the cap is refused before it fetches anything with `429`, `reason` `LIVE_JOBS_BUSY`, the cap as `limit`, `retry_after_secs` and a `Retry-After` header; `Crawler review console listening` logs the cap as `max_concurrent_live_jobs`. Live previews, of any URL (`/api/live-inspect`, `/api/live-html`) and of a review page (`/api/review-pages/{id}/inspect`, `/html`), and review-page additions fetch one page each outside the cap. The live previews serve humans only and answer the [review agents](#review-agents)' tokens `401`, so no agent fetches a page through them past the cap or for a review that waits for a human; no `review-mcp` tool uses them, and the agents read a page as its projection (`inspect_page`) instead. A live fetch the shop answers with a [bot challenge](networking.md#bot-challenges) instead of the page fails with `502`, `reason` `BOT_CHALLENGE`, the page's `url` and an `error` that says so. A matrix read without `refresh` never fetches: it answers the stored matrix, `202` while a refresh runs, the last refresh's failure, or `404` with `reason` `NO_MATRIX` while the review stores no matrix of its current candidate. The console then offers **Evaluate on live pages**, and the agents call `refresh_matrix`; both ask for `refresh=true` explicitly.

The page previews (`/api/live-inspect`, `/api/review-pages/{id}/inspect`) render untrusted shop HTML in the operator's browser under their own Content-Security-Policy; every other console response, including the raw HTML of `/api/live-html` and `/html`, keeps the strict console policy. The preview disables the page's scripts, refresh and referrer directives, and its policy runs only the injected selector inspector (pinned by its hash), in a sandbox without `allow-same-origin`, with no connections, frames, objects, media or form submissions and only the console as framer. It loads the page's stylesheets, images and fonts from any `https:` host (images and fonts also as `data:`), resolving relative paths through an injected `<base>`. Opening a preview therefore makes the operator's browser request those assets from the shop and every host the page names, such as CDNs and the tracking pixels of `<noscript>` fallbacks, which see the operator's IP address, user agent and any cookies the browser sends to them, but no referrer; CSS can reveal to those hosts which element the operator hovers or picks. Assets of `http:` pages are not loaded, so such pages render unstyled. The inspector reveals lazy images itself: it copies an image's address from the attributes lazy-loading scripts read (`data-src`, `data-lazy-src`, `data-original`, `data-lazy`, `data-srcset`, `data-lazy-srcset`) into `src` or `srcset`, and drops `loading="lazy"` from every image, because native lazy loading never loads the slides of a horizontal gallery; the images load under the same policy. Content a shop script builds, such as a gallery assembled from a JSON feed, stays blank because shop scripts never run in a preview; the captured data is unaffected. A preview cannot reach the console's session, API or cookies.

`GET /api/listing_sources` is the operator's overview: each ListingSource with its pending reviews, URL counts, `last_successful_scrape`, the latest time the scraper evaluated one of its product pages (a failed fetch, a wait on a pending review or a removal the mass-removal guard held does not move it; `null` before the first), `blocked_urls` and `blocked_since` and `blocking_review_id`, the pending review `blocked_since` dates (`null` while nothing is blocked), `held_removal_urls` and `held_since`, the earliest time a currently held URL was last held (a scrape that holds a URL again moves it), `mass_removal_confirmed_until` and `mass_removal_confirmed_by`, the end and the actor of a live [mass-removal confirmation](scheduling-and-retries.md#mass-removal-guard) (`null` without one), `crawling_since` and `scraping_since`, since when the spider or the scraper of this process has been working the source (`null` while it is not), `url_error_kinds` and the source's `crawl_root_url` (`null` while the scope gives it none), last crawl outcome, failure kind, failure count and next crawl time as [crawl completion](scheduling-and-retries.md#spider-crawl-completion) records them, and the scraper circuit's `scrape_failure_streak`, `last_scrape_error_kind` and `last_scrape_status_code`, the HTTP status the circuit last recorded with its kind (`null` without one), with `scrape_failing_since`, when that streak began, and `scrape_paused_until`, the circuit's cooldown end (`null` without a cooldown) ([scraper circuits](scheduling-and-retries.md#scraper-circuits)); the outcome is `null` before the source's first crawl and after a URL-pattern decision released it, until its next crawl records one. `blocked_urls` counts the product URLs waiting on a product-schema review that is still pending, which the scraper does not retry until it is decided: those whose scrape recorded the wait, and every product URL of a ListingSource that has no product schema while its first product-schema review is pending, and `blocked_since` is the creation time of the oldest such review (`null` while nothing is blocked); a pending review nothing waits on blocks nothing. `held_removal_urls` counts the product URLs whose removal the [mass-removal guard](scheduling-and-retries.md#mass-removal-guard) held (`MassRemovalHeld`), and `url_error_kinds` lists the last error kind of the product URLs that carry one with the number of URLs per kind (`[{"kind", "count"}]`, the most frequent first). `GET /api/listing_sources` pages through all ListingSources and ranks the ones that need an operator first by default, so none is cut off; see [console lists](#console-lists). The console opens on its **Overview** (`#overview`): tiles for what the crawler does now and what needs a human (`GET /api/overview`; the tile for reviews waiting for a human only in `agent` mode) above the table of all ListingSources, which is also the **Sources** view (`#sources`): search, status and activity filters, sortable columns and 100 rows a page, one worded status badge per source (crawl needs operator, failing to scrape, blocked by a review, removals held, healthy, not scraped yet, crawling disabled, or its label) with what the source is doing now. A source's own page (`#source=<id>`) shows its health with the actions that resolve it (**Confirm bulk removal** with a duration of 6 hours to 7 days, 24 hours preselected, and **Revoke** on a live confirmation; the pages missing a value, each with **Add to review**), its review history, and the live URL pattern, product schemas and removed-page templates. **Reviews** (`#reviews`) lists the reviews with filters for status, type, what they wait for and source, in the agents' queue order unless sorted. A review (`#review=<id>&page=&schema=`) shows its source's reviews in a rail, which `rail=0` or the console's remembered choice hides. The Overview also lists the last day's recent activity: the decisions, repair requests and hand-overs of the review trail and what the crawler did to sources (`GET /api/review-events` and `GET /api/source-events`), those since the reviewer's previous visit marked, and its tiles show how they moved since then (the visit is kept in the browser). A review opened from a list carries that list and its place in the fragment (`queue`, `i`) and shows a queue bar with the previous and next review, which `J` and `K` open; after a verdict the banner offers **Undo** (restore, or revoke a manual-schema rejection) and the next review (`Enter`), and `A`, `R`, `N` and `E` open the approve, reject and needs-repair panels and start an evaluation; `G` then `O`, `S` or `R` goes to a view and `/` focuses the search. The fragment is the state of every view, so a link restores it, and a list returned to keeps its scroll position and marks the row left from. The header counts and the list on screen refresh every 15 seconds while the tab is visible and the header says when it last did, that it is paused, or what failed, dimming what it shows meanwhile; relative times are brought up to date every 30 seconds. A review is never reloaded by that refresh, but one that changed elsewhere says so, and **Refresh** then keeps the reviewer's unsaved edits, applied to the new candidate, instead of discarding them. A human confirms a source's mass removal with `POST /api/listing-sources/{id}/mass-removal-confirmation` (`hours`, 1 to 168) and revokes it with `DELETE` on the same path; the contract is in the [mass-removal guard](scheduling-and-retries.md#mass-removal-guard). A human resumes a source whose crawl waits for an operator with `POST /api/listing-sources/{id}/crawl-resumption` (**Resume crawl** on the source's page): it clears `NEEDS_OPERATOR`, the failure kind, the streak and the next crawl time, so the source is crawled again as the schedule makes it due, and answers `{"resumed": true}`; a source that does not wait for an operator is left alone with `{"resumed": false}`. A human [labels](README.md#listingsource-scope) a source the crawler should not crawl with `PUT /api/listing-sources/{id}/label` (`label`, one of `NOT_AN_ESHOP`, `APPROACH_NOT_APPLICABLE`, `BOT_PROTECTION`, `JAVASCRIPT_RENDERED`, `LOGIN_REQUIRED` and `OTHER`, and an optional `note` of at most 500 characters that `OTHER` requires; **Label source…** on the source's page), which replaces an earlier label and answers the stored label, and clears it with `DELETE` on the same path (**Clear label**), which answers `{"ok": true}` also for a source without a label. An overview carries the label as `source_label` (`label`, `note`, `labelled_at`, `labelled_by`; `null` without one), and the console shows it as the source's status. `GET /api/reviews` is the console's review queue; see [console lists](#console-lists).

`GET /api/pending-reviews` is the agents' queue, which the [review agent runner](#review-agent-runner), its [digest](#digest) and `review-mcp`'s `list_pending_reviews` read instead: the pending reviews of crawl-enabled ListingSources only, oldest first by creation time and then review id, without their candidate and validation summary, page by page, so the agents work reviews in the order they opened and newer ones never keep the longest-waiting review from them. `human_required=false` or `true` lists only the reviews the agents can work or only those that wait for a human ([repair cap](#review-agents)), so those never take a workable review's place; `limit` is the page size (default 100, at most 500); `after=<review id>` reads the page after the review the previous page ended with, which that page names as `next_after` (`null` on the last page). A page starts after that review's creation time and id, so a review that closes or comes to wait for a human between two reads moves no other review across a page boundary, and an `after` that names no review answers `404`; any other value that is not accepted answers `400`. Each review carries `handed_back`, the time of its latest `HUMAN` event, from which its `agent_rounds` count (`null` while no human acted on it). Every page answers `totals`, counted in SQL over the whole queue whatever page or filter was asked for: the pending reviews of crawl-enabled ListingSources the agents can work (`workable`) and those that wait for a human (`waiting_for_human`).

### Console lists

The console's lists answer one window of every row and filter, search, order and count in SQL; nothing is cut at a fixed size. A list answers the envelope `{ "items": [...], "total", "limit", "offset" }`: `total` counts the rows that match the filters, `limit` is the window size (default 100, at most 200) and `offset` the rows skipped, so a client pages with `offset` steps of `limit`. A window is read at the moment of the request, so rows that change between two reads can move across a boundary; the console re-reads its current window every 15 seconds. A parameter that is not accepted, an unknown parameter and a value outside what is accepted answer `400` with what is accepted. `q` is searched case-insensitively as plain text (`%` and `_` match themselves), at most 100 characters; a blank `q` is no search. `dir` is `asc` or `desc`, and a sort key has its own default direction.

| Route | Parameters | Items |
|---|---|---|
| `GET /api/reviews` | `q` (the ListingSource's name), `status` (`PENDING_REVIEW`, `APPROVED`, `REJECTED`, `SUPERSEDED`), `artifact` (`URL_PATTERN`, `PRODUCT_SCHEMA`), `waiting` (`human`: `human_required`; `repair`: a pending review with an open needs-repair verdict that the agents have not stopped on), `listing_source` (an id), `sort` (`queue`, the default; `created`, `updated`, `source`), `dir`, `limit`, `offset` | review summaries |
| `GET /api/listing_sources` | `q` (name or crawl host), `status` (`needs_attention`, `healthy`, `disabled`, `labelled`, `crawl_failing`, `crawl_needs_operator`, `blocked`, `failing`, `held`), `activity` (`crawling`, `scraping`, `idle`), `sort` (`attention`, the default; `name`, `pending_reviews`, `last_successful_scrape`, `next_crawl_at`), `dir`, `limit`, `offset` | ListingSource overviews |
| `GET /api/listing-sources/{id}/reviews` | `status`, `artifact`, `limit`, `offset` | the ListingSource's review summaries, newest first, each with `candidate_is_live`, `last_actor` and `rejection_revoked` |

The `queue` order is the order the review agents work: pending reviews of crawl-enabled ListingSources, then pending reviews of disabled ones, each oldest first, then the closed reviews, newest first; it ignores `dir`. A review summary has `review_id`, `listing_source_id`, `listing_source_name`, `listing_source_crawl_enabled`, `artifact_type`, `status`, `reason`, `repair_request`, `human_required`, `auto_schema_evaluation` and `created` and `updated`; it carries no candidate, version or validation summary, which `GET /api/reviews/{id}` answers. `candidate_is_live` is true for the latest approved review of its artifact type, which is what is live unless a live edit or a restore replaced it since; `last_actor` is the actor of the review's latest event (`null` without one) and `rejection_revoked` whether a human revoked its rejection. The `attention` order puts crawl-enabled ListingSources first, then those whose crawl waits for an operator, with blocked URLs, the longest scrape failure streaks, held removals, the most pending reviews and the most recently updated; the other sorts put `null` times last, and every sort ends with the ListingSource id. A ListingSource has the status `crawl_needs_operator`, `blocked`, `failing` or `held` only while crawl-enabled, `needs_attention` is any of the four, and `healthy` is a crawl-enabled source with none; `labelled` is a source with a label, and `disabled` one with crawling off and no label. The `attention` order puts labelled sources last. `activity` reads the work locks of the process that serves the console. An overview carries the fields the console shows, including `url_error_kinds` only on a ListingSource's own page.

`GET /api/listing-sources/{id}` is one ListingSource's page, `404` when it does not exist: its overview fields plus `url_pattern`, the live pattern as `{ "value", "exclude", "matching", "approved_review_id", "approved_at", "approved_by" }` (`null` while there is none; the approval is the latest approved URL-pattern review, `null` fields when none is recorded), `product_schemas` and `removed_page_schemas`, the live schemas in the order the scraper applies them and the live removed-page templates, `live_schema_review_id`, the latest approved product-schema review, and `live_schemas_since`, when the live schemas were last stored, and `failing_urls`, up to three product URLs whose last scrape failed as examples of why the source fails (the most repeated failures first, from one read of the URLs' persisted fields; a wait on a review, a held removal and a missing value are not failures): `url`, `error_kind`, `status_code`, `failure_count`, `error_message`, cut to 200 characters, and `next_retry_at`. A stored schema that does not read as one fails the request.

`GET /api/overview` counts, in SQL, `sources` (`crawling_now` and `scraping_now`: the sources this process works; `needs_attention`, and the overlapping `crawl_failing` (the last crawl ended `FAILED`; the schedule retries it), `crawl_needs_operator`, `blocked_by_review`, `failing_to_scrape` and `held_removals` conditions of crawl-enabled sources, and `labelled`, the labelled sources), `reviews` (`pending_total`, `pending_by_artifact` with `PRODUCT_SCHEMA` and `URL_PATTERN`, `pending_disabled_sources`, the pending reviews of ListingSources with crawling disabled, and `waiting_for_human`, all over every ListingSource's pending reviews) and `agent_mode`, whether review agents work the reviews; `waiting_for_human` is 0 outside it. The agents' queue totals count the pending reviews of crawl-enabled ListingSources only.

`GET /api/source-events?since=<RFC 3339 time>` (optional `limit`, at most 1,000) lists what the crawler did to crawl-enabled ListingSources since then, newest first, with `truncated` set when more exist: `SCRAPE_FAILING` when the current scrape failure streak began (`error_kind`, `count` failures in a row) and `CRAWL_FINISHED` when the spider's latest run ended (`outcome`, `error_kind`, `count` failed crawls in a row). The crawler keeps each source's current state and when it entered it, not a history, so an event is that state dated within the window: a streak that ended, or a crawl that a later one replaced, is not listed. The Overview's recent-activity feed merges it with `GET /api/review-events?since=&dir=desc` (the [review trail](extraction-and-review.md#approval-guard)).

A read that reaches a stored row it cannot decode fails closed with `500` and `reason` `INVALID_PERSISTED_ROW`, naming the `object` (`review`, `ListingSource`, `review event`, or `row` when the failure names none) and its `id` when known, and logging the detail; the console shows that message in the list or card the read feeds and keeps the others working. A plain `GET /api/reviews/{id}/matrix` of a review without a stored matrix answers `404` `NO_MATRIX`, as the agents' reader expects; with `probe=true` it answers `200` with `status` `none` instead, which the console uses so a normal state is no failed request.

The console says why a crawl or a scrape fails from the persisted failure kinds, in one table of labels, causes and the next step each cooldown profile implies; a kind the table does not know shows as persisted, and a test keeps the table complete for the crawler's crawl and circuit kinds. A source whose last crawl `FAILED` is a `crawl_failing` source: it needs attention, ranks right after those whose crawl waits for an operator, and never shows as healthy. The source page shows the failing pages' `failing_urls` as examples. Nothing the crawler does not persist is shown: a crawl failure carries no start time or status code, so only the scrape circuit names a failing-since time and a status.

The lists are for the console: `review-mcp` and the review agent runner read the agents' queue (`GET /api/pending-reviews`) and single reviews (`GET /api/reviews/{id}` and its sub-routes) and none of the routes above, so their shape is the console's alone.

### Authoring modes

`CRAWLER_AUTHORING_MODE` decides, for URL patterns and product schemas alike, who authors them and whether they wait for human review:

| Value | URL patterns | Product schemas |
|---|---|---|
| `auto` | Inferred by the LLM and applied directly through an approved review. | Generated by the LLM; approved without review when deterministic coverage and every [plausibility check](extraction-and-review.md#plausibility-checks) pass and the LLM evaluation is a high-confidence approval, otherwise pending review. |
| `review` (default) | Inferred by the LLM, pending review. | Generated by the LLM, pending review. |
| `manual` | No LLM; see [manual authoring](#manual-authoring). | No LLM; see [manual authoring](#manual-authoring). |
| `agent` | As `manual`, without keyword classes; the author agent labels the URL sample and stages the pattern, and the reviewer agent approves or rejects it within the approval guard ([review agents](#review-agents)). | As `manual`; the author agent stages the schemas and the reviewer agent approves or rejects them within the approval guard. |

Every mode records artifacts as reviews, so the console always shows what became active and why; a pending review for a ListingSource blocks new generation in every mode. A pending product-schema review does not stop scraping in any mode: pages a cached schema extracts are scraped as usual, and only a page that fails every cached schema waits on the review with a [growing retry delay](scheduling-and-retries.md#fetch-retries) and is [attached to it](extraction-and-review.md#review-rail). A ListingSource without cached schemas waits on its initial review entirely. Approving or rejecting the review releases the waiting pages for an immediate retry. The LLM confidence evaluation is recorded on every generated schema review. The default is `review`, so auto-approval is always an explicit opt-in. An empty or whitespace-only value (a `NAME=` placeholder) counts as unset; any other value fails startup with an error naming the variable, the rejected value and the accepted values. The crawler logs the effective mode, whether it came from the environment or the default, and what the mode does, once at startup.

`CRAWLER_REVIEW_REQUIRED`, `CRAWLER_REVIEW_URL_PATTERN_REQUIRED` and `CRAWLER_SCHEMA_LLM_REVIEW_MODE` are removed; a non-empty value in any of them fails startup so a dead setting cannot be mistaken for an active one. Their combinations map to the new modes as follows: review required with `auto_approve_high_confidence` → `auto`; review required with `human_only` or `report_only` → `review`. Running without review gates has no equivalent: `auto` is the closest mode, but unlike the old setting it holds a generated schema for review when the LLM evaluation is not a high-confidence approval, so its review queue needs an operator.

### Manual authoring

With `CRAWLER_AUTHORING_MODE` `manual` or `agent`, where the LLM would run the crawler opens a pending review instead, or joins the one already pending, and the affected work waits until an operator, or in `agent` mode the [review agents](#review-agents), approve it. Persisted review reasons are the same in both modes:

| Review reason | Opened when | Candidate | Operator action |
|---|---|---|---|
| `manual_url_pattern_required` | A ListingSource needs a product URL pattern | Decision `UNDECIDED` with the crawled URL sample | Enter a regex or `NO_PATTERN` as the candidate, then approve. An undecided candidate cannot be approved. The crawl that opened the review finishes discovery and stores its URLs; approval classifies them with the decision and releases the crawl, and when that crawl still runs, it classifies the URLs it stores with the decision too instead of waiting ([crawl completion](scheduling-and-retries.md#spider-crawl-completion)); a running crawl that has not classified yet uses the pattern too, without opening another review. |
| `manual_schema_required` | A ListingSource has no product schema, or its cached schemas stop matching a page | The cached schemas plus a generic starter schema, with the seed or triggering page | Rewrite the starter schema, check it with the live matrix, then approve. Approval replaces the ListingSource's schemas with the reviewed list. For a sold or withdrawn item the shop serves at HTTP 200 with a removal notice and no product markup, [declare the page removed](extraction-and-review.md#removed-page-templates) on the same review instead of authoring a schema for it; rejecting the review would classify it as a non-product page and leave its listing visible. |

A ListingSource the spider records as `NEEDS_OPERATOR` ([repeated failures](scheduling-and-retries.md#spider-failure-escalation)) opens no review: the console lists it under the `crawl_needs_operator` status filter and shows its last failure kind and failure count. Once the shop or its configuration is fixed, the operator resumes its crawl on the source's page (**Resume crawl**), fixes the source's presentation URL in the admin API, disables its `WEB_CRAWL` ingestion, or [labels](README.md#listingsource-scope) a shop the crawler cannot scrape. A scope refresh that gives the source another crawl root [moves it](README.md#listingsource-scope): it keeps its URL pattern, crawled URLs and scrape state, and loses the crawl state of the old root, including `NEEDS_OPERATOR` and a [rate-limit hold](scheduling-and-retries.md#rate-limited-crawls), so the next spider cycle crawls the new root. A crawl of the old root that is still running when the source moves records nothing over the move: its outcome, frontier and full-crawl time are written only while the source still has the crawl root the crawl started from. It logs `ListingSource moved to another crawl root while the spider run crawled this one` with the outcome it left unrecorded, and the error of a failed run; the URLs it stored stay, like every crawled URL. A source moved back to that root before the crawl ends records the crawl's outcome as one of its root, counting on from the failure, truncation and rate-limit state the source had when the crawl started. The console has no action that resets a wrong `NO_PATTERN` decision on an unchanged crawl root.

A page that is not a product page should be excluded by narrowing the URL pattern. Rejecting a `manual_schema_required` review classifies its seed and triggering pages as non-product pages, in every spelling the console treats as the same page: with or without their [trailing slash](networking.md#stored-urls), on `http` or `https`, with or without `www.`. A rejection is persisted state of the ListingSource, so it applies in every authoring mode, also after a switch from `manual` or `agent` to `review` or `auto`: a later scrape classifies such a page `other` before any cached schema extracts it, so it is not captured as a product even once another review approves a schema that extracts it, and the review is not reopened for it, until a human revokes the rejection. A crawler URL that redirects onto such a page is a verified removal of the product it named ([duplicate targets](networking.md#duplicate-targets)); only a URL requested as the rejected page is classified `other`. The rejection also outranks the URL pattern wherever stored URLs are classified by it: a crawl that finds such a page again, and the approval of a URL pattern, keep it `other` instead of making it a product URL the next scrape would only classify `other` again. Only a removal the scrape verifies first, an HTTP 404 or 410, a [redirect](networking.md#redirect-removal-evidence) to the shop's homepage, a page outside the pattern that robots.txt disallows, or a matching [removed-page template](extraction-and-review.md#removed-page-templates), still captures it as removed. A listing captured from the page before stays visible with its last capture. Its waiting and reviewer-added pages keep their class. To keep a candidate that is not ready yet, give the review the needs-repair [verdict](extraction-and-review.md#review-rail) instead of rejecting it. A product page that leaves its title or state empty is captured without it and opens no review ([optional fields](extraction-and-review.md#optional-fields)), so an untitled product is never rejected as a non-product page.

A human revokes a mistaken rejection of a `manual_schema_required` review, the reviewer agent's included, with `POST /api/reviews/{id}/revoke-rejection` (optional `notes`) or the console's **Revoke rejection** action on the rejected review. The review stays rejected and keeps its history: the revocation is recorded as a `REJECTION_REVOKED` event of its actor, the console marks the review **Rejection revoked**, and from then on the rejection classifies none of its pages. It classifies the review's seed and triggering pages again with their ListingSource's URL-pattern decision, as the spider classifies a URL it finds, and clears their retry delay, so a page the pattern takes is scraped again when due like any product page: captured when a cached schema extracts it, otherwise waiting on a new or pending `manual_schema_required` review. A page that another, unrevoked rejection covers stays `other`. A rejection is revoked once: a second revocation answers `409`, one of any other review `400`, and an agent's `403` with `reason` `REVOKE_NEEDS_HUMAN`; no `review-mcp` tool revokes.

### Review agents

With `CRAWLER_AUTHORING_MODE=agent` the crawler works as with `manual`, and two review agents work its reviews through the review console as an operator does, each with a credential of its own: the author agent stages URL patterns and product schemas, the reviewer agent approves or rejects them. The [event trail](extraction-and-review.md#review-rail) records them as the actors `AGENT_AUTHOR` and `AGENT_REVIEWER`.

In `agent` mode the crawler does not guess what a product page is; Claude decides. On a URL-pattern review neither agent reads a page or labels a URL: the author induces one pattern from the review's URL sample alone, the sample's paths and queries in a fixed pseudorandom order, by its product route families with delimiter-bounded variable segments, as a regex fully matching path and query with an optional exclude, audited for product-looking URLs it misses and other routes it takes; it hands the review to a human (`NEEDS_HUMAN`) when the sample supports no defensible shop-wide distinction. The reviewer agent sees the pattern applied to every sample URL and approves it when it passes the [approval guard](extraction-and-review.md#approval-guard)'s local checks, which read no sample label, or gives needs-repair naming the URLs it misses or takes wrongly, until the [repair cap](#review-agents) hands the review to a human. Neither agent stages or approves `NO_PATTERN`; a human decides it. The spider, a URL-pattern review's URL sample and the classification that approving or restoring a pattern applies classify a URL by the ListingSource's approved pattern alone: a URL the pattern takes is `product`, every other URL stays `other`, unclassified. The keyword classes `category`, `imprint` and `info` that the other modes derive from words in a URL, its host included, are never assigned. Until the pattern is approved every crawled URL stays unclassified, so nothing is scraped yet; the crawl stores its URLs and waits on the URL-pattern review it opens with its URL sample, as in [manual authoring](#manual-authoring), and approval classifies the stored URLs with the pattern.

| Request | Author agent | Reviewer agent |
|---|---|---|
| Console API reads, including a product-schema review's live matrix (`GET /api/reviews/{id}/matrix?refresh=true`), a page's projection (`GET /api/reviews/{id}/page-projection`), a selector probe (`POST /api/reviews/{id}/selector-probe`) and the evaluation of a proposed candidate (`POST /api/reviews/{id}/evaluate`), which store nothing ([review rail](extraction-and-review.md#review-rail)) | Yes; the live jobs not on a review that waits for a human (below) | As the author agent |
| Candidate and schema-field edits, removed-page declarations, sample labels (`POST /api/reviews/{id}/candidate`, `/schema-field`, `/sample-labels`), review page additions and removals (`POST /api/reviews/{id}/pages`, `DELETE /api/review-pages/{id}`) and marks as no product page (`POST` and `DELETE /api/reviews/{id}/pages/{review_page_id}/not-product`) | Yes | `403` `REVIEWER_CANNOT_CHANGE_CANDIDATES` |
| The approval guard's dry run of a review's current candidate (`GET /api/reviews/{id}/approval-checks`, `failed_checks` as an approval would answer them, `[]` when it would pass; a product-schema review is judged on its stored matrix, so one missing, outdated or expired is the answer; `409` for a review no longer pending) | Yes | Yes |
| Needs repair with its notes (`POST /api/reviews/{id}/needs-repair`) | Yes | Yes |
| Hand to a human with its reasoning (`POST /api/reviews/{id}/hand-to-human`) | Yes | Yes |
| [Label](README.md#listingsource-scope) the review's ListingSource (`POST /api/reviews/{id}/source-label`, `label` and `note` as for a human's label; an agent's label needs a `note` naming its evidence, `400` without one), which answers the stored label | Yes | `403` `REVIEWER_CANNOT_CHANGE_CANDIDATES` |
| Approve and reject (`POST /api/reviews/{id}/approve`, `/reject`) | `403` `AUTHOR_CANNOT_DECIDE` | Within the approval guard; a rejection needs non-blank `notes` (`400`) |
| Restore (`POST /api/reviews/{id}/restore`) and revoking a rejection (`/revoke-rejection`) | `403` `RESTORE_NEEDS_HUMAN`, `REVOKE_NEEDS_HUMAN` | `403` `RESTORE_NEEDS_HUMAN`, `REVOKE_NEEDS_HUMAN` |
| Browser sessions (`POST /api/session`, `/api/session/logout`), live previews (`GET /api/live-inspect`, `/api/live-html`, `/api/review-pages/{id}/inspect`, `/html`), the mass-removal confirmation and its revocation (`POST`, `DELETE /api/listing-sources/{id}/mass-removal-confirmation`), resuming a crawl that waits for an operator (`POST /api/listing-sources/{id}/crawl-resumption`), labelling any ListingSource and clearing a label (`PUT`, `DELETE /api/listing-sources/{id}/label`) | `401` | `401` |

Nobody configures the agents' tokens. At every start in `agent` mode, `server` and `dev` generate a fresh 256-bit token per role from the operating system's CSPRNG and write both to `review-agent-tokens.json` in the crawler's working directory, its state directory (`/var/lib/crawler` under the [systemd unit](#systemd-unit)): `{"author": "<64 hex characters>", "reviewer": "<64 hex characters>"}`. The file is written under a temporary name with mode `0600` and renamed into place, so a reader never sees a partial file and only the crawler's user can read it; the [review MCP server](#review-mcp-server) runs as that user and reads its role's token from it. A start that cannot write the file fails. The console compares a bearer with every token in constant time. Tokens are never logged or printed: the startup log names the file's path, and `Crawler review console listening` logs `agent_access`. A restart replaces both tokens and so revokes the old ones. In every other mode no agent acts: the crawler writes no token file and removes one an earlier start left.

The agents always work next to a human. `server` in `agent` mode fails startup without `CRAWLER_REVIEW_AUTH_TOKEN`, so a human can reject, restore, revoke a rejection and override what the agents do. In `dev` the tokenless loopback console stands in for it: same-origin requests without a token keep acting as `HUMAN` while the agents send their tokens. A request without an agent's token never acts as an agent.

Agents change pending reviews only: their candidate and field edits, removed-page declarations, sample labels and page additions and removals on any other review, including the approved review whose candidate is live, answer `403` `AGENT_CHANGES_ONLY_PENDING_REVIEWS` and record nothing, so they change the live configuration only through an approval. The reviewer agent's approval is taken only when the [approval guard](extraction-and-review.md#approval-guard) passes, and one that carries `acknowledged_coverage` answers `403` `AGENT_COVERAGE_ACKNOWLEDGEMENT`. No agent approves its own work: an agent's approval is refused with `409` and `failed_checks` `[{"check": "APPROVER_IS_AUTHOR"}]` when the event trail shows that the approving agent changed the candidate version it approves or the review's pages; humans approve as before. `CRAWLER_REVIEW_AGENT_MAX_DECISIONS_PER_HOUR` (default 60) caps the agents' approvals plus rejections within any rolling hour, counted from the event trail so a restart does not reset it; above it the API answers `429` with `reason` `AGENT_DECISION_LIMIT`, the cap as `limit`, `retry_after_secs` and a `Retry-After` header. `CRAWLER_REVIEW_AGENT_MATRIX_MAX_AGE_MINUTES` (default 30) bounds how long ago the live matrix an agent approval of product schemas rests on fetched its pages. `CRAWLER_REVIEW_AGENT_MAX_REPAIR_ROUNDS` (default 3) caps the agents' needs-repair rounds on one review, below, which count for `CRAWLER_REVIEW_AGENT_REPAIR_ROUND_WINDOW_DAYS` (default 7), and `CRAWLER_REVIEW_AGENT_NO_PATTERN_MAX_AGE_DAYS` (default 30) is how long an agent-approved `NO_PATTERN` holds ([approval guard](extraction-and-review.md#approval-guard)). Empty or whitespace-only values count as unset; any other value that is not a whole number of at least 1 fails startup with the variable and the value, in every mode. At start the crawler builds one agent decision policy from `CRAWLER_AUTHORING_MODE` and these settings, and the console, the scraper and the spider all apply it. `GET /api/review-agent-limits` answers its limits as `max_decisions_per_hour`, `matrix_max_age_minutes`, `max_repair_rounds`, `repair_round_window_days` and `no_pattern_max_age_days` to anyone who may read the console API, the agents' tokens included, so the [runner](#review-agent-runner) applies the console's limits instead of keeping a copy of these settings. `Crawler review console listening` logs `agent_access` and the limits as `agent_max_decisions_per_hour`, `agent_matrix_max_age_minutes`, `agent_max_repair_rounds`, `agent_repair_round_window_days` and `agent_no_pattern_max_age_days`.

The agents' back-and-forth on a review is bounded. Each needs-repair verdict of either agent on a review is one round, counted from the event trail since the review's latest `HUMAN` event and within the last `CRAWLER_REVIEW_AGENT_REPAIR_ROUND_WINDOW_DAYS` days. The verdict that reaches `CRAWLER_REVIEW_AGENT_MAX_REPAIR_ROUNDS` is taken, and from then on the pending review waits for a human: every further change and verdict of an agent on it (candidate and field edits, removed-page declarations, sample labels, page additions and removals, needs-repair, approve and reject) and every [live job](#review-service) of an agent that fetches the shop's pages for it (a live matrix refresh, a candidate evaluation, a page projection and a selector probe) answers `409` with `reason` `HUMAN_REQUIRED`, `agent_rounds` and the cap as `limit`, and records and fetches nothing, so the agents spend no shop requests on a review they cannot change or decide. The console checks it under the review's row lock in the transaction of the refused request, the lock every review change holds while it records its event, so no agent request racing the verdict that reaches the cap gets past it; a matrix refresh is checked before it fetches and again when it stores. A refresh the store refuses this way answers only the agent whose refresh it was: a human, or the other agent, who joined it learns that it stored nothing, and the next matrix read of anyone else finds the matrix stored before, or `NO_MATRIX`, never the agents' refusal. That agent's own matrix reads answer the refusal only while the review waits for the human it came to wait for: once a human hands the review back they find the stored matrix or `NO_MATRIX` too, also should the agents bring it to the cap again before their next refresh. Other reads stay open, and humans are unaffected. The review list, the [agents' queue](#review-service) and `GET /api/reviews/{id}` report `agent_rounds` and `human_required`, the console marks such a review **Needs a human**, `review-mcp`'s `get_review` passes both on to the agents while `list_pending_reviews` only counts such reviews, and the [runner](#review-agent-runner) starts no process for it and lists it in its [digest](#digest). A human hands the review back to the agents with any change or verdict of their own on it: an edit, a page or sample-label change, or, to tell the agents what to do, a needs-repair verdict with notes; the count restarts from that event. Approving or rejecting it closes it. An agent that cannot take a review further hands it to a human at once with `POST /api/reviews/{id}/hand-to-human`, non-blank `notes` (`400` without them), a `reason` and a `category` (`400` for a value not listed here; one left out, as a runner older than them sends, is taken as `NEEDS_HUMAN` and `NONE` with a WARN): the reason is the runner's, `NEEDS_HUMAN` when the author cannot decide the review from what it can read, `NOTHING_TO_STAGE_AFTER_REVIEW` when it has nothing to change on a candidate the reviewer already judged; the category is the author's report's `handover_category`, `PAGES_UNREADABLE`, `NO_SHOP_WIDE_PATTERN`, `CANDIDATE_ALREADY_HOLDS`, `NO_WORKABLE_CANDIDATE`, `OTHER` or `NONE` when it named none. Both are kept in the event's details and logged on `crawler.review.decided`; the notes stay in the event trail only. the review waits for a human exactly as one at the cap does, without a needs-repair round, and a human's own change or verdict hands it back. A review no human answers returns to the agents on its own once its rounds and its hand-over leave the round window, so the reviews waiting for a human never pile up with ListingSources nobody looks at; the agents try it afresh and bring it back to a human only with new rounds. The hand-off is a `HANDED_TO_HUMAN` event whose note is the agent's reasoning and whose details keep its `reason` and `category`, so the [digest](#digest) and the console's trail show why; a human calling it gets `403` `HAND_OVER_NEEDS_AGENT`, and a review that already waits for a human `409` `HUMAN_REQUIRED`. `human_required` is reported only in `agent` mode: in every other mode no agent acts and a human decides every review, so it stays `false`, also for a review that an earlier `agent` start's agents left at the cap, and the agents' queue counts every pending review as `workable`; `agent_rounds` still counts their verdicts.

The kill switch needs no deploy: set `CRAWLER_AUTHORING_MODE=manual` and restart. The restart removes the token file, the agents' tokens answer `401`, and humans work the reviews as in [manual authoring](#manual-authoring); a human [restores](#review-service) any agent approval that should not stay live.

### Review MCP server

The agents reach the console only through `review-mcp`, an MCP server over stdio that the agents' MCP client starts once per agent process, in exactly one role: `review-mcp --role author` or `review-mcp --role reviewer`. `--review <review id>` scopes the process to that one review: it then lists no `list_pending_reviews` and refuses every tool call whose `review_id` names another review, or none, with `REVIEW_OUTSIDE_SCOPE`, before any request. The [runner](#review-agent-runner) always starts it scoped to the review of the agent process, so page content an agent reads cannot turn it on another review; without `--review`, for an MCP client a person drives, it works every review. Build it with `cargo build --release --locked -p crawler --bin review-mcp` next to `server` and run it as the crawler's user, the only one who can read the token file. It is a thin client of the console API: it has no database access and no review rule of its own, so the console's role refusals, [approval guard](extraction-and-review.md#approval-guard), decision cap and URL rules apply to every tool call.

| Setting | Meaning |
|---|---|
| `CRAWLER_REVIEW_CONSOLE_URL` | The console's base URL, default `http://127.0.0.1:7878`. Plain http is accepted for a loopback host only; credentials, a query or a fragment fail startup. |
| `CRAWLER_REVIEW_AGENT_TOKEN_FILE` | The token file, default `review-agent-tokens.json` in the working directory. Point it at the crawler's state directory, `/var/lib/crawler/review-agent-tokens.json` under the [systemd unit](#systemd-unit). |
| `LOG_LEVEL` | Level of its JSON log on stderr, default `info`. |

An empty or whitespace-only setting counts as unset. A missing or unknown `--role`, a `--review` that is no review id, a flag given twice, or any other argument, fails startup with exit code 2. The role's token comes from the token file only, never from a setting, an argument or a tool call: `review-mcp` reads it at startup, and fails when it cannot, as outside `agent` mode, and reads it again when the console answers `401`, retrying the request once when a crawler restart has rotated the token. It connects to the console directly, ignoring proxy settings, and follows no redirect, so the token reaches only the configured console. stdout carries the MCP session only; the log names each tool call with its outcome and duration, never its arguments, its answer, a page or a token.

A role's server lists and runs only its own tools; the tool descriptions in [`review_mcp/tools`](../../src/crawler/src/review_mcp/tools) are the agents' contract. `list_pending_reviews` answers one page of the [agents' queue](#review-service) with `human_required=false`: at most 50 of the pending reviews of crawl-enabled ListingSources the agents can work, oldest first, each with its `agent_rounds`, with `total_pending`, the count of all of them, `waiting_for_human`, the count of those that wait for a human, which it does not list, and `more`; when `more` is true, or `truncations` names the list, the agent reads on with `after` set to the `review_id` of the last review listed. `get_review` reports a review's `agent_rounds` and `human_required`, and for a product-schema review the `source_product_urls` that `GET /api/reviews/{id}` answers: up to 40 active or sold product URLs of its ListingSource that are not review pages, those that scraped without an error first and the most recently scraped first, each with `last_scraped` and `last_error_kind`, for picking live, sold or unusual pages to test or add; `get_review` answers the whole review only for the first sample page (`sample_offset` 0), with the latest 10 events, their notes cut to 400 characters, since the needs-repair request comes whole as `repair_request`; a later sample page carries just the sample page with the review's `candidate_version`, so the agent keeps the first answer and reads the review again only when that version changed. `inspect_page` answers a window of a page's outline, at most 24,000 characters, from which a product-schema review's selectors are written; `offset` reads on. With `view` `MARKDOWN` (the console's `view=markdown`) it answers the page's readable content as markdown instead, without tags, attributes or URLs and about a quarter of the outline's size, for reading what a page shows; with `view` `FIELDS` it answers the page's [field candidates](extraction-and-review.md#review-rail), a fraction of the outline, from which selectors can be written like from the outline. Each view is recorded as an inspection. One `review-mcp` process, one agent process, answers at most 12 (`MAX_INSPECTIONS_PER_PROCESS`) `inspect_page` calls with a page, in either view and offset reads included, and answers later ones `INSPECT_LIMIT_REACHED` without a request; a call that answers an error, such as a busy console, a bot challenge or a URL off the review's source, holds no page and is not counted. `probe_selectors` (the console's `POST /api/reviews/{id}/selector-probe` with `pages`, each a review page as `page` or a `url` of the ListingSource, and `selectors`, each a `selector` and an optional `attribute`) fetches up to 4 pages, one after the other at the shop's pacing within 22 seconds, and answers for each of up to 8 selectors only what it matches on each page: `matches`, the elements with a value, `empty`, those without visible text, and the first 3 `values`, each cut to 300 characters, extracted as a rule with cardinality `all` would (the attribute where an element has a non-blank one, its text otherwise), or `error` for a selector that does not parse. A page it could not fetch answers `error` with `reason` `BOT_CHALLENGE` or `TIMEOUT` instead of results. It is a live job like a projection, refused on a URL-pattern review and on a review that waits for a human, and records each page it fetched as inspected. One `review-mcp` process answers at most 12 (`MAX_PROBES_PER_PROCESS`) `probe_selectors` calls and later ones `PROBE_LIMIT_REACHED`, a call that answers an error not counted. Neither agent reads a page of a URL-pattern review: its servers list no `inspect_page` and the console refuses an agent's page projection of one with `403` `AGENTS_CANNOT_INSPECT_URL_PATTERN_PAGES`, so the author finds the pattern in the sample's URLs and the reviewer checks it against them. Neither can therefore stage or approve `NO_PATTERN`, which only a human approves (`NO_PATTERN_NEEDS_HUMAN`): the author reports `NEEDS_HUMAN` for a shop whose URLs show no product shape. Both tools tell the agents to leave a review that waits for a human. Besides that cap, `review-mcp` keeps no limit of its own: the numbers it passes on are the console's, in its refusals' `limit`.

| Role | Tools |
|---|---|
| Both | `list_pending_reviews` (not when scoped with `--review`), `get_review`, `inspect_page`, `probe_selectors` and `refresh_matrix` (product-schema reviews), `check_approval`, `mark_needs_repair` |
| Author | `update_candidate` and `label_source`; on a product-schema review `evaluate_candidate`, `stage_and_check` (a whole candidate staged, the matrix refreshed and the guard's dry run in one call, or without schemas the current candidate refreshed and checked), `update_schema_field`, `add_review_page`, `remove_review_page`, `mark_page_not_product`, `declare_removed_page`, `record_no_sold_page`; on a URL-pattern review none besides `update_candidate` and `label_source`: sample labels are a human's, on the console |
| Reviewer | `approve`, `reject` |

A server scoped with `--review` reads the review's artifact type from the console at startup and lists only the tools that work on it, with `update_candidate`'s candidate argument narrowed to that type's kind, since every listed tool is in the agent's context on every turn; when the review cannot be read at startup, it logs so and lists the role's whole set.

A console refusal comes back as a tool error whose text is a JSON object with `kind`, `error`, `status` and the console's own `reason`, `failed_checks`, `candidate_version`, `coverage`, `retry_after_secs`, `limit`, `agent_rounds` and `details`. A tool taking a URL refuses one that is not a plain http(s) URL on the crawl host of the review's ListingSource (`URL_OUTSIDE_REVIEW_SOURCE`) before any request, and the console refuses it again. No answer carries a token, cookie or header. Every answer stays below 48 KiB of JSON, so it fits the 50,000 characters Claude Code keeps of a tool result in the agent's context (a longer one is replaced by a preview of a file the agents cannot read): long texts end in a `[truncated: ...]` marker, `inspect_page` answers at most 36,000 characters of a page's projection (fewer for text in non-Latin scripts), with a marker line where it stops and an `offset` to read on from there, and each shortened list is named in the answer's `truncations`. A review's `candidate` is never shortened, because `update_candidate` takes it back whole; when the rest cannot be cut enough, the tool answers `ANSWER_TOO_LARGE`. `refresh_matrix` and `evaluate_candidate` wait for the console's background work for up to 15 minutes, then answer `STILL_RUNNING`.

For the Claude Code CLI, one role's MCP configuration reads:

```json
{"mcpServers": {"crawler_review": {"command": "/opt/crawler/bin/review-mcp", "args": ["--role", "author"],
  "env": {"CRAWLER_REVIEW_AGENT_TOKEN_FILE": "/var/lib/crawler/review-agent-tokens.json"}}}}
```

### Review agent runner

`review-agent-runner` works every pending review with the two review agents, end to end and with no human in the loop: per review a fresh author agent process writes, tests and stages the candidate, then a fresh reviewer agent process approves, rejects or gives needs-repair within the [approval guard](extraction-and-review.md#approval-guard). Each process is a headless `claude -p` of the Claude Code CLI that is logged in on the machine, with only its role's [review MCP server](#review-mcp-server) as tools. The runner is an operator of the console like a human with a browser: it lists reviews and events with the author agent's token, has no database access and makes no review decision itself; the crawler makes no LLM call. Humans oversee after the fact through the [event trail](extraction-and-review.md#review-rail) and the [digest](#digest). Its code is the `crawler` crate's [`review_agent_runner`](../../src/crawler/src/review_agent_runner/mod.rs), outside the crawler's services.

#### Team seat and CLI login

The agents run on a dedicated member of Aura's Claude for Teams plan, never on a person's seat, so they draw only from that seat's five-hour and weekly allowance; nobody else signs in to it. A Team admin invites the crawler member (for example a `crawler@` mailbox), gives it a Premium seat and leaves usage credits off; an admin can turn them on with an individual spend limit in **Organization settings > Usage** when a busy week needs more.

On the crawler host, install a pinned Claude Code version (auto-update off) outside `/home` and `/root`, which the runner's [sandbox](#sandbox) hides, for example as `/usr/local/bin/claude`, and sign in once as the crawler member with the `HOME` and crawler-only configuration directory the service uses:

```sh
install -d -m 0700 -o crawler -g crawler /var/lib/crawler-review-agents
sudo -u crawler env HOME=/var/lib/crawler-review-agents CLAUDE_CONFIG_DIR=/var/lib/crawler-review-agents/claude claude   # then /login with the crawler member
sudo -u crawler env HOME=/var/lib/crawler-review-agents CLAUDE_CONFIG_DIR=/var/lib/crawler-review-agents/claude claude auth status --json
```

The status must show `"loggedIn": true`, `"authMethod": "claude.ai"` and Aura's organization. No `claude setup-token` and no `CLAUDE_CODE_OAUTH_TOKEN` are needed; a `CLAUDE_CODE_OAUTH_TOKEN` in the runner's environment is used if present (`authMethod` `oauth_token`). Every run starts with this probe and refuses to run, with the reason in the journal, unless the CLI is logged in with a Claude subscription; when the login expires, sign in again the same way. `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` must not be set for the runner: in print mode they silently take over billing. The runner never passes them, or any other variable outside its [allowlist](#invocation), to a child.

#### Production and development

In production the crawler runs `server` with `CRAWLER_AUTHORING_MODE=agent` from the start, and the runner runs on the same host. `review-agent-runner` and `review-mcp` ship in the same [release](#build-and-release) as `server` and reach `/opt/crawler/bin/` with it ([deploy and roll back](#deploy-and-roll-back)). Install the example unit [`review-agent-runner.service`](../../src/crawler/scripts/linux/review-agent-runner.service) and the environment file [`review-agent-runner.env.example`](../../src/crawler/review-agent-runner.env.example) as `/etc/crawler/review-agent-runner.env`, then `systemctl daemon-reload && systemctl enable --now review-agent-runner`. The service runs as the `crawler` user, the only one who can read the token file, with its own state directory `/var/lib/crawler-review-agents` and the CLI login there; its environment file holds runner settings only, never the crawler's, so no agent process inherits the console's human token. The runner starts a run, rests `CRAWLER_REVIEW_AGENT_RUNNER_INTERVAL_SECONDS` after it ends, and starts the next until it is stopped. A run that fails, such as on an unreachable console or an expired login, is logged and the next follows after the interval; systemd restarts a runner that crashed, but not one that refused its settings (exit code 2). A run with no review to work makes no agent call: it lists the queue and probes the login.

For development, build the runner and `review-mcp` with `dev` and run `dev` with `CRAWLER_AUTHORING_MODE=agent` and the developer's own logged-in CLI:

```sh
cargo build --locked -p crawler --bin dev --bin review-mcp --bin review-agent-runner
CRAWLER_AUTHORING_MODE=agent target/debug/dev
```

`dev` then starts `review-agent-runner` from next to itself as its child, as systemd runs it next to `server`: in `dev`'s working directory, where `dev` writes the token file, from an empty environment holding only the runner's settings (`CRAWLER_REVIEW_AGENT_*`, `CRAWLER_REVIEW_CONSOLE_URL`, `LOG_LEVEL`) and the variables of the [allowlist](#invocation), never the crawler's database URLs, cloud credentials or `CRAWLER_REVIEW_AUTH_TOKEN`. Unless they are set, the runner works the console `dev` serves every 30 seconds and keeps its state in `target/review-agents`. Its log lines join `dev`'s, and stopping `dev` stops it as `systemctl stop` stops the service ([stop and undo](#stop-and-undo)): a Ctrl+C in `dev`'s terminal reaches the runner at once, and `dev` sends it SIGTERM once its own [shutdown](#stopping-the-crawler) ended, waiting for it to exit as long as the runner's stop deadline. The agents spend the developer's own seat. With `CRAWLER_DEV_START_REVIEW_AGENT_RUNNER=false`, `dev` starts no runner; `review-agent-runner --once`, started by hand from the same directory, works the pending reviews once and then writes a digest of the last day at once. `manual` mode stays for development without agents.

#### Sandbox

The agent processes read untrusted shop pages, so the example unit runs the runner and everything it starts in a systemd sandbox. `ProtectSystem=strict` makes the whole file system read-only except `ReadWritePaths=/var/lib/crawler-review-agents`, the runner's state directory, and the private `/tmp` of `PrivateTmp=true`; `ProtectHome=yes` hides `/home`, `/root` and `/run/user`. The unit points `HOME` and `CLAUDE_CONFIG_DIR` into the state directory, so the CLI keeps its login, settings and caches there; the runner itself writes only its state there and its agents' empty working directories in `/tmp`, and reads the token file in `/var/lib/crawler`. A `review-agent-runner --once` started from a shell runs outside the sandbox.

A CLI version can start writing somewhere new, so verify the sandbox with the real login after installing or changing the unit and after every CLI upgrade:

1. `systemctl daemon-reload && systemctl restart review-agent-runner`; the restart starts a run at once.
2. `journalctl -u review-agent-runner -n 50 -o cat` shows `Review agent runner started with the CLI's Claude login`: the login probe read the login inside the sandbox. A line with `the runner refuses to start` names what failed.
3. Once a workable review is pending (a run with none makes no agent call), `journalctl -u review-agent-runner -f -o cat` shows `Review agent process finished` with `end` `REPORTED`, `LIMIT_REACHED` or `USAGE_LIMIT`, and `tail -n 1 /var/lib/crawler-review-agents/review-agent-processes.jsonl` shows its record. `FAILED` after `The review agent process printed no result envelope` points at the sandbox when its `stderr_tail` names a path.
4. `journalctl -u review-agent-runner --since -1h -o cat | grep -i -E 'read-only file system|EROFS|permission denied|EACCES'` prints nothing.

`systemd-analyze verify` checks only the unit file; only these steps show that the CLI logs in and runs inside the sandbox. When a step fails because the CLI needs a path the sandbox denies, add that path to `ReadWritePaths` in a drop-in (`systemctl edit review-agent-runner`) rather than relaxing `ProtectSystem` or `ProtectHome`, and repeat the steps.

#### Invocation

Per review and role the runner starts, from a new empty directory of its own outside any project, with the prompt on stdin:

```text
claude -p --output-format stream-json --verbose --json-schema <role's report schema>
  --mcp-config <role's review-mcp> --strict-mcp-config --allowedTools "mcp__crawler_review__*"
  --permission-mode dontAsk --no-session-persistence --setting-sources "" --model <model>
  --effort <effort> --max-turns <turns> --tools ""
```

The process prints its messages as JSON lines. The runner keeps the end of that stream in memory, never logs or stores it, and reads three kinds of line: the last `result`, the envelope with the report, `subtype`, `terminal_reason`, tokens and `total_cost_usd`; the last `rate_limit_event`, whose `resetsAt` is the reset time of a usage limit that rejected a request; and the agent's messages, of which it keeps only the input tokens of the first model request (system prompt, tool definitions and task) and, per tool, the calls and the characters of their answers, never what a tool answered ([`context_use.rs`](../../src/crawler/src/review_agent_runner/context_use.rs)); `-p` takes `stream-json` only with `--verbose`. `--tools ""` disables every built-in tool (no shell, files, web or browser), `--system-prompt` replaces the CLI's default system prompt, written for a coding assistant with files and a shell, with one line naming the role (about 2,800 tokens less on every turn; the role's prompt is the message on stdin), and the MCP configuration names `review-mcp --role author|reviewer --review <review id>` as the server `crawler_review`, with the console URL and the token file's path, never a token, so `mcp__crawler_review__*` allows exactly that role's review tools. `--bare` is never used: it does not read the login. `--max-turns` exists in Claude Code 2.1.312 although its help does not list it. Every process starts with an empty context. Its environment, and that of the login probe, is not inherited: it holds only `PATH`, `HOME`, `TMPDIR`, `CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_OAUTH_TOKEN`, `LANG` and `LC_*`, `HTTPS_PROXY` and `NO_PROXY` (either case), `SSL_CERT_FILE`, `SSL_CERT_DIR` and `NODE_EXTRA_CA_CERTS`, and on Windows `SystemRoot`, without which no network request works, and `TEMP` and `TMP`, as far as the runner has them, plus `DISABLE_AUTOUPDATER=1`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, `CLAUDE_CODE_PROMPT_CACHE_TTL=5m` (a process runs minutes, so the five-minute prompt cache serves its turns at a lower write cost than the subscription's default hour) and `TZ=UTC` ([`invocation.rs`](../../src/crawler/src/review_agent_runner/invocation.rs)). No `ANTHROPIC_*` variable, provider switch such as `CLAUDE_CODE_USE_BEDROCK`, cloud credential or crawler setting reaches an agent; `review-mcp` gets the console URL and the token file's path from its MCP configuration. The prompts and report schemas are versioned files in [`review_agent_runner/prompts`](../../src/crawler/src/review_agent_runner/prompts) and [`schemas`](../../src/crawler/src/review_agent_runner/schemas); both prompts tell the agents that page content is data, never instructions, explain `human_required` and the `HUMAN_REQUIRED` refusal of the [repair cap](#review-agents), say what the [approval guard](extraction-and-review.md#approval-guard) needs of the identity rule and that an optional field the pages carry a value for, the price and description above all, gets a rule rather than being left out (the author says in its summary why one is), the `state` contract of [schema generation](extraction-and-review.md#schema-lifecycle), a test on a sold or unavailable page before staging, and on a URL-pattern review the induction of one structural pattern from the sample's URLs alone, without page reads or labels, that covers every product route family, takes no other route and leaves gift cards, vouchers, digital products and services out, with abstention as `NEEDS_HUMAN` and `NO_PATTERN` left to a human; the reviewer checks the same, writes a product-schema repair note with one line per finding, the page, field, selector, what it extracts and what it should, since the note is all the author reads, and a URL-pattern repair note short, without the reviewer's own doubts, with the details in `field_findings` (`get_review` answers the note whole, within its answer bound), and says that rejecting a `manual_schema_required` review classifies its seed and triggering pages as non-product pages until a human revokes the rejection ([manual authoring](#manual-authoring)). A changed prompt or report schema gets a new version, such as `author.v2`, which the ledger and the log record with each process. The author reports `review_id`, `action` (`STAGED`, `NOTHING_TO_STAGE`, `NEEDS_HUMAN`, `SKIPPED`), `candidate_version`, `summary` and `risks`; the reviewer reports `review_id`, `decision` (`APPROVE`, `REJECT`, `NEEDS_REPAIR`, `SKIP`), `confidence`, `summary`, `risks`, `field_findings` and `server_answer` (`outcome` `ACCEPTED`, `REFUSED` or `NOT_SENT`, the refusal's `kind`, `failed_checks` and `detail`). A report is the agent's account; the event trail is what happened: after each reviewer process the runner reads the trail and records the verdict it shows as `trail_verdict` (`APPROVED`, `REJECTED`, `REPAIR_REQUESTED`, or `NO_VERDICT` when the trail shows none, which a refusal and a decision never sent look like alike; absent in older records and when the trail cannot be read), and the digest and the ledger show it next to the report's `server_answer`, which they label as reported.

The limits of the agents' decisions are the console's, never the runner's: after the login probe each run reads them from `GET /api/review-agent-limits` with the author token, and times a reviewer pause at the decision cap by the console's `max_decisions_per_hour`. #### Limits

The defaults are sized for a backlog of every ListingSource's pattern and schema review. Each agent process holds at most one of the console's [live jobs](#review-service) at a time, so `CRAWLER_REVIEW_AGENT_RUNNER_MAX_PROCESSES` matches `CRAWLER_REVIEW_MAX_CONCURRENT_LIVE_JOBS` (both 20): a further process would only wait with `LIVE_JOBS_BUSY`. Processes of different shops fetch in parallel, each at its own shop's crawl delay, and a ListingSource never has a pattern and a schema review open at once. A review takes an author and a reviewer process, about two minutes for a URL pattern and longer for a product schema, so twenty processes decide roughly 300 to 500 reviews an hour; `CRAWLER_REVIEW_AGENT_MAX_DECISIONS_PER_HOUR` (300) on the console stops a runaway without throttling that. The usage limits of the login pause the runner on their own. With fewer pending reviews than a run's budget, a run ends early and the next starts after the interval, so the defaults cost nothing when the queue is short. Raise the live-job cap and the processes together for a larger backlog; lower them, or the decision cap, to slow the agents down.

- A run takes the lock `review-agent-runner.lock` in the state directory and releases it when it ends, so a `--once` started during the service's run does nothing and exits 0, and one started between two runs works.
- A run works at most the configured reviews: pending product-schema and URL-pattern reviews of crawl-enabled ListingSources, leaving out reviews that are cooling down and reviews that wait for a human ([repair cap](#review-agents)). It reads every page of the [agents' queue](#review-service), the reviews the agents can work and then those that wait for a human, so it sees every pending review however many there are, and none that waits for a human takes a workable review's place; a review that comes to wait for a human between the two reads counts as waiting. A review that waits for a human is no agent work: the run starts no process for it and gives it no cooldown, so it is workable again as soon as a human hands it back, and `Review agents pass started` and `Review agents pass finished` count it as `waiting_for_human`. Reviews no agent process worked in the ledger's eight days come first, oldest first, then those worked longest ago, so a review the agents hand back and forth with needs-repair verdicts never holds the others back. A review a human handed back after its last agent process, such as one that waited for a human at the repair cap, counts as not worked, so the agents answer the human ahead of the reviews they worked since. At least half of the run's budget, rounded up, goes to product-schema reviews as far as the queue has them: a source gets its schema review only after its pattern passed, so schema reviews are younger than a URL-pattern backlog and would never win a slot in that order, although approving one unlocks a source that cleared its first gate. The share is counted over the whole run, across refills, and slots the queue has no schema review for go to the other reviews in the order above, so none idles. A review of a disabled ListingSource holds nothing back and waits until the source is crawled again. The run is a rolling pool: whenever one of the `CRAWLER_REVIEW_AGENT_RUNNER_MAX_PROCESSES` slots frees and the run's budget of reviews is not spent, it reads the queue again and starts the next workable reviews, so a slot never waits for the slowest process of a batch, and a review that opened or was handed back meanwhile is worked in the same run while one that came to wait for a human is not started. A review is worked at most once per run, so a needs-repair verdict is answered on the next run, and the run ends when its budget is spent, no unworked review is workable, or a [pause or stop](#stop-and-undo) applies; a pause stops the refill while running processes finish.
- An author that labelled the review's ListingSource reports `SOURCE_LABELLED`: the label took the review out of the agents' queue, so no reviewer runs and nothing is handed to a human; the review stays pending for a human, who sees the label on the source.
- The reviewer runs when the author staged a candidate or found nothing to stage, the review does not wait for a human after the author's pass, and the approval guard's dry run (`GET /api/reviews/{id}/approval-checks`) does not already refuse the candidate (a product-schema review's stored matrix that is missing, outdated or expired refuses nothing, since the reviewer refreshes it): a reviewer could only be refused then, so the review cools down instead and `Review agents pass finished` counts it as `guard_blocked`; a dry run the runner cannot read lets the reviewer run. The runner reads the review after each author process, whether it reported or not: a review that the author's own needs-repair verdict handed to a human at the repair cap gets no reviewer process, whose every verdict the console would refuse with `HUMAN_REQUIRED`, and `Review agents pass finished` counts it as `handed_to_human`. A process that hits its turn or context limit ends without a decision, as does one that fails, outlives its timeout or reports no usable report, and an author `SKIPPED`: the runner records the envelope's `subtype` and `terminal_reason`, the review stays pending, and it cools down before its next pass. After each reviewer process the runner reads the event trail since the process started: the reviewer decided when it shows an `AGENT_REVIEWER` approval, rejection or needs-repair verdict on the review, whatever the report says the console answered, and otherwise, or when the trail cannot be read, the review cools down. A review that waits for a human after either process gets no cooldown, whichever agent's verdict brought it to the cap, as the runner reads the review then; one the runner cannot read counts as not waiting, so it gets its reviewer or cools down. A needs-repair verdict the trail records is worked again on the next run. An author that reports `NOTHING_TO_STAGE` on a candidate the reviewer already judged, so the review's trail ends with an `AGENT_REVIEWER` needs-repair verdict at its current candidate version and no review page was stored after that verdict, gives the reviewer nothing new; a later event that leaves the version as it is, such as a page the author added or its [no-sold-page record](extraction-and-review.md#approval-guard), and a waiting page the crawler attached, which records no event, are new to the reviewer, and a reviewer process would only repeat its verdict as one more round toward the cap. The runner then starts no reviewer: it hands the review to a human at once (`POST /api/reviews/{id}/hand-to-human` with the author's token, [review agents](#review-agents)) with the reason `NOTHING_TO_STAGE_AFTER_REVIEW`, the report's `handover_category` and the author's report summary as the note of the `HANDED_TO_HUMAN` event, counts it in `handed_to_human`, and gives it no cooldown. A hand-over the console does not take cools the review down, so no reviewer round is spent; on a candidate the reviewer has not judged yet, such as one that already holds on the first pass, the reviewer runs as before. An author that reports `NEEDS_HUMAN` cannot decide the review from what it can read, such as a sample behind a login wall or bot challenge, and gets the same immediate hand-over with the reason `NEEDS_HUMAN`, its `handover_category` and its summary as the note, whether or not the reviewer judged the candidate before. Agents decide `NO_PATTERN` themselves under the [approval guard](extraction-and-review.md#approval-guard).
- When a process ends on a usage limit of the login, a session (five-hour), weekly or model limit or a spend limit, the runner starts no further process and skips work until the limit resets. The reset time is the `resetsAt` of the `rate_limit_event` that rejected the request; without one the runner reads it from the CLI's message, such as `You've hit your weekly limit · resets Mon 12:00am`, in UTC, the zone it starts the CLI in. A reset time it cannot read pauses it for an hour and logs the message's line at WARN, so a changed wording shows in the journal. Pending reviews simply wait, and cached schemas keep working.
- When a reviewer's report shows the console's cap on the agents' decisions (`server_answer` `detail` or `kind` names `AGENT_DECISION_LIMIT`, whether the console refused the verdict or the reviewer saw the refusal coming, or the console refused the verdict as `RATE_LIMITED` without `LIVE_JOBS_BUSY`), the runner starts no reviewer process until the cap has room again, since a reviewer that cannot decide only spends budget; authors keep running, and the cap itself and the console's API are unchanged. The report carries no retry time, so the runner computes the one the console computes: from the agents' approvals and rejections in the event trail, read from a few minutes before the last hour so a runner clock ahead of the database misses none, and the console's `max_decisions_per_hour`, the cap has room when enough of the oldest leave the hour. A trail it cannot read in full pauses the reviewers for the whole hour; a report that shows the cap while the trail shows room under it sets no pause and logs a WARN. The pause is kept in `review-agent-runner-state.json` and survives a restart; it is no usage-limit pause, so a review whose author staged during it gets no reviewer process and cools down only until the pause ends, and the refused review keeps its normal cooldown. The runner logs `The agents reached the console's decision cap; no reviewer process starts until it resumes, authors keep running` once with `resumes_at`, `The reviewer pause after the agents' decision cap ended; reviewer processes start again` once when a pass first looks after it, and the pass counts the held-back reviewers as `reviewers_held_back`; the digest names the pause under **Usage**. Reviewer processes that started before the cap showed still end without a decision.
- The agents share the login's subscription with whoever else uses it, so the runner paces them before its limits ([`usage_pacing.rs`](../../src/crawler/src/review_agent_runner/usage_pacing.rs)). After each process it reads the last `rate_limit_event` of the stream whose `unifiedWindows` report the used share (`utilization`) and `resetsAt` of the `five_hour` and `seven_day` windows. Once the five-hour use reaches `CRAWLER_REVIEW_AGENT_RUNNER_FIVE_HOUR_SHARE_PERCENT`, it starts no further process until that window resets. The weekly share `CRAWLER_REVIEW_AGENT_RUNNER_WEEKLY_SHARE_PERCENT` is paced over the window: of it, a seventh is allowed at the window's start and the whole at its end, growing linearly, and a use above what is allowed now pauses the runner until the window's elapsed part allows it, or until the window resets once the use reaches the whole share. Both default to 100, so the agents may use the whole window; lower them to leave the rest to the people on the same login. Running processes finish, the pause is kept like a usage limit's, `The agents took their share of the login's usage window; they pause until it allows more` logs both utilizations, and the digest names it as the agents' share of the limit. A stream without the windows paces nothing. The runner sets no dollar limit of its own: the usage limits above stay the hard stop. Each process's `total_cost_usd` is still recorded and summed over the rolling five hours and seven days for the log and the digest.
- The CLI reports a process's cost only in its result envelope. A process that outlives its timeout, or runs when the runner [stops](#stop-and-undo), gets SIGINT, on which the CLI ends its turn and prints its envelope with the cost so far; SIGTERM would end it without one. Once it has closed its output, or five seconds later, its process group gets SIGTERM, and SIGKILL five seconds after that; what it prints until then is read. A process stopped at its timeout or by the runner's stop, or killed by a signal, that reported no cost is charged the highest cost a process reported in the ledger's eight days; the ledger and `Review agent process finished` mark it `cost_charged`, the digest `cost charged`, and the rolling sums count it like a reported cost. The charge is an estimate, not an upper bound: a process that ran longer than any that reported may have spent more, and while the ledger holds no reported cost the charge is zero. The login's usage limits stay the only spending stop.

State between runs is in the state directory: `review-agent-runner-state.json` (pauses, cooldowns, last digest), written as soon as a pause or cooldown is set, and the process ledger `review-agent-processes.jsonl`, one record per process with its review, role, `prompt_sha256` (the first 12 hex characters of the SHA-256 of the role's prompt template for the review's artifact type and its report schema, which tells runs on different prompts apart), `repair_round` (whether the review waited on a needs-repair verdict, so the author's process repaired and the reviewer's judged a repair), outcome, report, tokens, cost and `context` (`opening_tokens` with the part of it read from and written to the prompt cache, `model_requests`, the model requests the process made, each response once however many tool calls it holds, unlike the CLI's `num_turns`, which counts every tool call, and `tool_answers` per tool with the characters each answer was read again as, `inspect_page` counted per view as `inspect_page_outline` and `inspect_page_markdown`, as far as the stream's kept end shows them), appended when the process ends, with the reviewer's `trail_verdict`, and kept for eight days. A state or ledger the runner cannot read fails the run instead of forgetting a pause or a cooldown; only a last ledger line an interrupted run left unfinished is completed or cut off.

#### Logging

Each process logs `crawler.review_agent.process_finished` at INFO (`Review agent process finished`) with its review, source, role, `prompt_sha256`, `repair_round`, outcome, the agent's `decision` (the author's action or the reviewer's decision), `subtype`, `terminal_reason` and `api_error_status` when set, turns, duration, models, token counts, `total_cost_usd` and `cost_charged`; the report is in the ledger, never in the log, and the process start is a DEBUG record. A run that started a process logs `crawler.review_agent.pass_completed` at INFO with its counts and the rolling cost sums; a run that started none logs it at DEBUG, and `crawler.review_agent.pass_started` is always DEBUG, and a run of the service that fails logs `Review agent run failed; the next run follows after the interval` with its error, or `Review agent run failed while the runner stops`. The log never holds a prompt, page content, a raw envelope or a token; a process that prints no envelope logs its exit code and the last line of its stderr, shortened, and a usage limit without a reset time the runner can read logs `The CLI reported a usage limit without a reset time the runner can read; the agents pause for an hour` with the line of the CLI's message as `limit_message`.

#### Digest

Once a day a run of the service writes a digest of the agents' work since the previous one to `digests/review-agents-<time>.md` in the state directory and logs it as `Review agents digest`: first, under **Needs a human**, every pending review of crawl-enabled ListingSources that waits for a human after the run's pass, read page by page from the [agents' queue](#review-service), each with its review, artifact type, shop, agent rounds, the hand-over's actor, time and reasoning when an agent handed it over, and last needs-repair note and time, headed by how many wait and when the oldest of them opened (`needs_a_human`, `needs_a_human_oldest_opened` and `needs_a_human_oldest_age_hours` in the log line, the age in whole hours since that review opened, so the human backlog shows in CloudWatch without the console); then, under **Agent NO_PATTERN decisions to spot-check**, every agent approval of `NO_PATTERN` in the window with its shop and note (`agent_no_patterns`), since each keeps a shop out of product crawling until it [expires](extraction-and-review.md#approval-guard), so an operator checks a few each day instead of every decision; the product-schema reviews the agents can work and since when the oldest waits (`workable_schema_reviews`); then approvals, rejections, needs-repair verdicts, hand-overs and no-sold-page records ([approval guard](extraction-and-review.md#approval-guard)) by agents and by humans, each listed with its note, restores and revoked rejections, from the console's event trail of all reviews (`GET /api/review-events`, read page by page), the server's refusals the reviewer reported by failed check (the trail records only what the console accepted, so a refusal is the agent's account), each process's outcome, the processes, turns, limit hits, tokens and cost per role and review type, so an operator sees where the tokens go, each review's tokens and cost, and under **Context use** per role the average opening request with its cache reads and writes and each tool's calls, answer characters and re-read characters, most re-read first, from the ledger, with the rolling cost sums and any pause. Operators read the file on the host and act on what it shows: restore an approval, revoke a rejection, or reject or repair a review by hand.

#### Stop and undo

- Stop the agents: `systemctl disable --now review-agent-runner`. The unit's `KillMode=mixed` sends SIGTERM to the runner alone, never straight to the agent processes, as on every `systemctl stop` or restart. The runner logs `Review agent runner stopping`, starts no further process and lets each running one finish for ten minutes, a run of an author or reviewer taking 30 to 100 seconds and a schema author several minutes. It then stops a process still running as at its [timeout](#limits), SIGINT first, so the ledger records it with its reported or charged cost and the `failure` `stopped when the runner's stop deadline passed`. A process that finishes during those ten minutes is read as usual, but no reviewer starts after an author that ends while the runner stops. Its review does not cool down, the stopped run writes no digest, and the cooldowns and pauses already set are kept. The runner exits with 143 within 620 seconds, the ten minutes plus the time stopping a process takes; whatever still runs then is killed, and a second signal does not shorten the stop, because `dev` sends the runner a second SIGTERM after the Ctrl+C that reached it. `TimeoutStopSec=660s` leaves room for that before systemd kills what is left of the unit. Ctrl+C stops `--once` the same way, with exit code 130. Or switch the crawler to `CRAWLER_AUTHORING_MODE=manual` and restart it: the token file is removed and every run refuses to start. Neither needs a deploy.
- Undo an agent's rejection of a `manual_schema_required` review: a human revokes it ([manual authoring](#manual-authoring)), so its seed and triggering pages are scraped again and may open a new review. Other rejections classify no page: the next crawl or scrape opens a new review.
- Undo an agent's approval: a human restores it ([review service](#review-service)). A needs-repair verdict leaves the review pending, and a human can approve, reject or edit it in the console at any time; a change or verdict of theirs hands a review that waits for a human back to the agents ([review agents](#review-agents)).

## Single-server deployment

Production runs one `server` process on one Linux host under systemd. Start from the example unit [`crawler-server.service`](../../src/crawler/scripts/linux/crawler-server.service) and environment file [`.env.example`](../../src/crawler/.env.example); real values live only on the host.

### Build and release

Production runs only CI-built releases: the host has no Git checkout, Rust toolchain or source tree. The manual [Crawler release](../../.github/workflows/crawler-release.yml) workflow takes a full lowercase `source_sha` and runs only from `develop` of `aura-historia/backend`. It requires that the commit is merged into protected `develop` and that the [CRAWLER test lane](../ci.md#required-ci) passes at that exact commit, so only a commit whose crawler tests passed is released. The workflow is independent of the AWS Release workflow: it uses none of its pinned control files, variables or approvals, and changing one does not affect the other. It builds `server`, `review-mcp` and `review-agent-runner` with `cargo build --release --locked -p crawler` on `ubuntu-24.04` (glibc 2.39, the host's), then [`package-release.sh`](../../src/crawler/scripts/linux/package-release.sh) packs them into a reproducible `crawler-<sha>.tar.gz` and its SHA-256 file. After the `crawler-release` environment's approval the workflow creates the GitHub Release `crawler-<sha>` with both files. It never overwrites a release: an existing release or `crawler-<sha>` tag fails the run, checked before the build and again right before publishing, so a published build never changes and its tag always names the source commit. The archive holds the three binaries, `deploy.sh` and `autodeploy.sh`, `systemd/` with the four example units (`crawler-server.service`, `review-agent-runner.service`, `crawler-autodeploy.service` and `crawler-autodeploy.timer`), `SOURCE_SHA` and `MIGRATIONS`: one `<sha256>  <file>` line per crawler-local migration the build embeds and applies at startup. Releases published before the checksums list names only; `deploy.sh` still reads them and compares those by name.

### Host setup

`server` connects to the database in `LOCAL_DB_URL` and applies pending crawler-local migrations; it never starts Docker or creates the database. Provide PostgreSQL 16, as in local development, with its contrib modules, on the host or reachable from it. Create a dedicated role that owns the database, so migrations can create their tables and the trusted `pgcrypto` extension without superuser rights:

```sql
CREATE ROLE crawler LOGIN PASSWORD '<random password>';
CREATE DATABASE crawler_server OWNER crawler;
```

Set `LOCAL_DB_URL=postgres://crawler:<password>@127.0.0.1:5432/crawler_server` in the environment file; percent-encode reserved characters in the password. A missing or blank value fails startup with `missing required environment variable: LOCAL_DB_URL`. Keep the Postgres port closed to the outside. The database holds all crawler state; back it up.

The host needs outbound HTTPS to the API and to SQS, and no route to the business PostgreSQL. A scope refresh that cannot reach the API or receives a failed or malformed page skips that pass and is retried at the next one; startup stops only on a missing or invalid setting. Raw capture into the business database is the ingestion consumer's job, so a failure there is not visible to the crawler.

Prepare the host once:

```sh
useradd --system --home-dir /var/lib/crawler --shell /usr/sbin/nologin crawler
install -d -m 0750 -o root -g crawler /etc/crawler
install -m 0640 -o root -g crawler src/crawler/.env.example /etc/crawler/crawler.env  # then fill in
```

Install the units from a release's `systemd/` directory and deploy the release ([deploy and roll back](#deploy-and-roll-back)):

```sh
install -m 0644 systemd/crawler-server.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable crawler-server
```

### Authoring mode

Launch with `CRAWLER_AUTHORING_MODE=agent` and the [review agent runner](#review-agent-runner) on the host, or `manual` to work the reviews by hand: neither makes an LLM call or reads a Vertex AI setting ([`config.rs`](../../src/crawler/src/runtime/config.rs)). A later switch to `review` or `auto` makes `VERTEX_AI_PROJECT_ID`, `VERTEX_AI_LOCATION` and Application Default Credentials on the host required; startup fails without them.

### Review console access

[`ReviewServerConfig`](../../src/crawler/src/review/server.rs) applies these rules:

- `CRAWLER_REVIEW_BIND_ADDR` defaults to `127.0.0.1:7878`; any value that is not `host:port`, including an empty one, fails startup.
- An empty or whitespace-only `CRAWLER_REVIEW_AUTH_TOKEN` counts as unset. A non-loopback bind without a token fails startup with `CRAWLER_REVIEW_AUTH_TOKEN is required for non-loopback bind addresses`.
- With `CRAWLER_AUTHORING_MODE=agent`, a missing `CRAWLER_REVIEW_AUTH_TOKEN` fails startup with `CRAWLER_AUTHORING_MODE=agent needs CRAWLER_REVIEW_AUTH_TOKEN, ...`, and the `crawler` user must be able to write the working directory, which `StateDirectory=crawler` provides, for the agents' token file.
- A decision cap, matrix age, repair-round cap or live-job cap (`CRAWLER_REVIEW_MAX_CONCURRENT_LIVE_JOBS`) that is not a whole number of at least 1 fails startup.
- `server` accepts review mutations only with the bearer token, so approving manual reviews needs the token even on loopback. Without a token, reads are open to anyone who reaches the port.

For launch, keep the loopback bind, set a random token, and tunnel: `ssh -L 7878:127.0.0.1:7878 <host>`, then open `http://127.0.0.1:7878`. The alternative is a non-loopback bind behind a TLS-terminating reverse proxy; the token is then mandatory and the session cookie is `Secure`, so browsers must use HTTPS.

### Logging

Logs are JSON on stdout, stored by the journal (`journalctl -u crawler-server`). `LOG_LEVEL` sets the base filter level (default `info`) in [`server.rs`](../../src/crawler/src/bin/server.rs); `RUST_LOG` is not read.

Setting `CRAWLER_CLOUDWATCH_LOG_GROUP` adds CloudWatch Logs export, which needs `logs:CreateLogGroup`, `logs:CreateLogStream` and `logs:PutLogEvents`; `server` creates the group and stream at every start and fails startup if that fails or either name is blank ([`logging.rs`](../../src/crawler/src/logging.rs)). Set `CRAWLER_CLOUDWATCH_LOG_STREAM`: its fallback, `HOSTNAME`, is not set by systemd, so the stream would be `unknown-host`. Credentials and region come from the AWS SDK default chain: an EC2 instance profile, a profile in the service user's `~/.aws` selected with `AWS_PROFILE` (including `credential_process`, for example IAM Roles Anywhere off AWS), or access keys in the environment file. Set `AWS_REGION` unless the profile or instance provides it.

#### Outcome events

Each crawler outcome an operator needs is one record with a stable `event` field, at INFO, or at WARN when the outcome is a failure that is not a per-URL result (a failed spider run, an opened scrape circuit); a scraped URL's failure is its `crawler.scraper.url_outcome` (DEBUG, see below) with `outcome` `failed:<kind>`. Every such record carries the top-level fields `listing_source_id`, `listing_source_name` and `domain`, so one query follows a shop through spider, scraper and LLM logs; the JSON records carry the current span, not the span list, so a WARN or ERROR of nested spider or scraper work names its source in those same fields. What repeats inside a loop or restates an outcome already logged is DEBUG: per-URL `crawler.scraper.url_outcome` records, per-review candidate edits of the review agents (the event trail keeps them), idle passes, and follow-up lines of an outcome. The events and their evidence live in the code that logs them; the contract is the name and these fields:

| Event | Answers |
| --- | --- |
| `crawler.spider.crawl_completed` | How a crawl ended: truncation, status histogram, product URL count, product pattern, sample match ratio and query-URL share. The spider library's own hard-timeout warning is filtered out; this event carries the truncation. |
| `crawler.spider.crawl_failed` | Why a run failed, with the diagnostics of its variant, the failure a bot challenge replaced, whether the failure waits for an operator (`needs_operator`), the retry (`next_crawl_at`, `cooldown_seconds`) and, after a rate-limit answer, `rate_limit_status`, `retry_after_seconds` and `rate_limit_streak`. |
| `crawler.spider.pass_completed` | A spider pass that started runs: how many ended in each way. |
| `crawler.spider.crawl_truncated` | A truncated run's retry: `truncation_count`, the remaining frontier size `frontier_left` (absent when the crawl could not tell), whether the crawl `ran_out_of_time` rather than ending early with only unfetchable pages left, `db_wait_ms`, `next_crawl_at` and `cooldown_seconds`, next to the `crawl_completed` that says `truncated`. `db_wait_ms`, which `crawl_completed` carries too, is the time the run waited on the database to load its seeds and store its crawled URLs, connection-pool waits included and URL-pattern work not: a large share of the crawl budget there means the run was starved, not that the shop is large. |
| `crawler.spider.crawl_rate_limited` | A run a shop's rate-limit answer stopped, WARN, with the status, `retry_after_seconds`, `rate_limit_streak` and the slowed next crawl. |
| `crawler.spider.root_moved` | A run whose result was dropped because the ListingSource moved to another crawl root meanwhile. |
| `crawler.spider.pattern_classified` | Which product URL pattern a classification stage settled on, or, at WARN, that it found none. |
| `crawler.spider.no_pattern_expired` | An agent's `NO_PATTERN` that outlived `CRAWLER_REVIEW_AGENT_NO_PATTERN_MAX_AGE_DAYS`: the crawl resets the source's classification and opens a new URL-pattern review. |
| `crawler.schema.generated` | The gate's verdict on generated schemas (`gate_result`) and the fields that failed (`failing_fields`). |
| `crawler.llm.invocation` | Every provider call of a generation, timeouts included, with the wait for the LLM governor. The source fields are absent for work no source scoped. |
| `crawler.scraper.url_outcome` | What happened to one scraped URL: `outcome` is `captured`, `unchanged`, `removed`, `awaiting_schema_review`, `skipped:<reason>` or `failed:<kind>`, with the page's HTTP status, `fetch_ms`, `process_ms`, the captured schema's index and score, `fields_present`, `image_probes` and `llm_calls`. `captured` means handed to raw capture; whether a product is sold is the worker's normalization to decide. A removal names its evidence in `removal_evidence`. |
| `crawler.scraper.pass_completed` | A scraper pass: totals, `unchanged` (the part of `skipped` that needed no work: a page whose raw input matches its last capture, and a recheck of a still-removed page), `skip_reasons` and `deferred_reasons` as JSON objects (`deferred_reasons` keys: `stopping`, `time_budget`, `schema_review_pending`, `robots_unreachable`, `url_lock`, `source_lock`) and a `by_domain` JSON array with each domain's counts, at most the 50 domains with the most URLs, `by_domain_truncated` counting the rest. |
| `crawler.review.opened` | A review opened, with its `reason` and `artifact_type`. |
| `crawler.review.decided` | A review decided: `decision` is `approved`, `rejected`, `needs_repair` or `handed_to_human`, with the `actor`, for an approval `incomplete_coverage`, and for a hand-over its `reason` (`needs_human` or `nothing_to_stage_after_review`) and the author's `handover_category` (`pages_unreadable`, `no_shop_wide_pattern`, `candidate_already_holds`, `no_workable_candidate`, `other` or `none`), never the agent's reasoning. A review the crawler created already decided (an LLM-approved schema) logs it as `decided` with `actor` `SYSTEM`. |
| `crawler.review.candidate_changed` | A change of a pending review's candidate (`change`: `candidate_edited`, `schema_edited`, `page_added`, `page_removed`, `labels_set`, `page_marked_not_product`, `mark_cleared`, `no_sold_page_recorded`). INFO for a human; DEBUG for the review agents, whose many edits the event trail keeps. |
| `crawler.review.restored`, `crawler.review.rejection_revoked`, `crawler.review.urls_retired_not_product` | A restored approval, a revoked rejection and the product URLs an approval retired as no product pages, with `affected_urls` where counted. |
| `crawler.source.mass_removal_confirmed`, `crawler.source.mass_removal_revoked` | A human's confirmation of a source's mass removal, with `hours`, `confirmed_until` and `rearmed_held_urls`, and its revocation. |
| `crawler.source.crawl_resumed` | A human resumed a crawl that waited for an operator, with the `crawl_error_kind` and `crawl_failure_count` it waited with. |
| `crawler.source.labelled`, `crawler.source.label_cleared` | A human [labelled](README.md#listingsource-scope) a source, with its `source_label` and whether a note came with it (`has_note`; the note's text is never logged), and cleared the label. |
| `crawler.review_agent.pass_completed` | A review agent runner pass that started processes, with its counts and cost sums; a pass that started none logs DEBUG, and `crawler.review_agent.pass_started` is always DEBUG. |
| `crawler.review_agent.process_finished` | One agent process: outcome, `decision` (the author's action `staged`, `nothing_to_stage`, `skipped` or `needs_human`, or the reviewer's `approved`, `rejected`, `needs_repair` or `skipped`, as in `crawler.review.decided`), usage and cost. The runner's queue serves no crawl host, so it has no `domain`. |
| `crawler.review_agent.handed_to_human`, `crawler.review_agent.waiting_for_human`, `crawler.review_agent.reviewers_paused`, `crawler.review_agent.decision_cap_ended` | The runner's decisions to leave a review to a human, `handed_to_human` with the hand-over's `reason` and `handover_category` as on `crawler.review.decided`, and the pause of the reviewers at the agents' decision cap. |

`crawler.raw_capture.batch` logs at INFO only when a batch persisted something or lost something; an idle batch logs at DEBUG.

### systemd unit

The example unit runs `server` as the unprivileged `crawler` user with `EnvironmentFile=/etc/crawler/crawler.env`, `Restart=on-failure`, `KillSignal=SIGTERM` and `TimeoutStopSec=90s`, a margin above the 60-second graceful-shutdown period before systemd sends SIGKILL. Its working directory is the empty state directory because `server` also loads a `.env` from its working directory or a parent; variables already in the environment take precedence. It starts after `network-online.target` and after `postgresql.service` when Postgres runs on the same host. A database that is still unreachable at start fails startup, and `Restart=on-failure` retries.

Run exactly one instance: no second host and no manual `server` next to the unit. The scheduler coordinates only through process-local locks ([scheduling and retries](scheduling-and-retries.md)), so a second process would crawl and capture the same work concurrently.

### Deploy and roll back

[`deploy.sh`](../../src/crawler/scripts/linux/deploy.sh) installs a released build on the host and is the only way to change the running build. Every release carries it (and `autodeploy.sh`) next to the binaries, so the host runs the script of its running build; for the first deploy fetch it from the repository at the release's commit (`https://raw.githubusercontent.com/aura-historia/backend/<sha>/src/crawler/scripts/linux/deploy.sh`). Run it as root with the commit SHA of a published `crawler-<sha>` release:

```sh
deploy.sh <sha>
```

The host pulls the release from GitHub, so CI holds no host credentials and the public repository needs no token. The script downloads the archive and its checksum, verifies the checksum and unpacks it next to `/opt/crawler/releases/<sha>/`, renaming it into place only when it is complete; a release directory without its completion marker is fetched again. Then it:

1. stops `review-agent-runner` and `crawler-server` together, skipping a unit the host has not installed, and fails if `crawler-server` is still active;
2. **dumps the crawler-local database** (`LOCAL_DB_URL` of `/etc/crawler/crawler.env`) with `pg_dump` into `/var/backups/crawler/`, but only when the release adds a crawler-local migration to the running build's `MIGRATIONS` or changes one's checksum, or when the running build's migrations are unknown, as on a host before releases. A failed dump aborts the deploy. At most 5 dumps are kept in total: after a new dump succeeds, the oldest are deleted. The host needs the PostgreSQL client tools. The backup covers the crawler-local database only: the business database is not reachable from the host;
3. repoints the `/opt/crawler/bin` symlink to the release directory atomically, so the units' paths stay unchanged. The first run keeps a previous directory of copied binaries as `releases/legacy-<timestamp>`;
4. starts `crawler-server`, and `review-agent-runner` if it was running, from the same build;
5. polls `http://127.0.0.1:7878/health` for `{"ok":true}` for up to `CRAWLER_HEALTH_TIMEOUT` seconds (default 600, every `CRAWLER_HEALTH_INTERVAL` = 5 seconds), long enough for startup to apply pending migrations, then prunes all but the newest five releases, the running one and the legacy binaries.

A failure after step 1 starts the stopped units again before the script exits. The script always switches `server`, `review-mcp` and `review-agent-runner` together: the runner fails every run against a console of another build ([review agent runner](#settings)). The example units are never overwritten silently: the script reports a unit that differs from the host's, and `--install-units` installs the release's units and runs `systemctl daemon-reload` before the restart. Use it when a release changes the example [`review-agent-runner.service`](../../src/crawler/scripts/linux/review-agent-runner.service): until the reload, systemd stops and starts the runner with the old unit's settings, such as its `KillMode` and `TimeoutStopSec`.

Roll back by running the script with an earlier release's SHA, or with `legacy-<timestamp>` for the binaries kept on the first run; an unhealthy deploy prints that command. Crawler-local migrations are applied at startup and never reverted, and startup refuses a database with an applied migration the binary lacks or whose checksum changed. So the script refuses a switch to a build that lacks a migration the running build applied or holds it with another checksum (including the legacy binaries, whose migrations are unknown), until you restore the dump taken before that migration (`pg_restore --clean --if-exists --no-owner --dbname "$LOCAL_DB_URL" <dump>`, with the crawler stopped) and rerun it with `--db-restored`. Never repair the schema by hand. A release that squashes crawler-local migrations into the baseline `20260101000000_initial_schema.sql` says so in its release notes: no database that applied the earlier chain can run it, so stop the unit, drop and recreate the crawler-local database as its owner (`db-reset` locally, see [Local database](#local-database)) and deploy it with `--db-restored`. This discards all crawler-local state: URL state, approved URL patterns and schemas, and reviews with their event trail. A binary that raises the [extractor version](extraction-and-review.md#extraction-contract), or changes what the page hash or the scraper-context fingerprint covers, extracts every page once more at its next scheduled scrape and validates its images again, and one that changes raw extraction does so for every page whose extraction it changes, so expect longer scraper passes until each such page has been scraped once.

### Automatic deploys

`crawler-autodeploy.timer` runs [`autodeploy.sh`](../../src/crawler/scripts/linux/autodeploy.sh) every five minutes so a published release reaches the host without anyone logging in. Install the example [service](../../src/crawler/scripts/linux/crawler-autodeploy.service) and [timer](../../src/crawler/scripts/linux/crawler-autodeploy.timer) from a release's `systemd/` directory, then `systemctl daemon-reload && systemctl enable --now crawler-autodeploy.timer`. It is opt-in: a release is always published after the `crawler-release` environment's approval, and nothing else triggers a deploy. The timer's only trigger is `OnCalendar=*:0/5`. To restrict the hours, add a drop-in (`systemctl edit crawler-autodeploy.timer`) whose `[Timer]` section first clears it with an empty `OnCalendar=` line and then sets the allowed times, for example `OnCalendar=Mon..Fri 08..16:0/5`; without the empty line the drop-in adds a schedule instead of replacing it. Stop it with `systemctl disable --now crawler-autodeploy.timer`.

Each run asks the GitHub releases API for the newest `crawler-<sha>` release. It does nothing when that release runs or is the one it handled last, and otherwise runs `deploy.sh --unattended <sha>`. The unattended mode:

- refuses a release that adds or changes crawler-local migrations, or when the running build's migrations are unknown, and a rollback over applied migrations (exit 3), before stopping anything: such a deploy is run by hand, so the backup is watched and the one step that cannot be undone has an operator;
- rolls an unhealthy release back to the build it replaced (exit 4), which is safe because no migration was applied;
- shares the deploy lock with manual runs, so two deploys never overlap.

A release that needs an operator or failed its health check is handled once: the service shows as failed (`systemctl --failed`, `journalctl -u crawler-autodeploy`) and the timer stays quiet until a newer release is published. So does a manual rollback: `deploy.sh <older sha>` is not undone by the next run. A download or API failure, and a deploy that found another one running, is retried at the next run. Every deploy stops the services; `review-agent-runner` takes up to 11 minutes to stop ([stop and undo](#stop-and-undo)), so the example service allows 60 minutes for a deploy and its rollback.


### After start

- The journal shows `Connected to crawler-local Postgres`, `Crawler authoring mode configured: ...` with `authoring_mode` `manual` or `agent` and `authoring_mode_source` `env`, in `agent` mode `Generated the review agents' tokens of this start and wrote them to their token file` with the file's `path`, and `Crawler review console listening`.
- `curl -fsS http://127.0.0.1:7878/health` returns `{"ok":true}`.
- `curl -fsS -H "Authorization: Bearer $TOKEN" http://127.0.0.1:7878/api/listing_sources` lists the ListingSources, with the ListingSources that need an operator first.
- The first spider pass does not log a `SPIDER_MAX_SIZE_BYTES` error: the spider checks that value, from 1048576 through 8388608, on each crawl, not at startup.

## Metrics and alarms

The crawler publishes metrics as CloudWatch [Embedded Metric Format](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch_Embedded_Metric_Format_Specification.html) records in its JSON log: each record is one log line whose top-level `_aws` block names the metrics, so the [CloudWatch log export](#runtime-prerequisites) turns them into metrics without a metrics client or extra permission. Without log export the records stay on stdout. Metric records ignore `LOG_LEVEL`, so a quiet log level cannot read as a metric gap.

All metrics use the namespace `AuraHistoria/Crawler`. Dimension values are ListingSource IDs and bounded kinds, never URLs or hosts.

| Metric | Unit | Dimensions | Recorded |
|---|---|---|---|
| `ScrapesSucceeded`, `ScrapesFailed`, `ScrapesAwaitingSchemaReview` | Count | `listing_source_id` | Per scraper batch: URLs whose scrape completed (changed or not), URLs whose scrape failed, and URLs whose page [waits on a product-schema review](scheduling-and-retries.md#fetch-retries), which is no failure and counts in neither `ScrapesFailed` nor `UrlFailures`. |
| `ScrapedOrAwaitingReview` | Count | `listing_source_id` | Per scraper batch: 1 when the batch completed a scrape or a page of it waited on a product-schema review, else 0. Per scraper pass, also 1 for each ListingSource that only a pending review keeps from scraping and so has no batch: it has a product URL pattern but no product schema and a pending product-schema review, or it has no pattern while its URL-pattern review is pending ([manual authoring](#manual-authoring)), and it is crawl-enabled with a crawl root and LLM budget left and its [scrape circuit](scheduling-and-retries.md#scraper-circuits) is not open. |
| `ScrapeCircuitOpened` | Count | `listing_source_id` | Per scraper batch: 1 when the batch opened the [scrape circuit](scheduling-and-retries.md#scraper-circuits), else 0. |
| `UrlFailures` | Count | `listing_source_id`, `failure_kind` | Per scraper batch and failure kind: the URL failures that recorded that `last_error_kind`, such as `HTTP_503` or `Timeout`. |
| `ProductsCaptured` | Count | `listing_source_id` | Per raw-capture batch: observations the ingestion queue accepted; 0 when every submission of the ListingSource failed. |
| `ProductsDiscardedUnsendable` | Count | `listing_source_id` | Per raw-capture batch, only when non-zero: observations discarded because they exceed the ingestion message limit or cannot be encoded. |
| `CrawlOutcome` | Count | `listing_source_id`, `crawl_outcome` | 1 per spider crawl that [recorded](scheduling-and-retries.md#spider-crawl-completion) a `last_crawl_outcome`, with that outcome. A URL-pattern decision that clears a ListingSource's `AWAITING_URL_PATTERN_REVIEW` is no crawl and emits none. |
| `CrawlsStoppedForOperator` | Count | none | 1 per spider crawl whose failure [stopped its ListingSource for an operator](scheduling-and-retries.md#spider-failure-escalation) (`NEEDS_OPERATOR`); recorded only then. |
| `CrawlProductUrls`, `CrawlTruncated` | Count | `listing_source_id` | Per spider crawl that classified its URLs with a product pattern, including a pattern that matched nothing on pages that were not mostly [bot challenges](networking.md#bot-challenges): the product URLs the crawl stored, each page once whether the shop links it with or without its trailing slash, and without the pages the pattern matches that are stored `other` because an operator [rejected](#manual-authoring) them, plus, for an [incremental crawl](scheduling-and-retries.md#discovery-coverage), the stored product pages it found linked and did not fetch again; and 1 when the crawl was cut short, else 0. |
| `ScraperDueUrls` | Count | none | URLs due for scraping when a scraper pass starts. |
| `ScraperPassDuration`, `SpiderPassDuration` | Milliseconds | none | Per scheduler pass, including a pass that finds no work. |
| `DbPoolMaxConnections`, `DbPoolInUsePeak`, `DbPoolSaturatedSamples` | Count | `db_pool` (`crawl` or `review`) | Once a minute per [Postgres pool](#postgres-pools): its connection limit, the most connections in use at one of the minute's one-second samples, and the samples at which every connection was in use. |
| `ReviewsWaitingForHuman`, `OldestReviewWaitingForHumanAge` | Count, Seconds | none | In `agent` mode only, every 5 minutes from the console's start: the pending reviews of crawl-enabled ListingSources that [wait for a human](#review-agents), as the [agents' queue](#review-service) counts them, and how long ago the oldest of them opened, 0 when none waits. A read that fails is warned about and skipped. |

Create these alarms from the metrics; each is an operator requirement, not a deployed resource:

| Alarm | Metric and statistic | Period and threshold | Missing data |
|---|---|---|---|
| A ListingSource made no successful scrape in 24 hours and waits on no review | `ScrapedOrAwaitingReview` Maximum per `listing_source_id` | 1 day, `<= 0` | Breaching: a ListingSource that is never scraped and waits on no review records nothing. |
| A product pattern matched no URL, or only pages an operator rejected | `CrawlProductUrls` Maximum per `listing_source_id` | 1 hour, `<= 0` | Ignore: the alarm holds until the next crawl records a count. |
| A scraper pass took more than 15 minutes, or none finished | `ScraperPassDuration` Maximum | 15 minutes, `> 900000` | Breaching: every pass records a duration, so silence means a stall. |
| A ListingSource's crawl now waits for an operator | `CrawlsStoppedForOperator` Sum | 1 day, `>= 1` | Not breaching: the metric is recorded only on an escalation. The console's `crawl_needs_operator` filter, and `crawler.spider.crawl_failed` with `needs_operator=true`, name the sources, their failure kind and streak. |
| The LLM governor made a call wait more than 60 seconds | Not recorded yet | 1 minute, `> 60000` | Not breaching |

The scrape alarm stays quiet for as long as the ListingSource's review stays pending, also when the review [waits for a human](#review-agents) or nobody decides it in `manual` mode: the console's review queue, and in `agent` mode the agents' [digest](#digest) and `ReviewsWaitingForHuman` with `OldestReviewWaitingForHumanAge`, report that review instead. The crawler does not record the LLM governor wait yet; with `CRAWLER_AUTHORING_MODE` `manual` or `agent` it makes no LLM call. The scrape alarm needs one alarm per crawl-enabled ListingSource: a CloudWatch Metrics Insights alarm evaluates only the latest three hours of data ([limits](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarm-limits.html#metrics-insights-alarm-limits)), less than its one-day period. The product-pattern alarm needs one alarm per crawl-enabled ListingSource, or one Metrics Insights alarm grouped by `listing_source_id`.

## Validation

Run targeted checks after crawler changes:

```sh
cargo check -p crawler
cargo test -p crawler --all-features
cargo test -p crawler --tests
```

For database or local-flow changes, verify migrations, both script folders, the compose file, and affected integration tests together.
