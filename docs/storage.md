# Storage Contracts

## Users and email-marketing consent

PostgreSQL is authoritative for registered User state. `users.email` is the canonical current account email; changing it does not transfer marketing permission to the new address. `users.marketing_email_consent` is a current grant for the single email-marketing purpose and that account email; it is not a delivery guarantee or permission for another channel. New users and rows present when the forward migration runs start with consent `false`. There is no consent-history table or client-supplied consent version.

Grant and revoke operations update the User aggregate, and a grant is accepted only when the confirmed address matches the canonical account email. Profile, preferences, tier, billing and other User changes preserve consent. Aggregate optimistic concurrency prevents a stale User write from restoring an older consent state. Email-based anonymous newsletter subscriptions remain separate and do not create Aura Users.

The user service coordinates accepted consent decisions and durable synchronization intent in one short PostgreSQL transaction through transaction-bound ports. `users.marketing_email_consent` is the current local decision; `users.marketing_email_consent_revision` (nonnegative, initially 0) fences older USER work independently of the root optimistic `version`. An accepted proof advances the revision even if the boolean stays true; replay of the same proof, including PostConfirmation after withdrawal, cannot regrant. Ordinary profile edits must not advance it. `users.marketing_email_consent_changed_at` is nullable accepted-decision metadata, not an audit trail; there is no `marketing_consent_events` table or checkbox-version column. Provider calls do not occur in this transaction. A User row change alone never proves Loops has been updated, and `users` CDC does not trigger provider synchronization.

`marketing_email_consent_sync_intents` holds one durable, immutable-target action per unique `source_key` (1–512 bytes; consent proof/action identity, never an HTTP request ID). Signup keys derive from canonical Cognito issuer/subject registration identity; accepted double-opt-in keys derive from the confirmation ID. A repeated key with identical immutable semantics reuses the committed result; conflicting reuse fails closed. Each intent has a native UUID `intent_id` (`mci`), an internal monotonic `intent_sequence` for ordering, `USER` or `EMAIL_ONLY` subject, a User-ID snapshot and positive `consent_revision` required for `USER` and absent for `EMAIL_ONLY`, exact target `email`, `recipient_key`, bounded optional `profile_snapshot`, desired consent boolean, `source` and `changed_at`. `EMAIL_ONLY` creates no User; standalone confirmation first resolves an exact existing account-email match, not the authenticated requester's identity. The service owns the per-recipient grouping/locking contract; the shared service function derives `recipient_key` as a domain-separated SHA-256 fingerprint of the typed email's ASCII-lowercase bytes, persisted as 64 lowercase hex characters. This grouping key does not prove account-email equality; no plus-tag or dot stripping is allowed. The original exact target email remains the Loops identity and must not be logged.

Persisted sources are `COGNITO_SIGNUP`, `AURA_DOUBLE_OPT_IN`, `USER_WITHDRAWAL`, `USER_DELETION`, `EMAIL_ONLY_WITHDRAWAL`; only signup and double opt-in can grant. Intent states are `PENDING`, `IN_PROGRESS`, `APPLIED`, `SUPERSEDED`, `BLOCKED`, `FAILED`, with checked transitions. Operational state includes a five-minute committed lease (token and expiry), attempt count, optional provider contact ID, safe error code, creation/completion times and a completion receipt binding the lease and stable result tuple. The PostgreSQL worker port can claim, recheck and finalize an intent; it is not a deployed runtime worker. Claims return immutable email, subject, desired action and revision, not a hydrated mutable User. Active leases defer work; claim/finalize use the same token, and exact confirmed finalize retries are no-ops. Missing or stale USER grants become `SUPERSEDED`; an absent User must never turn a USER grant into EMAIL_ONLY. A grant's `not_after` is exactly seven days after its `changed_at`; expired/archived grants must not be applied automatically. Revokes have no `not_after` and must not expire into permission to send. A lost finalize response is resolved from the persisted receipt, not by assuming success or sending again. No database transaction spans network I/O.

Local changes and provider back-sync share a short per-recipient transaction/advisory-lock protocol: insert a new intent and supersede older pending or leased grants atomically; provider-originated decisions update local state and cancel obsolete work without ordinary outbound echo. Only trusted service paths may supply a verified local grant (`COGNITO_SIGNUP` or `AURA_DOUBLE_OPT_IN`), never an HTTP `verified` assertion. Backend account email is immutable; this contract does not provide an email-change command or intent. If an upstream Cognito/OAuth address changes, it cannot migrate backend marketing permission; reconciling that identity requires a separately designed, verified flow. Deletion cancels USER grants but retains any needed old-address revoke: do not cascade-delete pending revokes or use `ON DELETE SET NULL` to reinterpret USER grants as anonymous. Running external calls cannot be rolled back; the later sender must recheck after sending and repair a raced revoke. The provider owns actual marketing membership/opt-out; these intents are PostgreSQL operational state, not historical events or CDC-selected `users` updates. See [event flow](events/flow.md#marketing-consent-sync-intent).

## Notifications

PostgreSQL is the sole production owner of notifications and external-delivery intent. Notification storage has no TTL.

- `notifications` stores one immutable typed content snapshot per semantic reason. `origin_event_id` is provenance only and is absent for partnership-application notifications. ProductListing references are snapshot provenance, not foreign keys: physical ProductListing deletion retains the Notification and its `notification_deliveries`; deleting a Notification cascades its deliveries.
- Watchlist idempotency is `(user_id, origin_event_id, kind)`. Search-filter idempotency is `(user_id, user_search_filter_id, product_listing_id, origin_event_id)`. Partnership-application idempotency is `(user_id, partnership_application_id)`.
- `notification_deliveries` owns durable external-delivery state separately. Multiple rows per Notification are unique by `(notification_id, channel, target_key)` and contain neither copied payload nor target value. The planner inserts requested rows with newly inserted notifications in one PostgreSQL transaction; the channel adapter resolves the current target. `EMAIL`/`PRIMARY` is the sole production plan and `EMAIL` the only valid stored channel; adding one requires a core enum, schema migration and sender. The claim commits before S3/SES I/O; finalization fences that lease. A send/finalize crash can duplicate delivery (at-least-once within seven-day source / 14-day DLQ retention, not exactly-once). For routing, activation and recovery see [event flow](events/flow.md#canonical-notification-delivery) and the [durable-worker runbook](durable-worker-runbook.md).
- Initial business schema defines paired `completed_lease_token`/`completed_at`. Finalization fences the active lease, then recognizes an exact committed token/result/time receipt on retry without rewriting it. Reclaim clears that receipt; terminal rows created before a completion remain null, never with invented tokens.
- Read models and REST mutations use `notification_id`, never `origin_event_id`. Corrupt persisted payload/version/source shape is an operation error, not a missing notification.

## Watchlist concurrency and intervals

- `product_listing_watchlist.version` is internal optimistic-concurrency metadata. Ordinary aggregate updates compare the loaded version and increment it once; a mismatch is a conflict, never not-found or a silent retry. REST never exposes it.
- Tier reconciliation locks the user row before affected watchlist rows and increments each changed row's `version`; stale concurrent writes fail.
- `product_listing_watchlist.active_since` is non-null only for `ACTIVE` rows and marks the beginning of the current active interval.
- `product_listing_watchlist.notifications_enabled_since` is non-null exactly when `notifications = true` and marks the beginning of the current email-enabled interval.
- Eligibility compares both interval starts with immutable `product_listing_events.event_time`; deactivation/reactivation and email disable/re-enable start new intervals. These timestamps are repository-owned persistence metadata, not REST fields.
- ProductListing withdrawal is reversible and does not mutate retained watch rows: active quota occupancy, watch state, and both current-interval timestamps remain. Create and inactive-to-active reactivation lock the authoritative user tier first, then lock the authoritative ProductListing lifecycle before evaluating quota and writing in the same PostgreSQL transaction. Notification-only updates and deactivation remain manageable for withdrawn listings. An explicit physical ProductListing delete cascades watchlist rows.

## Partnerships and Party

PostgreSQL is authoritative for Partnerships, Party identity, membership, and ListingSource grants.

- `partnerships` has one row per Party (`party_id` is unique); `partnership_members` and `partnership_listing_source_grants` hold membership and source access. Both `listing_sources.operator_party_id` and `partnerships.party_id` use restrictive Party foreign keys.
- Party hard deletion locks the Party row, checks indexed ListingSource and Partnership blockers in that same transaction, and makes a version-checked Party-only delete. It never cascades Partnership, member, or grant state; active and dissolved Partnerships both block.
- Source-grant revocation explicitly deletes only the targeted `(partnership_id, listing_source_id)` join row; deleting an absent row is a successful no-op and does not remove historical or referenced records. Eligible ListingSource hard deletion explicitly removes all of that source's grant rows in its own business transaction.
- Admin collection counts distinct members/grants in one joined query; exact `partyId`, `memberUserId`, `listingSourceId` filters use `EXISTS` without reducing counts. Detail uses one joined statement with UUID-ordered arrays limited in SQL to 100 member and 100 source IDs, complete counts and empty arrays for no associations. Safe read models include only Partnership ID, Party ID/immutable slug/name, references or counts, and `created`/`updated`; never Party contact, `version`, credentials, webhook secrets or crawler configuration.

## ListingSource provider ingestion configuration

- PostgreSQL stores Shopify and WooCommerce configuration in provider-specific rows linked to the ListingSource. The WooCommerce row owns its required nonblank `webhook_secret`; service state uses a redacted validated secret type, and the value is never included in read models or REST responses.
- ListingSource service writes the ingestion-method row and matching provider configuration in one transaction. Reads fail closed when a declared method is missing configuration, when provider rows are orphaned, or when a WooCommerce secret is invalid. Partner provider PUTs authorize against Partnership grants before mutation and use the ListingSource optimistic version for changed writes.
- Migration adds `listing-sources:write` to persisted scope constraints and enforces database-level nonnull/nonblank WooCommerce secrets. It does not remove or disable provider configuration; invalid existing secrets fail the migration so the environment can be repaired explicitly.

## Auctions

PostgreSQL is authoritative for standalone source-scoped Auction state. `auctions` stores the immutable `(listing_source_id, source_auction_id)` key, an optional canonical name, four optional exact `timestamptz` schedule columns, and a positive root optimistic-concurrency version. Its ListingSource foreign key is restrictive, so any retained Auction blocks source deletion.

`auction_events` is an immutable journal of `AUCTION_DISCOVERED` and `AUCTION_CHANGED` payloads. The current schema version is `1`; state snapshot and semantic event commit atomically. It has no CDC, projection, or worker route. Rehydration and event encoding validate canonical IDs, enum codes, localization pairs, URLs, RFC3339 instants, and version values; invalid persisted state is an explicit operation error.

## Credentials

PostgreSQL is authoritative for User access tokens and canonical OAuth credentials:

- `access_tokens` stores only token short/hash material, never a raw User access token. It has an internal optimistic-concurrency version; `user_id` cascades on User deletion. OAuth-origin tokens retain their client ID through a foreign key with `ON DELETE CASCADE`, so deleting a client revokes its issued tokens.
- `oauth_clients` stores only client-secret short/hash material, never a raw client secret. Client metadata updates use optimistic concurrency. Deleting a client cascades pending authorization codes, issued OAuth-origin access tokens, and their third-party exchange codes.
- `oauth_authorization_codes` and `oauth_third_party_exchange_codes` are one-time rows consumed atomically with `DELETE ... RETURNING`; third-party exchange codes reference their access-token row and cascade with it.
- Authorization-code exchange atomically consumes the code and creates the User access token and third-party exchange code. Semantic misuse commits deletion of a found code; persistence failure rolls a valid exchange back.
- Expiry remains service correctness. Plain `expires_at` indexes support `cleanup_expired_credentials_and_provider_receipts(batch_size)`, a physical-only PostgreSQL operation. It deletes at most 1,000 already-expired rows per target invocation with `FOR UPDATE SKIP LOCKED`; callers commit each call before starting another. Non-expiring access tokens have `expires_at IS NULL`.
- Credential tables are operational only. They must not enter DMS CDC selection, historical Sequin subscriptions, projections, analytics, or credential-bearing logs. The raw token in a third-party exchange-code row is short-lived escrow needed by that exchange only.
- Cleanup removes expired third-party exchange codes first and retains expired access tokens referenced by unexpired exchange codes. Authentication and redemption enforce expiry independently of cleanup.

Business schema migration needs no `pg_ttl_index` extension or background worker; only manual `Migrate (CD)` runs it, not Deploy or FX-only Initialize. Real-stage hourly UTC Scheduler cleanup begins after manual Deploy `scope=all` and [operator prerequisites](../infra/README.md#first-time-stage). `EXPIRY_CLEANUP_BATCH_SIZE=100` is validated before database access; each invocation makes one cleanup call. Delayed physical cleanup cannot extend logical credential or receipt validity; see [event flow](events/flow.md#aws-survivor-event-flow) for runtime failure handling.

## ProductListing events and revisions

`product_listings` remains the authoritative ProductListing write model. Its optional `auction_id`, lot label/order, and exact lot timestamp columns are listing-owned facts written and version-fenced only through the root ProductListing repository. All absent leaves mean no supplied fact; there is no context-presence row or boolean. A nullable composite foreign key ensures any Auction ID belongs to the listing's ListingSource, while independently auctioned listings may retain lot times without an Auction ID. The schedule check rejects bidding-open after scheduled-close.

Distinct revision fields:

- `version` is numeric aggregate optimistic-concurrency metadata. It starts at 1, advances once for each changed domain write, and never advances for enrichment or assessment writes.
- `current_event_id` identifies the latest projection-visible ProductListing event.
- `projection_version` is the positive monotonic external source version for complete OpenSearch projection writes.
- `content_source_event_id` identifies the title/description source used by content assessment and translation.
- `embedding_source_event_id` identifies the title/description/first-image source used by embedding. Discovery initializes it; an image change advances it and clears the stored embedding atomically.

Projection-visible enrichment advances `current_event_id` and `projection_version`, not aggregate `version`.

`product_listing_events` is the immutable ProductListing event journal and selected DMS CDC source after approved activation, not an outbox. Every row has immutable event ID/time, a positive persisted schema version, and an object JSON payload. Allowed groups are `DOMAIN` and `ENRICHMENT`, with the initial schema constraining domain events to `PRODUCT_LISTING_DISCOVERED`/`PRODUCT_LISTING_CHANGED` and enrichment events to `ENRICHMENT_EMBEDDED`/`ENRICHMENT_TRANSLATED_TITLES`. Application and router code fail closed on the concrete v1 type/group/version/payload contracts. Deferred same-listing foreign keys tie current and source marker IDs to journal rows.

`product_listing_raw_streams` is a mutable change-only capture head for `WEB_CRAWL`, `SHOPIFY`, `WOOCOMMERCE` with a restrictive ListingSource FK: retained streams block source deletion; late capture after source removal returns a typed missing-source outcome, never a replacement identity. `product_listing_raw_revisions` retains immutable evidence with independent optional `source_event_id` and provenance. `product_listing_raw_normalization_heads` serializes progress/binding; `product_listing_raw_normalizations` retains immutable terminal outcomes and stable codes. Raw JSON has no broad GIN index. Only raw revisions enter normalization CDC, never `product_listing_events` or downstream ProductListing consumers. See [event flow](events/flow.md#cdc-routing) for routing and the [durable-worker runbook](durable-worker-runbook.md) for custody; crawler dormancy is separate.

`product_listing_raw_provider_observation_receipts` is operational Shopify/WooCommerce idempotency state, not revisions or CDC. Only mapped raw capture creates/reuses a row; FIFO admission and authorized ignored WooCommerce create/update statuses (even with a delivery ID) do not. Each `(raw stream, provider scope, delivery ID)` stores only a canonical source-evidence digest, never evidence/JSON, for a 90-day logical window. Capture deletes a matching expired row in its transaction before lookup/reuse; bounded physical cleanup may run later. Expiry neither resets source ordering nor alters revisions. Intake does not require delivery identity or source timestamp. The FIFO consumer commits capture and its separate command receipt together; mapped HTTP `204` proves neither receipt (see [ProductListing ingestion](product-listing.md#asynchronous-ingestion-submission)).

Public history reads only `DOMAIN` discovery/change rows, strictly decodes v1 without aggregate reconstruction, orders by `event_time ASC, event_id ASC`, and fails on invalid persisted data.

## ProductListing ingestion command receipts

`product_listing_command_receipts` is PostgreSQL-only execution idempotency state, not queue admission or a submission registry. Primary key `command_id` is versioned (`plic1_` plus 64 lowercase hex characters); `submission_id` is correlation only. A committed receipt stores the verified 32-byte semantic fingerprint, ListingSource ID, operation, sole completion code `APPLIED`, and database-assigned `completed_at`; only successful applications get receipts, never business rejections. No raw command, credentials, provider evidence, exception text or response payload is stored. No TTL or business-row FK: deleting a listing/source does not permit replayed execution.

Execution holds a namespaced transaction advisory lock per `command_id`, reads the receipt and rejects conflicting fingerprint/metadata. A matching committed receipt is a duplicate; absent receipts permit execution only under the lock. Completion and canonical/raw writes commit in **one PostgreSQL transaction**; rollback, rejection and retryable failure leave no receipt. The PK is the final duplicate fence. The lock does not order distinct commands or replace aggregate concurrency; 64-bit hash collisions only serialize extra work, never merge identities.

DMS mappings select only `product_listing_events`, `product_listing_raw_revisions`, `search_filters`, `search_filter_matches`, and `notification_deliveries` (asserted in `infra/test/dms-cdc.test.ts`). Keep command receipts excluded from DMS/Kinesis, historical Sequin, analytics, projections and worker routing.

## Indexed read paths

- User watchlist lists use `created DESC, product_listing_id ASC`; reverse product watcher reads use `product_listing_id, user_id ASC`.
- Saved-filter matches support both `created ASC, product_listing_id ASC` and `created DESC, product_listing_id ASC` for a fixed filter.
- Product domain-event history orders by `event_time ASC, event_id ASC` for one product.
- Canonical ProductListing identity is unique `(listing_source_id, source_listing_id)`. No full `(listing_source_id, url)` B-tree: long valid URLs remain storable; withdrawal uses ID or the source-listing key.
- Unique raw-revision `(product_listing_raw_stream_id, revision)` supplies its B-tree; no duplicate index.
- `product_listings.listing_source_id` and `product_listing_raw_streams.listing_source_id` use `ON DELETE RESTRICT`. The `EXISTING_LISTING_SOURCE` JSON proposal trigger takes `FOR KEY SHARE`; deletion takes `FOR UPDATE`. A committed proposal blocks deletion, or deletion wins and proposal creation fails. The partial `partnership_applications_existing_source_proposal_idx` supports the check.
- Admin Partnership lists use keyset pagination in fixed `created DESC, partnership_id DESC` order; the `partnerships_created_id_idx` index matches this cursor path.
- Public Auction directories use keyset pagination in fixed `created DESC, auction_id DESC` order; the `auctions_created_id_idx` index matches this cursor path.

## FX snapshots

PostgreSQL is authoritative for canonical FX data.

- `fx_rates` stores immutable snapshot identity, database-assigned monotonic `generation`, capture time, provider source and idempotent provider event ID. `fx_rate_quotes` stores one positive scaled `units_per_eur` quote per supported currency, including `EUR = 1_000_000`; parent and quotes commit together, not as arbitrary pairwise rates. Product reads/writes/search/projections use persisted snapshots, never the provider; OpenSearch documents are rebuildable, not FX authority.
- ProductListing source pricing never stores an FX ID. An explicit `ListingSaleObservation` stores paired immutable `sale_observation_fx_rate_id` and `sale_observed_at`; both are null or both present. Only the dedicated observation write selects the latest `captured_at <= observed_at`. Generic create, update, and upsert never read FX or infer an observation from availability.
- Detail/watchlist/saved-match readers return source pricing and optional observation. Current pricing selects latest `captured_at <= valuation_at`; `SoldOut` or intentional withdrawn history uses the stored observation snapshot, but active relisted listings use current FX. Conversion uses scaled-integer HalfUp; missing/invalid/mismatched snapshots fail.
- ProductListing OpenSearch stores optional native `sourcePrice { amount, currency }`. `SoldOut` may project paired `saleObservationFxRateId`/`saleObservedAt` and complete target-currency `salePrices`; active relisted listings omit them. Partial metadata or `salePrices` is invalid; estimates are excluded.
- First search pages pin `valuation_at` and latest persisted `captured_at <= valuation_at`; continuations load the cursor's exact `fx_rate_id`. Display ranges compile to native `sourcePrice` intervals for active listings, or immutable sold `salePrices` in the requested currency; sold listings without `salePrices` do not match. No price sort.
- `product_listings.projection_version` increases for aggregate, embedding and translation changes; Product OpenSearch uses it for external versioning. Saved-filter documents retain the price range, compile against private temporary `priceByCurrency.<currency>` and store no FX ID/generation. Current-event percolation uses the immutable sale snapshot when present; otherwise latest `captured_at <= product_listing_events.event_time` ordered by `captured_at DESC, generation DESC`, converting the native main price to every supported currency with checked HalfUp arithmetic. FX capture alone triggers no filter rewrite, Product reproject, match or notification.
- `search_filter_matches.price_valuation_basis` and `price_fx_rate_id` are null together for non-price matches. Price matches persist `CURRENT` with the periodic run snapshot, `EVENT` with the event-effective snapshot, or `SALE_OBSERVATION` with the immutable observation snapshot. The FX ID references immutable `fx_rates`.
- `search_filter_periodic_match_state` stores per-filter progress, initially the authoritative filter creation timestamp if absent; ordinary filter reads exclude it. Runs use dedicated advisory-lock keys `0x4155_5241` / `0x5346_504d` on a separate connection from the size-one business pool. Idempotent match facts and checkpoints commit in use-case transactions; compare-and-set advances progress monotonically through the fixed window end only for completed eligible work. Retryable/incomplete work cannot advance it; deployments/timeouts/cancellation/lost locks cannot erase committed progress. See [event flow](events/flow.md#consumers-and-scheduled-matching) for scheduling.

`fx_rates.source_event_id` is the scheduled/bootstrap capture idempotency key. Manual FX-only `Initialize (CD)` after separate successful migration uses `deployment:fxrate:initial:{stage}:v1` across retries and SHAs, deduplicating the row even if the provider is called again. Deploy does not recapture initial FX or mark readiness. Captures serialize and require `captured_at` strictly newer than the previous capture except duplicate source IDs; historical import needs a separate workflow. `generation` orders snapshots; `captured_at` supports historical selection.
