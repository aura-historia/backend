# Event Flow

Target (not verified live): PostgreSQL → DMS → Kinesis → router Lambda → scoped SQS → worker Lambdas. Ten existing CDC scopes remain Standard; C06 declares the marketing-consent FIFO source/DLQ pair, the real C04 consumer binary and its versioned mapping. DMS selection changes and first start, router mapping activation, Sequin decommissioning and backlog settlement need separate operator proof. [Architecture §12](../arch.md#12-cdc-and-projection-architecture) owns invariants; the [durable-worker runbook](../durable-worker-runbook.md) owns activation, custody and recovery; [Infrastructure DMS notes](../../infra/README.md#dms-cdc-declaration-and-evidence-1781) describe the declared resources; live DMS evidence still requires an approved operator plan.

## Components

PostgreSQL owns business state, `product_listing_events` (domain/enrichment journal), immutable `product_listing_raw_revisions` (normalization wake-ups), `notification_deliveries` (intent/lease) and `auction_events` (atomic Auction discovery/change journal). No Auction worker/projection exists yet; a future schedule notifier must use event snapshots, not fabricate member ProductListing changes. DMS/Kinesis/router and ten Standard plus one consent FIFO SQS source/DLQ pairs carry selected CDC to dedicated Lambdas; OpenSearch holds rebuildable projections. The separate ProductListing FIFO is command ingress, not CDC. See [CDC routing](#cdc-routing), [consumers](#consumers-and-scheduled-matching), and [AWS survivor event flow](#aws-survivor-event-flow).

## Cognito post-confirmation registration

Cognito issuer, `sub`, and the supplied email remain the one-time registration identity inputs; `users.email` is immutable after creation and is not synchronized from later Cognito or IdP changes. The provider-agnostic post-confirmation adapter can map optional standard Cognito `given_name`, `family_name`, and `locale` attributes into initial Aura Historia profile values. These bootstrap values apply only when the PostgreSQL user is first created; replays do not synchronize provider refreshes over application profile data.

The public Cognito client accepts the optional immutable string attribute `custom:marketing_consent` during initial native `SignUp`. Its only values are exactly `"true"` and `"false"`; absence means no requested consent. This is an original signup request, not current consent, a consent version, or an authorization/JWT claim. It is not mapped from Google or another IdP. A grant requires `PostConfirmation_ConfirmSignUp`, Cognito-supplied `email_verified == "true"`, a valid exact email and canonical issuer/subject, and the attribute value `"true"`. The trigger grants only on a newly created User, committing the User decision and one C02 intent in the same PostgreSQL transaction. Missing, false, malformed, unverified, forgot-password, federated-without-proof, and replay cases create no grant. Malformed optional values produce a safe diagnostic without logging the event or email. `ConfirmSignUp` needs no consent `ClientMetadata`, so resend/reload/another-device confirmation relies on the stored Cognito attribute. The trigger makes no Loops, SES-newsletter, queue, or Step Functions call; a database failure is returned for Cognito retry, but Cognito confirmation itself is not rolled back. If trigger processing never recovers, account registration recovery remains an operator concern; this change adds no identity migration system.

## Marketing consent sync intent

A verified local grant or local revoke commits the registered User decision/fence (where applicable) with an immutable-target PostgreSQL consent synchronization intent in one transaction. An accepted standalone email confirmation may create `EMAIL_ONLY` intent without a User; signup identity and accepted confirmation identity are distinct durable source keys, not request IDs. Provider-originated changes update local state and invalidate obsolete grants without an ordinary outbound echo. The service owns transaction/recipient-lock decisions and the intent repository; Loops owns actual membership/opt-out. The service worker port claims a specific typed intent ID in a short transaction; missing, terminal (including `BLOCKED`), and active-lease/deferred outcomes are distinct from custody. On initial `claim_by_id` for the exact FIFO intent ID, commit `Claimed` before provider I/O; `Terminal(Applied | Superseded | Failed)` may be acknowledged after commit, `Deferred` must not be acknowledged, and `Missing` requires retry/investigation, not acknowledgement. `Terminal(Blocked)` forbids any provider grant but is not itself enough to acknowledge: in that same claim transaction C04 must call `MarketingConsentCoordinator::repair_raced_grant_if_needed(original_grant_intent_id, changed_at)`, then commit before acknowledging the original FIFO job. `NoRepairNeeded`, `ExistingRepair(id)` and `RepairScheduled(id)` each permit acknowledgement only after that commit; DB failure or uncertain commit must leave the job unacknowledged. C04 does not inspect the internal block reason. Recheck the authoritative decision in short transactions before and after the send, and finalize under the matching live token and result receipt. No transaction spans network I/O. An active lease defers; uncertain provider acceptance or lost finalize responses are not proof of completion. C04 sequence: claim the exact `MarketingConsentSyncIntentId` with `MarketingConsentIntentWorker::claim_by_id`, commit; `recheck` before provider I/O, commit; call the provider without a database transaction; begin finalization transaction and `recheck` again. If still ready, `finalize_claim` the same lease and result; otherwise call `MarketingConsentCoordinator::repair_raced_grant_if_needed(original_grant_intent_id, changed_at)` and do not finalize the stale grant as applied; commit. The result `GrantRaceRepairOutcome::{NoRepairNeeded, ExistingRepair(id), RepairScheduled(id)}` is decided under the recipient lock, never inferred from coarse `BLOCKED`. A local newer revoke may already provide durable corrective work; provider back-sync has no ordinary echo, so an already-running grant may require the exceptional `PROVIDER_RACE_REPAIR` revoke. If the worker crashes after the provider grant may have succeeded but before post-send repair, a retry enters through `Terminal(Blocked)` and the guarded check durably schedules or finds corrective work before acknowledgement; ordinary blocks return `NoRepairNeeded`. This contract does not imply exactly-once provider delivery. See [storage](../storage.md#users-and-email-marketing-consent) for revision, expiry, deletion and state rules.

### Loops consent adapter contract

The user service owns a focused, provider-neutral grant/revoke capability and current-state read for recovery; only an eligible committed consent intent may cause a grant. The Loops adapter owns contact requests, authentication, response validation and safe error classification, not consent decisions or transaction/recipient fencing. The earlier direct newsletter upsert remains in place until the API cutover; profile-only writes must not change global subscription or list membership, and must not become an all-user profile sync.

Identify the contact solely by the intent's **exact email** (no plus-tag/dot folding, account-email substitution or Loops `userId`). The optional `auraUserId` is custom profile metadata, never identity or authorization: one Aura requester may have different newsletter addresses. Send only confirmed optional name/language/currency snapshot values; omit absent fields instead of clearing them. Use the configured *ID* of the single marketing-purpose list, not its display name. A fresh eligible grant may explicitly request global `subscribed: true` and that list's `mailingLists` entry `true`; a revoke requests global `subscribed: false` and only that list's entry `false` under the single-purpose policy. A missing contact is already safely revoked: read first rather than using Loops' update upsert to create a contact merely to unsubscribe. `PROVIDER_RACE_REPAIR` uses that same revoke operation, never a new provider identity or endpoint. Do not alter unrelated lists, delete/recreate contacts or remove suppression.

Loops [update contact](https://loops.so/docs/api-reference/update-contact) is an upsert; only its documented success status/object with a nonempty contact ID confirms update acceptance, **not** target-list eligibility or email delivery. Loops [list management](https://loops.so/docs/contacts/mailing-lists) says the team's API cannot override a contact's Preference Center list opt-out, and globally unsubscribed contacts cannot be added to lists. Before and after a grant, perform bounded [email-keyed find](https://loops.so/docs/api-reference/find-contact) and [suppression](https://loops.so/docs/api-reference/check-contact-suppression) reads. A documented suppression `404` explicitly means contact missing: it permits a fresh grant only when pre-grant find independently agrees; contradictory preflight or missing post-write observations never prove success. After an accepted grant write, both readbacks must identify the accepted contact ID before reporting either applied or blocked-by-provider-preferences; inconsistent observations are uncertain. A suppressed contact is blocked without a grant write. Confirm both global `subscribed` and configured list membership on readback; global true with target list false/absent is blocked, not a successful re-subscription. Distinguish newly applied, already applied and blocked-by-provider-preferences outcomes without fabricating a local revocation event. Treat missing, malformed or inconclusive readback as uncertainty, not permission to send. The find response documents global and positive list membership, but does not expose a definitive reason for an absent/false list entry or all suppression causes; a readback cannot prove future deliverability. Bounce/complaint [suppression](https://loops.so/docs/contacts/suppression) independently prevents sends; never bypass a preference, suppression or deleted contact with another identity, list, Form or suppression-removal API. C04/C13 must keep local send eligibility conservative when the provider blocks or the outcome is unknown.

Definite pre-write failures, documented rejections and throttles release only the matching live lease back to retryable state with a durable no-write marker. If the release commit response is unconfirmed, retry the same lease and marker in a fresh transaction: confirm the exact marker if it committed or apply the release if the first transaction rolled back. The attempt count prevents an older claim from confirming a later retry. Superseding that retryable intent clears the marker while retaining a valid terminal state, so an old wake-up cannot block a later withdrawal. A recovered unclassified `IN_PROGRESS` grant first reads current Loops state; if global subscription, target-list membership and absence of suppression cannot be confirmed while the local fence remains open, C04 finalizes `BLOCKED` and requires fresh consent or operator investigation instead of subscribing again. The C04 invocation cap is 45 seconds with at most 35 seconds per record. It uses `ReportBatchItemFailures` and stops a FIFO batch at the first incomplete record, returning that record and every unprocessed successor as failures.

Bound client work, deadlines and response sizes; use the trusted `https://app.loops.so/api` base, preserve `/api/v1/...` when joining paths, and reject redirects with credentials or contact data. Distinguish documented invalid-email rejection, definite throttling (including `429`/`Retry-After`), known pre-write connection failure, and protocol/auth/config failures by phase. A protocol failure from grant/revoke preflight reads is a definite no-write outcome and releases the lease for retry; a malformed or unexpected response after the state-changing update request (including update `405`) may follow a request Loops received and enters C04 reconciliation. Timeouts, connection loss and `5xx` writes are likewise potentially accepted. Do not automatically retry state-changing grants in the HTTP client: C04 owns reconciliation and retries after ambiguous acceptance. Do not log or expose API keys, email query strings, contact bodies or raw responses. These are target semantics from provider documentation and mockable contracts, not evidence of live Loops behavior; verify actual readback and suppression behavior only with separately authorized, isolated provider checks.

`marketing_email_consent_sync_intents` is operational persistence, not a domain-event journal. The Rust router accepts only `INSERT` and emits one schema-2 `MARKETING_CONSENT_SYNC_INTENT_CREATED` job with the typed `marketing_consent_sync_intent_id`; updates (including finalization), deletes and `users` changes emit no job. Its DMS row contract is exactly PostgreSQL `intent_id` (canonical UUIDv7 text) plus the opaque 64-character lowercase-hex `recipient_key` for inserts, updates and deletes. DMS must select and publish only those two fields; the router rejects extra fields on every consent operation before a record can be checkpointed or published. Email, profile, source key, proof, lease and provider data must never enter Kinesis or SQS.

The compact job carries one specific `mci_` intent ID to `claim_by_id`, never a global database scan. Its stable FIFO fields are `MessageGroupId=marketing-email:<recipient_key>` and `MessageDeduplicationId=marketing-consent:<canonical mci_ TypeID>`. Recipient grouping serializes anonymous and registered actions for the same mailbox without putting email or User ID in the group. Retries preserve the body and both IDs. The router accepts the consent queue URL from `AURA_HISTORIA_ROUTER_QUEUE_URL_MARKETING_CONSENT_SYNC`; C06 supplies it and grants send/attribute access only to the intended source pair.

C06 resource contract: source `aura-worker-marketing-consent-sync-{stage}.fifo`, DLQ `aura-worker-marketing-consent-sync-dlq-{stage}.fifo`, both in the router's stage, region and AWS account. Source attributes: `FifoQueue=true`, `ContentBasedDeduplication=false`, 7-day retention, 330-second visibility, 20-second long polling, SQS-managed encryption, TLS enforcement, `RedriveAllowPolicy=denyAll`, and redrive to the matching FIFO DLQ after five receives. DLQ attributes: `FifoQueue=true`, `ContentBasedDeduplication=false`, 14-day retention, SQS-managed encryption, TLS enforcement, redrive allow limited to that source, and no redrive policy. Dev and prod source/DLQ deletion and replacement retain their messages. Keep the existing ten Standard pairs unchanged. Compute creates an active batch-one mapping against the published C04 consumer only after the applied schema and real artifact are selected. The router mapping stays separately disabled until operator approval; no API or Cognito queue publisher is added.

FIFO deduplication lasts five minutes, Lambda may invoke a consumer again, and Loops is outside the queue transaction. C02/C04 durable receipts, claim/finalize leases, authoritative decision/revision checks and raced-grant repair remain mandatory. FIFO cannot prove exactly-once external API execution, reconstruct upstream order after archive replay, or prevent stale grants without application checks. See AWS on [FIFO deduplication](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/FIFO-queues-exactly-once-processing.html) and [Lambda with SQS](https://docs.aws.amazon.com/lambda/latest/dg/with-sqs.html), plus [storage](../storage.md#users-and-email-marketing-consent) for the durable consent rules.

`newsletter_subscription_confirmations` is likewise operational proof/idempotency state, not a selected DMS/Kinesis source, event journal or queue input. Its raw tokens never persist; rows are looked up by SHA-256 digest and changed by the user service's short PostgreSQL transactions. A bounded cleanup port removes expired unconfirmed rows; confirmation rows are never published to DMS, Kinesis or SQS.

## Loops preference webhooks

The authenticated C16 transport passes the verifier's `NewsletterWebhookVerification` and exact raw-body SHA-256 to `ApplyLoopsPreferenceEventUseCase::execute`. The service owns application and transaction completion; it does not begin background work after a success result. `CommittedApplication`, `Duplicate` and `Ignored` are safe to acknowledge. `Conflict` means a provider webhook ID was reused with different authenticated body bytes and must not be acknowledged as success. `Retryable` and `InvalidEventTime` are non-success outcomes. A matching retry is deduplicated only after the receipt and application effects have committed together; a failed or uncertain commit is retried and resolved by looking up the receipt.

`loops_webhook_receipts` stores the unique delivery ID, digest of the exact verified bytes, original event name/time, bounded exact email/contact/list identity where available, committed disposition/time and a 35-day expiry. It never stores the complete payload, webhook signature or secret. C15 owns bounded expiry cleanup. Receipts and preference fences are operational PostgreSQL state and are not DMS/Kinesis/SQS inputs. A separate durable preference fence is keyed by the exact mailbox and survives receipt cleanup; it retains the latest accepted provider preference event time, contact binding and marketing-purpose state. The exact mailbox is authoritative and the contact ID is only an additional binding: a non-stale signed negative event may rotate that binding while applying the withdrawal. A positive event for a new contact ID may rotate it only when the bounded current-state read confirms that exact contact for the mailbox and the captured fence is unchanged at commit. Provider `userId` or custom Aura metadata is never an identity lookup, and an event for a different address cannot change a User even if it carries that User's ID.

Use Loops `eventTime` for ordering and the webhook ID only for delivery deduplication. Arrival time is used for receipt processing/expiry, never substituted for the provider decision time. Loops supplies event time at whole-second precision, so compare negative-event ordering against local decision time at that same resolution: a negative in the same provider second as a subsecond local grant is uncertain and blocks. A negative older than the provider fence is stale; equal-time negatives conservatively win and may rebind the contact ID for the exact mailbox. Future-dated positive observations are ignored as untrustworthy ordering. A positive event must be strictly newer than the provider fence and any recorded local consent decision; older or equal positive events are ignored. On `email.resubscribed`, first capture the exact User/recipient and provider fences in a short transaction, release them, and perform the bounded current provider read outside the transaction. Apply a local grant only if the read identifies the event contact, confirms global subscription and the configured marketing list, reports no suppression, and the captured fences remain unchanged at commit. A missing contact, wrong contact, suppression, false/absent target-list membership or uncertain read never grants. No account is created for an anonymous email; anonymous withdrawals still cancel matching pending grants and confirmation challenges.

Global `contact.unsubscribed` and `email.unsubscribed`, `contact.deleted`, target-list `contact.mailingList.unsubscribed`, and spam complaints apply a provider withdrawal/block through C02 and invalidate matching pending challenges in the receipt transaction, with no ordinary outbound intent. A deletion and complaint retain their actual source name/disposition; neither is reported as a user click. Unrelated-list changes do not affect this one marketing purpose. `contact.mailingList.subscribed` is an observation/possible API echo and never grants. Hard bounce is recorded as an operational delivery signal, not consent evidence or a synthetic withdrawal. The Loops writer must continue checking provider suppression and current send eligibility; local permission alone is not proof that Loops will accept or deliver a message.

Loops documents up to eight delivery attempts over about 28 hours, requires an endpoint response within 15 seconds, retries any non-2xx result, and retains webhook history for 30 days ([webhook retry and history contract](https://loops.so/docs/webhooks)). The 35-day receipt window exceeds that history window. C16 must provide the same configured marketing-list ID to this use case and the current-state Loops reader. Provider timestamps do not establish a complete distributed order, and Loops reads are outside PostgreSQL transactions: a provider change can still occur after a successful read and before local commit. The strict timestamp/fence policy is conservative protection against stale deliveries, not exactly-once processing or instantaneous cross-system consistency.

## DMS/Kinesis routing (target; live cutover unverified)

DMS captures committed selected rows only; no outbox or custom CDC transport. Source removal does not decommission external Sequin subscriptions or drain native-worker in-flight work. See the [runbook](../durable-worker-runbook.md#activation-and-legacy-handoff).

### Target Kinesis router checkpoint and recovery contract

The real-stage `cdc-router-lambda` is outside the customer VPC and has no database credentials. It accepts only a native Kinesis envelope with a usable sequence number and strict DMS data (`{ data, metadata }`) or control (`{ control, metadata }`) record, then validates the entire single-record route, all destinations, and schema-2 encoded compact jobs before publishing. Source data is base64-decoded only in memory and never logged or embedded in SQS jobs.

`CdcRouterEnabled` independently gates the immutable version mapping (off by default): `TRIM_HORIZON`, up to 100 records/one second, partial batch response, error bisection, three retries, one-hour record age. After whole-record prevalidation and confirmed fanout, only then checkpoint; on failure return the earliest unconfirmed **Kinesis sequence number** and stop, leaving successors unprocessed. Valid non-trigger operations/informational controls acknowledge with no job. Malformed rows/schema controls/envelopes, expired budget and uncertain/partial publication fail.

Exhaustion archives the complete failed invocation in private S3 (90-day expiry), **not** the worker DLQ; confirmed SQS jobs have seven-day source / 14-day DLQ retention. The DMS mapping selects the five existing R6 tables plus the consent-intent table, restricted to only `intent_id` and `recipient_key`. Only listed operations trigger jobs. See the [runbook](../durable-worker-runbook.md#failure-custody-and-controlled-redrive) for replay; no checked-in fixture proves live DMS delivery.

## ProductListing write flow

Partner writes bypass raw capture and commit `product_listings` plus zero or one `product_listing_events` domain event atomically; the journal is a DMS CDC source, **not** an outbox. Initial state emits `PRODUCT_LISTING_DISCOVERED`; later semantic changes emit one non-empty `PRODUCT_LISTING_CHANGED`. Discovery includes immutable source identity, initial facts and image count; change dimensions separate main price, estimates, availability, URL, images, listing-owned Auction/lot facts, lifecycle and sale observation. No image URLs or redundant `kind` appear in event payloads. Sale observations are `None → Some` / `Some → None`, never `Some → Some`; generic create/update/upsert neither capture FX nor infer sale from `SoldOut`. See the [ProductListing domain contract](../product-listing.md#behaviors-and-events) for exact event/auction fields and [Auction contract](../auction.md) for Auction ownership.

Crawler, Shopify and WooCommerce map raw-only observations to generic `raw_values` and immutable changed revisions; only the normalization Lambda converts them to canonical state/events, preserving stored Auction membership and lot facts without mutating Auctions. CDC wake-ups persist in Standard SQS; bounded PostgreSQL progress drains retry/redrive, with **no scheduled raw reconciliation**. Shopify/WooCommerce `CAPTURE_RAW` commands carry validated raw evidence in the separate FIFO; raw provider JSON never enters CDC jobs or logs, and signatures, headers and signed bytes never enter command jobs or logs. Provider receipts contain only an evidence digest, exist only for mapped capture, logically expire after 90 days, and may be physically cleaned later; raw revision provenance/optional `source_event_id` survives receipt expiry. An authorized ignored WooCommerce create/update status creates no receipt (even with a delivery ID). Mapped `204` means confirmed FIFO admission, not capture; consumer-side receipt/source-order/capture conflicts retry/redrive, not immediate HTTP `409`. See [source anti-corruption](../product-listing.md#source-anti-corruption-rules) and [WooCommerce handoff](../durable-worker-runbook.md#woocommerce-webhook-queue-handoff).

Synchronous partner writes commit state/event in one service-owned PostgreSQL transaction before replying; selected committed changes then traverse DMS → Kinesis → router → SQS → projection workers asynchronously. A successful write does not imply search visibility; router failures retry/archive and worker failures retry/DLQ.

Synchronous partner writes and crawler capture remain direct; Shopify and WooCommerce submit mapped raw commands to the separate FIFO. Neither code nor infrastructure declarations prove live producer cutover. See [asynchronous ingestion](../product-listing.md#asynchronous-ingestion-submission).

### V1 command admission versus CDC delivery

Async partner/trusted internal commands and mapped Shopify/WooCommerce `CAPTURE_RAW` use **FIFO admission**, distinct from DMS/Kinesis → **Standard SQS** CDC delivery. Provider acknowledgment requires confirmed FIFO `Accepted`; REST reports per-item admission, not business completion. A consumer commits a per-`commandId` receipt with canonical state/event or raw evidence; normalization and projection happen later. Neither FIFO nor source declarations prove live delivery.

V1 outcomes: `Accepted` confirms custody only; `Unconfirmed` may have enqueued; `Rejected` before send consumes no FIFO position; an unconfirmed same-group predecessor blocks successors as `NotAttempted(BlockedByFifoPredecessor)`, while other groups may advance. Retry a partial/lost response with the unchanged original ordered batch, effective key, actor and source; never renumber failures. FIFO orders per-group shared-queue acceptance, not upstream or synchronous-write chronology, and there is no submission registry/exactly-once guarantee. [ProductListing submission](../product-listing.md#asynchronous-ingestion-submission) owns wire and limits.

Admission does not check execution-time partner/source membership, listing/Auction existence, lifecycle or conflicts. Its FIFO discipline neither orders nor changes Standard SQS CDC worker redrive; PostgreSQL remains business truth.

### V1 ingestion command execution (installed consumer)

`product-listing-ingestion-lambda` verifies envelope/fingerprint and invokes the service-owned use case. Per command, the service serializes by `commandId` and atomically commits either canonical state/event or raw capture with an `APPLIED` PostgreSQL receipt; the queue adapter owns no transaction. Matching committed receipts replay without effects; fingerprint/metadata conflicts fail closed. `submissionId` is correlation, not atomicity or a registry. Failure/rejection/rollback creates no receipt; uncertain commit requires receipt check on retry, never speculative acknowledgment. Receipts have no TTL and survive business-row deletion.

A batch of at most ten stops at the first non-complete record, across groups: `ReportBatchItemFailures` includes its actual SQS ID and every unprocessed successor; only confirmed `APPLIED`/matching-receipt completions acknowledge. FIFO is not exactly-once and does not order synchronous writes or normalization; aggregate/source concurrency guards still apply. Command receipts differ from provider raw-capture receipts and are not CDC sources. See the [execution contract](../product-listing.md#downstream-command-execution-consumer-installed-shopify-producer-forwarding-gated-by-deployment) and [FIFO recovery](../durable-worker-runbook.md#productlisting-ingestion-fifo-command-recovery).

### Shopify queue forwarding boundaries (runtime deployment gated)

Shopify keeps EventBridge → Standard `shopify-lambda-queue`/DLQ → `shopify-lambda` (PostgreSQL source lookup/credentials); mapped `CAPTURE_RAW` forwards to separate `product-listing-ingestion-queue-${stage}.fifo` with source-ARN-only `sqs:SendMessage`. No upstream rule/queue or CDC worker queue is replaced. Production forwarding remains deployment-gated.

After EventBridge confirms upstream delivery, **Shopify SQS** acknowledges a mapped observation only on confirmed FIFO `Accepted`; otherwise report its upstream ID as failed for Shopify-DLQ retry. A lost reply can enqueue: replay with the same command identity/fingerprint. **FIFO SQS** independently acknowledges only committed `APPLIED`/receipt replay; failure or uncertainty retries to the ingestion DLQ. Neither boundary proves raw normalization or search visibility. Verify FIFO consumer and receipt schema before enabling the producer; see [two-queue handoff](../durable-worker-runbook.md#shopify-forwarding-handoff).

## Router fanout and custody

Strict ProductListing v1 group/type/payload, typed IDs, domain-first keys and compact schema-2 job serialization apply; unknown additive job fields are tolerated, but schema 1/malformed requirements fail. Partial fanout or lost confirmation may duplicate previously confirmed jobs on Kinesis retry. Standard SQS may duplicate/reorder, and redrive retains original enqueue age (seven-day source / 14-day DLQ are not additive). Only completed service outcomes acknowledge; no user-tier queue, worker inbox, processed-job table or scheduled raw reconciliation exists. See [architecture §12](../arch.md#12-cdc-and-projection-architecture) and the [runbook](../durable-worker-runbook.md#failure-custody-and-controlled-redrive).

## Domain jobs

Schema-2 `ProductListingEventJob`, `ProductListingRawRevisionJob`, `SearchFilterChangedJob`, `SearchFilterMatchCreatedJob`, `NotificationDeliveryCreatedJob` and `MarketingConsentSyncIntentCreatedJob` carry compact typed IDs/revisions, never source evidence or CDC JSON. For consent, recipient grouping and intent deduplication are validated top-level job metadata used to set FIFO attributes; the payload contains only the typed intent ID. Handlers reread PostgreSQL via service ports; SQS IDs/receipts/redrive times are transport-only. See [architecture §12.8](../arch.md#128-schema-evolution).

## Canonical ProductListing OpenSearch projection

PostgreSQL `product_listings`, `product_listing_translations`, and immutable `fx_rates` are authoritative. The `product-listings` OpenSearch index is rebuildable only. Each committed `product_listing_events` insert creates one ProductListing projection job with stable `(event_id, product_listing_id)` IDs. The handler rereads complete current ProductListing state and rejects a trigger whose event ID is no longer current. It loads the exact observation FX snapshot only for an active `SoldOut` listing with both an observation and a monetary main source price, commits its PostgreSQL read transaction, then writes the complete private document with `product_listings.projection_version` as OpenSearch external version.

Current `Withdrawn` state replaces the full document with content-free `{productListingId, projectionDeleted: true}` at that external version. Raw OpenSearch GET returns 200 with this marker, not 404. All product search, hybrid BM25/KNN and similar-listing readers exclude true before pagination/ranking; absent markers remain live. Current `Active` state, including restore, writes a full document only at a newer source version. Live documents have optional `availability` but no lifecycle field. Duplicate/older writes and stale withdrawals after restore are stale no-ops. Missing required observation FX fails for retry.

This fence survives physical-delete `index.gc_deletes`; never TTL or physically delete tombstones. Deploy mappings and all readers before writers, fence old physical-DELETE writers including in-flight requests, and use the [fenced rebuild procedure](../durable-worker-runbook.md#projection-fences-and-rebuild), not index reset. Withdrawn source rows support backfill; absent historical deletion facts do not.

The document stores native tagged `sourcePrice` (`MONETARY` or `ON_REQUEST`), immutable HalfUp `salePrices` only when a qualifying observation has a monetary source price, and `saleObservationFxRateId` / `saleObservedAt` independently. A sold no-main-price document has observation metadata but no `sourcePrice` or `salePrices`; an on-request document retains `sourcePrice: ON_REQUEST` with no `salePrices`. Both remain searchable by non-price criteria; on-request maps to an on-request display price. All existing search fields and the authoritative embedding remain. It never stores estimates. ProductListing search cursor chains and similar-listing KNN reads pin one persisted snapshot for active summary conversion; sold summaries use indexed immutable sale amounts when present and preserve the valuation basis. The dedicated Lambda needs `POSTGRES_*`, `STAGE`, `OPENSEARCH_ENDPOINT_URL`, and OpenSearch credentials in dev and prod. It processes one record per invocation; only applied/deleted/stale service outcomes acknowledge. Retry, poison, timeout, panic, cancellation, and acceptance-unknown results are `batchItemFailures` for the source queue's native retry/DLQ. No Lambda receipt loop, visibility adjustment, HTTP CDC ingress, or health server participates in this scope.

## Canonical search-filter percolator

The percolator scope accepts only `product_listing_events` inserts. It enqueues only `DOMAIN` and `ENRICHMENT` ProductListing events, parsing typed event and ProductListing IDs once at CDC ingress, rereads the committed typed ProductListing match source including immutable `product_listing_events.event_time`, and invokes `MatchProductListingEventUseCase`. The use case compares the source event ID with `product_listings.current_event_id` before percolating; a superseded trigger is skipped, never evaluated against newer ProductListing state with its old origin ID. A current withdrawn listing is an explicit inactive-source skip: it performs no percolation, evaluation, or match write. For an accepted active current event with a monetary main source price, it uses the immutable sale snapshot when present; otherwise it reads latest persisted FX with `captured_at <= origin_event_time`, ordered by capture then generation. It converts that monetary price into every supported currency only in the private temporary percolation document. On-request and absent prices omit numeric percolation fields. Stored filter queries remain FX-independent. Current active events percolate the canonical OpenSearch filter projection, then the shared service evaluator batches enhanced candidates through the neutral `classifier-model` capability. Each request passes the original enhanced description, localized title and description using existing language fallbacks, and at most the first listing image. The service asks only `hard_conflict` and `should_show`; `hard_conflict` is diagnostic only, while an inclusive service-owned `should_show >= 0.50` threshold controls acceptance. There is no generated match explanation. Cloudflare Workers AI Clef Flash is the default runtime model, with Clef selectable in configuration; provider, model, authentication and protocol handling stay inside the classifier adapter. The final short PostgreSQL transaction locks/rechecks the ProductListing current event, then batch-locks active filters through match commit. Candidates must still have the exact evaluated semantic search plus embedding; changed inputs/deactivation/deletion suppress them, but unrelated name/notification edits remain eligible. It stores eligible idempotent plain or successful-enhanced matches. An enhanced candidate provider failure never prevents those writes: retryable failures are returned after commit for normal worker retry; permanent candidate-specific failures are explicit in the use-case result and never create a match.

`search-filter-percolator-lambda` consumes only its Standard queue (batch one) with PostgreSQL, OpenSearch and Cloudflare Workers AI configuration; it sends no notifications. Unsupported group/type/version or malformed payload fails at router, irrelevant supported events produce no job. Match uniqueness protects redelivery; price matches record `EVENT` or `SALE_OBSERVATION` provenance, non-price matches null valuation provenance. Stale/inactive/ignored outcomes skip; missing source, provider/transaction failure, timeout/panic and ambiguous commit retry/DLQ; only committed outcomes acknowledge. FX capture triggers no percolation, projection, match or notification route.

## Search-filter match notification generator

The match-notification scope accepts only `search_filter_matches` inserts. Its job and source read use `(user_id, user_search_filter_id, product_listing_id, origin_event_id)`, so a stale or superseded CDC row cannot notify a different match. It reads the committed Product source and invokes `GenerateSearchFilterMatchNotificationUseCase` for every persisted matching filter. The use case locks the user tier and calculates the event's stable monthly notification rank; this gates delivery eligibility only, never match persistence. PostgreSQL inserts the notification and optional external-delivery rows atomically. Exact CDC redelivery and concurrent filters are protected by the SearchFilter semantic identity, so each matching filter remains distinct.

`search-filter-match-notification-lambda`: PostgreSQL/queue-only; batch one, 45s timeout / 300s visibility. ## Canonical watchlist notification generator

The watchlist worker scope accepts only `product_listing_events` inserts and enqueues canonical price/availability events. The ProductListing service reads the immutable source and uses persisted `product_listing_events.event_time` as the eligibility timestamp. `product_listing_watchlist.active_since` is the beginning of the current active interval; `notifications_enabled_since` is the beginning of the current email-enabled interval.

At processing time, a recipient must still have `state = ACTIVE` and `active_since <= product_listing_events.event_time`. Email delivery additionally requires `notifications = true` and `notifications_enabled_since <= product_listing_events.event_time`. Thus late activation and late email enablement do not receive older events; a late email enablement can still receive the in-app notification. Deactivation and reactivation start a new active interval, and disabling and re-enabling email starts a new email interval. The current state is authoritative, so an entry inactive when processed receives neither channel.

Before writing, the use case reads the exact ProductListing event and uses its immutable event time for recipient eligibility. A later unrelated `current_event_id` does not suppress this historical fact. The source query locks the current ProductListing row with `FOR SHARE`; that lock remains held while recipients, notifications, and delivery intents are written through commit. The current listing must still be `ACTIVE`; a withdrawn listing is explicitly suppressed to avoid creating a snapshot for a hidden listing. Changed events without main-price or availability changes are acknowledged as ignored; a missing committed source remains retryable for native SQS retry/DLQ. Worker logs distinguish applied work, duplicates, ignored events, missing sources, and withdrawn suppression.

Watchlist semantic identity is `(user_id, origin_event_id, kind)`, so a price change and availability change remain distinct. Recipients with email disabled or email enabled after the event receive the in-app notification without a `notification_deliveries` row.

The PostgreSQL unique key guards duplicates. Price-change payloads keep source prices only; rendering uses current user preferences, not invented FX.

`watchlist-notification-lambda`: PostgreSQL/queue-only; batch one, 45s timeout / 300s visibility. Applied, duplicate, ignored and withdrawn acknowledge; missing committed source, malformed job, dependency failure, timeout/panic or unknown commit retry/DLQ. Router sends only eligible event inserts here.

## Canonical notification delivery

The `notification-delivery` scope accepts only `notification_deliveries` inserts and publishes schema-2 SQS jobs carrying the `nd_` TypeID `notification_delivery_id`; idempotency/ordering is `notification-delivery:{delivery_id}`. Deliveries are unique per `(notification_id, channel, target_key)`. The service atomically claims a five-minute PostgreSQL lease and loads source, commits before channel I/O, then dispatches once within a four-minute total budget. EMAIL alone resolves current `PRIMARY`, renders S3 templates and calls SES with SDK max attempts 1.

Active claims defer until persisted expiry +5s; reclaimable `PENDING`/expired-claim races defer 1s. Neither acknowledges. Current runtime retries missing delivery rows too. Known transient rejection/pre-send failures finalize back to `PENDING`; permanent/source failures require confirmed `FAILED` finalization. Ambiguous SES timeout/transport/unknown/5xx/missing-receipt outcomes keep the lease, give no acknowledgment and never resend inside the attempt.

Retry only finalization with the original lease token, completion time and provider receipt/error tuple. The initial business schema stores `completed_lease_token`/`completed_at`, so an exact persisted completion can confirm a lost response without another write/send. Only confirmed terminal outcomes permit SQS deletion; lease loss/unconfirmed finalization remains retryable. A crash after SES acceptance can still cause duplicate email after reclaim. See [notification recovery](../durable-worker-runbook.md#notification-recovery-limits).

`notification-delivery-lambda`: batch one, 45s invocation / 35s service attempt / 330s visibility (lease + 30s); never extend visibility or acknowledge deferred claims. Only confirmed `Delivered`, `AlreadyDelivered`, finalized permanent failure or finalized `SourceMissing` acknowledge. Missing/unfinalized delivery, deferral, lost lease, timeout/panic, ambiguous SES acceptance or finalization retry/DLQ. It has PostgreSQL, staged S3 templates (`s3:GetObject` on `${stage}/${commitSha}/*`), approved-sender `ses:SendEmail` and queue-consume access, not SES administration/redrive/purge. Fence old consumption before activation; rollback needs approval, disabled mapping and compatible code.

`search_filters` in Postgres is authoritative. `user_search_filters` is the single rebuildable canonical OpenSearch projection.

## Retry and failure handling

Worker mappings use `ReportBatchItemFailures`, batch one except normalization (ten), five receives before DLQ. ProductListing projection, saved-filter projection and translation: 45s / 300s visibility; content assessment and normalization: 45s / 270s; embedding: 60s / 360s; delivery: 45s / 330s with 35s service budget and five-minute PostgreSQL lease. No worker changes visibility. Saved-filter applied/stale acknowledges only after authoritative reread or deletion fence, including missing-upsert sources. Only confirmed completion acknowledges: timeout, panic, setup failure, bad wire job or uncertain response retries/DLQ; malformed upstream CDC instead fails the earliest Kinesis sequence and may enter the S3 archive. Repair before separately authorized controlled redrive; never purge. See the [runbook](../durable-worker-runbook.md#failure-custody-and-controlled-redrive).

## Operations notes

Monitor DMS lag/WAL, queue age/DLQ, Lambda errors/duration and search lag; prod alarms cover source age ≥900s, DLQ-visible ≥1 and Lambda errors. Use safe IDs/outcome categories only, never credentials, recipients, content or provider payloads. After ambiguous SES acceptance, verify PostgreSQL and provider evidence under approved access before controlled recovery; never automatically resend historic mail. External owners must prove Sequin delivery/identities/credentials retired and reconcile old in-memory work; source removal recovers none. See [runbook](../durable-worker-runbook.md).

## Test guidance

Use PostgreSQL integration tests, strict synthetic DMS/Kinesis envelopes for router fanout, and LocalStack SQS plus real OpenSearch for projection/percolation. Cover stale/duplicate/crash cases, schema/poison/visibility failures, deletion fences beyond GC and notification finalization ambiguity. Live DELETE/control envelope probes and AWS smoke require separate sandbox approval; fixtures or documentation are not live proof. See [architecture test rules](../arch.md#1211-required-tests) and the [runbook](../durable-worker-runbook.md).
